## StateTree Task / Condition 작성법 정리

> 지금까지 태스크와 조건을 **필요할 때마다 만들면서** 배웠는데, 팀원에게 넘길 가이드를 쓰면서 규칙을 한 번에 정리했습니다. 만들 때는 몰랐다가 정리하면서 이해된 것들이 꽤 있었습니다.

---

### 1. 한 줄 분업

| 구분 | 역할 | 질문 형태 | 반환 |
| :--- | :--- | :--- | :--- |
| **Condition** | 이 상태에 **들어갈 자격**이 되는지 판정 | "~인가?" | `bool` |
| **Task** | 상태에 들어간 동안 **실제로 행동** | "~해라" | `EStateTreeRunStatus` |

> **Condition은 문을 여닫고, Task는 방 안에서 일한다.** Condition은 상태를 **고르는** 쪽, Task는 상태가 **하는 일** 쪽입니다.

---

### 2. 실행 모델 — 이걸 알아야 나머지가 이해된다

```
1. 선택(Selection)  Root의 자식을 위에서 아래로 훑으며 Enter Condition 테스트
                    → 처음 true가 나온 상태로 진입, 나머지는 보지 않음
2. 진입(EnterState) 진입한 상태와 그 조상 상태의 Task들이 EnterState() 호출
3. 틱(Tick)         매 프레임 활성 Task의 Tick() 호출
4. 완료             Succeeded/Failed 반환 → 상태 종료 → Transition이 다음 목적지 결정
5. 퇴장(ExitState)  상태를 떠날 때 호출. 뒷정리 담당
```

*   **상태 순서가 곧 우선순위**입니다. `Leave`가 조건 없이 맨 아래 있는 이유 = 아무 조건도 안 맞을 때 떨어지는 fallback.
*   4번에서 보통 `Root`로 돌려보내 1번부터 다시 선택하게 합니다. 어제 정리한 *"전이는 재평가 지점으로 보낸다"* 가 이 모델에서 나온 결론이었습니다.

### 3. 왜 값을 InstanceData에 두는가 — 입문자 최다 실수

**핵심 사실 하나만 기억하면 됩니다.**

> `FCSCond_HasItemsInCart` 같은 **본체 구조체는 트리 에셋에 1개만 존재**합니다. 손님 100명이 같은 트리를 쓰면 **100명이 이 구조체 하나를 공유**합니다.

여기서 나머지가 전부 따라 나옵니다.

| 사실 | 그래서 |
| :--- | :--- |
| 본체 구조체는 트리당 1개 | 멤버에 상태를 두면 **100명이 같은 값을 공유** → 타이머·순번 충돌 |
| 그래서 `TestCondition()`이 **`const`** | 여기서 멤버를 바꾸면 전원에게 영향 → 언어 차원에서 막아둔 것 |
| 손님마다 다른 값은 InstanceData로 | InstanceData는 **실행 컨텍스트마다 별도 사본**이 생김 |

```cpp
// ❌ 절대 금지
struct FCSCond_Something : public FStateTreeConditionCommonBase
{
    float CachedTime = 0.0f;   // 모든 손님이 공유 → 버그
};

// ✅
struct FCSCond_SomethingInstanceData { UPROPERTY() float CachedTime = 0.0f; };
```

> `TestCondition`과 `Tick`이 `const`인데도 `Data`를 수정할 수 있는 건, `GetInstanceData()`가 **구조체 자신이 아니라 외부 저장소에 대한 참조**를 주기 때문입니다. `const`의 의미를 처음엔 오해했는데, **"본체는 못 바꾸고 인스턴스는 바꿔라"** 는 설계 의도였습니다.

**필수 3종 세트** — 셋 중 하나라도 빠지면 컴파일 또는 에디터 등록이 안 됩니다.

| 요소 | 이유 |
| :--- | :--- |
| `using FInstanceDataType = ...` | `Context.GetInstanceData(*this)`가 타입을 찾는 통로 |
| `GetInstanceDataType()` 오버라이드 | 엔진이 인스턴스 데이터를 몇 바이트 잡을지 알아야 함 |
| `USTRUCT()` + `GENERATED_BODY()` | 리플렉션에 등록돼야 에디터 목록에 나옴 |

### 4. Condition 작성 패턴 — 5단계 골격

```cpp
bool FCSCond_HasUnvisitedShelf::TestCondition(FStateTreeExecutionContext& Context) const
{
    const FInstanceDataType& Data = Context.GetInstanceData(*this);   // ① const 참조

    bool bResult = false;                                             // ② 기본값을 의도적으로

    if (Data.Actor != nullptr)                                        // ③ 바인딩 누락 방어
    {
        // ④ 판정 로직은 여기 쓰지 않는다 — Subsystem/Component 한 방 호출
        bResult = Subsystem->HasUnvisitedShelf(State->VisitedShelves);
    }

    return Data.bInvert ? (bResult == false) : bResult;               // ⑤ 반전 처리
}
```

*   ⑤ **`bInvert`를 넣어두면 "~아닐 때" 조건을 위해 클래스를 하나 더 만들 필요가 없습니다.** 어제 `HasAbandonedCheckout`에 Invert를 걸어 재진입을 막은 게 이 설계 덕분이었습니다.
*   ④ 판정 로직이 Condition에 들어가기 시작하면 **같은 판정을 Task도 하게 되고 두 곳이 어긋납니다.**

### 5. Condition에서 하면 안 되는 것

| 금지 | 이유 |
| :--- | :--- |
| 상태를 바꾸는 부수 효과 (재고 차감, 대기열 등록, 로그 스팸) | **몇 번 호출될지 모른다** |
| 무거운 연산 (`TActorIterator` 전체 순회, 경로 탐색) | 매 선택마다 전부 실행된다 |
| 대기 / 타이머 | Condition에는 Tick이 없다. 그건 Task의 일 |

#### 확률 조건의 함정

`WantsMoreItems`가 `FMath::FRand()`를 씁니다. 편리하지만 알고 써야 합니다.

*   Condition은 **상태 선택이 일어날 때마다 다시 평가**되고, **몇 번 평가되는지 보장이 없습니다.**
*   같은 프레임에 두 번 평가되면 **다른 답이 나올 수 있습니다.**

| 상황 | 대응 |
| :--- | :--- |
| "진열대 하나 볼 때마다 한 번 굴린다" 수준 | 현재 구현으로 충분 (평가 시점 = 쇼핑 루프 1회전) |
| **결과가 흔들리면 안 되는 경우** | **Task에서 한 번 굴려 `StateComponent`에 저장**하고, Condition은 그 저장값만 읽는다 |

> 이 구분을 몰랐다면 나중에 "가끔 이상하게 동작하는" 재현 안 되는 버그로 만났을 것 같습니다. **평가 횟수가 보장되지 않는 자리에는 부작용도 무작위성도 두지 않는다**로 정리했습니다.

### 6. Task 생명주기 3함수 — `ExitState`가 핵심

| 함수 | 호출 시점 | 여기서 할 일 | 프로젝트 예시 |
| :--- | :--- | :--- | :--- |
| `EnterState` | 진입 시 1회 | 초기화, 명령 발행, 즉시 판정 | `MoveToLocation()`, `ElapsedTime = 0`, `JoinQueue()` |
| `Tick` | 매 프레임 | 진행 감시, 완료 판정 | 이동 완료 폴링, 시간 누적, 순번 갱신 |
| `ExitState` | 이탈 시 1회 | **뒷정리 (필수)** | `StopMovement()`, `LeaveQueue()`, 남은 상품 드롭 |

> **`ExitState`는 성공·실패·외부 전이·트리 중단 모든 경로에서 호출됩니다.** 그래서 **"무슨 일이 있어도 반드시 정리해야 하는 것"** 의 자리입니다.
>
> `StopMovement()`를 빼먹으면 이동 명령이 남아 **상태가 바뀌었는데도 계속 걸어갑니다.** `ReturnProducts::ExitState`가 어떤 경로로 빠져나가도 남은 상품을 떨구는 것도 같은 이유 — 재고 증발 방지.

**`EnterState`에서 타이머·캐시 초기화**도 잊으면 안 됩니다. 재진입 시 값이 이어지면 두 번째 진입에서 즉시 완료돼 버립니다.

### 7. `EStateTreeRunStatus` — 반환값이 곧 흐름 제어

| 반환 | 결과 |
| :--- | :--- |
| `Running` | 상태 유지, 다음 프레임 `Tick` |
| `Succeeded` | 상태 종료 → **On Succeeded / On Completed** 전이 |
| `Failed` | 상태 종료 → **On Failed / On Completed** 전이 |

> **`Failed`는 "에러"가 아니라 "다른 길로 가라"는 신호입니다.** `PickNextShelf`가 더 볼 진열대가 없으면 `Failed`를 반환하는데, 이건 버그가 아니라 **"쇼핑 종료" 신호**이고 `On Failed` 전이가 Root로 돌려보내 `Checkout`이 선택되게 만듭니다. **별도의 종료 코드 없이 전이 설정만으로 흐름이 완성됩니다.**

**반대로 `Failed`를 안 쓰는 판단도 있습니다.** 예제로 만든 `FaceActor`(진열대를 향해 몸 돌리기) 태스크는 대상이 없어도, 타임아웃이 나도 **전부 `Succeeded`** 로 흡수합니다.

> 회전에 실패했다고 손님을 내보낼 이유가 없기 때문입니다. **`Failed`는 "다른 상태로 보내고 싶을 때만" 씁니다.** 실패를 어디로 흘려보낼지 없으면 성공으로 흡수하는 게 맞습니다.

---

### 8. 데이터 홀더 패턴 — 부모 Task가 `Running`을 유지하는 이유

`PickNextShelf`는 값만 계산하는데 `Succeeded`가 아니라 **`Running`** 을 반환합니다.

| 반환 | 결과 |
| :--- | :--- |
| `Succeeded` | `Shopping` 상태가 **즉시 종료** → 자식(`MoveToShelf`, `BrowseShelf`)이 실행될 기회조차 없음 |
| **`Running`** | `Shopping`이 살아있고, 자식들이 부모 Task의 **Output을 바인딩해서 읽을 수 있음** |

그리고 짝으로 **`bShouldCallTick = false`** 를 생성자에서 설정합니다.

```cpp
FCSTask_PickNextShelf()
{
    bShouldCallTick = false;   // 값만 들고 있으면 되므로 매 틱 호출은 낭비
}
```

> **`Tick()`을 오버라이드하지 않는 Task는 전부 이 플래그를 꺼두는 게 좋습니다.** 손님 수 × 프레임만큼 빈 호출이 사라집니다. 이건 오늘 정리하면서 처음 알았고, 기존 태스크들도 점검해봐야겠습니다.

### 9. Category 4종 — "누가 이 값을 채우는가"

엔진이 강제하는 게 아니라 **팀 약속**입니다. 에디터에서 그룹으로 묶여 보이고, **이름만으로 채우는 주체를 알려줍니다.**

| Category | 값을 채우는 주체 | 에디터 작업 | 예시 |
| :--- | :--- | :--- | :--- |
| `Context` | 스키마 (AIController / Actor) | 스키마 대상에 바인딩 | `Actor`, `AIController` |
| `Input` | **다른 Task의 Output** | 부모/이전 Task Output에 바인딩 | `MoveToLocation::TargetLocation` |
| `Output` | 이 Task가 계산해서 내보냄 | 다른 Task가 가져다 씀 | `PickNextShelf::TargetShelf` |
| `Parameter` | 사람이 직접 입력 | 값 타이핑 | `BrowseTime`, `bInvert` |
| (없음) | 코드 내부 전용 | 노출 안 됨 | `ElapsedTime`, `CachedQueueIndex` |

**`UPROPERTY`는 노출이 필요 없어도 붙입니다.**

```cpp
UPROPERTY()                 // EditAnywhere 없음 = 내부 전용이지만 리플렉션에는 등록
float ElapsedTime = 0.0f;
```

> 안 붙이면 **리플렉션 밖**이라 초기화·복사가 보장되지 않고 **GC 대상에서 누락**됩니다. "에디터에 안 보여도 되니까 생략"이 아니라, **인스턴스마다 따로 존재해야 하니까 반드시 붙이는 것**입니다.

**`Parameter`에 `0`을 "미지정"으로 쓰는 패턴**도 정리했습니다.

```cpp
float Patience = Data.PatienceOverride;      // 0이면 미지정
if (Patience <= 0.0f)
{
    Patience = Subsystem->GetPatienceSeconds(Data.Actor);
}
```
Task에 하드코딩 없이 **개별 오버라이드를 허용**하는 방법입니다.

### 10. Condition으로 만들까, Task로 만들까

| 질문 | Yes → |
| :--- | :--- |
| 시간이 걸리는가? (대기, 이동, 애니메이션) | **Task** |
| 월드에 변화를 주는가? (재고 차감, 대기열 등록, 파괴) | **Task** |
| 결과가 다음 상태 선택에만 쓰이는가? | **Condition** |
| 즉시 참/거짓으로 답할 수 있는가? | **Condition** |
| 여러 번 호출돼도 결과가 같아야 하는가? | **Condition** (아니면 Task에서 굴려 저장) |

> **이름 붙이기 테스트:** `Has~` / `Is~` / `Wants~`가 자연스러우면 **Condition**, `Do~` / `Move~` / `Pick~`이 자연스러우면 **Task**.
>
> 네이밍 규칙이 단순한 스타일 문제가 아니었습니다. `FCSCond_CheckShelf`처럼 **동사로 시작하면 Task와 구분이 안 되고, 조건 안에서 뭘 "하려는" 유혹이 생깁니다.** 이름이 설계를 지켜주는 사례.

### 11. 증상별 원인 — 디버깅 표

| 증상 | 유력한 원인 |
| :--- | :--- |
| 손님이 스폰 직후 사라짐 | `Actor` / `AIController` **바인딩 누락** → `Failed` → `Leave` 직행 |
| 같은 진열대를 무한히 왕복 | `MarkVisited()` 호출 누락 |
| 상태가 바뀌었는데 계속 걸어감 | `ExitState`의 `StopMovement()` 누락 |
| 여러 손님의 타이머가 서로 간섭 | 시간 변수를 **InstanceData가 아니라 본체 구조체**에 둠 |
| 부모의 Output이 자식에서 안 읽힘 | 부모 Task가 `Running`이 아니라 `Succeeded` 반환 |
| 포기한 손님이 다시 줄을 섬 | `Checkout`에 `HasAbandonedCheckout` **Invert** 조건 누락 |
| 상품이 사라지고 재고가 증발 | `ExitState`의 `DropCustomerItems` 누락 |
| 에디터 목록에 새 Task가 안 보임 | 리컴파일 안 됨 / `USTRUCT` 누락 / 에디터 재시작 필요 |

디버깅은 **StateTree Debugger를 가장 먼저** 엽니다. 어느 상태에 있고 **어느 조건이 왜 false인지** 시각적으로 확인됩니다. 이동·NavMesh 문제는 Visual Logger.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **본체는 트리당 1개, 인스턴스는 손님마다** | 이 사실 하나에서 `const`, InstanceData, 필수 3종 세트가 전부 따라 나온다 |
| **`const`는 제약이 아니라 안내** | "본체는 못 바꾸고 인스턴스는 바꿔라"는 설계 의도를 언어로 표현한 것 |
| **실패 시 기본값은 설계 판단** | "정보를 못 얻었을 때 덜 이상해 보이는 쪽". 특히 **기능 추가가 기존 동작을 깨지 않게** |
| **평가 횟수가 보장 안 되는 자리** | Condition에는 부작용도 무작위성도 두지 않는다. 흔들리면 안 되면 Task에서 굴려 저장 |
| **`ExitState`는 모든 경로에서 호출** | "무슨 일이 있어도 정리해야 하는 것"의 자리 |
| **`Failed`는 분기 신호** | 흘려보낼 곳이 없으면 `Succeeded`로 흡수한다 (`FaceActor`) |
| **`bShouldCallTick = false`** | Tick을 안 쓰는 Task는 전부 꺼둔다. 손님 수 × 프레임만큼 빈 호출 제거 |
| **이름이 설계를 지킨다** | `Has~`면 Condition, `Do~`면 Task. 동사로 시작하는 조건은 조건 안에서 뭘 하려는 유혹을 만든다 |
| **만들 때보다 정리할 때 이해된다** | 규칙을 문서로 옮기면서 `bShouldCallTick`, `UPROPERTY` 생략의 위험을 처음 알았다 |
