## 손님 입장 판정 버그 연쇄 추적 — 하나를 고치니 다음이 드러났다

> 거리 통행 + 개폐 입장 기능(`Approach` 상태)을 배선하고 검증하는데, **증상 하나를 고칠 때마다 다른 증상이 나타났습니다.** 결과적으로 원인이 4겹으로 쌓여 있었고, 앞의 버그가 뒤의 버그를 **가려주고** 있었습니다.

### 1. 오늘의 흐름 한눈에

| 차수 | 보고된 증상 | 처음 의심한 곳 | **실제 원인** |
| :---: | :--- | :--- | :--- |
| 1 | 닫아도 손님이 계속 들어옴 | 개폐 플래그 / 배선 | **레벨 지점 배치** (판정 지점이 입구에서 43.9 m) |
| 2 | 열면 손님이 가게 앞에 멈춰 섬 | `ST_Customer` 배선 | **C++ 한 줄 no-op** (`MarkEnteredStore`) |
| 3 | 이번엔 닫아도 **전원** 입장 | 레벨 / 배선 | **스폰 초기화 순서** (`SpawnActor`가 `BeginPlay` 동기 호출) |
| 4 | 손님 비주얼이 안 나옴 | — | **3차 수정의 부작용** (`SpawnActorDeferred`가 BP 컴포넌트까지 미룸) |

> 1·2·3차 모두 **처음 의심한 곳은 전부 정상**이었습니다. 배선과 개폐 플래그는 매번 결백했는데도 세 번을 다시 확인했습니다. **증상이 나타나는 곳과 원인이 있는 곳이 다르다**는 걸 오늘 하루에 세 번 겪었습니다.

### 2. STEP 6 — `Approach` 상태 배선

```
Root (Selector)
├─ ForceLeave   [ShouldForceLeave]                      (기존, 맨 위 유지)
├─ Approach     [HasEnteredStore, bInvert = True]       ← 신규, index 1
│               Task: ApproachStorefront (AcceptanceRadius 80)
│                          ✓→ Root    ✗→ Leave
├─ Shopping / Shoplift / Checkout / ReturnItems / Leave (기존, 손대지 않음)
```

**기존 상태의 순서·조건·전이를 하나도 안 고쳤습니다.** 어제 `Shoplift`를 넣을 때와 같은 방식으로, **위치만으로** 분기를 만들었습니다.

**작업 중 걸린 함정 하나** — StateTree 노드 추가 API가 조건의 **`bInvert`를 조용히 무시**해서 최초에 `False`로 들어갔습니다. 그대로 뒀다면 *"이미 들어온 손님만 가게 앞으로 나가는"* 정반대 동작이 됩니다.

> 스크립트/자동화로 에셋을 편집하면 **일부 속성이 조용히 누락**될 수 있습니다. 편집 후에는 반드시 **값을 다시 읽어 확인**해야 한다는 걸 배웠습니다.

`Actor` / `AIController` 바인딩이 비어 있는 것은 **정상**입니다. `UPROPERTY(..., Category = "Context")`로 선언하면 컴파일 시 스키마가 이름·타입이 맞는 컨텍스트 데이터를 자동으로 물려줍니다. 기존 태스크들도 전부 비어 있는 채로 잘 동작하고 있었습니다.

### 3. 1차 — "닫아도 계속 들어온다" → 레벨 배치 문제

**코드 버그가 아니었습니다.** `StorefrontPoint`(판정 지점)가 실제 가게 입구에서 **43.9 m** 떨어진 거리 반대편 끝에 있었습니다.

| 구간 | 수정 전 | 수정 후 |
| :--- | :--- | :--- |
| Enter → Storefront | 763 cm / 2.5초 | 6470 cm / 21.6초 |
| **Storefront → 진열대** | **5151 cm / 17.2초** | **1020 cm / 3.4초** |
| Storefront → Exit | 784 cm / 2.6초 | 6250 cm / 20.8초 |

**두 현상이 겹쳐서 하나로 보였습니다.**

*   **① 이미 판정을 통과한 손님은 돌아서지 않습니다 (설계상 정상).** 스폰 2.5초 만에 입장을 확정하고 **17초 동안** 걸어가므로, 그 사이에 폐점해도 재판정이 없습니다. 판정 지점이 문 앞에 있었다면 1초 안에 끝나 **눈에 띄지 않았을 동작**입니다.
*   **② 폐점 후 새 손님이 아예 안 나왔습니다.** `MaxAliveCustomers = 8`인데 손님 한 명의 생애가 1분을 넘으니 슬롯이 안 비고, 5초마다 오는 스폰 타이머가 매번 상한에서 되돌아갔습니다. → **"지나가는 손님"이 생성되지 않아 볼 수가 없었습니다.**

> **"닫았는데 계속 들어온다"는 사실 두 개의 서로 다른 사실이었습니다.** 하나는 정상 동작이 과장되어 보인 것이고, 하나는 관측 자체가 불가능했던 것입니다. **증상 문장 하나를 여러 사실로 분해**하는 게 진단의 첫 단계라는 걸 배웠습니다.

지점 3개를 옮기고 `MaxAliveCustomers` 8 → 12, `SpawnInterval` 5초 → 3초로 올려 **관측 가능한 상태**부터 만들었습니다.

### 4.  2차 — "열면 제자리에 선다" → C++ 한 줄 no-op

```cpp
// 수정 전
void UCSCustomerStateComponent::MarkEnteredStore()
{
	void MarkEnteredStore();   // ← 대입문이 아니라 "지역 함수 선언문"
}
```

**C++ 문법상 완전히 합법인 함수 선언**이라 컴파일 에러도, 경고도 나지 않습니다. 전체 소스를 검색해도 `bHasEnteredStore`를 `true`로 만드는 곳이 **한 군데도 없었습니다.**

```cpp
// 수정 후
bHasEnteredStore = true;
```

**왜 "멈춰 서 있는" 것처럼 보였나**

```
Approach 도착 → ShouldEnterStore() = true → MarkEnteredStore()  ← 아무 일도 안 일어남
             → Succeeded → Root 재선택
             → Approach ? HasEnteredStore=false → bInvert → 참 → 또 Approach !!
             → MoveToLocation(Storefront) → 이미 그 자리(반경 80) → 즉시 완료
             → Tick → 또 판정 → ...  (매 틱 왕복)
```

이동 명령이 매번 "이미 도착"으로 끝나니 화면상으로는 **제자리에 서 있는 것**으로 보입니다. 간판을 닫으면 그 루프 안의 판정이 처음으로 `false`가 되어 `Failed → Leave`로 빠져나갑니다.

> **이 버그는 open일 때만 겉으로 드러납니다.** 닫혀 있으면 첫 판정에서 바로 `Failed → Leave`라 루프에 진입할 일이 없습니다. *"닫으면 정상, 열면 이상"* 이라는 비대칭 증상 자체가 **"루프에 들어가는 경로가 한쪽뿐"** 이라는 단서였습니다.

**같은 한 줄이 망가뜨리고 있던 다른 것들**

| 영향 | 내용 |
| :--- | :--- |
| **통계** | `HasEnteredStore() == false` 게이트에 **전원**이 걸려 `OnCustomerDespawned`가 한 번도 방송 안 됨 → 누적 인원이 0에서 안 늘어남 |
| **"판정은 손님당 1회" 보장** | 루프마다 재판정하므로 설계 보장이 깨짐 |
| **시드 재현성** | 루프 횟수만큼 굴림이 소모되어 `cs.Seed` 고정이 무의미 |

**한 줄이 세 개의 무관해 보이는 기능을 동시에 망가뜨리고 있었습니다.** 플래그 하나가 여러 게이트에 쓰이면 파급이 이렇게 넓어진다는 걸 실감했습니다.

### 5. 3차 — "이번엔 전원 입장" → 초기화 순서 버그

2차를 고치자 **정반대 증상**이 나왔습니다. 이제 개폐와 무관하게 **전원이 입장**합니다.

**PIE 실측이 결정적이었습니다.**

```
BP_CSCustomer_C_0  pos(-10793, -9140)  entered=True  storefront=(-6750,-8830)
BP_CSCustomer_C_1  pos(-10828,-10039)  entered=True  storefront=(-6750,-8830)
```

판정 지점에서 **40 m 이상 떨어진 곳**에 있는데 `bHasEnteredStore`가 이미 `True`입니다. 그런데 `storefront` 값 자체는 **제대로 들어가 있습니다.** → **스포너 설정은 정상이고, StateTree가 그보다 먼저 출발했다**는 뜻입니다.

```cpp
ACSCustomerCharacter* Customer = GetWorld()->SpawnActor<...>(...);
//  ↑ 이 한 줄 안에서 BeginPlay까지 끝남
//    → StateTree 시작 → Approach::EnterState 실행

State->StorefrontLocation = StorefrontPoint->GetActorLocation();   // ← 이미 늦음
```

월드가 이미 BeginPlay 상태면 `SpawnActor` 내부에서 `PostActorConstruction()` → `DispatchBeginPlay()`가 **동기로** 실행됩니다. 그 시점의 `StorefrontLocation`은 아직 `ZeroVector`이고, 태스크의 폴백이 걸립니다.

```cpp
// 판정 지점이 배치 안 됐으면 통행을 건너뛰고 바로 매장 이용으로
if (State->StorefrontLocation.IsNearlyZero())
{
    State->MarkEnteredStore();
    return EStateTreeRunStatus::Succeeded;   // 로그 없음, bIsStoreOpen 확인 안 함
}
```

#### 앞의 버그가 뒤의 버그를 가려주고 있었다

| | 첫 `EnterState` (Storefront = Zero) | 그 다음 |
| :--- | :--- | :--- |
| **no-op 수정 전** | 폴백 → `Succeeded`, 근데 플래그가 안 켜짐 | Root 재선택 → **`Approach` 다시 선택** → 이번엔 값이 채워져 있어 **정상 이동 + 판정** |
| **no-op 수정 후** | 폴백 → `Succeeded` + 플래그 실제로 ON | `Approach` 재선택 안 됨 → **판정 영영 없음** |

**`[입장판정]` 로그 건수가 그대로 말해줍니다.**

| 세션 | 건수 | 의미 |
| :--- | :---: | :--- |
| no-op 수정 전 | **1517건** | 무한 루프 |
| no-op 수정 후 | **0건** | 판정 자체가 실행 안 됨 |
| 정상 | **손님당 1건** | 목표 상태 |

> **버그가 버그를 우연히 상쇄하고 있었습니다.** no-op이 *"한 프레임 더 돌아서 결과적으로 제대로 동작하게"* 만들고 있었고, 그걸 고치자 아래 깔려 있던 진짜 버그가 드러났습니다. 1차에서 "닫으면 지나가던 것"도 사실 이 우회 경로 덕분이었습니다.
>
> **"고쳤더니 더 나빠졌다"가 곧 오작동은 아닙니다.** 가려져 있던 문제가 표면으로 올라온 것일 수 있습니다.

**해결: A안 + C안 병행**

*   **A안 (근본)** — `SpawnActorDeferred` + `FinishSpawning`으로 `BeginPlay`를 보류하고, 그 사이에 초기값을 전부 주입. 늦게 설정되던 **6개 항목**(`StorefrontLocation`, `ExitLocation`, `Archetype`, 시드, 빌런 배정, 평가 예산)이 한 번에 정리됩니다.
*   **C안 (재발 방지)** — 폴백을 조용히 통과시키지 않고 **`Failed` + `Warning` 로그**로 변경.

> **조용한 폴백이 이 사고의 진짜 공범이었습니다.** "값이 없으면 그냥 넘어간다"가 편의였는데, **개폐 판정이 통째로 사라졌는데도 로그가 0건**이라 원인 추적이 불가능했습니다. **폴백은 동작을 계속하게 하되, 흔적은 반드시 남겨야** 합니다.

### 6. 4차 — A안 적용 후 비주얼 회귀

A안을 넣자 손님 **비주얼이 기본 메시로 나오는** 회귀가 생겼습니다.

**`SpawnActorDeferred`가 미루는 것은 `BeginPlay`만이 아닙니다.**

| 단계 | `SpawnActor` | `SpawnActorDeferred` |
| :--- | :--- | :--- |
| 네이티브 컴포넌트 (`CreateDefaultSubobject`) | 즉시 | 즉시 |
| **BP 컴포넌트 (SCS)** | 즉시 | **`FinishSpawning`까지 보류** |
| 컨스트럭션 스크립트 | 즉시 | **보류** |
| `BeginPlay` (= StateTree 시작) | 즉시 | **보류** |

**노렸던 건 마지막 줄 하나인데 두 번째 줄이 딸려 왔습니다.**

`UCSPurchaseDecisionComponent`는 C++ 네이티브가 아니라 **`BP_CSCustomer`에 블루프린트로 추가된 SCS 컴포넌트**였습니다. 그래서 `FindComponentByClass`가 `nullptr`을 반환하고 **`if (Decision != nullptr)` 블록이 통째로 스킵**됐습니다.

```
CDO 컴포넌트 목록      : CustomerState, BasketAnchor, DropOrigin... (CSPurchaseDecision 없음)
런타임 인스턴스 목록   : ... + CSPurchaseDecision   ← 런타임에만 존재 = SCS 컴포넌트
```

**그 블록 하나에 5가지가 묶여 있었습니다.**

| 항목 | 결과 |
| :--- | :--- |
| `Decision->Archetype` | `None` — 종족 미배정 |
| **비주얼** (메시 / 애님BP / 폴백 애니) | BP 기본값 ← **보고된 증상** |
| `InitializeRandomStream(CustomerSeed)` | 미호출 → **`cs.Seed` 재현성 깨짐** |
| 빌런 배정 | 미실행 → **절도범이 안 나옴** |
| `RemainingEvaluationBudget` | 헤더 기본값 8 고정 |

PIE 실측에서 `Archetype = None`, `SKM_Manny_Simple`, `Budget = 8`을 확인해 **스포너가 배정을 시도조차 안 했다**는 걸 특정했습니다.

> **눈에 보이는 증상은 비주얼 하나였지만 실제로 깨진 건 5개**였습니다. 앞선 검증에서 입장/퇴장이 잘 돌아 보였던 건 `StoreEntryChance` 기본값이 1.0이라 **종족 데이터 없이도 판정이 성립했기 때문**입니다. 검증이 통과했다고 그 주변이 다 정상인 건 아니었습니다.

**해결 방향 3안** (아직 미적용 — 다음 작업)

| 안 | 방식 | 판단 |
| :--- | :--- | :--- |
| **1안** | `PurchaseDecision`을 **네이티브로 승격** | **권장.** A안의 전제("초기화 대상이 전부 네이티브")가 성립하고 5개가 한 번에 정상화. 손님에게 이 컴포넌트가 반드시 붙는다는 **계약이 C++에 드러남**. BP 에셋 수정 필요 |
| 2안 | Decision 초기화만 `FinishSpawning` 뒤로 | 가장 빠름, 에셋 무수정. 단 **StateTree가 이미 시작한 뒤**라 순서 문제가 그대로 남음 |
| 3안 | A안 롤백 + StateTree 자동 시작 끄기 | 시작 책임이 스포너·BP 두 곳으로 흩어짐 |

### 7. 진단 방법으로 배운 것

| 방법 | 내용 |
| :--- | :--- |
| **로그 건수가 상태를 말해준다** | 0건 = 폴백에 먹힘 / 1건 = 정상 / 1517건 = 루프. **개수 자체가 진단 지표** |
| **PIE 실측으로 특정** | 추론 대신 살아있는 손님의 UPROPERTY를 직접 조회. `entered=True`인데 `pos`가 40 m 밖 — 이 한 쌍이 원인을 확정했다 |
| **정상인 것도 기록한다** | 개폐 플래그·간판 경로·배선을 세 번 확인했는데 전부 정상. **"여기는 아니다"를 적어두니** 다음 차수에서 다시 안 봐도 됐다 |
| **비대칭 증상은 단서** | "닫으면 정상, 열면 이상" = 문제 경로가 한쪽뿐이라는 뜻 |
| **증상 문장을 분해한다** | "닫아도 들어온다" = ①재판정 없음(정상) + ②통행인 미생성(관측 불가) 두 사실 |
