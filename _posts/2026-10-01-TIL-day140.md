## 날씨 환경 연출 — 속성마다 주인을 하나로 정했다

> 날씨가 바뀔 때 **화면 색감과 레벨 조명**이 같이 바뀌게 만들었습니다. 팀원이 관리하는 낮밤 조명 컨트롤러와 **같은 액터를 건드려야** 해서, 구현보다 **"누가 무엇을 쓸 것인가"** 를 정하는 데 시간을 더 썼습니다.


### 1. 포스트 프로세스만으로는 안 된다

처음엔 **색감(포스트 프로세스)만으로 날씨를 표현할 수 있지 않을까** 했는데, 확인해보니 안 됐습니다.

> 포스트 프로세스는 **완성된 화면에 색을 덧칠할 뿐**이라, **하늘은 파랗고 그림자는 선명한 채로** 남습니다. 비가 오는데 쨍한 그림자가 지면 색만 푸르스름한 맑은 날입니다.

그래서 **역할을 세 단계로 나눴습니다** — 색감(포스트 프로세스) / 환경 액터(해·하늘·안개·달빛) / 구름.

`Env. Light Mixer`로 값을 맞춰보고 싶었는데 **에디터 전용 창이라 런타임에 못 씁니다.** 기준값을 잡을 때만 쓰고, **날씨별 변경은 코드가** 담당하게 했습니다.

---

### 2. 값은 BP에, 적용은 컨트롤러가

날씨별 수치를 **별도 데이터 에셋 없이 각 날씨 이펙트 BP**에 넣었습니다. 다만 **실제로 레벨 액터에 값을 넣는 일은 레벨에 배치한 컨트롤러**가 합니다.

**이펙트 액터가 직접 적용하면 안 되는 이유 세 가지**

| 문제 | 내용 |
| :--- | :--- |
| **복구가 꼬임** | 이전 액터 Destroy와 새 액터 Spawn이 **같은 프레임**에 일어납니다. 이전 액터가 `EndPlay`에서 원래 값을 복구하면 **새 액터가 넣은 값을 덮어씁니다** |
| **맑음은 주체가 없음** | 맑음은 이펙트 액터가 아예 없어서 **비 → 맑음 전환 시 되돌릴 주체가 없습니다** |
| **보간 불가** | 이전 액터가 즉시 사라지므로 **서서히 전환할 수 없습니다** |

> **"값을 아는 쪽"과 "값을 적용하는 쪽"을 분리**한 셈입니다. 이펙트 액터는 수명이 짧아 **원래 값을 기억할 주체가 될 수 없습니다.** 레벨에 상주하는 컨트롤러만이 *"맑음일 때의 원래 값"* 을 들고 있을 수 있습니다.

**컨트롤러가 이펙트 액터 값을 읽을 수 있는 근거**도 코드로 확인했습니다.

> 모든 날씨 변경 경로(세이브 로드·영업일 전환·날씨의 돌·디버그)에서 서브시스템이 **이펙트 액터를 먼저 스폰한 뒤 방송**합니다. 그래서 컨트롤러가 이벤트를 받는 시점에는 **항상 새 날씨의 액터**를 읽습니다.
>
> 이건 운이 좋았던 게 아니라 **확인하고 의존한 순서**라, 문서에 호출 지점 네 곳을 전부 적어뒀습니다.

**별도 데이터 에셋을 안 만든 이유**는 단순합니다 — **색감 바로 옆에서 같이 조정**하면 *"비 하나의 연출(파티클·색감·조명)이 BP 하나에"* 모입니다. 값을 고치러 두 군데를 오가지 않아도 됩니다.

### 3. 속성 하나는 한 곳에서만 쓴다

가장 걱정한 게 **낮밤 컨트롤러가 내 값을 덮어쓰는 것**이었습니다. 그래서 **속성별로 주인을 표로 그렸습니다.**

| 액터 | 속성 | 낮밤 | 날씨 |
| :--- | :--- | :---: | :---: |
| 해 | 회전 | **씀** | — |
| 해 | 밝기·색 | — | **씀** |
| 달 | 회전·색·밝기 | **씀** | 배수만 전달 |
| SkyLight·대기·안개 | 전부 | — | **씀** |

> **덮어쓰기는 두 곳이 같은 속성에 최종 값을 직접 쓸 때만** 생깁니다. 표를 그려보니 **겹치는 건 달빛 밝기 하나**뿐이었습니다.

그 하나는 **최종 값이 아니라 배수를 넘기는 방식**으로 풀었습니다.

```
낮밤 컨트롤러가 계산: 최대 밝기 × 시간 계수 × 날씨 배수
```

> 날씨 쪽은 **배수만** 넘기고 **최종 값은 낮밤이 계산**하므로, **실행 순서와 무관하게 유지**됩니다. 날씨가 먼저 켜지면 배수만 저장됐다가 첫 계산에서 반영되고, 낮밤이 먼저면 배수를 받는 순간 재계산합니다.
>
> UE가 `BeginPlay` 순서를 보장하지 않는데, **"최종 값을 쓰지 않으면 순서가 문제가 되지 않는다"** 는 게 이번에 배운 것입니다.

**다만 주의도 적어뒀습니다.** 나중에 낮밤 컨트롤러가 **해 밝기도 바꾸게 되면 겹칩니다.** 그때는 해도 달빛처럼 배수 방식으로 바꿔야 합니다.

### 4. 합치는 게 더 깔끔한데 안 합친 이유

*"조명은 낮밤 컨트롤러 하나가 시간과 날씨를 다 보고 계산하면 되지 않나"* 를 검토했습니다. **동작상 문제가 없었습니다.**

| 방식 | 낮밤 파일 수정 | 순서 문제 |
| :--- | :--- | :---: |
| **별도 컨트롤러 + 배수 전달** ✅ | **몇 줄 추가** | 없음 |
| 낮밤에 합치기 | 크게 추가 | 없음 |
| 낮밤의 밝기 기능을 가져오기 | 제거 + 이동 | 없음 |

**그런데도 별도 컨트롤러를 택했습니다.**

> **낮밤 컨트롤러는 다른 팀원이 관리해 온 파일**입니다. 합치면 그 파일을 크게 고쳐야 하고, 그러면 충돌과 리뷰 부담이 생깁니다. 겹치는 속성이 **달빛 하나뿐인 지금**은 배수 방식으로도 순서 문제가 없습니다.
>
> *"기술적으로 더 깔끔한 쪽"* 과 *"남의 파일을 덜 건드리는 쪽"* 이 갈렸고, **지금 조건에서는 후자로도 문제가 없다는 걸 확인한 뒤** 후자를 골랐습니다.

곱셈(`시간 계수 × 날씨 배수`)은 **어느 방식이든 남습니다.** 값 자체가 두 조건에 따라 정해지기 때문입니다. **없어지는 건 클래스 간 배수 전달뿐**이라, 합쳐서 얻는 게 생각보다 적었습니다.

### 5. 실내외 가중치를 둘로 나눈 이유

날씨 색감을 **실외는 1.0, 실내는 0.4**로 따로 뒀습니다.

$$\text{최종 값} = \text{레벨 기본값} + (\text{날씨 값} - \text{레벨 기본값}) \times \text{가중치}$$

| 이유 | 설명 |
| :--- | :--- |
| 실내 상품 색 보호 | 비의 푸른 톤을 매장 안에 그대로 얹으면 **조명과 상품 색이 칙칙해집니다** |
| 그래도 0은 아님 | 0으로 두면 **문을 들어서는 순간 날씨 느낌이 완전히 사라집니다** |
| **게임플레이 신호** | 날씨가 **상품 수요에 영향을 주는 요소**라, 실내에서도 *"오늘 비가 온다"* 가 보여야 합니다 |

> 세 번째가 결정적이었습니다. **플레이 시간 대부분이 실내**인데 실내 가중치가 너무 낮으면 **날씨를 체감할 수 없습니다.** 연출이 아니라 **정보 전달**의 문제입니다.

전환 시간이 **두 값의 차이에 비례**한다는 것도 정리해뒀습니다.

$$\text{전환 시간} = |\,\text{실외} - \text{실내}\,| \times \text{페이드 시간}$$

기본값이면 약 1.2초입니다. **속도가 고정이라 차이가 클수록 오래 걸립니다.**

**한계도 적었습니다.** 포스트 프로세스는 **화면 전체**에 적용되므로, *"안은 밝고 창밖은 비 오는"* 식의 **영역별 색감은 만들 수 없습니다.**
