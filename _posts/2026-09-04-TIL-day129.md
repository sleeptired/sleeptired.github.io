# Part 1. [진단] 바닥이 두 겹이었다

### 1. 증상

매장 **안쪽**에서, 특히 **벽에 붙이려는 자리**에서 진열대를 설치하려 하면:

*   프리뷰가 나무 바닥을 뚫고 **아래로 매몰**된 채 표시됨
*   프리뷰가 빨갛게 되고 HUD에 **"매장 밖에는 놓을 수 없습니다"**
*   시설에 따라 그대로 **나무 바닥 아래 지면에 설치**되기도 함

**매장 한복판인데 "매장 밖"이라는 게** 이상해서 파고들었습니다.

### 2. 원인 — 조준면이 바닥인지 검사하지 않는다

레벨을 실측해보니 **매장 바닥이 두 겹**이었습니다.

| 면 | Z | 비고 |
| :--- | ---: | :--- |
| 나무 바닥 판 윗면 | **291.6** (일부 289.6) | 액터 63개, **벽까지 깔려 있지 않음** |
| `Inside` 셸의 바닥 슬래브 | **234.0** | 나무 판 아래, **벽 아래까지 이어짐** |

그리고 배치 좌표 계산이 이렇게 동작합니다.

```
1. 카메라 정면으로 라인 트레이스 → AimPoint
   ★ 조준면이 바닥인지 검사하지 않는다. 벽을 보면 벽면이 그대로 AimPoint가 된다.
2. AimPoint의 XY에서 수직 아래로 트레이스 → 바닥 채택
3. 탈락하면 1uu 더 파고들어 최대 32회 재시도
```

> **벽 밑동을 조준하면 `AimPoint`의 XY가 벽 안쪽이 되고, 그 XY에는 나무 판이 없습니다.** 그래서 수직 트레이스가 **아래 슬래브(234)를 "정상 바닥"으로 채택**합니다. 법선 Z가 1.0이니 검사도 통과합니다.

그리고 판정 영역 TriggerBox의 **Z 하한이 270**이라, **`234 < 270 < 291.6`** — 영역 바닥면이 **두 바닥 사이에 끼어** 있습니다. 아래 슬래브에 스냅되는 순간 자동으로 "매장 밖"이 됩니다.

**한 줄로:** 조준면 검증이 없어서 **잘못된 바닥을 잡고**, 영역 Z 하한이 두 바닥 사이라 **그 즉시 매장 밖 판정**이 납니다.

### 3. 실측으로 빈도를 정량화하기

*"왜 특정 부분에서만 나는가"* 를 말로 설명하는 대신, **코드와 동일한 트레이스를 에디터에서 재현**해 매장 내부 조준 방향 **1456개를 샘플링**했습니다.

| 결과 | 개수 |
| :--- | ---: |
| 정상 (291.6 채택) | 1255 |
| **바닥 아래 (234 채택)** | **141 (약 10%)** |
| 바닥 못 찾음 | 60 |

**바닥 아래로 떨어진 141건은 전부 벽 근처**였습니다.

> **"특정 자리에서만 난다"는 관찰이 "약 10%, 전부 벽 근처"라는 수치가 되니** 원인 가설과 정확히 맞아떨어졌습니다. 며칠 전 오크 버그에서 **경계값을 특정하니 원인이 특정됐던** 것과 같은 방식인데, 이번엔 **분포를 재는** 형태였습니다.
>
> 재현 스크립트를 짜는 데 시간이 들었지만, 그게 **"벽 근처"라는 조건을 확정**해줬습니다. 안 했으면 *"어쩌다 되고 어쩌다 안 되는"* 문제로 남았을 겁니다.

### 4. 여유가 애초에 없었다

조사하다 보니 **정상 바닥을 잡아도 위험한 상태**였습니다.

시설의 판정용 콜리전 박스가 **시설 바닥보다 70uu 아래로 튀어나와** 있었습니다.

| 채택 바닥 | 콜리전 박스 밑면 | 영역 하한 270 |
| :--- | ---: | :--- |
| 정상 (291.6) | **221.0** | **49 낮음** ← 이미 밖 |
| 아래 슬래브 (234.0) | 163.4 | 106 낮음 |

> **정상 동작해도 이미 영역을 벗어나 있습니다.** 지금 안 터지는 건 다른 조건이 가려주고 있는 것뿐입니다. **"증상이 나는 케이스"를 조사하다가 "안 나는 케이스도 위험하다"를 발견**한 셈이라, 수정 방향에 이 항목도 넣었습니다.

부수 요인도 정리했습니다. 나무 판이 **63개 개별 액터**이고 윗면 높이가 **291.6 / 289.6 두 종류로 섞여** 있어 판 경계에서 판정이 더 쉽게 흔들립니다. 심플 콜리전(자동 생성 convex hull)이 보이는 메시와 미세하게 달라, **시각적으로는 바닥인데 트레이스 결과가 다를** 수도 있습니다.

### 5. 팀원에게 전달

원인을 확정하고 **담당 팀원에게 전달**했습니다.

# Part 2. [설계] 계산대 대기줄 도착 판정

### 6. 원안이 틀렸다는 결론부터

원래 요구는 *"줄 판정 영역(박스)을 만든다"* 였는데, 조사하니 **박스로는 안 고쳐집니다.**

**진짜 원인은 위치 판정이 없는 것이 아니라, `Queue` 배열에 들어간 순간을 곧 "계산 가능"으로 쓰고 있는 것**입니다.

```
t=0.0s  손님이 Checkout 진입 → JoinQueue() → Queue[0] 확정
                             → MoveToLocation(슬롯0)  ← 30m, 12초 걸어야 함
        ─── 이 시점부터 이미 계산 대상 ───
t=0.1s  플레이어 상호작용 → 손님이 널이 아니므로 통과 → 계산 UI 열림
t=3.0s  결제 완료
t=3.1s  손님은 매장 중앙에서 쇼핑백을 든 채 출구로 방향을 바꿈
```

**계산대 위에 손님이 없는데 상품이 스폰되고, 카메라가 빈 계산대를 비춥니다.**

**박스로 고치려면** 줄 전체를 덮어야 하니 길이가 `슬롯 간격 × 슬롯 수` = 600cm가 됩니다. 그러면 **줄 꼬리에 막 들어온 손님도 박스 안**이라, 그 손님이 `Queue[0]`일 때 여전히 **6m 밖에서 계산**됩니다.

> **증상이 30m에서 6m로 줄어들 뿐 원인은 그대로 남습니다.** 원안을 그대로 구현했으면 *"고쳤는데 여전히 이상하다"* 가 됐을 겁니다.
>
> 요구사항이 **해결 방법의 형태로 들어오면** 그 방법이 원인에 닿는지 먼저 확인해야 한다는 걸 배웠습니다. *"영역을 만들어 달라"* 는 요구는 사실 *"걸어오는 중에 계산되지 않게 해 달라"* 였습니다.

### 7. ⭐ `Queue[0]`이 네 가지를 겸하고 있었다

원인을 한 겹 더 들어가니 이렇게 정리됐습니다.

| `Queue[0]`의 의미 | 언제 참이어야 하나 | 현재 |
| :--- | :--- | :--- |
| ① 줄 순번 = 0 (설 자리 좌표) | **결심한 순간부터** | 맞음 |
| ② 인내심 카운트다운 대상 | 자리에 **도착한 뒤부터** | **걷는 동안에도 깎임** |
| ③ 플레이어가 계산할 수 있는 손님 | 자리에 **도착한 뒤부터** | **결심한 순간부터** ← **버그** |
| ④ 지금 응대 중인 손님 | 계산 UI가 열려 있는 동안 | **구분 안 됨** |

> **두 시점이 다른데 하나의 배열이 넷 다를 표현하고** 있었습니다.
>
> 그래서 수정 방향이 *"①은 그대로 두고 ③만 떼어낸다"* 로 정해졌습니다. **①을 도착 기준으로 바꾸면 안 됩니다** — 두 손님이 0번 자리를 두고 경합해서 순번이 계속 뒤바뀌고 이동 명령이 매 틱 재발급됩니다.
>
> 하나의 값이 여러 의미를 겸하는 건 며칠 전 *"하나의 반환값을 성질 다른 곳에 쓰지 않는다"* 와 같은 이야기인데, 이번엔 **의미마다 유효해지는 시점이 달랐습니다.** "무엇을 뜻하는가"가 아니라 **"언제부터 참인가"로 쪼개야** 했습니다.

### 8. 정답 패턴이 프로젝트 안에 이미 있었다

**진열대가 똑같은 문제를 똑같은 방법으로 이미 풀어 놨습니다.**

| 진열대 (기존) | 계산대 (신규) |
| :--- | :--- |
| `TryGetBrowseZone()` | `TryGetQueueSlotZone()` |
| `IsPointInsideBrowseZone()` | `IsPointInsideQueueSlotZone()` |
| `BrowseZoneRadius = 75` | `QueueSlotRadius = 50` |
| "영역 안에 멈췄는가"가 유일한 도착 조건 | 같음 |

**본문은 기준점만 바꿔 그대로 씁니다.** XY만 고정하고 Z만 NavMesh에 투영하는 것, `Dist2D`로 종족별 캡슐 높이 영향을 배제하는 것까지 동일합니다.

> **"이 프로젝트에는 이미 정답 패턴이 있고 계산대만 그 패턴을 안 쓰고 있다"** 가 이번 설계의 핵심 문장이 됐습니다. 새 방식을 고안하는 대신 **베낄 대상을 찾은 것**이 설계 시간을 크게 줄였습니다.
>
> 8월 중순에도 *"폴링으로 우회하려던 문제를 이미 두 곳에서 같은 패턴으로 풀고 있었다"* 를 겪었는데, 그때 배운 걸 이번엔 **처음부터 적용**했습니다. 새 문제를 만나면 **프로젝트 안에서 같은 문제를 이미 푼 곳부터 찾는 것**이 습관이 되어가는 것 같습니다.

컴포넌트를 안 만드는 것도 결론이었습니다. 슬롯 좌표를 이미 정확히 알고 있으니 **좌표 + 반경이 더 적은 코드로 같은 일을** 합니다. 새 콜리전도, 오버랩 이벤트도, 물리 쿼리 오염도 없습니다.

값 부등식도 명시했습니다.

```
이동 허용 반경(30)  <  QueueSlotRadius(50)  <  QueueSlotSpacing / 2 (60)
```

왼쪽을 어기면 **손님이 멈춘 자리가 영역 밖이어서 영원히 계산이 안 되고**, 오른쪽을 어기면 **0번과 1번 영역이 겹칩니다.** 그래서 `OnConstruction()`에서 자동 보정해 **진실의 출처를 슬롯 간격 하나로** 유지하기로 했습니다.

### 9. 부분 수정이 회귀를 만든다

게이트만 넣으면 **연쇄 계산이 망가집니다.**

> 영수증 퇴장 연출이 끝나면 즉시 다음 손님 주문을 만들고, **실패하면 계산 세션 전체를 닫습니다.** 게이트를 넣으면 다음 손님은 아직 120cm를 걷고 있으므로 **항상 실패**합니다. 그러면 손님이 줄줄이 서 있는데도 **매번 카메라가 튕겨 나가고** 플레이어가 다시 상호작용해야 합니다. **지금보다 나빠집니다.**

그래서 실패를 **"없음"과 "아직 안 옴"으로 구분**하는 부속 작업을 같은 커밋에 묶었습니다.

```
다음 손님 도착함        → 기존 경로
Queue에 손님은 있음      → 카메라·UI 유지하며 대기  (신규)
Queue가 비었음          → 세션 종료 (기존 경로)
```

> **"이 부속 작업을 빼면 회귀입니다"** 라고 문서에 굵게 적었습니다. 버그 하나를 고치면서 **다른 동작을 깨뜨리는 부분 수정**이 되기 쉬운 자리라, 커밋 단위를 나누지 말라고 못 박았습니다.
>
> 8월에 *"커밋의 경계는 빌드가 깨지지 않는 최소 단위"* 를 배웠는데, 이번엔 **"게임 동작이 퇴행하지 않는 최소 단위"** 였습니다.

남는 빈틈도 인정했습니다. 손님이 **영역 경계를 스치는 순간** 게이트가 열려 최대 **50cm 앞**에서 계산이 시작될 수 있습니다. 이동 정지 조건을 추가하면 완전히 막히지만 **권장하지 않았습니다** — 다른 손님에게 밀려 미세하게 움직이는 동안 게이트가 닫혀 **"손님이 앞에 있는데 계산이 안 되는" 반대 증상**이 생깁니다.

### 11. 현재의 결함이 우연히 안전장치였다

인내심 타이머도 같은 원인의 문제입니다. 지금은 **걸어오는 12초가 인내심에서 깎입니다.** 매장이 크면 **줄에 아무도 없어도 도착 전에 포기**할 수 있습니다.

이것도 게이트가 생기면 한 줄로 정리되는데, **그것만 넣으면 더 나빠집니다.**

> 경로가 막혀 손님이 영원히 자리에 못 가면 **인내심이 흐르지 않아 `Queue[0]`에 영구히 박혀서 줄 전체가 정지**합니다.
>
> **지금은 인내심이 무조건 흐르기 때문에 이 상황이 자동으로 해소되고 있습니다.** 즉 **현재 동작은 우연히 안전장치 역할을 하고 있습니다.**

그래서 인내심 시점 교정은 **접근 타임아웃과 한 묶음**이어야 합니다. 그리고 두 시간을 구분해서 방송해야 **경로 실패로 못 온 손님을 "오래 기다려서 화난 손님"으로 집계하지 않습니다.**

> 이틀 전 *"버그가 버그를 가린다"* 를 정리했는데, 이번엔 **"결함이 다른 결함을 막아주고 있다"** 였습니다. 고칠 때 **그것이 무엇을 대신 막고 있었는지** 확인해야 합니다.

### 12. 조사하다 발견한 별도 결함

인내심 코드를 읽다가 **원인은 같은 계열이지만 재현이 다른** 문제를 하나 더 찾았습니다.

인내심 누적에 **"지금 계산 UI가 열려 있는가"라는 조건이 없습니다.** 그래서 플레이어가 스캔을 느리게 하면 **응대 중인 손님이 인내심 만료로 줄을 떠납니다.** 그러면:

```
Queue = [A, B],  위젯 = A의 주문
A 인내심 만료 → LeaveQueue(A) → Queue = [B]
플레이어가 결제 → GetFrontCustomer()는 B → A의 주문이 기록됨
   → B에게 계산 완료 처리
결과: A의 물건값이 매출로 기록되고, B의 물건은 공짜로 나간다
```

이게 §8 표의 **④ "지금 응대 중인 손님"이 `Queue[0]`과 구분되지 않는** 문제입니다.

> **응대받는 중인 손님이 "기다리다 지쳐" 나가는 건 게임 규칙으로도 틀렸습니다.** 그래서 응대 중 인내심 정지 + 결제 대상을 `Queue[0]`이 아니라 **"UI를 연 그 손님"으로 못 박는** 두 수정을 같이 제안했습니다.
>
> **원래 버그와 파일은 같은데 원인과 재현이 다르므로 별도 이슈로 분리**하기로 했습니다. 같이 고치면 어느 수정이 무엇을 고쳤는지 알 수 없게 됩니다.

### 13. 원안은 버리지 않고 용도를 바꿨다

박스 영역은 **버그 수정용으로는 부적합**하지만, **건축 모드에서 대기줄 자리를 보호하는 용도로는 그것이 정답**입니다.

> 며칠 전 설계한 접근 영역 문서의 **2단계가 정확히 이것**입니다. 계산대 BP에 태그 박스를 붙이면 그 문서의 규칙이 **자동으로 적용**됩니다.
>
> **두 작업은 상충하지 않고 직교합니다.** *"원안이 틀렸다"* 가 아니라 *"원안은 다른 문제의 답이었다"* 로 정리한 게 이번 설계에서 마음에 드는 부분입니다.

그래서 순서를 이렇게 잡고, **1단계와 4단계를 같은 브랜치에 넣지 말라**고 적었습니다.

```
1단계  슬롯 도착 게이트 (+ 연쇄 계산 대기)   ← 게임플레이 버그 수정
2단계  스캔 중 이탈 결함                    ← 별도 이슈
3단계  인내심 시점 교정 (+ 접근 타임아웃)
4단계  대기줄 건축 보호                     ← 레벨 배치 규칙 추가
```

> 4단계는 **기존 레벨 배치를 전부 빨강으로 만들 수 있어** 롤아웃을 따로 관리해야 합니다. **성격이 다른 변경을 한 브랜치에 담으면 롤백 단위가 사라집니다.**
