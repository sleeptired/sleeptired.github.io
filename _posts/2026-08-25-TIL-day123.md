## 손님 유입 평판 등급 구동 — 완료된 구조와 남긴 판단

> 손님 스폰의 구동 축을 **상점 레벨 → 평판 등급**으로 전환하는 작업이 끝났습니다(`3ac18ca`). 코드는 완료됐고, 오늘 문서를 정리하면서 **"만들지 않기로 한 것"** 과 **"고치지 않고 기록만 해둔 것"** 을 판단 근거와 함께 남겼습니다.

---

### 1. 개점 스냅샷 — "반영 시점"은 가드가 아니라 읽는 방식의 문제

사양은 **"평판 점수·등급은 실시간으로 바뀌어도 되지만, 유입에 반영되는 시점은 다음 개점으로 고정한다"** 입니다.

처음 떠올린 방법은 *"콜백 앞에 `Open`이면 `return`"* 이었는데, **그것만으로는 안 됐습니다.**

| 값 | 반영 경로 | 콜백 가드로 막히나 |
| :--- | :--- | :---: |
| 스폰 간격 | 등급 콜백 → `ApplySpawnTimer()` | 막힘 |
| **동시 인원 상한** | **`TrySpawnCustomer()`가 매 회차 `GetCurrentMaxAlive()` 재조회** | **안 막힘** |

**두 값이 서로 다른 경로로 반영되고 있었습니다.** 타이머는 콜백이 다시 걸지만, 상한은 타이머와 무관하게 매 스폰마다 새로 읽습니다. 콜백만 막으면 **간격은 고정되는데 상한만 즉시 바뀌는 반쪽 상태**가 됩니다.

```cpp
// 해결: 두 값이 원래부터 공유하던 지점을 얼린다
ECSReputationGrade ACSCustomerSpawner::GetReputationGrade() const
{
    return AppliedReputationGrade;   // GameState를 직접 읽지 않는 것이 핵심
}
```

> **갈라지는 경로를 각각 막는 대신 갈라지기 전 공통 지점을 찾아 막으니 한 번에 해결됐습니다.** 그러고 나니 등급 콜백에 남는 일이 없어서 **구독 자체를 제거**했습니다. 지금 스포너가 구독하는 건 **피크(`OnScheduleEventFired`)와 단계 전환(`OnStorePhaseChanged`) 둘뿐**입니다.

**부수 효과:** 콜백만 막았다면 **피크 시작 시 `ApplySpawnTimer()`가 `GetReputationGrade()`를 다시 부르면서 그 시점의 실시간 등급을 끌어들였을** 겁니다. 지금은 누가 언제 부르든 평판 인자가 스냅샷입니다.

그리고 **피크는 일부러 스냅샷 대상에서 뺐습니다.** 하루 안에서 바뀌는 값이라 즉시 반영돼야 하기 때문입니다. **무엇을 얼리고 무엇을 안 얼릴지가 곧 사양**이었습니다.

### 2. `BeginPlay` 시딩 — 캐시가 덮여 있던 문제를 드러냈다

스냅샷을 넣자 **1일차 유입이 틀어지는** 문제가 나왔습니다.

**원인:** `InitializeStoreProgression()`은 **값이 실제로 바뀐 항목만** 방송하는데, 초기값과 헤더 기본값이 **둘 다 6000 / `Normal`** 이라 값이 같습니다. → **게임 시작 시 평판 델리게이트가 한 번도 안 울립니다.**

**예전에는 이 문제가 자동으로 덮여 있었습니다.** 값을 캐시하지 않고 매번 GameState에서 직접 읽었기 때문에 초기화 순서와 무관하게 현재 등급이 반영됐습니다.

> **스냅샷은 곧 캐시**라, 그 순간 덮여 있던 함정이 되살아났습니다. 1일차는 시작 단계가 `Preparation`이라 `Open` 전환을 기다릴 수도 없어서, **1일차 전체가 멤버 기본값으로** 돌게 됩니다.

```cpp
RefreshAppliedReputationGrade();   // ← 반드시 앞에서
ApplySpawnTimer();                 //   타이머가 스냅샷을 읽어 간격을 계산하므로
```

**"실시간 조회"가 성능이 아니라 초기화 순서를 덮어주고 있었다**는 게 이번 작업에서 가장 인상적이었습니다. 캐시로 바꾸는 최적화는 **원래 있던 문제를 드러나게** 합니다.

새 규칙도 하나 세웠습니다. **`CachedStoreGameState->GetReputationGrade()`를 부르는 곳은 `RefreshAppliedReputationGrade()` 하나뿐**이고, 호출처는 **`BeginPlay()`와 개점 전환 둘로만** 제한합니다.

### 3. 만들지 않기로 한 것들

이번 작업에서 새로 만든 타입은 **`FCSReputationTrafficRow` 구조체 하나**뿐입니다. 후보로 떠올랐다가 기각한 것들을 이유와 함께 남겼습니다.

| 만들 뻔한 것 | 기각 사유 |
| :--- | :--- |
| `CSCustomerTrafficTypes.h` (별도 파일) | 쓰는 곳이 **데이터 에셋과 스포너 둘뿐.** 파일을 나눌 이유가 없다 |
| `FCSTrafficContext` (입력 묶음) | 입력이 **등급 + 피크 둘뿐.** 나중에 요일·날씨가 붙어도 **인자를 하나 늘리는 편이 싸다** |
| `FCSTrafficProfile` (결과 묶음) | 필요한 건 간격 하나, 인원 하나. **게터 두 개면 충분** |
| `DailyTargetCustomers` | **간격에서 계산되어 나오는 값.** 저장하면 진실이 둘이 된다 |
| `EstimateDailySpawnCount()` | 스폰에 관여하지 않는 **디버그 계산**. 필요하면 손계산 |
| 점수 → 배율 커브 | 등급이 하루 1회만 바뀌면 **연속 곡선의 이점이 없다** |

> **"나중에 필요할지도"로 만드는 추상화가 가장 비쌉니다.** 특히 입력/결과 묶음 구조체는 만들기 쉬워서 자주 만들게 되는데, **인자가 둘뿐이면 구조체가 오히려 한 단계를 더 만듭니다.** 기각 사유를 문서에 적어두니, 나중에 누가 같은 걸 제안해도 논의가 빨라질 것 같습니다.

**하루 목표를 저장하지 않은 것**이 특히 중요했습니다. 하루 목표는 간격에서 나오는 결과라, 둘 다 저장하면 **간격만 고치는 순간 저장된 목표가 거짓말**이 됩니다. 그래서 코드는 그 숫자를 아예 모르고, **문서의 표와 생성자 주석에만** 근거로 남겼습니다.

### 4. 구조체 하나는 왜 필요했나

등급별 테이블을 에디터에서 편집하려면 **배열 원소가 리플렉션이 아는 타입**이어야 합니다. `(등급, 간격, 인원)` 세 쌍을 묶을 방법은 `USTRUCT`뿐입니다.

```cpp
// 예전 구조 (제거됨) — 배열 두 개가 따로 논다
TArray<float> LevelSpawnIntervalSeconds;   // [0]=Lv1, [1]=Lv2, ...
TArray<int32> LevelMaxAliveCustomers;      // 길이가 어긋나면 조용히 깨짐

// 지금 — 한 행에 세 값이 묶여 있다
TArray<FCSReputationTrafficRow> GradeRows;
```

> 예전 코드에 `HasValuesForLevel()` 같은 **방어 함수가 있던 이유가 이것**이었습니다. **묶여야 할 값이 따로 있으면 그걸 지키는 코드가 따로 필요해집니다.** 구조체로 묶으니 그 방어 함수 자체가 사라졌습니다. 며칠 전 `SelectItemIds` 통합에서 *"두 배열 병행은 동기화 책임만 늘린다"* 고 정리했던 것과 같은 패턴입니다.

`FindRowForGrade()`는 **정확히 일치하는 등급이 없으면 그보다 낮은 등급 중 가장 높은 행**으로 폴백합니다. `GetReputationGradeForScore()`와 같은 사고방식이라 **배열 순서에 의존하지 않습니다.**

### 5. `MaximumAliveCustomers`가 왜 별도 필드인가

등급 행과 배율만으로는 **"비피크 10명, 피크 12명"을 표현할 수 없습니다.**

| 시도 | 결과 |
| :--- | :--- |
| `Excellent` 행을 10으로 | 피크가 무조건 **20명** (10 × 2.0) |
| 행 값을 6으로 낮춤 | 피크는 12명이 되지만 **비피크가 6명으로 줄어듦** |

곱셈은 두 값을 **같이** 움직이므로, 한쪽만 제한하려면 **"위로만 자르는" 별도의 상한**이 필요합니다.

### 6. 수치를 고치지 않고 편차를 기록한 판단

하루 유입량을 검증해보니 **현재 값이 목표를 13~29% 초과**합니다.

$$\text{하루 스폰 수} = \frac{T-P}{I} + \frac{P}{I/2} = \frac{T+P}{I} = \frac{680}{I}$$

($T$ = 영업 600 실제초, $P$ = 피크 80 실제초)

| 등급 | 현재 간격 | 예상 스폰 수 | 하루 목표 | 편차 |
| :--- | ---: | ---: | ---: | :--- |
| `VeryBad` | 60 | 11.3 | 10~12 | 범위 안 |
| `Bad` | 40 | 17.0 | 15~17 | 범위 상단 |
| `Normal` | 27 | 25.2 | 22 | **+15%** |
| `Good` | 20 | 34.0 | 30 | **+13%** |
| `Excellent` | 15 | 45.3 | 35~40 | **+13~29%** |

현재 값은 `600 ÷ 목표`로 계산된 것인데, **피크 구간에서 간격이 절반이 되는 걸 빼먹은 계산**이었습니다. 600이 아니라 **680**으로 나눠야 합니다.

**그런데 값을 고치지 않았습니다.** 대신 역산표(`680 ÷ 목표`)를 함께 적어두고 **조정 여부를 기획 판단으로 남겼습니다.**

> 초과가 **버그가 아니라 밸런스 선택지**이기 때문입니다. *"목표에 정확히 맞춘다"* 와 *"손님이 좀 더 많이 온다"* 중 어느 쪽이 재미있는지는 **제가 정할 문제가 아닙니다.** 코드는 이미 어느 쪽이든 될 수 있는 상태라, **판단에 필요한 숫자만 만들어두고 결정은 넘기는 것**이 맞다고 봤습니다.
>
> 며칠 전 *"개선 가능 ≠ 내가 결정"* 이 남의 파트 코드 얘기였다면, 이번엔 **밸런스 수치**에 같은 원칙을 적용한 셈입니다.

그리고 이 표는 **피크 길이나 배율을 바꾸면 통째로 흔들립니다.** 수치를 손댈 때 산식을 다시 돌리라는 경고를 함께 남겼습니다.

### 7. 클램프가 임계 체류시간을 바꾼다

`TrySpawnCustomer()`는 상한에 걸리면 **그 회차를 그냥 건너뜁니다.** 밀렸다가 나중에 나오지 않습니다.

$$\text{상한에 걸림} \iff \text{평균 체류시간}(L) > \text{동시 상한} \times \text{간격}(I)$$

| 등급 | 비피크 | 피크 |
| :--- | ---: | ---: |
| `VeryBad` | 60 × 3 = **180초** | 30 × 6 = 180초 |
| `Normal` | 27 × 5 = **135초** | 13.5 × 10 = 135초 |
| `Good` | 20 × 7 = **140초** | 10 × 12 = **120초** ← 클램프 |
| `Excellent` | 15 × 10 = **150초** | 7.5 × 12 = **90초** ← 클램프 |

> **여기서 구조가 하나 보였습니다.** 피크는 간격을 나누고(`÷2`) 상한을 곱하므로(`×2`) **곱이 그대로**입니다. 즉 **클램프에 안 걸리는 등급은 피크가 임계치를 전혀 바꾸지 않습니다.**
>
> 반대로 **하드 상한 12에 걸리는 `Good`·`Excellent`만** 상한이 덜 오르면서 임계치가 내려갑니다. 가장 빡빡한 구간이 **`Excellent` + 피크의 90초**인 것도 그래서입니다.
>
> **상한을 두는 순간 "안전장치"가 아니라 "밸런스 변수"가 됩니다.** 12라는 숫자가 최고 등급의 피크에서만 하루 목표를 깎는 구조라, 이걸 모르고 12를 올리면 다른 등급은 아무 변화가 없는데 최고 등급만 움직입니다.

손님이 스폰 → 이동 → 입장 → 쇼핑 → 계산 → 퇴장에 **90초를 넘게 쓰면** 실제 스폰 수가 예상보다 적게 나옵니다. 조정 수단 세 가지(하드 상한 완화 / 피크 배율 완화 / 체류시간 단축)를 적어뒀는데, **어느 걸 만질지는 실제로 돌려본 뒤에** 정할 일입니다.

### 8. 남은 것

| 항목 | 내용 |
| :--- | :--- |
| **간격 재조정 여부** | 기획 판단. 조정 시 `680 ÷ 목표` 역산값 사용 |
| **스포너 BP 클래스 기본값** | `TrafficDataAsset`이 **네 맵의 인스턴스에만** 지정돼 있어, 새 맵에 스포너를 놓으면 **폴백(5초/5명)으로 돈다** |
| `AddReputation()` 호출자 없음 | C++ 호출자 0건. 디버그 BP 둘뿐 → 평판이 6000(`Normal`)에 고정 |
| 평판 해금 코드/데이터 불일치 | 시설은 **코드는 있는데 데이터가 전부 `None`**, 상품은 **필드에 값이 있는데 읽는 코드가 없음** |

> 두 번째가 **실패하는 종류**라 눈에 띄었습니다. 새 맵에 스포너를 놓으면 아무 경고 없이 폴백 값으로 돌아갑니다. 클래스 기본값에 지정해두면 인스턴스마다 꽂을 필요가 없어집니다.
>
> 네 번째는 **코드와 데이터가 서로 다른 방향으로 어긋난** 사례입니다. 한쪽은 판정 코드가 살아 있는데 데이터가 비어 무효화됐고, 다른 쪽은 데이터에 값이 들어 있는데 읽는 코드가 없습니다. **"동작하지 않는다"는 결과는 같지만 정리 방법은 반대**입니다.

**테스트 방법도 바뀌었습니다.** 디버그 액터를 눌러도 그 자리에서는 유입이 안 바뀌고, 하루를 넘겨 **개점 로그**로 확인해야 합니다.

```
[CSCustomerSpawner] 개점 - 오늘 적용 평판 등급 Normal / 생성 간격 27.00초 / 동시 상한 5명
```

HUD 등급이 올라갔는데 개점 로그의 등급이 그대로면 스냅샷 갱신 쪽을 의심하면 됩니다. *(디버그 액터는 `±1000`이라 초기 6000에서 등급을 넘기려면 **두 번** 눌러야 합니다.)*

| 배운 것 | 내용 |
| :--- | :--- |
| **"반영 시점"은 가드가 아니라 읽는 방식** | 두 값이 다른 경로로 반영되고 있었다. 갈라지기 전 공통 지점을 얼리는 게 답 |
| **무엇을 얼리고 무엇을 안 얼릴지가 사양** | 등급은 스냅샷, 피크는 즉시. 둘을 구분하는 것 자체가 설계 |
| **캐시는 덮여 있던 문제를 드러낸다** | 실시간 조회가 초기화 순서 문제를 가려주고 있었다 |
