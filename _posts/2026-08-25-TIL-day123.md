## 손님 유입 평판 등급 구동

> 손님 스폰의 구동 축을 **상점 레벨 → 평판 등급**으로 전환하는 작업이 끝났습니다(`3ac18ca`). 코드는 완료됐고, 오늘 문서를 정리하면서 **"만들지 않기로 한 것"** 과 **"고치지 않고 기록만 해둔 것"** 을 판단 근거와 함께 남겼습니다.

---

### 1. 개점 스냅샷 — "반영 시점"은 가드가 아니라 읽는 방식의 문제

사양은 **"평판 점수·등급은 실시간으로 바뀌어도 되지만, 유입에 반영되는 시점은 다음 개점으로 고정한다"** 입니다.

처음 떠올린 방법은 *"콜백 앞에 `Open`이면 `return`"* 이었는데, **그것만으로는 안 됐습니다.**

| 값 | 반영 경로 | 콜백 가드로 막히나 |
| :--- | :--- | :---: |
| 스폰 간격 | 등급 콜백 → `ApplySpawnTimer()` | 막힘 |
| **동시 인원 상한** | **`TrySpawnCustomer()`가 매 회차 `GetCurrentMaxAlive()` 재조회** | **안 막힘** |

**두 값이 서로 다른 경로로 반영되고 있었습니다.** 타이머는 콜백이 다시 걸지만, 상한은 타이머와 무관하게 매 스폰마다 새로 읽습니다. 콜백만 막으면 **간격은 고정되는데 상한만 즉시 바뀌는 반쪽 상태**가 됩니다.

```cpp
// 해결: 두 값이 원래부터 공유하던 지점을 얼린다
ECSReputationGrade ACSCustomerSpawner::GetReputationGrade() const
{
    return AppliedReputationGrade;   // GameState를 직접 읽지 않는 것이 핵심
}
```

> **갈라지는 경로를 각각 막는 대신 갈라지기 전 공통 지점을 찾아 막으니 한 번에 해결됐습니다.** 그러고 나니 등급 콜백에 남는 일이 없어서 **구독 자체를 제거**했습니다. 지금 스포너가 구독하는 건 **피크(`OnScheduleEventFired`)와 단계 전환(`OnStorePhaseChanged`) 둘뿐**입니다.

**부수 효과:** 콜백만 막았다면 **피크 시작 시 `ApplySpawnTimer()`가 `GetReputationGrade()`를 다시 부르면서 그 시점의 실시간 등급을 끌어들였을** 겁니다. 지금은 누가 언제 부르든 평판 인자가 스냅샷입니다.

그리고 **피크는 일부러 스냅샷 대상에서 뺐습니다.** 하루 안에서 바뀌는 값이라 즉시 반영돼야 하기 때문입니다. **무엇을 얼리고 무엇을 안 얼릴지가 곧 사양**이었습니다.

### 2. `BeginPlay` 시딩

스냅샷을 넣자 **1일차 유입이 틀어지는** 문제가 나왔습니다.

**원인:** `InitializeStoreProgression()`은 **값이 실제로 바뀐 항목만** 방송하는데, 초기값과 헤더 기본값이 **둘 다 6000 / `Normal`** 이라 값이 같습니다. → **게임 시작 시 평판 델리게이트가 한 번도 안 울립니다.**

**예전에는 이 문제가 자동으로 덮여 있었습니다.** 값을 캐시하지 않고 매번 GameState에서 직접 읽었기 때문에 초기화 순서와 무관하게 현재 등급이 반영됐습니다.

> **스냅샷은 곧 캐시**라, 그 순간 덮여 있던 함정이 되살아났습니다. 1일차는 시작 단계가 `Preparation`이라 `Open` 전환을 기다릴 수도 없어서, **1일차 전체가 멤버 기본값으로** 돌게 됩니다.

```cpp
RefreshAppliedReputationGrade();   // ← 반드시 앞에서
ApplySpawnTimer();                 //   타이머가 스냅샷을 읽어 간격을 계산하므로
```

**"실시간 조회"가 성능이 아니라 초기화 순서를 덮어주고 있었다**는 게 이번 작업에서 가장 인상적이었습니다. 캐시로 바꾸는 최적화는 **원래 있던 문제를 드러나게** 합니다.

새 규칙도 하나 세웠습니다. **`CachedStoreGameState->GetReputationGrade()`를 부르는 곳은 `RefreshAppliedReputationGrade()` 하나뿐**이고, 호출처는 **`BeginPlay()`와 개점 전환 둘로만** 제한합니다.

### 3. 구조체 생성 이유

등급별 테이블을 에디터에서 편집하려면 **배열 원소가 리플렉션이 아는 타입**이어야 합니다. `(등급, 간격, 인원)` 세 쌍을 묶을 방법은 `USTRUCT`뿐입니다.

```cpp
// 예전 구조 (제거됨) — 배열 두 개가 따로 논다
TArray<float> LevelSpawnIntervalSeconds;   // [0]=Lv1, [1]=Lv2, ...
TArray<int32> LevelMaxAliveCustomers;      // 길이가 어긋나면 조용히 깨짐

// 지금 — 한 행에 세 값이 묶여 있다
TArray<FCSReputationTrafficRow> GradeRows;
```

> 예전 코드에 `HasValuesForLevel()` 같은 **방어 함수가 있던 이유가 이것**이었습니다. **묶여야 할 값이 따로 있으면 그걸 지키는 코드가 따로 필요해집니다.** 구조체로 묶으니 그 방어 함수 자체가 사라졌습니다. 며칠 전 `SelectItemIds` 통합에서 *"두 배열 병행은 동기화 책임만 늘린다"* 고 정리했던 것과 같은 패턴입니다.

`FindRowForGrade()`는 **정확히 일치하는 등급이 없으면 그보다 낮은 등급 중 가장 높은 행**으로 폴백합니다. `GetReputationGradeForScore()`와 같은 사고방식이라 **배열 순서에 의존하지 않습니다.**

### 4. `MaximumAliveCustomers`가 왜 별도 필드인가

등급 행과 배율만으로는 **"비피크 10명, 피크 12명"을 표현할 수 없습니다.**

| 시도 | 결과 |
| :--- | :--- |
| `Excellent` 행을 10으로 | 피크가 무조건 **20명** (10 × 2.0) |
| 행 값을 6으로 낮춤 | 피크는 12명이 되지만 **비피크가 6명으로 줄어듦** |

곱셈은 두 값을 **같이** 움직이므로, 한쪽만 제한하려면 **"위로만 자르는" 별도의 상한**이 필요합니다.
