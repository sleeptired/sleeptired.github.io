# **[UE5] 빌런 제압 래그돌 개선과 저장·UI 흐름 점검**

오늘은 빌런 제압 시 쓰러지는 래그돌을 개선하고, 계산대 이동 제한과 빌런 표시 차단을 적용했습니다. 자동 저장·빌런 알림을 공용 토스트에 연결하고, 세이브 누락 및 지팡이 물리 복원 문제도 점검했습니다.

작업하면서 중요했던 것은 **비슷하게 보이는 증상이라도 상태 전환·물리·표시 중 어느 단계에서 문제가 생기는지 구분하는 것**이었습니다. 공격 직후 사라지는 현상은 조기 삭제 가능성과 물리 폭주를 따로 조사했고, 복원한 지팡이가 되돌아가는 현상도 재부착이 아닌 물리 위치 문제로 확인했습니다.

---

## **1. 래그돌(Ragdoll)이란?**

래그돌은 캐릭터의 몸을 여러 물리 몸체와 관절로 구성하고, 애니메이션 대신 물리 시뮬레이션으로 움직이게 하는 방식입니다.

| 구성 | 역할 |
| :--- | :--- |
| **Skeletal Mesh** | 뼈에 따라 변형되는 캐릭터 메시 |
| **Physics Asset** | 뼈에 연결된 물리 몸체와 관절 구성 |
| **Body** | 충돌·질량·속도를 가지는 물리 몸체 |
| **Constraint** | 두 몸체 사이의 이동·회전 범위 제한 |

단순히 시뮬레이션을 켜는 것만으로 원하는 쓰러짐이 보장되지는 않습니다. **시작 자세·스케일·충돌 응답·관절 축·제한 범위**가 함께 맞아야 합니다.

<br>

## **2. 제압 판정과 제압 상태 진입을 구분하기**

### **① 피격 직후 이동을 멈추면 기존 퇴장 로직과 충돌할 수 있다**

기존 퇴장 태스크는 이동 상태가 `Idle`이면 소멸 처리했습니다. 피격 함수에서 바로 이동을 멈추면, StateTree가 제압 상태로 전환하기 전에 퇴장 태스크가 `Idle`을 보고 삭제할 수 있는 경로가 있었습니다.

| 처리 | 의미 |
| :--- | :--- |
| `MarkSubdued()` | 제압 상태 플래그 기록 |
| StateTree의 `Subdued` 진입 | 실제 제압 태스크 실행 시작 |

플래그를 켰다고 태스크가 즉시 바뀌는 것은 아닙니다. 조사한 실행 흐름에서는 활성 태스크 실행 후 전이를 검사하므로, 전이 우선순위를 높여도 이미 실행된 삭제를 되돌릴 수 없습니다.

당시 삭제 호출 위치까지 기록한 로그는 없어 개별 테스트의 원인으로 확정하지 않았지만, 이 충돌 경로는 코드에서 차단했습니다.

<br>

### **② 피격 데이터는 저장하고 연출은 상태 진입에서 시작**

현재 흐름은 다음과 같습니다.

1. 공격 명중 시 제압 가능 여부 판정
2. 제압 기록, 상품 회수·드롭 처리
3. 최초 피격 방향과 강도 보관
4. `Subdued` 진입에서 AI·CharacterMovement 중지
5. 래그돌 시작
6. 상태 진입부터 기본 3초 대기 후 소멸

일반 `LeaveAndDespawn`의 진입·Tick에도 제압 여부 가드를 추가해 제압 전환을 기다리는 동안 일반 퇴장 삭제가 실행되지 않도록 했습니다.

**이동 중지는 AI가 캡슐을 이동시키는 것을 멈추는 처리**입니다. 래그돌 몸체는 이후 중력과 충격을 받아 계속 움직입니다.

> **배운 점**
> 상태 플래그 변경과 실제 상태 진입은 서로 다른 시점입니다. 여러 태스크가 같은 액터를 이동·삭제한다면 전환 사이의 실행 경로도 보호해야 합니다.
{: .prompt-tip }

## **3. 화면에서 사라짐과 액터 삭제는 다르다**

후속 조사에서는 오크·엘프가 약 3초 동안 살아 있는데도 몸체 위치와 속도가 비정상적으로 커져 화면에서 사라지는 현상을 확인했습니다. 이번에는 소멸 시간보다 **물리 폭주**가 문제였습니다.

실제 연결된 자산을 비교하니 일부 종족은 골반의 참조 자세 스케일이 `1`인데 애니메이션 스케일은 `0.01`이었습니다. 드워프는 골반 스케일이 참조 자세·애니메이션 모두 `1`이었습니다.

이를 바탕으로 래그돌 시작 시 **현재 애니메이션 자세와 스케일을 기준으로 물리 몸체·관절을 다시 준비**하도록 수정했습니다.

| 단계 | 처리 목적 |
| :--- | :--- |
| 병렬 애니메이션 평가 완료 | 아직 계산 중인 자세와 물리 초기화 충돌 방지 |
| 메시 월드 변환 보존 | 행동 애니메이션·메시 보정 취소 시 위치 변화 방지 |
| 현재 자세 동기 평가 | 현재 골반 변환과 스케일 확인 |
| `RecreatePhysicsState()` | 현재 조건으로 물리 몸체·관절 재생성 |
| 새 골반 몸체 검증 | 유효하지 않은 상태에서 시뮬레이션 시작 방지 |
| 선형·각속도 정리 | 이전 물리 상태의 속도 제거 |
| 골반 충격 1회 적용 | 제압 반응 시작 |

사용자는 공통 코드 수정 후 빌드 성공과 기존 문제 해소를 보고했습니다. 이 결과를 모든 종족·자세·충돌 조건의 개별 계측 완료로 해석하지는 않았습니다.

**화면에서 사라졌다는 관찰만으로 `Destroy()`를 원인으로 판단하면 안 됩니다.** 액터 생존과 몸체 위치·속도 로그를 함께 봐야 합니다.

<br>

## **4. 쓰러짐 강도와 관절 자유도 조정**

### **① 충격량을 줄이는 것과 관절 폭주를 고치는 것은 별개**

현재 손님 BP의 제압 값은 수평 배율 `0.05`, 수평 상한 `350cm/s`, 위쪽 추가 속도 `0`입니다. 투사체 입력이 1200일 때 골반에 더하는 수평 속도는 다음과 같습니다.

$$
\min(1200 \times 0.05, 350) = 60\text{cm/s}
$$

위쪽 추가 충격을 없애고 작은 수평 충격과 중력으로 쓰러지도록 조정했습니다. 이는 위로 뜨는 모든 물리 움직임을 금지하거나 실제 이동 거리를 일정하게 보장하는 설정은 아닙니다.

점검 문서에서는 C++ 기본값과 BP 값이 달라, 새 BP나 네이티브 생성 경로에는 이전 값이 적용될 수 있다는 보완 사항도 확인했습니다.

<br>

### **② 관절은 Locked·Limited·Free를 구분해야 한다**

| 회전 Motion | 의미 |
| :--- | :--- |
| **Locked** | 두 연결 몸체 사이의 해당 회전 자유도 잠금 |
| **Limited** | 지정 범위 안에서 회전 허용 |
| **Free** | 해당 축의 회전 제한 없음 |

초기에는 허리·팔다리에 제한 각도와 Hard Limit, 감쇠, 인접 몸체 충돌 해제를 적용했습니다. 이후 요청에 따라 척추·목·어깨 일부는 완전 잠금으로 변경했습니다.

### **최신 저장 상태**

| 종족 / 메시 | 척추 잠금 | 목·머리 잠금 | 어깨 연결 |
| :--- | :--- | :--- | :--- |
| 모험가 / Human | 3개 | 2개 | 4개 Locked |
| 오크 / Orc | 3개 | 2개 | 4개 Locked |
| 고블린 / Goblin | 3개 | 2개 | 4개 Limited 유지 |
| 엘프 / Elf | 3개 | 2개 | 3개 Locked |
| 드워프 / Dwarf | 3개 | 1개 | 4개 Locked |
| 마법사 / Witch | 3개 | 2개 | 3개 Locked |

합계는 **척추 18개·목/머리 11개·어깨 18개**입니다. 6종 양쪽 고관절은 `Limited`, Swing1 / Swing2 / Twist `65° / 35° / 20°`를 유지했습니다.

관절 회전을 잠그는 것은 몸체의 월드 이동·회전을 고정하는 것과 다릅니다. 몸통 전체는 떨어지고 회전할 수 있지만 연결된 척추 사이의 추가 굽힘·비틀림을 막습니다.

또한 이번 잠금은 **기존 관절 참조 프레임 기준**입니다. 피격 순간의 임의의 굽은 자세를 그대로 잠그는 런타임 프레임 재설정은 추가하지 않았습니다.

<br>

### **③ 본이 있어도 독립 물리 몸체가 있다는 뜻은 아니다**

드워프는 스켈레톤에 팔·다리 본이 있어도 일부 본의 독립 물리 몸체가 없습니다. 예를 들어 아래팔이 어깨에 바로 연결된 구성이 있어 다른 종족과 같은 팔꿈치 규칙을 그대로 적용할 수 없습니다.

따라서 **실제 Physics Asset 연결을 확인하고 기존 연결별로 조정**했습니다. 독립 몸체 추가·관절 재연결은 수행하지 않았습니다.

사용자는 허리·목 문제 개선과 앞선 어깨 잠금 후 자연스러워졌다는 결과를 보고했습니다. 드워프 어깨 잠금 후 테스트와 6종 전체의 자세·환경별 확인은 남아 있습니다.

<br>

## **5. 래그돌 충돌을 별도 채널로 분리하기**

`SubduedBody` 채널을 추가하여 제압 몸체가 무엇과 충돌할지 별도로 관리했습니다.

* 캐릭터 캡슐은 충돌을 끄고 메시 물리 몸체가 환경과 충돌합니다.
* 상품·도구·봉인석은 제압 몸체를 Ignore하도록 설정합니다.
* 배송 상자 메시도 Ignore하고, 래그돌을 받쳐 주는 별도 비시뮬레이션 프록시를 사용합니다.

목표는 쓰러진 몸이 바닥·환경에는 안착하면서 작은 물리 아이템을 과하게 밀지 않도록 하는 것입니다. 코드·에셋 설정 일치는 점검했지만 상자 프록시 추종과 종족별 환경 충돌의 전체 런타임 검증은 남아 있습니다.

## **6. 빌런 표시 차단과 계산대 이동 제한**

### **① 표시와 게임 규칙을 분리하기**

빌런으로 배정된 손님은 머리 위 느낌표와 마법봉 피격 시 속마음 UI를 표시하지 않도록 했습니다.

| 위치 | 처리 |
| :--- | :--- |
| `ShowHeadIcon` | 빌런이면 기존 아이콘을 숨기고 반환 |
| `ApplyMagicHit_Implementation` | 속마음 표시 조건에 `!State->IsVillain()` 추가 |

공통 표시 함수에서 차단하여 여러 호출 위치에 같은 조건을 반복하지 않았습니다. 일반 손님 표시·빌런 절도와 제압·평판 집계는 유지했습니다.

**느낌표를 숨겨도 평판 계산이 사라지는 것은 아닙니다.** 실제로 훔친 빌런을 평판 집계에서 제외하는 변경은 보류했습니다.

<br>

### **② 계산대는 시설 판정을 유지하면서 들기만 차단**

계산대에 `CS.BuildLocked` Actor Tag를 지정하고 다음 두 곳을 막았습니다.

1. `UpdateBuildModeHUD`: 들기 안내 표시 제외
2. `TryPickUpBuildableFacility`: 실제 들기 요청 거부

```cpp
// 고정 태그가 있는 시설은 들기 요청을 거부
if (FacilityActor->ActorHasTag(BuildLockedTag))
{
    return false;
}
```

위 코드는 태그 판정만 보여주는 축약 예시입니다. 실제 함수는 액터 유효성 등 기존 조건도 확인합니다.

시설 인터페이스를 제거하면 배치 겹침 검사·접근 영역·설치 바닥 판정에서도 계산대가 빠질 수 있습니다. 그래서 시설로서의 역할은 유지하고 **들기라는 특정 행동만 제한**했습니다.

빌런 표시와 계산대 이동 차단은 빌드·테스트 완료가 기록되어 있습니다. 계산대가 들리지 않는지뿐 아니라 다른 시설 이동과 계산대 겹침 설치 방지도 확인했습니다.

## **7. 공용 토스트에 자동 저장·빌런 안내 추가**

### **① 성공한 자동 저장에만 알림**

기존 공용 토스트를 재사용하여 영업 종료 저장 성공 직후 안내를 호출하도록 했습니다.

| 알림 | 호출 조건 |
| :--- | :--- |
| 자동 저장 | `ExecuteClosingAutoSave()`에서 저장 성공 직후 |
| 빌런 출몰 | `OnShopliftStarted`, 한 게임에서 처음 1회 |

모든 저장 완료 이벤트에 연결하면 다른 저장 경로에서도 안내가 나올 수 있으므로 실제 영업 종료 자동 저장 위치에서 호출합니다. 다음 날 뒤늦게 안내가 나올 수 있는 마감종 경로에서는 알림을 생략했습니다.

<br>

### **② 한 게임에 한 번 표시한 사실도 저장 상태다**

빌런 알림은 등장 횟수를 제한하는 것이 아니라 처음에 제압 방법을 알려주는 안내입니다. 이후 빌런은 계속 등장합니다.

`bVillainAlertShown`을 GameState 세이브 레코드에 기록해 불러온 뒤에도 반복 안내를 막도록 했습니다. 새 게임에서는 false로 시작합니다.

이런 플래그는 UI에만 보관하면 레벨 이동·불러오기 후 잊어버릴 수 있습니다. **게임 단위 규칙이라면 저장 데이터에 포함해야 합니다.**

<br>

### **③ 우선 알림은 현재 알림을 끊지 않는다**

빌런 알림은 대기열 맨 앞에 삽입하지만 이미 표시 중인 알림은 끝까지 보여줍니다.

| 방식 | 결과 |
| :--- | :--- |
| 현재 알림 중단 후 재표시 | 거의 끝난 배달 알림이 다시 나오는 어색함 |
| **대기열 맨 앞 삽입** | 현재 알림 종료 후 빌런 안내를 먼저 표시 |

우선순위와 선점은 다른 정책입니다. 이번에는 **대기 순서만 조정**하는 방식을 선택했습니다. 정산창·수면 등 기존 보류 조건도 유지합니다.

토스트 관련 작업은 첨부 문서 기준 **코드 완료, 빌드·테스트 전**입니다.

## **8. 세이브 점검 — 액터가 돌아와도 사용할 수 있는가?**

세이브 참가자 13개와 비참가 서브시스템, 월드 액터, 슬롯 UI를 점검했습니다. 의도적으로 저장하지 않는 런타임 상태와 실제 진행 손실을 만드는 누락을 구분했습니다.

| 발견 항목 | 문제 |
| :--- | :--- |
| 미제출 엔딩 아이템 | 바닥·전시 상태 유실, 퀵바 복원 시 ID·관리자 연결 누락 |
| 바닥 구매 지팡이 | 돈은 차감됐지만 도구는 사라짐 |
| 구매 기본 지팡이 퀵바 복원 | 같은 클래스의 거치대 지팡이를 재사용해 개수 감소 가능 |
| 메타 파일 손상 | 본 세이브가 있어도 카드가 빈 슬롯으로 표시될 수 있음 |
| 본 슬롯 손상 후 백업 | 손상 데이터를 정상 백업 위로 복사할 위험 |
| 세이브 버전 변경 | 버전 완전 일치 검사로 기존 슬롯 로드가 거부될 수 있음 |

엔딩 아이템은 구매 순번만 저장하고 실물을 잃으면 재구매할 수도 없어 진행을 막을 수 있습니다. **클래스·위치뿐 아니라 아이템 ID와 관리 시스템 연결까지 복원해야 합니다.**

점검 보고서는 문제 발견과 수정 방향을 정리한 자료이며 모든 항목을 수정 완료한 결과는 아닙니다.

<br>

### **지팡이·엔딩 아이템 저장 확장 방향**

* 지팡이: 구매 여부와 거치대 소속을 구분하고, 레벨 지팡이는 원래 거치대의 실물을 사용하며 구매 지팡이는 별도로 생성합니다.
* 바닥 지팡이: 클래스·트랜스폼·물리 상태·거치대 시설 SaveId를 기록합니다.
* 엔딩 아이템: ID·월드 위치·전시대 슬롯·줍기 대기 상태를 기록하고, 생성 시 관리자와 다시 연결합니다.
* 퀵바 엔딩 아이템: 일반 도구보다 먼저 처리하고, 관리자 상태 복원을 퀵바 복원보다 앞에 둡니다.

이 확장 문서는 계획과 미완료 테스트 체크리스트를 포함합니다. 아래 지팡이 위치 문제는 별도 후속 문서에서 수정·테스트 결과를 확인했습니다.

<br>

## **9. 복원한 지팡이가 거치대로 돌아가는 물리 문제**

### **① 재부착이 아니라 물리 위치가 되돌아갔다**

바닥에 둔 레벨 지팡이를 불러오면 저장 위치에 잠깐 보였다가 거치대 자리로 돌아갔습니다. 시간차 진단 로그로 위치·부모·물리 상태를 비교했습니다.

| 시점 | 위치 | 부착 부모 | 물리 |
| :--- | :--- | :--- | :--- |
| 복원 전 | 거치대 | 거치대 앵커 | 꺼짐 |
| 복원 직후 | 저장한 바닥 위치 | 없음 | 켜짐 |
| 1초 뒤 | 거치대 좌표 부근 | 없음 | 켜짐 |

지팡이는 계속 1개이고 부착 부모도 없었습니다. 따라서 중복 생성이나 다시 꽂는 코드보다 **물리 바디와 컴포넌트 위치 불일치**가 원인이었습니다.

거치대에서 부착·결합됐던 물리 바디가 이전 위치에 남아 있었고, 일반 트랜스폼 적용 후 시뮬레이션이 시작되며 컴포넌트가 그 바디 위치를 따라갔습니다.

<br>

### **② TeleportPhysics로 물리 바디까지 이동**

복원 위치 적용에 `ETeleportType::TeleportPhysics`를 지정하고, 물리를 켠 직후에도 저장 위치를 다시 적용했습니다.

```cpp
// 남아 있던 물리 바디도 저장 위치로 이동
MagicWand->SetActorTransform(
    WandRecord.Transform, false, nullptr,
    ETeleportType::TeleportPhysics);

if (WandRecord.bWorldDropPhysics)
{
    MagicWand->EnableWorldDropPhysics();

    // 시뮬레이션 시작 시점의 위치를 저장 위치로 확정
    MagicWand->SetActorTransform(
        WandRecord.Transform, false, nullptr,
        ETeleportType::TeleportPhysics);
}
```

수정 후 불러온 지팡이가 저장 위치를 유지하는 것을 확인했고 임시 진단 로그는 제거했습니다.

> **배운 점**
> 물리 액터 복원은 화면상의 위치만 맞추는 작업이 아닙니다. 부착·결합 이력과 시뮬레이션 바디 위치까지 함께 확인해야 합니다.
{: .prompt-tip }

## **10. 타이틀 설정창과 튜토리얼 재개 설계**

### **① 같은 설정창을 열어도 실행 환경은 다르다**

타이틀에서 기존 인게임 설정창을 재사용할 때 다음 문제를 조사했습니다.

| 기존 의존성 | 타이틀에서 생기는 문제 | 설계 방향 |
| :--- | :--- | :--- |
| 인게임 컨트롤러 캐스트로 닫기 | 일반 타이틀 컨트롤러에서 닫기 실패 | 닫기 요청 이벤트로 소유 화면에 전달 |
| 캐릭터 캐스트 성공 뒤 UI 초기화 | Pawn이 없어 밝기·해상도 초기화까지 중단 | Pawn과 무관한 초기화 분리 |
| 마우스 감도를 캐릭터 멤버에만 보관 | 레벨 이동 시 값 리셋 | 캐릭터 밖 설정 저장소 사용 |
| 게임 시작 때 해상도 배율 88% 강제 | 타이틀에서 선택한 값 덮어씀 | 사용자 설정을 존중하는 초기화 |

위젯 재사용에서는 외형뿐 아니라 **누가 소유하고 어떤 월드에서 초기화되는지**도 확인해야 합니다. 첨부 설정 문서는 구현 가이드로, 완료 테스트는 기록되어 있지 않습니다.

<br>

### **② 튜토리얼 재개는 저장 시점의 월드 상태와 맞아야 한다**

1일차 마감 세이브를 불러오면 튜토리얼이 시작되지 않고, 마감 안내도 다시 재생되지 않아 3부 진입 계기가 없는 문제를 정리했습니다.

설계는 진행 스텝 전체를 저장하는 대신 `bTutorialPart3Pending` 하나로 **3부 첫 스텝부터 재시작**하는 방식입니다.

* 1일차 마감에 미완료 3부가 대기·진행 중이면 true 저장
* 마감 체크포인트 복원 후 true일 때 발주 단계부터 재개
* 2일차 마감 세이브는 false로 저장
* 마감 전 전체 건너뛰기를 한 경우에는 재개하지 않음

마감 세이브 이후 발주·제조 행동은 저장되지 않을 수 있으므로, 불러온 월드도 그 시점으로 돌아갑니다. 안내만 마지막 스텝부터 재개하면 돈·발주·재료 상태와 맞지 않을 수 있습니다.

**튜토리얼 재개는 안내 진행도와 저장된 월드 상태를 함께 맞추는 문제**입니다. 이 문서도 구현 설계와 확인 시나리오이며 완료 결과는 기록되어 있지 않습니다.
