## 절도 손실을 "어느 날 장부"에 기록할 것인가

> 어제 정리한 절도 통계에서 **금액 계산과 UI 연동은 이미 다 되어 있다**는 걸 확인했으니, 오늘은 남은 하나 — **"언제 손실을 확정할 것인가"** 만 설계했습니다. 바꿀 건 타이밍 하나인데, 파고들다 보니 **버그 하나와 착각 하나**가 같이 나왔습니다.

---

### 1. 시작은 "내가 모르는 코드가 이미 있었다"

절도 손실 기능이 **두 사람의 작업으로 나뉘어** 들어와 있었습니다.

| 범위 | 담당 |
| :--- | :--- |
| 빌런 판정, 절도 행동, 손실액 계산, **방송** | 나 |
| 방송 **구독** → 일일 정산 누적 → 요약 UI | 다른 팀원 |

**그런데 방송하는 쪽인 내가 구독 측 구현을 모르고 있었습니다.** 이유가 두 개였습니다.

*   그 PR 제목이 `[fix] 기존 ui 세부 조정 작업`이라 **절도 정산이 포함된 것이 제목에서 드러나지 않았습니다.**
*   팀원이 *"팀 시스템의 완료 이벤트만 구독해 발주와 절도 로직을 직접 수정하지 않습니다"* 라는 원칙으로 붙였기 때문에, **절도 쪽 파일에는 변경이 전혀 남지 않았습니다.**

> 두 번째가 흥미로웠습니다. **결합도를 낮춘 좋은 설계인데, 그래서 내 쪽에서는 알 방법이 없었습니다.** 남의 파일을 안 건드리는 것이 협업의 미덕이라고 계속 정리해왔는데, 그 미덕의 뒷면이 **"변경 이력에 흔적이 남지 않는다"** 는 것이었습니다.
>
> 그래서 남는 단서가 **PR 제목뿐**입니다. 8월 초에 *"squash 머지에서 PR 제목이 곧 main의 커밋 메시지"* 라고 규칙을 정리해뒀는데, 그게 왜 중요한지를 **반대쪽 입장에서** 겪었습니다. `[fix] UI 세부 조정`이라는 제목으로는 **한 달 뒤에 내가 이걸 찾을 수가 없습니다.**

### 2. 착수 시점의 가정이 틀렸다

설계를 시작할 때 *"마감 종을 누르면 손님이 모두 파괴된다"* 고 가정했는데 **사실이 아니었습니다.**

전체 소멸 함수의 호출부를 검색해보니 **저장소 전체에서 단 하나**였고, 그것도 **다음 영업일 시작 방송**에 묶여 있었습니다.

```
HandleBusinessDayStarted  ← OnBusinessDayStarted 구독
  └─ DespawnAllCustomers()
```

즉 **마감 종은 플래그를 세우고 방송만 할 뿐, 매장에 남은 손님을 건드리지 않습니다.**

> 가정을 확인하는 데 든 시간이 검색 한 번이었는데, **확인 안 하고 설계했으면 전제부터 어긋난 설계**가 됐을 겁니다. "이 함수가 언제 불리는가"는 **호출부를 세는 것으로 끝나는 질문**입니다.

---

### 3. 리셋이 방송보다 먼저였다

가정을 고치고 실행 순서를 따라가니 **핵심 버그**가 나왔습니다.

```
BeginNextBusinessDay()
  :840   DailyShopliftLossGold = 0;              ← 먼저 리셋
  :850   OnBusinessDayStarted.Broadcast();       ← 그 다음 방송
           └─ DespawnAllCustomers()
                └─ 도주 중 절도범 → ReportShopliftEscaped
                     └─ RecordShopliftLoss()     ← 리셋 이후에 더해짐
```

**양쪽으로 틀립니다.**

| 결과 | 내용 |
| :--- | :--- |
| ① | 마감까지 잡히지 않은 절도범의 손실이 **전날 정산에서 누락** |
| ② | **새 영업일이 `0이 아닌 상태`로 시작** |

> **의도는 맞고 확정 시점만 한 칸 늦은 상태**였습니다. 해당 분기의 주석에 *"마감까지 잡히지 않았으면 도주 성공으로 본다"* 는 의도가 정확히 적혀 있었습니다.
>
> **"틀린 로직"이 아니라 "옳은 로직이 잘못된 시점에 놓인 것"** 이라, 코드만 읽으면 아무 문제가 없어 보입니다. 이런 건 **실행 순서를 따라가야만** 보입니다.

---

### 4. 공용 방송의 순서는 건드리지 않는다

가장 직관적인 수정은 **리셋과 방송의 순서를 뒤집는 것**입니다. 그런데 그 방송을 구독하는 곳을 세어보니 **네 곳**이 더 있었습니다.

*   상품 액터의 상함 VFX 처리
*   배송 상자의 상함 VFX 처리
*   발주 서브시스템
*   상점 HUD

> **한 줄 순서 변경의 영향 범위가 내 파트를 한참 넘어갑니다.** 그래서 순서를 뒤집는 안은 **미채택**하고, **내 쪽에서 확정 시점을 앞으로 옮기는** 방향을 택했습니다.
>
> **"공용 지점을 바꿔서 내 문제를 푸는 것"과 "내 쪽 시점을 옮기는 것"** 중 후자가 안전합니다. 전자는 지금 동작하는 네 개를 위험에 빠뜨리고, 후자는 내 것만 책임집니다.

채택안은 두 겹입니다.

1.  **마감 종 시점에** 도주 중인 절도범의 손실을 확정하는 함수를 신설
2.  **날짜 경계에서** 손님 정리를 리셋보다 **먼저** 수행 (방어선)

두 번째는 기존 경로를 지우지 않고 그대로 둡니다. **두 번째 호출은 no-op이라 무해**하기 때문입니다.

### 5. 구독 대신 명시적 호출 — 등록 순서 의존을 피하려고

새 함수를 어디서 부를지도 선택지가 있었습니다.

| 안 | 장점 | 문제 |
| :--- | :--- | :--- |
| **GameMode에서 명시적 호출** ✅ | 순서가 코드에 드러남 | GameMode 1줄 수정 필요 |
| 요약 요청 방송을 구독 | **GameMode 무수정** | **멀티캐스트 내 호출 순서가 등록 순서에 의존** |

> 구독 방식이 더 깔끔해 보였는데, **서브시스템의 초기화와 위젯의 생성 중 무엇이 먼저 등록되는지**에 결과가 걸립니다. **지금은 서브시스템이 먼저 등록되어 우연히 동작하겠지만**, 그 우연에 기대는 구조가 됩니다.
>
> 며칠 전 *"자동 초기화는 시점을 의심한다"* 를 배웠는데, 이번엔 **"자동 구독은 순서를 의심한다"** 였습니다. 남의 파일을 안 건드리는 게 원칙이지만, **그 대가가 "우연히 동작하는 구조"라면 한 줄 수정하는 쪽이 낫습니다.**

### 6. 순서가 UX를 만든다

호출 위치를 **요약 요청 직전**으로 못 박았습니다.

```
RequestClosingDailySummary()
  ├─ [신규] SettleActiveShopliftersForClosing();   ← 여기서 확정
  └─ RequestDailySummary();                        ← 요약 위젯이 여기서 생성됨
```

> 요약 위젯은 **스냅샷이 아니라 실시간 구독**입니다. 그래서 확정을 뒤에 두면 **플레이어 눈앞에서 금액이 튀어오릅니다.** 앞에 두면 **첫 프레임부터** 올바른 금액이 보입니다.
>
> 기능상으로는 둘 다 맞는데 **보이는 게 다릅니다.** 실시간 갱신 구조는 편리한 만큼 **"언제 값이 들어가는가"가 그대로 화면에 드러난다**는 걸 처음 의식했습니다.

### 7. 구현 시 함정 3개

설계 문서에 미리 적어둔 것들입니다.

| 함정 | 내용 |
| :--- | :--- |
| **이터레이터 파괴** | 월드를 순회하면서 파괴하면 이터레이터가 깨진다 → **먼저 전부 배열에 모으고 두 번째 루프에서 처리** |
| **상품 목록을 비우는 함수 순서** | 먼저 부르면 `SelectProducts`가 비어 손실이 **0으로 집계**된다. 기존 주석이 경고하는 그 함정 |
| **제압된 빌런 체크** | 금액상으로는 자동 필터되지만, 소멸 타이머가 도는 중에 외부에서 파괴하면 그 태스크가 `Failed`를 반환한다 |

세 번째는 **크래시가 아니라 "로그가 오염되는" 수준**입니다.

> 그래도 검사를 넣기로 했습니다. **로그가 지저분해지면 다음에 진짜 문제가 생겼을 때 못 찾습니다.** 요즘 계속 로그로 원인을 찾고 있는데, **로그의 신뢰도도 관리 대상**이라는 걸 느꼈습니다.

두 번째 함정은 **이번 달에 세 번째로 만났습니다.** 상품 목록을 비우는 시점이 손실 집계의 전제라, **새 경로를 만들 때마다 같은 확인이 필요합니다.**

### 8. 경로가 늘면 멱등성이 필요하다

지금은 손실 확정 경로가 **정문 퇴장 하나**뿐이라 중복이 없습니다. 그런데 이번 변경으로 **세 개**가 됩니다.

```
정문 퇴장  /  마감 종  /  날짜 경계
```

그래서 상태 컴포넌트에 **한 번만 통과시키는 플래그**를 추가하기로 했습니다.

```cpp
bool bShopliftLossReported = false;
```

> 제압 처리에서 **이미 쓰러진 손님에 대해 `false`를 반환해 중복을 막는 것과 정확히 같은 패턴**입니다. 프로젝트 안에 이미 있는 방식을 따랐습니다.
>
> **진입점을 늘리는 변경은 거의 항상 멱등성 문제를 같이 데려옵니다.** 하나였을 때는 필요 없던 방어가, 셋이 되는 순간 필수가 됩니다. **"경로를 몇 개로 늘리는가"를 셀 때 방어 코드도 같이 세야** 합니다.

### 9. 고쳤더니 실패 

이번 설계에서 가장 배운 부분입니다. 날짜 경계에서 **정리를 리셋보다 먼저** 하도록 바꾸면, **파괴 시점의 기록이 어느 날 장부에 들어가는지가 뒤집힙니다.**

| | 파괴 시점 기록이 들어가는 곳 |
| :--- | :--- |
| 변경 전 | 리셋 **이후** → **다음 날 장부로 샌다** |
| 변경 후 | 리셋 **이전** → 전날 장부, 직후 리셋으로 **소거된다** |

절도는 마감 종에서 이미 확정되므로 이 시점에 남지 않아 무관합니다. 하지만 **앞으로 추가할 빌런 타입**에는 그대로 걸립니다.

> **"다음 날로 새는 것"보다 "조용히 사라지는 것"이 발견하기 어렵습니다.**
>
> 새면 다음 날 숫자가 이상해서 눈에 띕니다. 사라지면 **아무 숫자도 이상하지 않습니다.** 기록이 있었어야 한다는 걸 아는 사람만 알아챕니다.
>
> **버그를 고치면서 실패 양상이 "눈에 띄는 쪽"에서 "안 띄는 쪽"으로 바뀔 수 있다**는 걸 처음 생각했습니다. 이번엔 다행히 설계 단계에서 알아채 문서에 경고로 남겼는데, 구현 후에 만났으면 한참 헤맸을 것 같습니다.

참고로 **평판 하락 빌런은 영향이 없습니다.** 평판 점수가 일일 리셋 대상이 아닌 **누적값**이라, 파괴가 리셋보다 먼저면 하락이 전날 몫으로 정확히 잡힙니다. **일일 리셋되는 카운터에 기록하는 타입만** 위험합니다.

해결책은 절도와 같습니다 — **마감 종에 그 타입용 확정 호출을 추가**하면 영업일 전환까지 살아남는 빌런이 없어집니다.

### 10. 미래 확장 분석 — 자동으로 되는 것과 안 되는 것

빌런 타입을 추가할 예정이라, **무엇이 공짜로 따라오고 무엇을 손봐야 하는지**를 미리 정리했습니다.

**코드 수정 없이 확장되는 것 3개**

| 항목 | 근거 |
| :--- | :--- |
| 빌런 행동 추첨 | 누적 가중 방식이라 **enum 값 + 데이터에셋 가중치**만 넣으면 종족별 배분까지 동작 |
| StateTree 분기 | 조건이 타입별 비교를 지원 → **새 상태와 태스크만** 추가 |
| 절도 손실 격리 | `!= Shoplift` 가드가 **네 곳**에 있어 새 타입이 절도 손실로 오집계되지 않음 |

**손봐야 하는 것 — 우선순위 1위**

```cpp
// 현재 — 절도범만 제압 대상
if (State->PlannedVillainAction != ECSVillainAction::Shoplift) { return false; }
```

> 이대로면 **평판 빌런은 지팡이로 때려도 잡히지 않습니다.** **플레이어가 막을 수 없는 빌런**이 되는데, 그건 기능이 아니라 결함입니다. 그래서 **새 타입을 추가하기 전에** `IsVillain()` 기준으로 넓히기로 했습니다.

함께 정리할 것도 적어뒀습니다.

*   스위치 이름이 `bAllowSubdueBeforeShoplift`로 **절도 전용**입니다 → 개명 필요. 의미는 그대로입니다.
*   **타입별로 제압 가부를 나누고 싶어지면 `ECSVillainAction`을 직접 비교하지 말고 판정 함수 하나로 모을 것.** 지금처럼 **비교문이 여러 파일에 흩어지면 타입이 늘 때마다 누락이 생깁니다.**

> 마지막 항목이 앞에서 본 *"격리 가드가 네 곳에 있다"* 와 짝을 이룹니다. **지금은 네 곳이 다 있어서 안전한데, 다섯 번째를 추가할 때 하나를 빼먹으면 조용히 오집계됩니다.** 흩어진 비교문은 **지금은 자산이고 나중은 부채**입니다.

**24:00 강제 퇴장 예외**도 절도 전용인데, 이건 넓히는 게 위험합니다.

> 넓히는 순간 *"행동을 마친 모든 빌런이 자정에도 안 나간다"* 가 되므로, **퇴장 경로가 확실히 있는 타입에만** 적용해야 매장에 손님이 남는 사고를 피합니다. **일반화가 항상 정답은 아닙니다.**

마지막으로 **새 타입 추가 체크리스트 6단계**를 남겼습니다. enum → StateTree → 제압 판정 → 강제 퇴장 예외 → 마감 종 확정 → 중복 방어 플래그.
