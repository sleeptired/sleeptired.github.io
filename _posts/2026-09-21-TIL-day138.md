### 1. 0.2 cm 단위로 훑어서 틈 6곳을 찾았다

지난주 분석에서 *"바닥 트레이스가 인정하는 조건 3가지"* 를 세웠는데, 오늘 **에디터에서 장바구니와 동일한 조건으로 직접 쏴봤습니다.**

```python
# 오브젝트 쿼리 ECC_WorldStatic 단일, bTraceComplex = False — 실제 코드와 동일
print(tz(-5000, -9386.6))   # -> (234.01, 'Inside')   ← 틈으로 빠짐
print(tz(-5000, -9390.0))   # -> (291.9,  'Wood...')  ← 정상 바닥
```

| 항목 | 실측 |
| :--- | ---: |
| 매장 바닥 (판자 상면) | **Z = 291.9** |
| 틈으로 빠졌을 때 맞는 것 | **`Inside` 메시, Z = 234.0** |
| **낙차** | **57.9 cm** |
| 관통 틈 | **6곳** (전부 Y축 이음매, **매장 전 폭 관통**) |
| 틈 폭 | **0.6 ~ 2.8 cm** |

**찾는 방법이 핵심이었습니다.**

> **100 cm 격자로 728회 쏴봤을 때는 틈이 0건**이었습니다. 폭이 1 cm 안팎이라 **격자 사이로 전부 빠져나갔습니다.**
>
> 그래서 접근을 바꿨습니다 — ① 바닥 판자 42장의 **월드 바운드를 수집** ② 사각형을 병합해 **덮이지 않는 구간을 산출** ③ 그 후보 구간만 **0.2 cm 간격으로 실제 트레이스**.
>
> **무작정 촘촘하게 훑는 게 아니라 "후보를 먼저 계산하고 거기만 정밀하게"** 가 답이었습니다. 전체를 0.2 cm로 훑었으면 시간이 감당이 안 됐을 겁니다.

레벨 작업을 바로 할 수 있게 **6곳의 좌표와 양쪽 판자 액터 이름까지** 표로 남겼습니다. 특히 판자 하나는 **Y축 양쪽 끝이 둘 다 관통 틈**이라, 그 위에서 장바구니가 앞뒤로 움직이면 양쪽에서 빠집니다.

### 2. 왜 손님은 멀쩡하고 장바구니만 꺼졌나

사진에서 **손님은 정상 높이에 서 있는데 장바구니만 묻혀** 있었습니다. 그 이유가 실측으로 설명됐습니다.

| | 바닥을 잡는 방식 | 1 cm 틈 |
| :--- | :--- | :---: |
| 손님 | `CharacterMovement`의 **반경 약 34 cm 캡슐 스윕** | **안 빠짐** |
| 장바구니 | **폭 0인 라인 트레이스** | **그대로 통과** |

> **같은 바닥 위에 있는데 검사 도구가 달라서 결과가 갈렸습니다.** 손님 이동을 아무리 들여다봐도 원인이 안 나왔던 이유입니다.
>
> 그리고 낙차 57.9 cm가 **"슬라임이 거의 다 묻히고 바구니 통 윗부분만 보이는"** 사진 상태와 정확히 일치했습니다. 수치가 사진과 맞는 순간 원인이 확정됐습니다.

지난주 세웠던 조건 중 **①(단순 콜리전 불일치)과 ②(`WorldDynamic`)는 전부 해당 없음**이었습니다. `Inside` 메시는 오히려 per-poly 콜리전이고 바닥은 전부 `WorldStatic`으로 정상 히트합니다. **순수하게 판자가 벌어져 있는 것**이었습니다.

### 3. 어제 넣은 방어 2개를 전부 원복하기로 했다

원인이 확정되니 **작업 트리에 들어 있던 코드 2개가 둘 다 불필요**해졌습니다.

| 넣었던 것 | 실측 후 판정 |
| :--- | :--- |
| **하한 방어** (손님 발 높이보다 50 cm 넘게 낮으면 무시) | 불필요 + **계단에서 상시 오작동** |
| **대기 스윕 높이 분리** (45 → 10 cm) | 이 레벨에서 **효과 0** + 계단에서 오히려 불리 |

**하한 방어가 계단을 망가뜨리는 걸 계산으로 확인했습니다.**

$$\text{뒤처진 단 수} = \frac{114.5}{75} = 1.53 \quad\Rightarrow\quad \text{낙차} = 37.45 \times 1.53 = 57.2\text{ cm}$$

> **57.2 cm > 임계값 50 cm → 하한 발동 → 장바구니가 손님 발 높이로 끌려 올라감 → 공중에 뜸.**
>
> 손님 캡슐 반경이 30~42 cm 어디여도 낙차는 55~61 cm라 **계단에서는 사실상 상시 발동**합니다. 그리고 **올라갈 때만** 발동합니다(내려갈 때는 뒤가 위쪽이라 조건 미충족). 방향에 따라 갈리는 것까지 맞았습니다.

**대기 스윕 분리는 효과 자체가 0이었습니다.**

> 감지 문턱을 10 cm로 낮췄는데, **매장 안 최대 단차가 2.5 cm**였습니다. 아무것도 안 잡힙니다. 지난주 분석이 상정한 *"45 cm 미만 단차"* 가 **이 맵에 존재하지 않았습니다.**
>
> 유일하게 걸리는 게 입구 계단(37.45 cm)인데, 문턱보다 높으니 **장애물로 판정되어 대기 후보 뒤쪽 3개가 전부 막힙니다.** 수정 전에는 리프트가 45 cm라 계단이 **아예 안 보였고** 후보가 통과했습니다. **고치기 전이 더 나았습니다.**

### 4. 값 하나로 두 요구를 만족시킬 수 없다

원복을 결정한 결정적 근거입니다.

```
계단 오작동을 피하려면  →  임계값 > 57.2 cm
틈으로 빠지는 걸 막으려면 →  임계값 < 57.9 cm
                              여유 = 0.7 cm
```

> **두 요구가 0.7 cm 폭 안에서 충돌합니다.** 어느 쪽으로 조정해도 다른 쪽이 깨집니다. **값을 튜닝해서 해결할 수 있는 문제가 아니었습니다.**
>
> 원인을 모른 채 값을 넣었을 때는 *"50이면 되겠지"* 였는데, 두 수치가 다 나오고 나니 **애초에 같은 손잡이로 다룰 문제가 아니었다**는 게 드러났습니다.

그래서 **레벨에서 틈을 메우고 코드는 전부 원복**하는 쪽으로 정리했습니다. 원복하면 파일이 **수정 전 원본과 완전히 동일**해집니다.

그리고 한 가지를 굵게 적어뒀습니다.

> **"틈을 메우는 것만으로는 계단 문제가 해결되지 않습니다."** 계단에서 뜨는 건 **틈과 무관하게 하한 방어가 만든 것**이라, **레벨 수정과 별개로 코드 원복이 필요**합니다.

재발 방지가 필요하면 **바닥 트레이스를 스윕(반경 5 cm)으로 교체**하는 선택지를 남겼습니다. 최대 틈이 2.8 cm라 **구조적으로 통과 불가**가 되고, 높이 계산 방식이 안 바뀌어 계단에도 영향이 없습니다. 다만 **지금 당장은 레벨 수정만으로 충분**해서 보류했습니다.

### 5. 대기열을 2단계로 분리

지난주 분석에서 *"새치기는 버그가 아니라 설계"* 라고 정리했던 걸 오늘 실제로 바꿨습니다.

```
[1단계] 접근 (Approaching)   순번 없음. 줄 꼬리 집결 지점으로 이동
           └ 정원에는 포함          → 몰림 방지
[2단계] 확정 (Queue)          집결 지점 도착 순으로 순번 부여
           └ 배열 인덱스 = 줄 순번
```

**기존 함수를 고치지 않고 해체한 이유**

> 순번을 "도착 순"으로 매기려면 **여러 손님을 한꺼번에 놓고 비교**해야 합니다. 그런데 기존 함수는 **손님 한 명만 받아서 호출 즉시 확정**하므로, **거리 비교에 필요한 정보가 함수에 들어오지 않습니다.**
>
> **수정으로 해결되는 문제가 아니라 함수의 입력 형태 자체가 새 규칙과 맞지 않는** 경우였습니다.

그래서 **확정 권한을 개별 손님(StateTree 태스크)에서 전체를 볼 수 있는 서브시스템 틱으로 옮기고** 3단계로 분해했습니다.

| 기존 함수가 하던 일 | 옮겨간 곳 |
| :--- | :--- |
| 정원 확인 | 접근 등록 함수 |
| 중복 등록 방지 | 같은 함수 상단 |
| **배열에 추가** ← 알맹이 | **서브시스템 틱의 일괄 확정** |
| 순번 반환 | 반환 없음. 태스크가 매 틱 조회 |

같은 프레임 도착자는 **0번 슬롯 거리순 → 동률이면 번호표 순**으로 정렬해 확정합니다. 지난주에 *"tie-breaker가 없으면 해결이 아니라 빈도 감소"* 라고 정리했던 부분이 그대로 들어갔습니다.

인터페이스에 추가한 두 함수는 **기본 구현을 두어 하위 호환**을 지켰습니다. 영역을 지원하지 않는 계산대는 **꼬리 슬롯 좌표를 쓰고 도착 판정을 항상 통과**시켜 기존과 동일하게 동작합니다.

### 6. 출발 게이트를 확정 인원 기준으로 완화

커밋 직후 어색한 게 하나 남았습니다.

```
정원 6, 줄 2명, 걸어오는 중 4명
  → 2 + 4 >= 6 → 정원 가득 참
  → 7번째 손님은 진열대 앞에서 즉시 포기

그런데 화면상 계산대에는 2명뿐이고 슬롯 4칸이 비어 보입니다.
```

처음엔 **버퍼(여유분) 프로퍼티를 추가하는 안**을 제안 문서로 정리했는데, 결국 **더 단순한 방식**을 택했습니다.

```cpp
- if (IsQueueFull())            // Queue + Approaching >= Limit
+ if (IsCommittedQueueFull())   // Queue >= Limit  ← 확정 인원만
```

> **버퍼 숫자를 얹는 대신 게이트의 기준 자체를 바꿨습니다.** 버퍼를 무제한으로 둔 형태와 같습니다.
>
> 이렇게 하면 **거부 판정이 "출발 시점"에서 "도착 시점"으로 옮겨갑니다.** 걸어오는 동안 맨 앞 손님이 계산을 마치면 **그대로 줄에 합류**합니다. 출발 시점 스냅샷으로 판정하면 이런 손님을 무조건 놓칩니다.
>
> **튜닝 값을 하나 더 만들지 않아도 됐다**는 게 컸습니다. 버퍼 방식은 *"1이 맞나 2가 맞나"* 를 계속 물어야 합니다.

**대신 리스크를 명시했습니다.** 이번에 삭제한 주석이 정확히 그 상황을 경고하고 있었습니다.

> *"걸어오는 인원을 빼면 정원 제한이 사실상 사라져, 몇 명이든 계산대로 몰려온 뒤 서로 통과하며 한 지점에 겹쳐 쌓입니다."*

> **주석이 경고한 그 동작을 알고 하는 것**이라, 겹침 상한을 넣는 대신 **손님끼리 충돌·회피가 없으니 겹쳐도 무방하다**고 판단하고 범위에서 뺐습니다. 겹침이 문제가 되면 **반경 튜닝으로 해결되는 데이터 문제**라 커밋 보류 사유는 아니라고 봤습니다.

### 7. 내가 만든 버그를 내가 막았다

게이트 완화가 **버그 하나를 상시 발현으로 승격**시켰습니다.

```
프레임 N   : 도착 후 정원 초과로 거부 → AbandonCheckout 1회차 → 방송 ①
프레임 N+1 : 태스크 안전망이 "순번 없음 + 접근 중 아님"을 보고 → 2회차 → 방송 ②
```

**실제 피해가 작지 않았습니다.**

*   평판 집계가 **2회 증가**하고, 그 과정에서 **난수를 추가 소모**
*   **진열대 반환 추첨 난수가 한 번 더 소모** → **이후 모든 손님의 추첨이 어긋남**
*   장바구니 숨김·상품 처리 재실행

> **재현성이 깨지는 게 가장 나빴습니다.** 난수 시퀀스가 밀리면 시드를 고정해도 결과가 달라집니다.

그래서 포기 함수 진입부에 **재진입 가드**를 넣었습니다. 2회차 분기는 **거부된 손님의 태스크를 끝내는 유일한 경로**라 제거할 수 없어서, **호출되는 쪽에서 막았습니다.**

**출처도 정직하게 적었습니다.**

| 시점 | 상태 |
| :--- | :--- |
| 이전 | 두 번 불릴 경로 **자체가 없음** |
| 오늘 커밋 | 경로 신설. 단 게이트가 빡빡해 **잠복** |
| 지금 | 게이트 완화로 **상시 발현** |

> **"원래 있던 버그가 아닙니다. 본인 작업에서 생겼습니다"** 를 문서에 그대로 썼습니다. `main`에 새어나간 적이 없다는 것도 확인해 같이 적었습니다.
>
> 그리고 **①(게이트)과 ②(가드)는 분리 불가**라고 못 박았습니다. **① 없이 ②는 의미가 없고, ② 없이 ①은 버그**입니다. 커밋을 나누면 중간 커밋이 깨진 상태가 됩니다.

부작용도 전수 확인했습니다 — 플래그를 **true로 쓰는 곳이 한 곳뿐**이고, 손님 액터에 **풀링이 없어** 리셋이 불필요하며, 나머지 포기 호출부 4곳은 전부 최초 진입이라 가드에 안 걸립니다.
