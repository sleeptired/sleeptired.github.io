## 시설 접근 영역 설계 — 코드는 안 쓰고 설계만 한 날

> 손님이 진열대 앞에 설 자리를 **건축 모드에서 침범할 수 없는 영역으로 승격**시키고 화면에 보여주는 기능을 설계했습니다. **구현은 하지 않았고 설계 문서만** 썼습니다. 쓰다 보니 코드보다 **"무엇을 안 만들 것인가"** 를 정하는 데 시간이 더 걸렸습니다.

---

### 1. 풀려는 문제

*   진열대 앞 통로에 다른 진열대나 쓰레기통을 놓으면 **손님이 그 진열대에 못 갑니다.**
*   그런데 플레이어는 **어디가 비워야 할 자리인지 볼 수 없습니다.**
*   반대로 **마주 보는 진열대가 통로를 공유하는 배치는 허용**돼야 합니다.

이 세 번째 조건이 설계 전체를 결정했습니다. *"영역끼리 겹치면 안 된다"* 가 아니라 **"영역끼리만 겹쳐도 된다"** 라는 비대칭 규칙이 필요했습니다.

---

### 2. 핵심 결정 3가지

| 결정 | 이유 |
| :--- | :--- |
| 영역을 **태그 붙은 `UBoxComponent`** 로 표현 | 기존 건축 판정 함수 3개를 **인자만 바꿔 재사용**. 캡슐로 가면 전용 수학을 150줄 새로 짜야 함 |
| **손님 도착 판정은 손대지 않음** | 원형 판정은 그대로 두고, 건축 판정만 그 원에 외접하는 박스를 씀 |
| **영역 박스에 콜리전 없음** | 물리 쿼리에 안 잡히므로 조준 트레이스·NavMesh를 오염시키지 않음 |

기존 코드가 이미 **태그 기반**으로 만들어져 있어서, **볼륨 종류를 하나 늘리는 것만으로** 대부분이 해결됐습니다. 신규 코드는 SAT 함수 25줄 + 결합부 30줄 수준으로 추산됐습니다.

> 설계를 시작할 때 **"재사용할 것들" 표를 먼저 만든 게** 컸습니다. 15개 항목 중 *변경 없음* 이 대부분이었고, 그걸 확인하고 나니 **새로 짤 것이 저절로 좁혀졌습니다.**

---

### 3.  "허용"을 예외 처리가 아니라 코드를 안 쓰는 것으로

규칙표는 이렇게 됐습니다.

| | 상대 몸통 | 상대 영역 | 매장 구역 |
| :--- | :--- | :--- | :--- |
| **내 몸통** | 불가 *(기존)* | **불가 (규칙 A)** | 밖이면 미설치 Drop *(기존)* |
| **내 영역** | **불가 (규칙 B)** | **허용** | **밖이면 불가 (규칙 C)** |

"영역 × 영역 허용"을 어떻게 구현할까 고민하다가, **구현할 게 없다는 걸** 깨달았습니다.

> 영역 박스는 콜리전이 없어서 **물리 쿼리에 잡히지 않고**, 모든 비교는 **내가 명시적으로 짠 루프에서만** 일어납니다. 규칙 A · B · C 세 개만 작성하면 **영역 × 영역은 발생할 수가 없습니다.** 특수 케이스 코드가 **0줄**입니다.

**"허용하려면 금지하는 코드를 안 쓰면 된다."** 예외 조건을 넣어 뚫는 게 아니라 **애초에 비교하지 않는** 구조라, 나중에 코드를 읽는 사람이 *"여기 왜 예외가 있지"* 를 고민할 일도 없습니다.

대신 문서에 이렇게 적어뒀습니다. **"여기에 Zone 대 Zone 루프가 없다는 점이 이 설계의 전부입니다. 나중에 이 함수를 고칠 때도 그 루프를 추가하지 마세요."**

---

### 4. 규칙 A와 B는 대칭이라 둘 다 필요하다

처음엔 규칙 A(*내 몸통이 남의 영역을 침범*) 하나면 될 줄 알았는데, **놓는 순서를 바꿔보니** 구멍이 있었습니다.

| 순서 | 규칙 A만 있을 때 |
| :--- | :--- |
| 진열대 먼저 → 그 앞에 쓰레기통 | **막힘** ✅ |
| 쓰레기통 먼저 → 그 자리가 접근 영역이 되게 진열대 배치 | **안 막힘** ❌ |

> **판정을 설계할 때는 "누가 먼저 놓였는가"를 뒤집어봐야** 합니다. 두 물체의 관계는 대칭인데 검사는 한 방향만 하기 쉽습니다.

**규칙 C**(내 영역이 매장 구역 밖이면 불가)는 다른 이유입니다. 접근 영역이 매장 밖으로 나가면 그 자리에는 **NavMesh가 없습니다.** 몸통만 매장 안에 있어도 손님이 접근할 수 없는 **죽은 진열대**가 됩니다. 덤으로 **외벽을 마주 보게 놓는 배치**도 대부분 같이 걸러집니다.

### 5.  원을 사각형으로 근사한 대가를 정량화했다

손님 도착 판정은 원(`Dist2D <= 반경`)인데 건축 판정은 박스입니다. **두 판정 모양이 다른 게 괜찮은가**를 따져봤습니다.

$$\text{외접 사각형의 초과분} = r\sqrt{2} - r \approx 0.41r \approx 31\text{cm}$$

*   **축 방향(정면)은 원과 정확히 일치**합니다 → 마주 보는 진열대 통로(220cm), 벽 앞 여유(195cm)에 **영향 없음**
*   대각선 방향으로만 31cm 더 요구 → **매장 모서리, 비스듬히 놓인 시설**에서만 빡빡해짐

> 결론적으로 **"손님은 갈 수 있는데 설치가 막히는"** 방향으로만 어긋납니다. **버그가 아니라 여유**입니다. 반대 방향(설치는 되는데 손님이 못 감)이었다면 못 쓸 근사였습니다.
>
> **근사를 쓸 때는 오차의 크기보다 오차의 방향을 먼저 봐야** 한다는 걸 배웠습니다.

그리고 박스는 **`OnConstruction()`에서 반경으로부터 자동 생성**합니다. 디자이너가 직접 편집하게 두면 원과 박스가 따로 놀게 되므로, **박스를 원의 파생 캐시로** 만들어 값을 고칠 곳이 하나로 유지되게 했습니다.

### 6.  아직 없는 기능이 지금 알고리즘을 정했다

박스 겹침 판정을 **코너를 서로 넣어보는 간이 검사**로 할지, **SAT(분리축 정리)** 로 할지 고민했습니다. 지금 필요한 건 진열대뿐이라 코너 검사로도 충분합니다.

**그런데 2단계 계산대를 생각하니 답이 정해졌습니다.**

```
긴 대기줄 박스  ┃
               ┃
━━━━━━━━━━━━━━━╋━━━━━━━━━━━  넓은 진열대 몸통
               ┃
```

**십자로 교차하면 어느 쪽 코너도 상대 안에 없는데 실제로는 겹칩니다.** 코너 검사는 이걸 놓칩니다. SAT는 25줄이고 한 번 짜면 계속 씁니다.

> 어제 *"아직 만들지도 않은 랙돌 때문에 지금 코드의 순서가 정해졌다"* 고 적었는데, **이틀 연속 같은 패턴**입니다. 이번엔 순서가 아니라 **알고리즘 선택**이었습니다.
>
> 다만 구분은 해야 합니다. **"나중에 필요할지도"로 추상화를 만드는 것**과 **"확정된 다음 단계가 지금 선택을 결정하는 것"** 은 다릅니다. 계산대 대기줄은 이미 요구사항에 있고 모양도 정해져 있어서, 이건 추측이 아니라 **알려진 제약**입니다.

### 7.  분기 순서가 기존 기능을 통째로 죽인다

배치 확정(`Q` 입력) 로직에 새 검사 두 개를 끼워 넣는데, **어디에 넣느냐가 중요**했습니다.

```
1. 다른 시설과 몸통 겹침       → 아무것도 안 함  (기존)
2. 영역 충돌 (규칙 A·B)        → 아무것도 안 함  (신규)
3. 몸통이 매장 밖              → 미설치 Drop     (기존)
4. 몸통은 안 + 영역만 밖 (규칙 C) → 아무것도 안 함  (신규)
```

> **몸통이 매장 밖이면 접근 영역도 당연히 밖입니다.** 그래서 규칙 C 검사를 3번보다 **앞에** 두면, 새 검사가 먼저 걸려서 **"매장 밖에 내려놓기(미설치 Drop)" 기능이 통째로 막힙니다.**
>
> 1·2번은 원래부터 Drop까지 막는 조건이라 순서 영향이 없습니다. **포함 관계가 있는 조건을 추가할 때는 넓은 조건보다 뒤에 놓아야** 합니다.

그리고 **HUD 안내 문구의 분기 순서도 똑같이 맞춰야** 합니다. HUD가 *"매장 밖에 내려놓기"* 라고 안내했는데 실제로는 차단되면, 플레이어는 버그로 인식합니다. **판정 로직과 안내 로직이 같은 순서를 공유해야 한다**는 게 설계 시점에 잡아둘 만한 제약이었습니다.

### 8.  기존 레벨을 깨지 않기 위한 스위치

이 규칙을 켜면 **최소 통로 폭이 강제**됩니다.

```
마주 보는 진열대 간격 ≥ 오프셋(120) + 반경(75) + 상대 몸통 절반(25) = 220cm
진열대 정면 매장 여유  ≥ 오프셋(120) + 반경(75)             = 195cm
```

**기존 레벨이 이 값을 안 지키고 있으면 켜는 순간 전부 빨강이 됩니다.** 그래서 롤아웃 스위치를 하나 넣기로 했습니다.

```cpp
bool bBlockPlacementOnAccessZoneRules = true;   // false면 경고만 뜨고 배치는 허용
```

**중요한 건 신규 두 조건만 이 스위치로 묶는다**는 점입니다. 기존 조건은 이미 검증된 동작이라 스위치에 넣으면 **끄는 순간 검증된 기능까지 함께 꺼집니다.**

켜기 전 순서도 정했습니다.

1.  `BuildPlacementArea` Box가 **실제 걸을 수 있는 바닥보다 작게 잡혀 있지 않은지** 먼저 확인 → 이게 좁으면 멀쩡한 자리도 대량으로 빨강이 됩니다
2.  스위치를 끈 채 레벨 한 바퀴 돌며 빨강 위치 정리
3.  정리 끝나면 켜기

> **1번을 먼저 하라고 적은 게 핵심**입니다. 안 그러면 *"내 규칙이 잘못됐나"* 를 의심하며 시간을 쓰게 되는데, 실제 원인은 **다른 데이터가 원래부터 부정확했던 것**일 수 있습니다.

### 9. 시각화 — "무엇을"보다 "언제"와 "얼마나"

보여줄 대상은 둘입니다.

| 대상 | 답하는 질문 |
| :--- | :--- |
| 들고 있는 시설의 예정 영역 | "얘를 놓으면 앞을 얼마나 비워야 하나" |
| **이미 설치된 시설들의 영역** | **"어디에 놓으면 안 되나"** |

없어서 곤란한 쪽은 아래입니다. 그게 *"그 위에는 놓지 마라"* 를 알려주는 표시이기 때문입니다.

**① 언제 켜나 — 건축 모드 진입이 아니라 시설을 들었을 때**

> 건축 모드 진입만으로 켜면, 아직 아무것도 안 든 상태에서 **매장 바닥 전체가 영역으로 덮입니다.** 그 시점에는 내릴 결정이 없어서 **정보가 아니라 소음**입니다.

**② 얼마나 보여주나 — 판정 거리와 표시 거리를 분리**

| 값 | 용도 |
| :--- | :--- |
| 판정 거리 2000 | **정확해야 하므로 넓게** |
| 표시 거리 900 | **주변만** |

판정 거리 20m 안에 진열대가 거의 다 들어오는데 30개를 전부 그리면 **바닥이 온통 청록이 돼서 오히려 아무것도 안 보입니다.** 표시 밖 영역 때문에 막히는 경우는 어차피 화면에 안 보이는 거리라 프리뷰가 빨강인 것으로 충분합니다.

**③ 색 — 내가 침범 중인 영역만 빨강**

전부 같은 색이면 진열대가 몰려 있을 때 **무엇 때문에 막혔는지 알 수 없습니다.** 그래서 판정 함수가 규칙 A로 걸린 상대 영역 박스를 **목록으로 돌려주고**, 시각화가 그것만 빨강으로 칠하게 설계했습니다. (그래서 규칙 A 루프는 첫 충돌에서 `return`하지 않고 끝까지 돕니다.)

**④ 기존 프리뷰 배열에 얹으면 네 가지가 공짜**

들고 있는 시설의 예정 영역은 기존 프리뷰 메시 배열에 평면을 하나 더 넣는 것으로 **머티리얼 스왑 · 표시 토글 · 위치 갱신 · 초록/빨강 전환**이 전부 따라옵니다. 신규 에셋 0개입니다.

**⑤ 표시 풀은 플레이어가 소유**

진열대마다 표시 메시를 들게 하면 **시설 클래스마다 생성·크기 동기화 코드를 각각 써야** 합니다. 플레이어가 태그로 영역 박스를 읽어 그리면 **시설 클래스에 코드가 한 줄도 안 들어갑니다.**

### 10.  태그로 설계한 것의 보상 — 2단계가 BP 작업만

이 설계에서 가장 마음에 드는 부분입니다.

> **2단계 계산대 대기줄은 `BP_CounterDesk`에 태그 Box를 하나 붙이는 것만으로** 규칙 A · B · C와 시각화에 **자동으로 편입됩니다. C++ 변경 0.**

영역을 인터페이스가 아니라 **태그**로 찾게 설계했기 때문입니다. 시각화도 마찬가지라, **계산대를 들었을 때 주변 진열대 영역이 보이고 진열대를 들었을 때 계산대 대기줄이 보이는 것**까지 BP 작업만으로 완성됩니다.

같은 이유로 **쓰레기통은 박스를 안 붙이면 그만**입니다. 빈 배열이 `true`를 반환하므로 규칙 C를 자동 통과하고, 규칙 B도 검사할 영역이 없어 통과합니다. 그런데 **규칙 A 때문에 진열대 앞에는 여전히 못 놓입니다.** 의도한 동작이 자동으로 나왔습니다.

| :---: | :--- | :--- |
| ① | 영역 박스에 **`SetCanEverAffectNavigation(false)`** 를 꼭 유지할 것 | 같은 진열대의 NavMesh 차단 박스 설정이 딸려오면 **손님이 서야 할 바로 그 자리의 NavMesh를 지웁니다** |
| ② | **콜리전을 켜지 말 것** | 조준 라인트레이스가 허공의 영역 박스에 맞아 **배치 위치가 엉뚱하게 잡힙니다** |
| ③ | 몸통 겹침 함수를 나중에 "태그 인자로 일반화"하면서 **영역 태그를 넘기지 말 것** | 그 순간 Zone × Zone이 생겨 **마주 보는 진열대 배치가 막힙니다** |

①이 특히 위험합니다. 증상이 **"왜 이 진열대만 손님이 안 오지"** 로 나타나고, 로그에는 *"NavMesh가 없어 갈 수 없습니다"* 만 남습니다. 원인이 **바로 옆 컴포넌트의 설정 한 줄**이라 찾기 어렵습니다.

> 요즘 계속 만나는 **조용한 실패** 패턴입니다. 이번엔 겪기 전에 **설계 문서에 미리 적어두는** 쪽으로 대응했습니다.

### 12. 인정한 구멍

**매장 안쪽의 기둥·칸막이는 아직 안 막힙니다.** 규칙 C로 외벽 쪽은 걸러지지만, `BuildPlacementArea` **안쪽**에 서 있는 기둥에 진열대를 바짝 붙여 마주 보게 놓으면 여전히 통과합니다.

해결책 두 가지를 적어두고 **첫 번째를 권했습니다.**

| 안 | 비용 |
| :--- | :--- |
| **기둥에 몸통 태그 Box를 붙인다** | 규칙 B가 바로 걸림. **C++ 변경 0** |
| 영역 중심에 NavMesh 투영을 쏴서 실패하면 불가 | 손님 AI와 기준이 정확히 일치하지만, 들고 있는 동안은 NavMesh가 재생성 전이라 **배치 후와 미세한 차이** |

> **완전한 해결책이 더 비쌀 때, 싼 우회로를 먼저 적어두는 것**도 설계의 일부라고 느꼈습니다. 두 번째 안은 "정확한데 실행 시점 때문에 불안정"하고, 첫 번째는 "덜 우아한데 확실"합니다.

그 외에 **이미 배치된 시설끼리는 검사하지 않는다**(건축 모드로 새로 놓는 것만 막음), **마주 보는 두 진열대의 손님이 같은 자리를 두고 경합할 수 있다**(손님 AI의 자리 예약 문제로 범위 밖) 도 한계로 명시했습니다.
