## 손님 구매 목록 자료구조 통합 — `SelectItemIds` → `SelectProducts`

> 새 기능(계산 포기 시 상품 반환)을 만들려다가 **기존 자료구조로는 불가능하다는 걸 발견**해서, 기능보다 자료구조를 먼저 고쳤습니다. 팀원 파일이 걸려 있어 진행 순서까지 설계해야 했던 작업입니다.

---

### 1. 왜 바꿨나 — 요구사항이 자료구조를 결정한다

만들려던 기능: **계산을 포기한 손님이 들고 있던 상품을 월드에 되돌려놓기.**

그런데 기존 구조로는 못 만듭니다.

```cpp
TArray<FName> SelectItemIds;   // ProductId(RowName)만 보관
```

| 되돌리려면 알아야 하는 것 | `FName`으로 알 수 있나 |
| :--- | :---: |
| 어떤 상품인가 (RowName) | ✅ |
| **어느 데이터 테이블**의 행인가 | ❌ |
| **어떤 BP 클래스**로 스폰해야 하나 | ❌ |

`RowName`만으로는 **상품 액터를 다시 만들 수 없습니다.** 같은 BP로 생성해야 DataAsset 기반 외형이 동일하게 적용되는데, 그 클래스 정보가 없습니다.

> **"기록해두지 않은 정보는 나중에 복원할 수 없다."** 상품 액터를 `Destroy()`하는 순간 원본 정보가 사라지므로, **집는 시점에 필요한 걸 다 남겨둬야** 합니다. 그 시점에 "나중에 뭘 하고 싶어질지"를 예측하는 게 어려운 부분이었습니다.

---

### 2. 병행하지 않고 통합한 이유

처음엔 `SelectItemIds`를 두고 새 배열을 **추가**하는 방안을 생각했는데, 관계를 따져보니 통합이 맞았습니다.

```
SelectProducts ⊃ SelectItemIds
(ProductRow.RowName이 곧 ProductId이므로 상위집합)
```

*   상위집합이므로 **두 배열을 병행할 이유가 없습니다.**
*   병행하면 오히려 **"개수가 어긋나면 계산 UI가 깨지는"** 위험만 남습니다. 한쪽에만 추가하는 실수가 나면 조용히 어긋납니다.

> 같은 사실을 두 군데에 저장하면 **동기화 책임**이 생깁니다. 한쪽이 다른 쪽의 상위집합이면 통합하고, **파생 값은 저장하지 말고 함수로 계산해서 제공**하는 게 안전합니다.

### 3. `FCSSelectProduct` 구조체

```cpp
USTRUCT(BlueprintType)
struct FCSSelectProduct
{
	GENERATED_BODY()

	// 상품의 데이터 테이블 행 (DataTable + RowName 쌍).
	// ProductRow.RowName이 곧 ProductId다.
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Customer")
	FDataTableRowHandle ProductRow;

	// 집었던 상품 액터의 클래스.
	// 같은 BP로 생성해야 DataAsset 기반 외형이 동일하게 적용된다.
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Customer")
	TSubclassOf<AActor> ProductClass;
};
```

**`FDataTableRowHandle`을 쓴 이유:** `FName`은 "어느 표의 몇 번 행"인지를 담지 못하지만, `FDataTableRowHandle`은 **테이블 포인터 + RowName을 한 쌍으로** 묶습니다. 행 하나를 가리키는 완전한 좌표인 셈입니다.

함께 정리한 필드:

| 필드 | 용도 |
| :--- | :--- |
| `SelectProducts` | 고른 상품 목록 (계산대 주문 생성 + 포기 시 반환) |
| `VisitedShelves` | 이번 방문에서 구경한 진열대 |
| `bCheckoutDone` | 계산 완료 |
| **`bCheckoutAbandoned`** | **계산 포기 — true면 다시 줄 서지 않음** (신규) |
| `ExitLocation` | 퇴장 좌표 |

### 4. 호환 함수 하나로 파급 범위를 2줄로 줄이기

**가장 중요한 판단이었습니다.** `SelectItemIds`를 **팀원 파일(`CSCheckoutCounterActor.cpp`)이 직접 참조**하고 있어서, 그냥 지우면 그쪽에 컴파일 에러가 납니다.

그래서 **조회용 함수**를 우리 쪽에 만들었습니다.

```cpp
// 고른 상품의 ID(RowName) 목록. 계산대 주문 생성 등 외부 조회용.
// 내부 저장 방식이 바뀌어도 이 함수만 유지하면 호출하는 쪽은 영향받지 않는다.
UFUNCTION(BlueprintPure, Category = "Customer")
TArray<FName> GetSelectProductIds() const;
```

**영향 범위**

| 파일 | 소유 | 수정량 |
| :--- | :--- | :--- |
| `CSCustomerStateComponent.h/.cpp` | 우리 | 구조체·배열·함수 전면 |
| `CSCustomerRuntimeSubsystem.cpp` | 우리 | `TakeProduct` 1곳 |
| `CSCustomerRuntimeSubsystem.h` | 우리 | 주석 2곳 |
| `CSCustomerStateTreeConditions.cpp` | 우리 | **수정 없음** |
| `CSCustomerStateTreeTasks.cpp` | 우리 | **수정 없음** |
| `CSCheckoutCounterActor.cpp` | **팀원** | **2줄** |

**태스크·조건이 수정 불필요한 이유:**

*   조건은 `HasSelectedItems()`를 부르는데 **함수명과 의미가 그대로**입니다.
*   태스크는 애초에 **장바구니를 직접 건드리지 않습니다** (`TakeRandomProduct`만 호출).

> 어제 정리한 *"태스크는 얇게, 로직은 Subsystem 경유"* 가 여기서 값을 했습니다. 태스크가 장바구니를 직접 조작했다면 5개 파일을 전부 고쳐야 했을 겁니다. **자료구조를 통째로 바꾸는데 태스크 수정 0줄**이라는 게 계층 분리의 실제 효과입니다.

**팀원 파일 변경 (2줄)**

```cpp
// 변경 전
if (!IsValid(CustomerState) || CustomerState->SelectItemIds.IsEmpty())
for (const FName ProductId : CustomerState->SelectItemIds)

// 변경 후
if (!IsValid(CustomerState) || !CustomerState->HasSelectedItems())
const TArray<FName> SelectedProductIds = CustomerState->GetSelectProductIds();
for (const FName ProductId : SelectedProductIds)
```

수량 합산·데이터 테이블 조회·가격 계산 로직은 **전혀 손대지 않았습니다.**

### 5. 의존 방향을 지키기 위한 설계 — 왜 액터가 아니라 값 2개를 받나

```cpp
// 액터를 받지 않고 값 2개를 받는다
void AddSelectProduct(const FDataTableRowHandle& InProductRow, TSubclassOf<AActor> InProductClass);
```

`AddSelectProduct(ACSProductPickupActor* Product)` 형태가 호출은 더 편합니다. 그런데 그러면 **컴포넌트가 `ACSProductPickupActor` 헤더를 include해야** 합니다.

| | 액터를 받는 설계 | **값 2개를 받는 설계** |
| :--- | :--- | :--- |
| 호출 편의 | 좋음 | 호출자가 값을 추출해야 함 |
| 컴포넌트의 의존 | 상품 클래스에 의존 발생 | **의존 0개 유지** |
| 상품 구조 변경 시 | 컴포넌트도 영향 | 컴포넌트 무관 |

> 지금 이 컴포넌트는 **다른 파트에 대한 의존이 하나도 없습니다.** 그 상태를 유지하는 편이 나중에 상품 구조가 바뀌어도 안전합니다. **값 추출은 Subsystem이 합니다** — 이미 팀원 코드를 아는 계층이라 거기서 하는 게 맞습니다.

```cpp
// Subsystem이 추출해서 넘긴다
CustomerState->AddSelectProduct(Product->GetProductRow(), Product->GetClass());
```

**의존을 어느 계층에 둘지가 곧 함수 시그니처를 결정한다**는 걸 체감한 지점입니다.

### 6. 기록 시점과 순서

```cpp
// TakeProduct 내부
if (ShelfActor->Implements<UCSShelfPlaceable>())
{
    ICSShelfPlaceable::Execute_RemovePlacedItem(ShelfActor, Product);
}

// 고른 상품을 기록한다. ★ 액터를 파괴하기 전에 뽑아둬야 한다
CustomerState->AddSelectProduct(Product->GetProductRow(), Product->GetClass());

Product->Destroy();
```

*   **`Destroy()` 전에 기록**해야 합니다. 파괴 후에는 `GetProductRow()`도 `GetClass()`도 읽을 수 없습니다.
*   `const FName ProductId = Product->GetProductId();` 와 유효성 검사는 **그대로 두었습니다.** `OnItemTaken` 방송과 반환값에 여전히 필요합니다.

**유효성 검사를 입구에서:**

```cpp
void UCSCustomerStateComponent::AddSelectProduct(...)
{
	// 행 정보가 없으면 나중에 상품을 되돌릴 수도, 가격을 조회할 수도 없으므로 기록하지 않는다.
	if (InProductRow.DataTable == nullptr || InProductRow.RowName.IsNone())
	{
		return;
	}
	...
}
```

> **쓰레기 데이터를 배열에 넣지 않는 게 꺼내는 쪽에서 거르는 것보다 낫습니다.** 넣어두면 계산 UI, 반환 로직, 매출 집계 세 곳에서 각각 방어해야 합니다.

### 7. 팀원 파일이 걸린 변경의 진행 순서

`SelectItemIds`가 사라지는 순간 계산대가 컴파일 에러를 냅니다. 그래서 **두 수정이 같은 커밋에 함께** 들어가야 합니다.

```
1. 팀원에게 사전 공유 (변경 이유 + 변경량 + 선택지)
2. 우리 파일 전부 수정
3. 같은 브랜치에서 계산대 2줄 수정
4. 빌드 → 테스트
5. PR (리뷰어 지정)
```

⚠️ **우리 파일만 먼저 커밋해서 push하면 안 됩니다.** 그 순간 main이나 공유 브랜치가 빌드 불가 상태가 됩니다.

> 앞서 정리한 Git 규칙이 *"브랜치 → PR"* 이었다면, 여기서 추가로 배운 건 **커밋의 원자성** 입니다. **"빌드가 깨지지 않는 최소 단위"가 커밋의 경계**이고, 그 단위가 파일 소유자를 넘어갈 수도 있습니다.

**사전 공유에 담은 것**

| 항목 | 내용 |
| :--- | :--- |
| **왜** | RowName만으로는 상품 액터를 재생성할 수 없어서 |
| **무엇을** | `SelectItemIds` → `SelectProducts` 통합, 대신 `GetSelectProductIds()` 제공 |
| **얼마나** | 변경 전/후 코드를 직접 붙여서 "2줄" 명시 |
| **선택지** | *"제가 같은 PR에 포함할까요, 아니면 직접 반영이 편하실까요?"* |

> 변경량을 **추상적으로 설명하지 않고 실제 코드로 보여준 것**, 그리고 **결정권을 넘긴 것**이 핵심이었습니다. "2줄 바뀝니다"보다 변경 전후 코드가 훨씬 빠르게 이해됩니다.

### 8. 일부러 하지 않은 개선

`FCSSelectProduct.ProductRow`에 `DataTable`이 이미 들어 있으므로, 계산대가 자기 쪽 `ProductMasterDataTable` 없이도 조회할 수 있습니다.

```cpp
const FCSProductDataRow* Row = Selected.ProductRow.GetRow<FCSProductDataRow>(TEXT("..."));
```

**하지만 이번엔 건드리지 않았습니다.** 계산대는 *"상품 마스터를 자기가 지정해서 쓴다"* 는 설계를 갖고 있고, 그건 **그쪽 파트의 판단 영역**이기 때문입니다.

> **개선 가능하다는 것과 내가 결정해도 된다는 것은 다릅니다.** 남의 파트 설계는 제안까지만 하고, 채택 여부는 소유자가 정하게 두는 게 맞습니다. 이번 변경의 목적은 "우리 자료구조 통합"이지 "계산대 개선"이 아니었습니다.

### 9. 검증

**컴파일 후**

- 프로젝트 전체에서 `SelectItemIds` 검색 → **0건**
- `AddToSelectItem` 검색 → 0건 / 빌드 성공

**런타임 회귀 테스트** (기존 기능이 안 깨졌는지)

- 상품을 집으면 `SelectProducts`에 쌓인다 (PIE 중 손님 선택 → CustomerState에서 확인)
- 각 항목의 `ProductRow`에 **DataTable과 RowName이 모두** 채워져 있다
- 각 항목의 `ProductClass`가 집었던 상품 BP다
- **산 손님만 계산대 줄에 선다** (`HasSelectedItems` 정상)
- **계산 UI에 상품 이름·수량·가격이 정확히 뜬다** ← 팀원 연동 확인
- 같은 상품 2개를 집으면 UI에 "수량: 2"로 합산된다
- 결제 후 HUD 매출 정상 증가 / 안 산 손님은 줄 안 서고 바로 퇴장

> 자료구조만 바꾸고 **동작은 완전히 같아야 하는** 작업이라, 새 기능 테스트가 아니라 **회귀 테스트**가 검증의 전부입니다. "무엇이 바뀌면 안 되는가"를 먼저 목록화한 게 도움이 됐습니다.

### 10. 후속 작업에 미친 영향

인내심 타임아웃(계산 포기) 기능의 `DropCustomerItemsAt`이 훨씬 단순해집니다.

```cpp
const int32 ItemCount = State->SelectProducts.Num();
...
RespawnCarriedProduct(State->SelectProducts[i], SpawnTransform);
...
State->ClearSelectItems();
```

**배열 하나만 비우면 되므로 "두 배열 개수 불일치" 걱정이 사라졌습니다.** 원래 계획했던 `CarriedProducts`라는 별도 배열도 필요 없어졌습니다.

> 기능을 만들기 전에 자료구조를 먼저 고친 판단이 맞았습니다. 그대로 진행했다면 **배열 3개(`SelectItemIds` + `CarriedProducts` + 동기화 코드)** 를 관리하게 됐을 겁니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **요구사항이 자료구조를 결정한다** | "되돌리기"가 필요해진 순간 `FName` 배열로는 불가능. 기능보다 자료구조를 먼저 고쳤다 |
| **기록하지 않은 정보는 복원할 수 없다** | `Destroy()` 전에 남겨둬야 한다. 무엇을 남길지는 미래 요구를 예측하는 문제 |
| **상위집합이면 통합, 파생값은 함수로** | 두 배열 병행은 동기화 책임만 늘린다. `GetSelectProductIds()`처럼 계산해서 제공 |
| **호환 함수가 파급을 막는다** | 내부 저장 방식을 통째로 바꿨는데 외부 수정은 2줄 |
| **의존 위치가 함수 시그니처를 정한다** | 컴포넌트의 의존 0개를 지키려고 액터 대신 값 2개를 받게 설계 |
| **커밋의 경계는 "빌드가 깨지지 않는 최소 단위"** | 그 단위가 파일 소유자를 넘어갈 수 있다 → 같은 커밋에 함께 |
| **개선 가능 ≠ 내가 결정** | 남의 파트 설계는 제안까지. 이번 작업의 목적 범위를 벗어나지 않는다 |
| **자료구조 변경의 검증은 회귀 테스트** | "무엇이 바뀌면 안 되는가"를 먼저 목록화 |
