## 접근 영역 구현 완료

> 며칠 전 설계만 해둔 **시설 접근 영역**을 구현했습니다. 설계대로 간 부분이 대부분이었지만 **결론이 뒤집힌 곳이 두 군데** 있었고, 마지막에 **화면에 그려지는 영역이 실제 판정의 2배로 커지는** 버그를 하나 잡았습니다.

---

### 1. 오늘의 두 갈래

| 구분 | 내용 |
| :--- | :--- |
| **구현** | 1단계 완료. 설계안 대비 **뒤집힌 결정 2개** + 달라진 점 3개를 문서에 반영 |
| **버그 추적** | 표시용 메시를 교체했더니 **그려지는 영역이 판정 영역의 약 2배**가 된 문제 |

설계 문서를 *"설계안 / 구현 기록"* 으로 바꾸고, 초안과 달라진 자리마다 **"실제 구현"** 표시와 이유를 남겼습니다.

> **설계 문서를 지우고 새로 쓰지 않고 "달라진 자리에 덧쓴" 게** 나중에 도움이 될 것 같습니다. 결과만 남기면 *"왜 이렇게 됐지"* 를 다시 추론해야 하는데, **뒤집힌 이유가 남아 있으면 같은 판단을 다시 하지 않아도** 됩니다.

---

### 2. 뒤집힌 결정 ① — 매장 밖 배치를 아예 막았다

초안은 *"몸통이 매장 밖이면 **기존대로 미설치 Drop**을 유지하고, 새 검사를 그 분기 **뒤에** 두라"* 고 못 박았습니다. 실제로는 **그 기능 자체를 없앴습니다.**

```cpp
// 삭제 전
if (!bIsHeldBuildableInsidePlacementArea)
{
    DropHeldBuildableFacilityAsUninstalled();   // 매장 밖 → 미설치 상태로 내려놓기
    return;
}

// 실제 구현 — 매장 밖에는 내려놓지도 못하게
if (!bIsHeldBuildableInsidePlacementArea)
{
    return;
}
```

**뒤집은 이유 세 가지**

*   **규칙 C와 정면으로 모순됩니다.** 몸통이 매장 밖이면 접근 영역도 **반드시** 밖입니다. *"몸통 밖 = 내려놓기 허용"* 과 *"영역 밖 = 차단"* 이 **같은 프레임에서 동시에 참**이 되고, 어느 쪽을 먼저 검사하느냐로 결과가 갈립니다.
*   **매장 밖에 방치된 시설은 규칙의 사각지대**입니다. 미설치 시설은 `IsFacilityInstalled()`가 false라 **판정과 시각화 양쪽에서 제외**됩니다. 즉 매장 밖에 쌓인 시설은 규칙 A·B·C 어디에도 안 걸리는 **유령**이 됩니다.
*   **"놓을 수 있는 곳"의 정의가 하나로 통일**됩니다. 시설은 오직 매장 구역 안에서만 손을 떠납니다. 예외가 없습니다.

> 며칠 전 설계할 때 **"순서를 바꾸면 기존 기능이 통째로 막힙니다"** 라고 굵게 경고를 적었는데, 구현하면서 보니 **그런 경고가 필요했다는 것 자체가 모순의 증상**이었습니다.
>
> **"이 순서를 지켜야만 동작한다"는 주석을 쓰게 되면, 순서 문제가 아니라 규칙이 서로 어긋난 건 아닌지 먼저 의심해야 합니다.** 순서로 봉합할 수 있으니 그냥 넘어갔는데, 한 겹 더 들어가니 애초에 공존할 수 없는 두 규칙이었습니다.

**부수 효과도 정리했습니다.** 호출부가 0이 된 함수는 삭제했지만, `InitializeAsUninstalledFacility` 인터페이스는 **픽업 실패 롤백 경로에서 계속 쓰이므로 유지**했습니다. HUD 문구는 노랑 *"[Q] 매장 밖에 내려놓기"* → 빨강 *"매장 밖에는 놓을 수 없습니다"* 로 바뀝니다.

한 가지 테스트 항목을 남겼습니다. **매장 밖에서 시설을 들고 있으면 매장 안으로 돌아올 때까지 Q가 아무 반응이 없습니다.** HUD가 빨간 사유를 띄우므로 안내는 되지만, 이 흐름은 실제로 확인해봐야 합니다.

### 3. 뒤집힌 결정 ② — "공짜"가 아니었다

초안은 들고 있는 시설의 예정 영역 평면을 **기존 프리뷰 메시 배열에 넣으면 머티리얼 스왑·표시 토글·위치 갱신이 전부 공짜**라고 봤습니다. 실제로는 **별도 배열 3개를 새로 만들었습니다.**

**진짜 이유는 Wall Snap 오염이었습니다.**

> `CalculateCombinedBuildPreviewBounds()`가 프리뷰 배열 **전체**의 바운딩 박스를 합쳐 **벽 스냅 거리**를 계산합니다. 여기에 접근 영역 평면을 넣으면 **시설 몸통보다 훨씬 넓은 바운딩**이 만들어져서, 진열대가 벽에서 **영역 크기(75cm)만큼 떨어져** 붙습니다. 벽 스냅 기능이 통째로 망가집니다.

초안이 걱정했던 **"세 배열의 길이가 같아야 한다"는 제약은 부차적인 문제**였고, 진짜 위험은 전혀 다른 곳에 있었습니다.

> **"기존 배열에 얹으면 공짜"라고 생각할 때는, 그 배열을 읽는 다른 코드가 무엇을 하는지부터 봐야** 합니다. 공짜로 따라오는 네 가지만 세고, **원치 않게 따라오는 다섯 번째**를 못 봤습니다. 재사용의 이득을 셀 때 **부작용도 같이 세야** 한다는 걸 배웠습니다.

**추가로 배운 것 — `Yaw`만 남기기**

위치 갱신에서 배치 예정 회전을 그대로 쓰면 안 됐습니다.

> 시설을 손에 들고 위아래를 보면 **카메라 Pitch가 배치 예정 회전에 섞여** 들어옵니다. 그대로 쓰면 바닥 평면이 기울어 **땅을 파고들거나 공중에 뜹니다.** 몸통 프리뷰는 3D 메시라 기울어도 티가 안 나는데, **평면은 바로 보입니다.**

같은 데이터를 쓰는데 **표현 형태가 달라서 문제가 드러나는 정도가 다른** 사례였습니다.

### 4. 표시가 판정의 2배로 그려진 버그

점선 룩을 위해 표시용 메시를 `SM_Plane` → `BuildArea`로 교체했더니, **눈으로는 점선 안쪽인데 게임은 아니라고** 하는 증상이 나왔습니다.

**결론부터: 판정 로직은 한 줄도 안 바뀌었습니다.** 바뀐 건 **"그리는 판"** 뿐입니다.

| 항목 | `SM_Plane` | `BuildArea` |
| :--- | :--- | :--- |
| 실제 크기 | **100.0 × 100.0** | **199.707 × 199.707** |
| 피벗 | (0, 0, 0) 정중앙 | (+0.463, +2.124, +2.356) **어긋남** |
| 두께(Z) | 0 (완전 평면) | 1.163 (Z = 1.775 ~ 2.938) |
| 삼각형 | 2 (꽉 찬 사각형) | 144 (점선 테두리) |

핵심은 **199.707 / 100 = 1.997 ≈ 2배** 한 줄입니다.

```cpp
const float UnitPlaneSize = 100.0f;   // ← 근본 원인

ZonePlane->SetWorldScale3D(FVector(
    ZoneScaledExtent.X * 2.0f / UnitPlaneSize, ... ));
```

> 이 식이 성립하려면 원본 메시가 **정확히 100uu 정사각형이고, 피벗이 정중앙이고, Z=0 평면**이어야 합니다. 코드 입장에서는 **"이 메시는 100짜리 단위 평면"이라는 암묵적 계약**이 있었는데, 새 에셋이 그 계약을 깼습니다.

**화면에 생긴 "유령 띠"**

```
실제 판정 경계  :  X = -75.0   ~  +75.0
그려진 점선 경계 :  X = -149.1  ~ +150.5
                    → 바깥으로 약 0.75m 폭의 "보이지만 판정 안 되는 띠"
```

점선 안쪽으로 들어간 것처럼 보여도 **점선의 절반 지점을 넘지 않으면** 게임은 겹치지 않았다고 판단합니다. 반대로 **점선 한참 안쪽에서 갑자기 빨강으로 바뀌니** *"범위가 이상하다"* 로 느껴집니다.

> **증상이 "판정이 이상하다"였는데 원인은 "표시가 이상하다"였습니다.** 사람은 화면을 기준으로 판단하니까, **표시가 틀리면 멀쩡한 판정도 틀린 것처럼 보입니다.** 시각화 기능은 편의가 아니라 **판정의 신뢰도 자체**에 영향을 준다는 걸 처음 실감했습니다.

부수적으로 **피벗이 어긋나 그림 전체가 밀리고**(영역이 클수록 비례해서 커짐), **Z 지오메트리가 떠 있어** 계단·문턱 근처에서 선이 떠 보이거나 파고들 수 있다는 것도 확인했습니다.

### 5. `SM_Plane`은 "맞았던" 게 아니다

```
extent 75 → scale 1.5 → SM_Plane  : 100     × 1.5 = 150.0  == 판정 폭 150   (오차 0)
extent 75 → scale 1.5 → BuildArea : 199.707 × 1.5 = 299.6  vs 판정 폭 150   (오차 +149.6)
```

> `SM_Plane`이 옳았던 게 아니라 **코드의 하드코딩된 가정과 우연히 일치했을 뿐**입니다. 그 가정을 **어디에도 적어두지 않은 채 에셋만 교체**했기 때문에 깨졌습니다.

그리고 조사하면서 알게 된 것 하나 — **점선은 머티리얼이 아니라 메시 형상에서 나옵니다.** 표시용 머티리얼은 표현식이 색상 파라미터 하나뿐인 단색 Unlit이라 **점선 패턴을 만들 능력이 없습니다.** 그래서 *"채워진 면 → 테두리 점선"* 이라는 룩 변화까지 같이 일어나 **경계가 어디인지 더 헷갈리게** 됐습니다.

### 6. 해결 — 상수를 지우고 실측으로

세 가지 안 중 **B안(코드에서 실측)** 을 택했습니다.

| 안 | 장점 | 단점 |
| :--- | :--- | :--- |
| A. 에셋 리사이즈 | 코드 무수정, 가장 빠름 | **같은 실수가 또 남** |
| **B. 코드에서 실측** ✅ | **어떤 메시를 꽂아도 맞음**, 피벗 어긋남까지 자동 보정 | 코드 수정 필요 |
| C. 원복 | 즉시 정상화 | 점선 룩 포기 |

```cpp
const FBox MeshBounds = AccessZoneDisplayMesh->GetBoundingBox();
const FVector MeshSize = MeshBounds.GetSize();

// 상수 100 대신 에셋의 실제 폭으로 나눈다
OutScale = FVector(ZoneScaledExtent.X * 2.0f / MeshSize.X, ... );

// 피벗이 정중앙이 아니거나 Z=0에 안 붙은 메시를 역보정
const FVector MeshCenter = MeshBounds.GetCenter();
const FVector PivotOffset(MeshCenter.X * OutScale.X,
                          MeshCenter.Y * OutScale.Y,
                          MeshBounds.Min.Z * OutScale.Z);
OutLocation = ZoneFloorCenter - OutRotation.RotateVector(PivotOffset);
```

**XY는 바운드 중심을, Z는 바운드 최저점을** 기준으로 잡습니다. 그래야 사각형이 판정 박스 중심에 정렬되고, 지오메트리 바닥이 정확히 원하는 높이에 놓입니다.

그리고 **손에 든 프리뷰와 설치된 시설 표시가 같은 헬퍼 하나를 쓰도록 통일**했습니다. 원래는 같은 계산이 **두 곳에 복사**되어 있었는데, 그래서 하나만 고치면 어긋날 위험이 있었습니다.

**검산 결과 오차 0**이고, `SM_Plane`을 다시 꽂으면 보정량이 0이 되어 **기존 동작과 완전히 동일**합니다. 하위 호환입니다.

> **A안(에셋을 고쳐 계약에 맞추기)이 훨씬 빨랐습니다.** 그래도 B안을 택한 건, **암묵적 계약을 지키게 하는 것보다 계약 자체를 없애는 게** 낫다고 봤기 때문입니다. A안으로 가면 *"이 슬롯에는 100×100 메시만 넣으세요"* 라는 규칙이 계속 남고, 그 규칙은 **코드 어디에도 안 쓰여 있습니다.**
>
> 며칠 전 *"규칙으로 지키기보다 구조로 지킨다"* 를 적었는데, 같은 판단을 다시 한 셈입니다.
