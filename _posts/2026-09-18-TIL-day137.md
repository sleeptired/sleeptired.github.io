### 1. NavMesh 수정

증상은 대기열이었는데 원인은 **바닥에 떨어진 물건**이었습니다.

```
계산을 포기한 손님이 자기가 서 있던 줄 자리 위에 들고 있던 상품을 쏟음
  → 그 상품들이 NavMesh를 도려냄
  → 뒷사람이 그 자리로 들어오지 못함
  → 0번 자리 도착 게이트를 영영 통과 못 함
  → 줄 전체 정지
```

**바닥 낙하물을 전수 조사했습니다.**

| 대상 | NavMesh 도려냄? |
| :--- | :--- |
| 바닥 **상품** | **예** ← 가장 유력한 주범 |
| 손님이 흘린 쓰레기 | 아니오 (이미 방어됨) |
| **레벨에 배치된** 쓰레기 | **예** — 방어 코드로 가는 길이 아예 없음 |
| 플레이어가 버리거나 던진 쓰레기 | **예** — 방어 코드가 그 경로를 안 탐 |
| 떨어뜨린 **도구** | **예** |
| 수레 · 진열대 | 예 — **의도된 동작** |

> 흥미로운 건 **쓰레기에 이미 방어 코드가 있었다**는 점입니다. 손님이 흘리는 경로에서만 불리는 함수에 들어 있어서, **레벨 배치분과 플레이어가 버린 것은 그 함수를 안 지납니다.**
>
> **"막아뒀다"가 "모든 경로에서 막혔다"는 아니었습니다.** 방어를 어디에 넣었느냐가 전부였습니다.

### 2. `Pawn`만 고쳐서는 안 됐던 이유

엔진 원본을 확인했더니 판정 규칙이 예상과 달랐습니다.

```cpp
bool UPrimitiveComponent::IsNavigationRelevant() const
{
    if (!CanEverAffectNavigation()) { return false; }
    ...
    return IsQueryCollisionEnabled() &&
        (Response.GetResponse(ECC_Pawn)    == ECR_Block ||
         Response.GetResponse(ECC_Vehicle) == ECR_Block);   // ★ Vehicle도 본다
}
```

> **`ECC_Pawn`을 `Overlap`으로 바꿔도 `ECC_Vehicle`이 `Block`으로 남아 있으면 여전히 NavMesh를 깎습니다.**
>
> 이 프로젝트에 **`Pawn`만 조정한 코드가 여럿** 있었고, 전부 *"막은 줄 알았는데 안 막힌"* 상태였습니다. `StaticMeshComponent`의 기본 프로파일이 **전 채널 `Block`** 이라 `Vehicle`이 자동으로 남습니다.

그리고 **NavMesh 판정은 충돌 판정과 규칙 자체가 다릅니다.**

| | 충돌 결과 | NavMesh 판정 |
| :--- | :--- | :--- |
| 보는 대상 | **양쪽 응답 중 약한 쪽** | **자기 응답표만** |
| 상대가 `Ignore`면 | 통과 | **상관없음. 내가 `Block`이면 깎음** |

> *"손님이 통과하니까 NavMesh도 괜찮겠지"* 가 성립하지 않습니다. **통과는 양쪽이 합의해서 정해지고, NavMesh는 혼자 정합니다.**

### 3. 콜리전을 안 건드리고 플래그 하나만 껐다

수정 방법이 두 갈래였습니다.

| 안 | 내용 | 채택 |
| :--- | :--- | :---: |
| 콜리전 응답 조정 | `Pawn`·`Vehicle`을 `Overlap`으로 | ✗ |
| **`bCanEverAffectNavigation = false`** | 응답표와 **별개 필드**를 끔 | ✅ |

**콜리전을 안 건드린 이유**

> 상품·쓰레기·도구는 **줍고 던지고 떨어뜨리는** 물건입니다. 응답표를 바꾸면 **물리·던지기·줍기·오버랩 이벤트가 전부 영향권**에 들어갑니다.
>
> 엔진 전수 검색으로 **`bCanEverAffectNavigation`이 읽히는 곳이 내비게이션 등록 경로뿐**이라는 걸 확인했습니다. 그래서 **물리 동작은 수정 전과 100% 동일**하고 NavMesh 생성 대상에서만 빠집니다.

**최초에 생각했던 안은 기각했습니다.** `Pawn = Ignore`를 생성자로 옮기는 방식이었는데, 그러면 **손님이 물건을 통과해 지나가는** 동작까지 같이 바뀝니다. 지금 문제는 *"NavMesh가 깎이는 것"* 이지 *"물리적으로 막히는 것"* 이 아니었습니다.

> **고쳐야 하는 것보다 넓게 고치지 않는 게** 이번 판단의 핵심이었습니다. 증상이 같아 보여도 **NavMesh 차단과 물리 차단은 다른 문제**입니다.

### 4. 생성자에서 끈 이유

```cpp
// 콜리전 응답표와는 별개 필드라 SetStoredForPlayerInteraction()의
// SetCollisionResponseToAllChannels() 같은 전면 재설정에도 살아남는다
ProductMesh->SetCanEverAffectNavigation(false);
```

> 이 물건들은 상태가 바뀔 때마다 **콜리전을 통째로 재설정**합니다(진열 → 손에 듦 → 바닥 낙하). 그 경로마다 플래그를 끄면 **경로가 하나 늘 때마다 또 빠뜨립니다.**
>
> 그런데 이 플래그는 **응답표 전면 재설정이 건드리지 않는 별개 필드**라, **생성자 한 곳에서 꺼두면 이후 어떤 재설정에도 살아남습니다.** 기존 낙하 처리 함수들을 **한 글자도 안 고쳤습니다.**

결과적으로 **헤더 변경 없음, include 추가 없음, 삭제된 줄 0개, 실코드 3줄**입니다.

### 5. 고치지 않은 것도 적어뒀다

| 대상 | 판단 |
| :--- | :--- |
| 수레 · 진열대 | **의도된 동작**이라 유지 |
| 런타임 NavMesh 리빌드 설정 | **끄면 안 됨** — 타이쿤 시설 배치가 즉시 동선에 반영돼야 함 |
| `AgentRadius`, `NavMeshBoundsVolume` 등 전역 설정 | 손대지 않음 |
| **`Pawn = Block`이 남은 것들** | A안이 해결하지 않는 범위로 **명시** |

> 문서 맨 앞에 **"런타임 리빌드는 반드시 유지"** 를 대전제로 박아뒀습니다. 이걸 끄면 증상이 사라지지만 **타이쿤 시스템이 죽습니다.** 가장 빠른 해결책이 가장 나쁜 경우라 미리 차단해두는 게 맞다고 봤습니다.
>
> 레벨 배치 쓰레기는 **NavMesh 구멍은 사라졌지만 손님이 물리적으로는 여전히 막힙니다.** 이건 A안 범위 밖이라 **"해결되지 않은 것" 표로 따로** 남겼습니다.

### 6. [분석] 슬라임이 땅으로 꺼진다 — "틈을 메웠다"로 부족한 이유

팀원이 **바닥 이음매를 전부 메웠다**고 해서, 그것만으로 해결되는지 확인했습니다. **결론은 "보장되지 않는다"** 였습니다.

바닥 트레이스가 **바닥으로 인정하는 조건이 시각적 이음매보다 까다롭습니다.**

| 조건 | 내용 |
| :--- | :--- |
| ① **단순 콜리전** | `bTraceComplex = false`라 **눈에 보이는 폴리곤을 안 봅니다.** 시각적으로 메워도 콜리전 박스가 안 닿으면 트레이스에는 여전히 틈 |
| ② **`WorldStatic`** | 등록된 채널이 이것 하나뿐. 바닥이 `WorldDynamic`이면 **틈이 없어도 관통** |
| ③ 법선 Z ≥ 0.7 | 경사면·옆면은 바닥이 아님 |

> ②가 특히 중요했습니다. **관통한 뒤 아래에 다른 `WorldStatic`이 있으면 그 높이로 꺼집니다.** 반대로 아래에 아무것도 없으면 **트레이스 실패 → 손님 발 높이 폴백**이라 증상이 안 납니다.
>
> 즉 **"뚫린 것"보다 "뚫린 아래에 뭐가 있느냐"** 가 증상 발생을 가릅니다. 트레이스 구간이 아래로 120 cm라, 그 안에 뭐가 있는지가 전부입니다.

**진단하기 좋은 장소도 같이 적었습니다.** 계산 대기 슬롯은 **월드 고정 좌표**라 손님이 매번 같은 자리에 섭니다. **특정 슬롯에서 항상 재현되면 그 좌표 하나만 조사하면 됩니다.**

### 7. 정지 중에는 바닥 재검사가 아예 안 돈다

바닥이 완벽해도 남는 코드 결함을 찾았는데, 그중 하나가 **증상이 유지되는 직접 원인**이었습니다.

```cpp
// 마지막 검사 위치에서 수평으로 0.5 이상 움직였을 때만 재검사
if (FVector::DistSquared2D(NewLocation, LastFloorTraceLocation) >= FMath::Square(0.5f))
{
    ... // FloorZ 갱신은 오직 이 안에서만
}
VisualZ = FInterpTo(VisualZ, FloorZ, ...);   // 이 바깥은 항상 실행
```

> 비교가 **2D(수평)** 이라 **정지 중에는 진입 자체가 안 됩니다.** 잘못된 값이 한 번 들어가면 **손님이 움직일 때까지 그대로**입니다.
>
> 그래서 *"멈추면 꺼진 채 유지되고, 움직이면 올라온다"* 는 관찰이 정확히 설명됩니다. 보간 시정수가 약 0.067초라 **툭 떨어지지 않고 0.2초 안팎에 스르륵 꺼지는** 것까지 맞습니다.

**초판에서 틀린 분석을 한 번 냈다가 정정했습니다.** 처음엔 *"45 cm 래칫 때문에 영구 고정"* 이라고 썼는데, **"다시 움직이면 올라온다"는 실제 관찰**과 맞지 않았습니다.

> **관찰과 안 맞는 가설은 논리가 그럴듯해도 틀린 것**입니다. 개정 이력을 문서에 남겨서, 나중에 읽는 사람이 **폐기된 가설을 다시 세우지 않게** 했습니다.

### 8. 새치기 버그

*"줄 맨끝에서 먼저 판정된 손님이 앞이고, 계산대에 더 가까운 손님이 기다린다"* 는 제보를 확인했더니 **코드와 정확히 일치**했습니다.

```
순번 확정 = 계산을 결심한 순간 (Checkout 상태 진입)
계산 가능 = 0번 자리에 도착한 순간
            └ 두 시점의 간격 = 걸어오는 시간 = 줄 전체 정지 시간
```

**거리는 순번에 전혀 반영되지 않습니다.** 매장 반대편에서 결심한 손님이 0번을 가져가고, 계산대 옆 손님은 **빈 0번을 비워둔 채 뒤에 섭니다.** 게다가 **손님끼리 충돌이 꺼져 있어** 멀리서 온 손님이 줄을 **몸으로 뚫고** 앞으로 갑니다.

> 그리고 코드 주석에 **설계 의도가 그대로 적혀 있었습니다.** *"줄 순번 확정은 결심 시점, 계산 가능은 도착 시점으로 두 시점을 나누는 지점"*, *"이 검사가 없으면 매장 반대편에서 걸어오는 손님의 결제가 바로 끝나버림"*.
>
> **주석이 없었으면 버그로 단정하고 고쳤을 겁니다.** 의도를 알고 나니 *"고칠 것인가"* 가 기획 결정이 됐고, 그래서 문서를 **"고쳐드립니다"가 아니라 "팀에 물어볼 것 4가지"로** 마무리했습니다.

같은 원인에서 나오는 **파생 문제 3개**도 같이 정리했습니다. 특히 **인내심 소모가 뒤집혀 있는 것** — 인내심은 자기 슬롯에 도착한 뒤부터 흐르므로 **가까워서 먼저 도착한 뒷사람이 먼저 태우고, 멀리서 오는 앞사람은 걷는 동안 0으로 유지**됩니다.

### 9. "해결"과 "빈도 감소"를 가르는 것 — tie-breaker

권장안(도착 순으로 순번 확정)을 정리하다가 **이것만으로는 해결이 아니라는 걸** 알았습니다.

**도착 판정이 "점"이 아니라 반경 80 cm 영역**이기 때문입니다.

| | 손님 X | 손님 Y |
| :--- | :--- | :--- |
| 슬롯 중심까지 | **78 cm** (가장자리에 겨우 걸침) | **5 cm** (이미 중앙) |
| 판정 통과 | 같은 프레임 | 같은 프레임 |
| 결과 (틱 순서 운) | **0번** | 1번 |

> **원래 버그와 똑같은 불공정이 축소판으로 재현됩니다.** 규모만 2000 cm에서 160 cm로 줄었을 뿐이고, 플레이어는 여전히 *"쟤가 더 앞에 있었는데?"* 를 봅니다.
>
> 게다가 같은 프레임이면 **어느 컨트롤러가 먼저 틱했는가**로 결정되는데, 손님이 계속 스폰·소멸해서 **틱 리스트가 매번 갈아엎어집니다.** 같은 상황을 재현해도 **매번 다른 순번**이 나옵니다.
>
> → **QA가 제보해도 재현이 안 되고, 고친 뒤에도 고쳐진 건지 우연인지 판별할 수 없습니다.** tie-breaker의 첫 번째 존재 이유가 **재현성**이었습니다.

**"거리순으로 매 프레임 정렬"은 오히려 새 문제를 만든다**는 것도 적어뒀습니다. 두 손님의 거리가 엎치락뒤치락하면 **순번이 프레임마다 뒤바뀌고**, 그때마다 이동 명령이 재발급되어 **서로의 자리로 왕복하는 진동**이 생깁니다.

> 그래서 올바른 형태는 **"한 번 확정하면 끝" + "확정 순간의 tie-breaker"** 입니다.
