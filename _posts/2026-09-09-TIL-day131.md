## 날씨 확률 조정 시스템 — "되돌리지 않는" 구조로 만들었다

> 어제 만든 날씨 시스템 위에 **확률을 게임 중에 바꾸는 기능**을 구현했습니다. *"이제부터 흐림이 10%로 나온다"* 같은 영구 변경과 *"저주받은 일주일, 비 60%"* 같은 기간제 이벤트를 **하나의 구조로** 처리합니다.

---

### 1. 만든 것

| 항목 | 내용 |
| :--- | :--- |
| **확률 3층 구조** | 원본 데이터(불변) → 영구층 → 유효표(매번 새로 만들고 버림) |
| **연산 3종** | `Set`(확률 지정) / `Multiply`(확률 배수) / `Weight`(가중치 배율) |
| **재분배 모드 2종** | `Proportional`(비례) / `Even`(균등) |
| **기간제 레이어** | 시작·종료 영업일차를 가진 지시서. 예약·중도 해제 지원 |
| **공개 API** | 영구 4개 + 기간제 3개, 전부 Blueprint 노출 |
| **순수 함수 6개** | 확률표를 인자로 받는 `static` 계산 함수 |

기존 `AddWeightModifier` 계열은 이 시스템으로 **완전히 대체해서 삭제**했습니다.

### 2. ⭐ 3층으로 나눈 이유 — 복원 코드를 안 만들려고

```
DA_WeatherSetting.BaseWeights    원본. 런타임에 절대 안 바뀜
        │  게임 시작 시 복사
        ▼
RuntimeWeights (영구층)           영구 이벤트가 직접 고침. 되돌리지 않음
        │  사본을 떠서
        ▼
Effective (유효표)                활성 기간제를 얹음. 매번 새로 만들고 버림
```

처음엔 기간제를 *"적용할 때 이전 값을 저장해두고, 만료되면 되돌리는"* 방식으로 생각했습니다. 그런데 그렇게 짜면 문제가 생깁니다.

> **기간제가 걸려 있는 동안 영구 변경이 들어오면 저장해둔 "이전 값"이 낡은 값이 됩니다.** 만료 시 그 값으로 되돌리면 **중간에 있었던 영구 변경이 사라집니다.**

그래서 **되돌리지 않는 쪽**을 택했습니다. 기간제는 값을 쓰는 게 아니라 **지시서를 목록으로 들고 있다가, 계산할 때마다 영구층 사본 위에 다시 적용**합니다.

```cpp
FCSWeatherWeightSet Effective = RuntimeWeights;   // 이 한 줄이 전부를 보장한다
```

> **만료되면 복원 작업이 필요 없습니다. 애초에 영구층을 건드린 적이 없기 때문입니다.** 기간제가 끝나면 그냥 목록에서 빠지고, 다음 계산부터 그 지시서가 적용되지 않을 뿐입니다.
>
> "되돌리는 코드"를 안 만들었더니 **되돌리기 버그도 안 생겼습니다.**

**원본 데이터 에셋을 안 건드린 이유**도 따로 있습니다. 로드된 `UDataAsset` 인스턴스를 고치면 **PIE를 껐다 켜기 전까지 값이 남고, 실수로 저장하면 원본이 바뀝니다.** 그래서 시작 시 한 번 복사한 뒤로는 원본을 읽지도 않습니다.

### 3. 레이어에는 결과가 아니라 "지시서"를 저장했다

```cpp
struct FCSWeatherChanceLayer
{
    FName                   SourceId;          // 해제할 때 쓰는 이름표
    ECSWeatherType          WeatherType;
    ECSChanceOpType         Op;                // Set / Multiply / Weight
    float                   Value;             // Set이면 확률, 나머지는 배수 ★
    ECSChanceRebalanceMode  Mode;
    int32                   StartBusinessDay;
    int32                   EndBusinessDay;    // 0이면 무기한
};
```

`Value`에 **계산 결과가 아니라 원본 값**이 들어갑니다.

> `Multiply ×2`를 등록할 때 *"현재 0.3이니까 0.6"* 으로 미리 계산해 저장하면, **중간에 영구층이 바뀌어도 0.6에 고정**됩니다. 배수로 저장해야 영구 확률이 움직일 때 결과도 따라 움직입니다.
>
> 실제로 검산해보니 12일차에 영구 변경이 들어갔을 때 `Set`은 60%를 유지하고 `Multiply`·`Weight`는 결과가 따라 움직입니다. **의도한 차이가 그대로 나왔습니다.**

`SourceId`를 필수로 한 이유는 두 가지입니다 — **중도 해제**와 **같은 이름 재등록 시 덮어쓰기**. 이름 없이 등록하면 뺄 방법이 없어서 아예 거부하게 했습니다.

### 4.  연산 세 개를 하나의 enum으로 묶었다

영구든 기간제든 **`ECSChanceOpType` 하나로 표현**하고, `ApplyOpTo()`가 **모든 연산의 단일 진입점**이 되게 했습니다.

```cpp
void UCSWeatherSubsystem::ApplyOpTo(FCSWeatherWeightSet& Weights, ECSWeatherType Type,
    ECSChanceOpType Op, float Value, ECSChanceRebalanceMode Mode)
{
    switch (Op)
    {
    case Set:      ApplyChanceTo(Weights, Type, Value, Mode); break;
    case Multiply: ApplyChanceTo(Weights, Type, GetChanceIn(Weights, Type) * Value, Mode); break;
    case Weight:   Weights.Weights.Add(Type, Weights.GetWeight(Type) * Value);
                   NormalizeSet(Weights); break;
    }
}
```

**연산별로 공개 함수를 따로 만들지 않은 이유**가 있습니다.

> `ApplySetChance()`, `ApplyMultiplyChance()` 식으로 나누면 **영구용과 기간제용을 각각 만들어야** 합니다. 그러면 연산 하나 추가할 때 **두 군데를 고쳐야 하고, 한쪽을 빠뜨리면 조용히 다르게 동작합니다.**
>
> `Op`를 인자로 받는 형태로 두니 **연산을 추가할 때 고칠 곳이 enum과 `switch` 두 곳뿐**입니다. 공개 API와 레이어 구조체는 손댈 필요가 없습니다.

### 5.  `Multiply`와 `Weight`를 둘 다 남긴 이유

같은 `×2`인데 결과가 다릅니다. **차이는 정규화 순서**입니다.

| 연산 | 0.3에 ×2 | 계산 순서 |
| :--- | ---: | :--- |
| `Multiply` | **60.0%** | 대상을 0.6으로 **못 박고** → 나머지만 0.4로 축소 |
| `Weight` | **46.2%** | 가중치를 곱하고 → **전체를 나눔** (대상도 함께 희석) |

큰 배수에서 성질이 완전히 갈립니다.

```
비가 0.4인 상태에서 ×3

Multiply   0.4 × 3 = 1.2 → 1.0으로 잘림 → 나머지 전부 0%
Weight     1.2 / (0.6 + 1.2) = 66.7%   → 나머지 33.3% 생존
```

**둘 다 남긴 이유**

*   **`Multiply`는 수치를 보장합니다.** *"비 확률 2배"* 라는 기획 문구가 그대로 60%가 됩니다. 대신 **1.0에서 잘리고, 그러면 나머지가 전부 0%** 가 됩니다.
*   **`Weight`는 100%에 점근할 뿐 도달하지 않습니다.** 배수를 아무리 키워도 다른 날씨가 살아남습니다.

> **기획자가 배수를 데이터로 직접 만지는 구조라면 `Weight`가 사고가 덜 납니다.** 실수로 큰 값이 들어와도 다른 날씨가 0이 되지 않으니까요. 반대로 *"정확히 몇 %"* 를 보장해야 하는 이벤트는 `Multiply`나 `Set`을 씁니다.
>
> 하나만 남겼으면 둘 중 한쪽 요구를 못 받았을 겁니다. **성질이 다르다는 걸 문서에 검산표로 적어두고 선택 기준을 표로 만든 게** 이번 작업에서 제일 신경 쓴 부분입니다.

`Set`은 **0에서도 올릴 수 있는 유일한 연산**입니다. 곱셈 계열은 `0 × n = 0`이라 *"흐림 해금: 0% → 10%"* 같은 걸 못 합니다.

### 6.  `Even` 재분배 — 오름차순 정렬이 알고리즘의 전부

`Proportional`은 나머지 전부에 같은 배율을 곱하면 끝이라 한 줄입니다. 문제는 `Even`이었습니다.

> 같은 양씩 빼야 하는데 **잔량이 부족한 날씨는 0에서 멈춰야** 하고, **그 부족분을 남은 날씨가 대신 부담**해야 합니다.

재시도 루프 없이 **한 번에** 처리하도록 짰습니다.

```cpp
Others.Sort([](const auto& A, const auto& B){ return A.Value < B.Value; });  // ★ 오름차순

float Remaining = Delta;
for (int32 Index = 0; Index < Others.Num(); ++Index)
{
    const int32 RemainingCount = Others.Num() - Index;
    const float Share = Remaining / RemainingCount;      // 남은 몫 ÷ 남은 대상 수
    const float Take  = FMath::Min(Share, Others[Index].Value);   // 가진 만큼만
    Weights.Weights.Add(Others[Index].Key, Others[Index].Value - Take);
    Remaining = FMath::Max(0.0f, Remaining - Take);
}
```

동작 원리는 두 갈래입니다.

```
Value >= Share  →  Take = Share. Remaining과 분모가 같은 비율로 줄어
                   다음 Share가 그대로 유지된다

Value <  Share  →  Take = Value (0이 됨). 덜 걷힌 만큼 Remaining이 남고
                   분모만 줄어 다음 Share가 커진다 → 부족분이 자동으로 뒤로 전가
```

> **오름차순 정렬이 이 알고리즘의 핵심 장치입니다.** 못 내는 날씨가 **먼저** 나와야 그 시점에 아직 낼 대상이 남아 있습니다.
>
> 정렬 방향을 뒤집으면 큰 값이 먼저 `Share`만 내고 빠져서, 마지막에 **부족분을 떠안을 대상이 사라집니다.** 그래서 주석에 **"부등호를 건드리면 안 됩니다"** 라고 적어뒀습니다.

마지막 원소에서는 `RemainingCount == 1`이라 남은 전액을 한 번에 처리합니다. **부동소수 오차가 마지막에 흡수되는** 구조라 총합이 항상 1.0으로 맞습니다.

### 7. 순수 함수를 `static`으로 만든 이유

계산 함수 6개를 **확률표를 인자로 받는 `static`** 으로 만들었습니다.

| 함수 | 역할 |
| :--- | :--- |
| `ApplyOpTo` | 연산 분기. **연산 추가 시 여기만** |
| `GetChanceIn` | 표에서 확률 읽기 |
| `ApplyChanceTo` | 확률을 세우고 나머지 재분배 |
| `NormalizeSet` | 합을 1.0으로 |
| `RebalanceProportionalIn` / `RebalanceEvenIn` | 재분배 두 종류 |

**같은 로직을 영구층과 임시 계산본 양쪽에 써야** 해서 표를 인자로 받게 한 건데, `static`으로 둔 데는 다른 이유가 있습니다.

> `static`은 필수가 아닙니다. 그런데 **멤버에 접근할 수 없으므로, 기간제 계산이 실수로 영구층(`RuntimeWeights`)을 건드리는 코드가 컴파일 단계에서 막힙니다.**
>
> 이 시스템에서 가장 위험한 사고가 *"기간제가 영구층에 박제되는 것"* 인데, 그걸 **주석이나 리뷰가 아니라 언어 기능으로** 막았습니다.

멤버를 읽어야 하는 `BuildEffectiveWeights` / `ApplyWeatherChance` / `AddChanceLayer`는 `static`이 아닙니다. **이 구분 자체가 "표만 보는 함수"와 "객체 상태를 보는 함수"의 경계**가 됐습니다.

### 8. 거부 조건 4개를 넣었다

`ApplyWeatherChance`와 `AddChanceLayer` 모두 **경고 로그를 남기고 아무것도 하지 않습니다.**

| 조건 | 이유 |
| :--- | :--- |
| `DT_Weather`에 행이 없는 날씨 | 표시 이름도 이펙트도 없어 내보낼 수 없음 |
| `Set`인데 `Value > 1.0` | 확률이 100%를 넘을 수 없음 |
| 곱셈 계열인데 현재 확률이 0 | `0 × n = 0` — 아무 일도 안 일어나는데 성공한 줄 알게 됨 |
| `SourceId`가 비어 있음 | 해제할 방법이 없어짐 |

> 세 번째가 특히 중요했습니다. **조용히 아무 일도 안 일어나면 "왜 안 되지"를 한참 찾습니다.** 거부하고 로그를 남기면 *"이 날씨는 `Set`으로 먼저 올려야 한다"* 를 바로 알 수 있습니다.

### 9. 남긴 한계와 그 이유

**기간제끼리 겹치면 순서에 의존합니다.** `A: 비 60%` + `B: 눈 40%` 를 동시에 `Set`으로 걸면 **둘 다 정확할 수는 없습니다.**

> 이건 알고리즘 문제가 아니라 **요구 자체가 모순**입니다. 그래서 해결하려 하지 않고 **결과가 결정론적이기만 하게** 만들었습니다 — `SourceId` 사전순으로 정렬해서 적용합니다.
>
> 어느 쪽이 이길지 의도적으로 정하고 싶어지면 `Priority` 필드를 추가하면 되는데, **그런 요구가 실제로 나오기 전에는 안 만들기로** 했습니다.

`Multiply`끼리, `Weight`끼리는 **순서와 무관하게 곱해지므로** 이 문제가 없습니다. 연산이 섞일 때만 순서가 결과를 바꿉니다.

**이미 뽑힌 날짜에는 영향이 없습니다.** 확정 배열이 append-only라, 실제 적용 시작일은 `max(시작일, 오늘 + 공개예보일수 + 1)`입니다. 어제 만든 *"보여준 예보는 안 바꾼다"* 규칙이 그대로 적용됩니다.

**만료는 조용히 일어납니다.** 활성 판정이 걸러줄 뿐 별도 알림이 없어서, *"저주가 풀렸습니다"* 같은 연출이 필요하면 별도 처리가 필요하다고 적어뒀습니다.

### 10. `AddWeightModifier`를 삭제했다

어제 만들었던 배율 시스템을 **통째로 제거**했습니다. 구조체 · 함수 2개 · 맵 · 계산 루프까지 전부입니다.

**삭제한 이유 — 제약이 셋이나 있었습니다.**

*   확률이 0인 날씨를 올릴 수 없음 (`0 × n = 0`)
*   배율 2를 줘도 확률이 2배가 되지 않음 (정규화 희석)
*   절대 확률을 지정할 수 없음

> **그 동작이 필요하면 `ECSChanceOpType::Weight`가 똑같이 재현합니다.** 가중치를 곱하고 정규화하는 것이 정확히 같은 계산입니다. 거기에 **기간제·중첩 관리까지 따라오므로 되살릴 이유가 없습니다.**
>
> 삭제 시점에 **C++ 호출부와 Blueprint 참조가 모두 0건**인 것을 확인했습니다. 어제 만든 걸 하루 만에 지우는 게 아깝게 느껴졌는데, **기능이 상위 호환으로 포함되면 남겨두는 쪽이 오히려 비용**입니다. 두 방식이 공존하면 *"어느 걸 써야 하나"* 가 계속 질문거리가 됩니다.
