### 2. 배달 탭을 그대로 베꼈다

이미 같은 게시판 안에 **배달 주문 탭**이 있어서, 구조도 위치도 그대로 따라갔습니다.

| 항목 | 배달 탭 | 날씨 탭 |
| :--- | :--- | :--- |
| C++ → BP 이벤트 | `RefreshDeliveryOrderListView(Orders, Count, Count)` | `RefreshWeatherTabView(Today, Tomorrow, bHasTomorrow)` |
| 넘기는 것 | **구조체 / 숫자** | **구조체 / bool** |
| 라벨 문구 | BP Format Text 패턴 (고정) | BP Format Text 패턴 (고정) |
| 데이터 없음 처리 | BP Branch → 고정 문구 | BP Branch → `내일의 날씨: 예보 없음` |
| 첫째 줄 위치 | `Text_Title` ("배달 주문") | `Text_TodayWeather` (**같은 슬롯**) |
| 둘째 줄 위치 | `HorizontalBox_Summary` | 같은 자리의 `Text_TomorrowWeather` |

**위치까지 맞춘 이유**가 있습니다.

> 탭을 오갈 때 **두 줄의 위치가 흔들리면 어색합니다.** 그래서 배달 탭 Designer에서 `Border_Main`을 통째로 복사해 붙여넣고, 안 쓰는 위젯만 지우고 이름을 바꿨습니다. **슬롯 설정(정렬·여백·폰트)을 손으로 다시 맞추지 않아도** 같은 자리가 나옵니다.
>
> 지운 위젯 중 `Border_NotificationPanel`은 원래 `Collapsed`라 **지워도 위치가 변하지 않는다**는 걸 확인하고 지웠습니다. Collapsed 위젯은 공간을 차지하지 않으니까요.

붙여넣은 뒤 `Border_Main` 슬롯의 Offset에 `-0.1`, `3.3` 같은 **미세값이 섞여 있어서 전부 0으로 맞췄습니다.** 원본이 손으로 드래그해서 만들어진 흔적입니다.

### 3. 문자열을 C++에서 만들지 않았다

`"오늘의 날씨: 맑음"` 이라는 완성된 문자열을 C++에서 만들어 넘길 수도 있었는데, **그렇게 안 했습니다.**

```cpp
// C++은 구조체만 넘긴다
UFUNCTION(BlueprintImplementableEvent)
void RefreshTodayWeatherDisplay(const FCSWeatherForecastEntry& TodayWeather);
```

```
BP: Format Text
      Format  = "오늘의 날씨: {Weather}"    ← 라벨은 BP에 고정
      Weather ← DisplayName                 ← C++에서 받은 값
```

**이렇게 나눈 이유 두 가지**

| 나중에 하고 싶은 것 | C++을 고쳐야 하나 |
| :--- | :--- |
| 라벨을 `"금일 날씨"` 로 변경 | **아니오.** BP Format Text 패턴만 |
| 날씨별 **아이콘** 추가 | **아니오.** 구조체째 넘겼으니 BP에서 `WeatherType`으로 분기 |
| 색을 날씨별로 다르게 | **아니오.** 같은 방법 |

> **문구를 C++에서 조립하면 표현을 바꿀 때마다 빌드해야 합니다.** 구조체를 통째로 넘기면 BP가 필요한 필드만 꺼내 쓰고, **표현 변경은 전부 BP 쪽에서 끝납니다.**
>
> 배달 탭이 이미 그 방식(`{Count}` ← 숫자)이라 새 규칙을 만든 게 아니라 **기존 경계를 그대로 따랐습니다.**

### 4.  `OnWeatherChanged`가 아니라 `OnWeatherForecastUpdated`를 구독했다

델리게이트가 둘 있는데 **의도적으로 후자를 골랐습니다.**

| 발생 지점 | `OnWeatherChanged` | `OnWeatherForecastUpdated` |
| :--- | :---: | :---: |
| 하루 시작 | O | O |
| 이벤트로 **오늘** 날씨 변경 | O | O |
| 이벤트로 **내일** 날씨 변경 | **X** | **O** |
| 디버그 커맨드 | O | O |

> **날씨 탭은 내일까지 보여줍니다.** `OnWeatherChanged`는 이름 그대로 *"오늘 날씨가 바뀌었다"* 만 알려주므로, **내일 예보만 바뀌는 경우를 놓칩니다.** 그러면 탭이 열려 있는데 값이 안 바뀌는 상태가 됩니다.
>
> 표면 위젯은 오늘만 보여주니 `OnWeatherChanged`로도 충분한데, **둘 다 같은 델리게이트를 쓰게** 했습니다. 두 위젯이 서로 다른 걸 구독하면 나중에 *"왜 표면은 바뀌는데 탭은 안 바뀌지"* 같은 걸 헷갈릴 것 같아서요.

### 5. 기존 이벤트를 고치지 않고 새로 추가

게시판 표면 위젯에는 이미 배달 알림용 이벤트가 있었습니다.

```cpp
void RefreshNoticeBoardDisplay(bool bHasPendingDeliveryOrder);   // 기존 — 그대로 둠
void RefreshTodayWeatherDisplay(const FCSWeatherForecastEntry&); // 신규 — 따로 추가
```

여기에 인자를 추가해 하나로 합칠 수도 있었는데, **안 했습니다.**

> `BlueprintImplementableEvent`는 **BP 그래프가 이름과 시그니처로 연결**되어 있습니다. 인자를 추가하면 **BP의 기존 배달 알림 노드가 깨지고**, 그래프를 다시 연결해야 합니다.
>
> 그리고 의미상으로도 다릅니다. **배달 알림과 날씨는 서로 독립적으로 바뀌는 값**이라, 하나가 바뀔 때 다른 하나까지 다시 그릴 이유가 없습니다.

주의사항 문서에도 **"이 시그니처를 바꾸지 마세요"** 라고 적어뒀습니다. C++만 보면 합치고 싶어지는 모양이라, **BP 쪽 비용이 코드에 안 보인다**는 게 이런 경우인 것 같습니다.

### 6. 날씨 서브시스템에 이미 구현

UI를 붙이면서 **서브시스템 쪽에 필요한 게 이미 다 있었습니다.**

| 필요한 것 | 이미 있던 API |
| :--- | :--- |
| 오늘 날씨 | `GetCurrentWeatherEntry()` |
| 오늘 + 내일 | `GetForecastEntries()` — `[0]=오늘, [1]=내일` |
| 표시 이름 | `FCSWeatherForecastEntry::DisplayName` |
| 갱신 알림 | `OnWeatherForecastUpdated` |

> 이틀 전에 *"소비 측이 `DT_Weather`를 참조하지 못하게 하고, 표시용 값이 필요하면 이름·설명·아이콘까지 채워서 준다"* 로 만들어뒀는데, **그게 그대로 값을 했습니다.** UI를 붙이는 쪽에서 데이터 테이블을 열어볼 일이 한 번도 없었습니다.
>
> 그때는 *"소유권 경계"* 를 지키려고 한 설계였는데, **결과적으로 소비 측 작업량이 줄었습니다.**

**`GetForecastEntries()`가 `const`가 아니라는 점**은 잠깐 걸렸습니다. 내부에서 확정 함수를 부르기 때문인데, **하루 시작 시 이미 공개 범위까지 확정해두고 배열이 append-only**라 **UI에서 불러도 날씨가 새로 굴려지지 않습니다.** 확인하고 그대로 썼습니다.

### 7. 구독하고 나서 한 번 더 읽게 했다

```cpp
void NativeConstruct()
{
    ... 구독 ...
    RefreshDisplay();   // ← 구독 직후 현재 값으로 한 번
}
```

**위젯과 서브시스템 중 무엇이 먼저 생성되는지 보장이 없어서**입니다.

| 순서 | 결과 |
| :--- | :--- |
| 서브시스템 먼저 → 위젯 | 첫 방송을 놓치지만 **직후 읽기로 올바른 값** |
| 위젯 먼저 → 서브시스템 | 읽을 땐 비어 있지만 **구독 중이라 방송을 받음** |

> 며칠 전 스포너에서 배운 **"구독 + 즉시 동기화"** 패턴을 그대로 썼습니다. 이번엔 세 번째 적용이라 고민 없이 바로 넣었습니다.

`NativeDestruct`에서 **구독 해제**도 같이 넣었습니다. 게시판을 닫으면 위젯이 파괴되는데, 해제를 안 하면 파괴된 위젯으로 방송이 가게 됩니다.

### 8. "내일 예보 있음" 플래그를 따로 넘겼다

```cpp
RefreshWeatherTabView(Today, Tomorrow, bHasTomorrowForecast);
//                                     ^^^^^^^^^^^^^^^^^^^^ 왜 필요한가
```

`PublicForecastDays`가 0이면 **내일 항목 자체가 없습니다.** 그때 빈 구조체를 넘기면 BP가 `내일의 날씨: ` 처럼 **값 자리만 빈칸**으로 그립니다.

> **"값이 비어 있음"과 "항목이 없음"을 구분해야** BP가 `내일의 날씨: 예보 없음` 이라는 고정 문구를 띄울 수 있습니다. 배달 탭이 주문 0건일 때 `현재 접수된 배달 주문이 없습니다.` 를 띄우는 것과 같은 처리라 방식도 맞췄습니다.

### 9. 지운 것 — "아침 / 점심 / 저녁"

게시판 표면에 원래 시간대별 날씨를 보여주는 자리가 있었는데 **삭제**했습니다.

> 날씨 서브시스템은 **하루에 날씨 하나만** 가지고 **시간대 개념이 없습니다.** 채울 데이터가 없는 칸을 남겨두면 *"여기는 왜 비어 있지"* 가 됩니다.
>
> 시간대별 날씨가 나중에 필요해지면 **서브시스템부터 바꿔야 하는 일**이라, UI 쪽에 자리만 미리 남겨두는 건 의미가 없다고 봤습니다.

### 10. ⭐= 확장 가이드를 미리 쓰고, 작업 순서를 못 박았다

지금 날씨 탭은 **오늘 + 내일 두 줄 고정**입니다. 그런데 `PublicForecastDays`를 3으로 올리면 **모레·3일 뒤가 안 보입니다.**

그래서 **목록형으로 바꾸는 가이드를 따로 썼습니다.** 배달 탭의 주문 목록 방식(행 위젯 + ForEach + AddChild)을 그대로 따르면, 그 뒤로는 **데이터 에셋 숫자만 바꿔도 줄이 늘어나거나 줄어듭니다.**

**지금 바로 목록형으로 안 만든 이유**

> 현재 값이 1이라 **두 줄이면 충분**하고, 목록형은 행 위젯 C++ 클래스와 BP를 하나씩 더 만들어야 합니다. **필요해지는 시점에 바꾸되, 그때 헤맬 일이 없게 순서만 적어둔** 것입니다.

**그리고 작업 순서를 굵게 못 박았습니다.**

```
1. BP 정리 (C++ 빌드 전)   ← 기존 두 줄용 위젯과 그래프 삭제
2. C++ 수정 + 빌드
3. BP 구성
4. 테스트
```

> **C++에서 이벤트를 먼저 지우면, BP를 열었을 때 "함수를 찾을 수 없음" 에러 노드가 남습니다.** 그 노드는 수동으로 찾아 지워야 하고, 컴파일도 안 됩니다.
>
> **BP를 먼저 정리하면 이 상황 자체가 안 생깁니다.** 순서 하나로 정리 작업이 사라지는 셈인데, C++만 보면 알 수 없는 종류의 제약이라 문서에 적어뒀습니다.

### 11. 디버그 출력을 끌 스위치를 남겼다

날씨 서브시스템에 이 매크로가 있습니다.

```cpp
// 게시판 위젯이 붙으면 0으로 바꿔 화면 출력만 끌 수 있습니다. 콘솔 커맨드는 남습니다.
#define CS_WEATHER_DEBUG 1
```

이틀 전에 *"UI가 없으니 화면 디버그 메시지로 표시한다"* 로 만들었는데, **오늘 게시판이 붙었으니 이제 끌 수 있습니다.**

> 다만 **바로 끄지 않고 담당자와 상의하기로** 했습니다. 아직 검증 중이라 화면 출력이 있는 게 편할 수 있고, **콘솔 커맨드는 매크로를 꺼도 남으므로** 급하지 않습니다.
>
> 임시 코드를 만들 때 **끄는 방법을 같이 만들어둔 게** 오늘 값을 했습니다. 매크로 하나 바꾸면 끝입니다.
