## 날씨 시스템 구현 — 기존 코드는 두 파일만 건드렸다

> 날씨 시스템을 C++로 구현했습니다. 하루가 넘어가면 날씨가 바뀌고, 비·눈 이펙트가 교체되고, 확률은 데이터로 조절합니다. **구현하면서 내린 판단마다 이유가 있어서** 그걸 중심으로 정리합니다.

---

### 1. 만든 것

```
Source/ConvenienceStore/
├── Data/
│   ├── CSWeatherTypes.h                   열거형 + DT 행 + 확률 구조체 + 예보 엔트리
│   └── CSWeatherSettingsDataAsset.h/.cpp  확률 표 + 예보 일수
├── Systems/Weather/
│   ├── CSWeatherSubsystem.h/.cpp          코어 (확정 · 추첨 · 전파 · 연출 교체)
│   └── CSWeatherDebug.cpp                 디버그 전부 (통째로 삭제 가능)
└── Features/Weather/
    └── CSWeatherEffectActor.h/.cpp        연출 액터 베이스 (Abstract, Blueprintable)
```

**기존 코드에 손댄 곳은 `ACSStoreGameMode` 두 파일뿐**입니다.

| 파일 | 변경량 |
| :--- | :--- |
| `CSStoreGameMode.h` | 전방 선언 1줄 + 프로퍼티 1개 + 함수 선언 1개 |
| `CSStoreGameMode.cpp` | include 1줄 + 게터 구현 4줄 |

하루 흐름을 담당하는 `StoreFlow` 코드는 **한 줄도 바뀌지 않았습니다.** 아래는 그렇게 만들기 위해 내린 판단들입니다.

### 2. 설정을 "받는" 게 아니라 "가져가게" 만들었다

`ACSStoreGameMode::BeginPlay()`를 건드리지 않았습니다. 거기서 서브시스템을 찾아 설정을 **주입하는(push)** 방식이 더 흔한데, 반대로 짰습니다.

```cpp
// UCSWeatherSubsystem::OnWorldBeginPlay
ACSStoreGameMode* GameMode = GetWorld()->GetAuthGameMode<ACSStoreGameMode>();
if (GameMode == nullptr) { return; }        // 조용히 종료
const UCSWeatherSettingsDataAsset* Settings = GameMode->GetWeatherSettings();
```

**왜 pull로 짰나**

*   `BeginPlay()`를 건드리면 **다른 담당자와 충돌 지점이 생깁니다.** 게임모드 `BeginPlay`는 이미 여러 시스템이 초기화되는 곳이라, 여기에 줄을 추가하면 순서 문제까지 따라옵니다.
*   **초기화 순서에 안 걸립니다.** 서브시스템이 자기 시점에 필요한 것만 가져가니, 누가 먼저 시작하는지 신경 쓸 필요가 없습니다.
*   프로젝트에 **선례가 있었습니다.** 튜토리얼 서브시스템이 `GetTutorialStepDataTable()`을 같은 방식으로 가져갑니다. 새 방식을 만들지 않고 그걸 따랐습니다.

`GameMode`가 없으면 **경고 없이 조용히 종료**하게 한 것도 의도적입니다. 슈팅·호러 배리언트 맵에서는 이 게임모드가 아예 없어서, 경고를 남기면 **정상 상황에서 로그가 더러워집니다.** 반대로 게임모드는 있는데 **설정 에셋이 없는 것**은 실수이므로 경고를 남겼습니다.

### 3. 델리게이트 하나만 구독했다

날씨 전환 지점을 찾으려고 하루 흐름을 코드로 따라가 봤는데, 이렇게 되어 있었습니다.

```
StartNextBusinessDay()
  ├─ BeginNextBusinessDay()
  │      ├─ ++CurrentBusinessDay                 ★ 일차 +1
  │      └─ OnBusinessDayStarted.Broadcast(N)    ★ 여기서 날씨 전환
  └─ StartStoreFlow()                            준비 단계로
```

**그래서 이 방송 하나만 구독하기로 했습니다.**

*   **일차가 올라가는 지점과 날씨가 바뀌어야 하는 지점이 같은 함수 안**입니다. 어긋날 여지가 구조적으로 없습니다.
*   이 방송이 `StartStoreFlow()`보다 **먼저** 나와서, **준비 단계 첫 프레임부터 새 이펙트가 켜져** 있습니다. 원하던 순서가 그냥 맞았습니다.
*   하루를 넘기는 **경로가 둘**(마감종 → 정산 확인 / 마감 업무 4종 완료)인데, **둘 다 같은 함수를 지납니다.** 날씨 쪽에서 경로를 구분할 필요가 없었습니다.

원래 계획은 **마감 위젯의 `NativeDestruct`에서 전환 함수를 호출**하는 것이었는데, 그렇게 했으면 **위젯 담당자 파일을 수정**해야 했고 경로 둘 중 하나만 잡혔을 겁니다.

> 구현 전에 **하루 흐름을 코드로 한 번 따라가 본 게** 이 판단을 만들었습니다. 안 봤으면 위젯에 호출을 심었을 겁니다.

### 4. 1일차만 직접 적용하게 했다

```cpp
OnBusinessDayStarted.AddDynamic(this, &UCSWeatherSubsystem::HandleBusinessDayStarted);
...
ApplyBusinessDay(GameState->CurrentBusinessDay);   // ← 1일차용
```

구독만 하면 될 줄 알았는데, **1일차에는 그 방송이 안 옵니다.** 게임을 켜자마자 1일차인 상태로 시작하기 때문에, *"다음 날이 시작됐다"* 는 신호가 발생하지 않습니다.

그래서 **구독 직후에 현재 일차를 직접 한 번 적용**했습니다.

> 8월에 *"구독만 하면 초기 신호를 놓치고, 읽기만 하면 이후 변화를 놓친다. 둘 다 해야 순서와 무관하게 안전하다"* 를 배웠는데, 이번엔 **처음부터 그렇게 짰습니다.** 그때는 버그를 만나고 나서 고쳤는데 이번엔 미리 넣었습니다.

### 5. 확정 배열을 append-only로 짰다

날씨를 `TArray<ECSWeatherType>`에 **1일차부터 순서대로 쌓고, 한 번 정해진 날짜는 절대 다시 굴리지 않게** 했습니다. 공개 예보는 그 배열을 **어디까지 보여줄지**로만 처리합니다.

**왜 이렇게 했나** — 요구가 *"지금은 내일 1일치만, 나중에 일주일로 늘려도 언제든"* 이었습니다. 처음 떠올린 슬라이딩 버퍼(`RemoveAt(0)` + 뒤에 1개 추가)로 짜면 두 가지가 걸립니다.

| 문제 | 증상 |
| :--- | :--- |
| 버퍼 크기가 곧 공개 범위 | 늘릴 때 **재컴파일**. 기획이 프로그래머를 기다려야 함 |
| **랜덤이 순차 소비형** | 범위를 1→7로 늘리는 순간 **이미 확정됐던 날씨가 바뀜.** 어제 본 예보가 오늘 달라짐 |

그래서 **"예보 일수는 배열 구조가 아니라 조회 범위"** 로 정하고, `EnsureDecidedThrough(N)`이 **빈 칸만 뒤에 채우게** 했습니다.

```
PublicForecastDays 를 1 → 7 로 바꾸면
  전 (3일차):  [Clear, Rain, Clear, Cloudy]           1~4일차 확정
  후:          [Clear, Rain, Clear, Cloudy, +6칸]      1~4일차 그대로 ★
```

**1일 → 7일로 늘릴 때 수정할 것: 데이터 에셋의 숫자 하나. C++ 0줄.** 화면 출력 줄 수도 자동으로 늘어납니다.

### 6. 추첨 후보를 걸러내는 조건을 아예 만들지 않았다

`BaseWeights`에 확률이 적힌 종류는 **매일 전부 후보**입니다. *"이 날은 눈 제외"* 같은 조건을 넣지 않았습니다.

**의도했던 이득 — 적은 값이 곧 실제 확률**

후보를 걸러내면 **빠진 종류의 비중이 남은 종류에 비례 배분**되어, 표에 적은 숫자와 실제 출현 빈도가 어긋납니다. 걸러내지 않으면 그 오차가 **0**이고 `0.3`은 정확히 30%입니다.

**그런데 짜고 보니 부수 효과가 더 컸습니다.**

```
RollWeather(N) = f(시드, N, 확률표)     ← 과거 확정값을 안 본다
```

*   **배열을 1일차부터 순서대로 채워야 할 이유가 사라졌습니다.**
*   **어디서 부르는지 신경 쓸 필요가 없어졌습니다.** 어느 일차든 단독으로 굴려 같은 결과가 나옵니다.

> 조건 하나를 넣으면 그 조건이 참조하는 상태가 생기고, 상태가 생기면 **순서 의무**가 생깁니다. **"넣지 않기"의 파급이 이렇게 클 수 있다**는 걸 처음 체감했습니다.

예외는 하나만 뒀습니다 — **데이터 테이블에 행이 없는 종류는 제외.** 표시 이름도 이펙트도 없는 날씨는 내보낼 수 없어서인데, **등장 조건이 아니라 데이터 오류 방어**라고 주석에 구분해 적었습니다.

`FixedClearBusinessDays`(기본 1)도 넣었습니다. 그 이하 일차는 무조건 맑음이라 **1일차 튜토리얼에서 비가 오지 않습니다.**

### 7. 확률을 데이터 에셋 한 곳에 몰고 총합 1.0으로 적게 했다

기존 방식도 가중치 추첨은 하고 있었는데, 값이 **정규화되지 않은 생 숫자**(`5.0` / `2.0` / `1.0`)로 **행마다 흩어져** 있었습니다.

| 문제 | 증상 |
| :--- | :--- |
| 생 숫자 | *"비를 30%로"* 를 손으로 역산해야 함. **종류를 하나 추가하면 나머지 전부의 실제 확률이 조용히 바뀜** |
| 흩어져 있음 | 총합을 보려면 행을 하나씩 열어야 함 |

**그래서 확률을 데이터 에셋의 `TMap` 하나가 단독으로 소유하게 하고, 데이터 테이블 행에서는 추첨용 필드를 아예 없앴습니다.**

> 확률이 두 곳에 있으면 *"어느 쪽이 이기는지"* 가 데이터 문제가 됩니다. 그리고 **총합 1.0으로 적게 하면 "종류를 추가할 때 다른 값을 줄여야 한다"가 강제로 드러납니다.** 생 숫자였을 때는 추가한 사람이 자기 값만 보고, 기존 세 개가 조용히 바뀌는 걸 모릅니다.

레이어는 **둘만** 뒀습니다.

```
① 기본 분포 (총합 1.0)  →  ② 런타임 배율 (×)  →  ③ 정규화  →  ④ 추첨
```

계절 시스템은 만들지 않고 `AddWeightModifier()` **통로만 열어뒀습니다.** 계절·이벤트·난이도가 전부 이 하나를 쓰면 됩니다. 기획이 안 정해진 걸 미리 만들지 않으려고요.

**등록할 때 `SourceId`를 필수로** 했습니다.

```cpp
// SourceId가 비어 있으면 등록하지 않는다.
// 해제할 수 없는 배율이 남으면 확률이 왜 그런지 추적할 수 없다.
```

> 거부하는 목적이 **입력 검증이 아니라 추적 가능성**입니다. 이름 없는 배율 하나가 끼면 *"왜 비가 이렇게 많이 오지"* 를 영원히 못 찾습니다.

### 8. 배율이 걸려도 이미 보여준 예보는 다시 굴리지 않게 했다

요구 두 개가 모순처럼 보였습니다 — *확률은 플레이 중에 바뀌어야 한다* / *공개한 예보는 틀리면 안 된다.*

`InvalidateUnpublishedTail()`이 **`오늘 + PublicForecastDays`까지는 남기고 그 뒤만** 버리게 짰습니다.

```
[1일][2일][3일][4일][5일][6일][7일][8일][9일][10일]
          └오늘┘
          ├──────── 공개 예보 ────────┤├─ 미공개 ─┤
             건드리지 않음                재굴림
```

**현재 설정(`PublicForecastDays = 1`)에서는 남길 개수가 배열 길이와 같아서 재굴림이 아예 일어나지 않습니다.** 조건 분기를 따로 넣지 않았는데 그렇게 됩니다.

**대가도 알고 택했습니다.** 예보를 길게 잡을수록 배율이 화면에 보이기까지 오래 걸립니다 — 7일 예보면 계절이 바뀌어도 여드레 뒤부터 티가 납니다. **정확도와 즉시성은 맞바꾸는 관계**이고 정확도를 택했습니다.

**재굴림할 때 시드는 그대로 뒀습니다.**

> 시드를 유지하면 그 날의 균등 난수값이 그대로라 **확률 분할만 달라집니다.** 결과적으로 **확률이 조금 바뀌면 예보도 조금만 바뀝니다.** 배율을 `×1.05`로 살짝 걸었는데 7일 예보가 통째로 뒤집히면 **아무도 그 배율을 못 씁니다.** 조정 가능한 시스템이려면 **입력의 작은 변화가 출력의 작은 변화**여야 합니다.

그리고 재굴림 함수가 **하루 전환 함수를 부르지 않게** 했습니다. 확률이 바뀐 것과 하루가 시작된 것은 다른 사건인데, 하루 전환을 부르면 변경 알림이 나가서 소비 측이 *"새 하루"* 로 오해하고 **내리던 비가 한 번 끊깁니다.**

### 9. 이펙트는 조건부로 교체하고, 알림은 항상 보냈다

`ApplyBusinessDay()` 안에서 이 둘을 **다르게** 처리했습니다.

```cpp
if (바뀌었으면) ApplyWeatherEffect(CurrentWeather);   // ← 조건부
OnWeatherChanged.Broadcast(New, Previous);            // ← 항상
```

| 대상 | 처리 | 이유 |
| :--- | :--- | :--- |
| 이펙트 | **같은 날씨면 재스폰 안 함** | 비가 이틀 연속이면 파티클이 끊기지 않아야 함 |
| 델리게이트 | **항상 방송** | 소비 측이 *"새 하루 + 날씨는 이것"* 을 한 번에 받아야 함 |

> 처음엔 둘 다 조건부로 짰다가 고쳤습니다. **소비 측 입장에서는 "날씨가 안 바뀐 새 하루"도 알아야 하는 정보**입니다. 유입량을 계산하는 쪽이 그 신호를 놓치면 어제 값을 그대로 씁니다.

그리고 **확정을 표시보다 먼저** 하게 했습니다. 출력할 때 굴리면 **볼 때마다 예보가 달라집니다.**

### 10. 이펙트 교체를 즉시 파괴가 아니라 2초 유예로 만들었다

```
기존 액터 StopEffect()  →  BP가 Niagara Deactivate  →  2초 뒤 Destroy
```

**즉시 파괴하면 공중에 떠 있던 빗방울이 한 프레임에 사라져서 눈에 띕니다.** 그래서 베이스 액터에 `StopDelaySeconds`를 두고 유예 후 파괴하게 했습니다.

**플레이어 추종은 C++이 아니라 BP 안에 뒀습니다.**

> 비·눈은 카메라를 따라다녀야 하는데, 나중에 폭염 같은 게 들어오면 **포스트프로세스 볼륨을 고정**하는 방식이 될 수도 있습니다. 추종을 C++에 넣으면 그때 C++을 고쳐야 합니다. **날씨마다 연출 방식이 달라도 C++이 안 바뀌게** BP에 맡겼습니다.

베이스를 `Abstract` + `Blueprintable`로 만든 것도 그래서입니다. C++은 **수명과 교체 타이밍만** 관리하고, 무엇을 어떻게 보여줄지는 BP가 정합니다.

### 11. UI를 안 만들었다

게시판 위젯을 **다른 팀원이 구현 중이고 아직 안 올라온 상태**라는 걸 확인했습니다. 그래서 **위젯을 만들지 않고** 화면 디버그 메시지로만 표시하게 했습니다.

```
[날씨] 오늘     3일차  비              ← 노랑
[날씨] 내일     4일차  맑음            ← 흰색
```

> **없는 것에 맞춰 만들면 두 번 만들게 됩니다.** 지금 위젯을 만들어두면 그쪽이 올라올 때 **버릴 코드**가 됩니다. 대신 게시판이 올라오면 넘길 **규격**만 문서에 적어뒀습니다.

이 디버그 출력도 **일수를 하드코딩하지 않게** 짰습니다. `PublicForecastDays`를 7로 바꾸면 출력이 자동으로 8줄이 됩니다. 나중에 위젯에 걸 계약과 똑같은 형태라, **위젯이 와도 C++이 안 바뀝니다.**

---

### 12. 디버그 코드를 파일 하나로 몰았다

`CSWeatherDebug.cpp` 하나에 콘솔 커맨드와 화면 출력을 전부 넣었습니다. 나중에 **파일 통째로 삭제 + 3곳 정리**로 제거됩니다.

그리고 문서에 **"디버그로 착각하기 쉬운데 지우면 안 되는 것"** 을 따로 적었습니다.

> 정리할 때 **화면 출력 코드와 함께 실제 로직을 지우는 사고**를 막기 위해서입니다. 디버그를 흩어 놓으면 나중에 어디까지가 임시인지 판단이 안 됩니다.

---

### 13. 소비 측이 데이터 테이블을 참조하지 못하게 했다

날씨는 **"오늘은 비다"까지만** 말합니다. *"비니까 우산이 3배 팔린다"* 는 각 담당자가 자기 데이터로 정합니다.

```cpp
const ECSWeatherType Weather = WeatherSubsystem->GetCurrentWeather();
const float Multiplier = MyTrafficDataAsset->GetWeatherMultiplier(Weather);
//                       ^^^^^^^^^^^^^^^^^ 배율은 각 담당자 소유
```

표시용 값이 필요하면 `GetForecastEntries()`가 **이름·설명·아이콘까지 채워서** 줍니다.

> 이 규칙을 지키면 **밸런스를 수정할 때 날씨 파일에 충돌이 나지 않습니다.** 여러 파트가 각자 배율을 넣으려고 `DT_Weather`에 열을 추가하기 시작하면, 그 파일이 곧 충돌 지점이 됩니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **주입 대신 가져가게 짜면 충돌 지점이 안 생긴다** | `BeginPlay`를 건드리지 않으니 순서 문제도 함께 사라졌다 |
| **구현 전에 흐름을 코드로 따라간다** | 델리게이트 하나로 끝날 일을 위젯에 심을 뻔했다 |
| **구독 + 초기 적용은 처음부터 같이 넣는다** | 1일차에는 방송이 안 온다. 8월에 버그로 배운 걸 이번엔 미리 |
| **확장성은 "무엇이 무엇의 함수인지" 정리하는 것** | 날씨를 일차의 함수로 못 박으니 예보 일수는 조회 인자가 됐다 |
| **조건을 안 만들면 순서 의무도 안 생긴다** | 후보 필터를 두지 않은 결정이 순수 함수를 만들어줬다 |
| **총합 1.0으로 적게 하면 실수가 강제로 드러난다** | 생 가중치는 종류를 추가할 때 기존 확률이 조용히 바뀐다 |
| **거부의 목적이 검증이 아니라 추적 가능성일 수 있다** | 이름 없는 배율 하나가 끼면 원인을 못 찾는다 |
| **입력의 작은 변화가 출력의 작은 변화여야 쓸 수 있다** | 시드를 유지해 `×1.05`가 예보를 통째로 뒤집지 않게 |
| **이펙트는 조건부, 알림은 항상** | "날씨가 안 바뀐 새 하루"도 소비 측에는 정보다 |
| **연출 방식이 달라질 여지는 BP에 남긴다** | 추종을 C++에 넣으면 폭염이 들어올 때 C++을 고쳐야 한다 |
| **없는 것에 맞춰 만들면 두 번 만든다** | 게시판이 안 올라와서 UI를 안 만들었다 |
| **디버그는 한곳에 몰고, 지우면 안 되는 것을 적어둔다** | 흩어 놓으면 어디까지 임시인지 판단이 안 된다 |
| **값을 정하지 말고 값을 아는 쪽에 넘긴다** | 엔진 기본값에 위임하니 종족별 체구가 분기 없이 반영됐다 |
