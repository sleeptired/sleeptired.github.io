### 2. 계단 — 손님 발 높이를 베끼지 않게 했다

어제까지 슬라임 높이가 **손님 발 높이를 그대로 복사**하는 한 줄이었습니다.

```cpp
NewLocation.Z = Foot.Z;   // 손님이 다른 단에 있으면 그만큼 뜨거나 파묻힘
```

입구 계단이 **한 단 37.4 cm, 7단**이라 손님과 슬라임이 다른 단에 있으면 **최대 70 cm까지 어긋납니다.**

**그래서 슬라임이 자기 발밑을 직접 보게 했습니다.**

| 값 | 설정 | 근거 |
| :--- | ---: | :--- |
| 위로 탐색 | **45 cm** | **계단 한 단(37.4)보다 커야** 오르막에서 윗단을 잡는다 |
| 아래로 탐색 | 120 cm | 내려갈 때 아랫단까지 닿아야 함 |
| 선행 탐색 시간 | 0.15초 | 진행 방향 앞을 미리 보기 |

**두 지점을 같이 트레이스하는 이유**

> 현재 위치만 보면 **계단 챌면에 정면으로 부딪힌 뒤에야** 높이가 올라갑니다. 그러면 한 단씩 **뚝뚝 튑니다.**
>
> **진행 방향 앞쪽(0.15초 × 현재 속도)** 을 같이 보면 **오르막을 먼저 반영**해서 발판 위로 부드럽게 올라섭니다. 다만 `BasketRadius` 이내로 제한해서, 너무 멀리 보다가 엉뚱한 바닥을 잡지 않게 했습니다.

**벽과 급경사면은 바닥으로 인정하지 않습니다**(`ImpactNormal.Z < 0.7`). 벽면에 트레이스가 맞아서 높이가 치솟는 걸 막습니다.

그리고 **표시 높이는 보간, 순간이동 때는 즉시**로 나눴습니다.

> 계단을 오르내릴 때는 보간이 자연스럽지만, **순간이동 직후에 보간하면 새 자리에서 땅속에서 솟아오릅니다.** 그래서 시작·순간이동에는 별도 함수로 **보간 없이 바로 맞춥니다.**

### 3. 충돌 검사에 "표시 높이"가 아니라 "바닥 높이"를 쓴 이유

계단 대응을 넣고 나니 **새 문제**가 생길 자리가 보였습니다.

```cpp
FVector MoveFrom = Current;
if (bFloorZValid) { MoveFrom.Z = FloorZ; }   // 보간 중인 표시 높이가 아니라 계산된 바닥 높이
```

> 계단을 오르는 동안 **표시 높이는 보간 중이라 아직 낮게 남아 있습니다.** 그 높이로 스윕을 쏘면 **계단 챌면에 걸려서 앞으로 못 갑니다.**
>
> 즉 **"보이는 위치"와 "물리적으로 판단할 위치"가 달라야** 합니다. 보간은 눈에 보이는 부드러움을 위한 것이고, 검사는 실제 도달 가능한 높이로 해야 합니다.

같은 이유로 스윕 구체를 띄우는 높이도 **계단 한 단보다 높게** 잡았습니다. 안 그러면 A(바닥 추적)를 넣은 순간 **계단 앞에서 막힙니다.**

> 어제 설계 문서에 *"A만 넣으면 C 때문에 막히고, B 없이 넣으면 뚝뚝 튄다"* 고 적어뒀는데, **구현하면서 그 말이 그대로 맞았습니다.** 세 개를 따로 넣었으면 각각에서 한 번씩 막혔을 겁니다.

### 4. 반경을 메시에서 자동 산출하고 74로 묶었다

`BasketRadius`를 손으로 넣던 값에서 **메시 바운드에서 계산**하도록 바꿨습니다.

```
BasketRadius = min(메시 로컬 바운드 × 컴포넌트 스케일, MaxBasketRadius = 74)
```

**왜 상한이 74인가**

> NavMesh `AgentRadius`가 **75**입니다. 반경이 그보다 작아야 **중심을 NavMesh 위에 두는 것만으로 진열대 관통이 막힙니다.**
>
> 자동 산출로 바꾸면 **아티스트가 메시를 키웠을 때 조용히 75를 넘길 수 있습니다.** 그러면 NavMesh 제한이 무의미해지고 스윕만 남는데, 스윕은 NavMesh에 반영 안 된 소품을 막는 **보강 장치**라 주력이 되면 안 됩니다.

**자동화하면서 상한을 같이 넣은 게 핵심**이었습니다. 자동화는 값을 편하게 만들지만 **범위를 벗어날 자유도 같이 줍니다.**

메시가 없으면 폴백 값을 쓰고 **경고를 남깁니다.** 그리고 `MaxBasketRadius`가 `AgentRadius` 전제라는 걸 **확인 사항에 적어뒀습니다** — NavMesh 설정이 바뀌면 같이 조정해야 합니다.

### 5. Park 자리를 못 찾으면 억지로 옮기지 않게 했다

대기 자리 후보 5개가 **전부 실패했을 때** 손님 발 위치로 보내던 것을, **현재 위치 유지**로 바꿨습니다.

> 후보가 전부 실패한다는 건 **주변에 설 자리가 없다**는 뜻입니다. 그런데 손님 발 위치로 보내면 **손님과 겹쳐 서고**, 그 자리도 좁으면 다음 프레임에 또 실패합니다.
>
> **"둘 자리가 없으면 지금 자리가 최선"** 입니다. 지금 위치는 적어도 **직전까지 유효했던 자리**니까요.

손님이 **NavMesh 밖**(가게 밖 인도 끝 등)에 있을 때는 **NavMesh 검사 두 개를 건너뛰고 스윕만** 합니다.

> 손님이 NavMesh 밖인데 후보를 NavMesh로 검사하면 **전부 실패**합니다. 손님이 갈 수 있는 곳이면 슬라임도 갈 수 있다고 보는 게 맞습니다.

### 6. 손님이 나갈 때 장바구니가 남는 경로 4개를 막았다

기존에는 **결제 성공** 경로에서만 장바구니를 숨겼습니다. 나머지 퇴장 경로에서는 **빈 슬라임이 계속 따라다녔습니다.**

| 경로 | 넣은 위치 | 결과 |
| :--- | :--- | :--- |
| 결제 성공 | (기존) | 숨김 → 봉투로 교체 |
| **계산 포기** | 포기 처리 함수 **1곳** | 숨김 |
| **빈손 퇴장 / 영업종료 강제 퇴장** | 퇴장 태스크 **1곳** | 숨김 |
| **제압 소멸** | 제압 소멸 태스크 | 숨김 |
| 절도 후 도주 | 위에서 **예외** | **계속 표시** |

**한 곳씩만 넣어도 되는 이유를 먼저 확인했습니다.**

> 계산 포기는 `AbandonCheckout()`이 **모든 포기 경로(줄 정원 초과 · 대기열 진입 실패 · 인내심 만료)의 단일 관문**이라 한 곳이면 충분합니다.
>
> 퇴장도 `LeaveAndDespawn`이 **모든 퇴장의 종착지**라, 빈손 퇴장과 영업종료 강제 퇴장이 **함께 해결됩니다.**
>
> 며칠 전 다른 시스템에서 *"모든 경로가 지나는 지점에 집계를 둔다"* 를 배웠는데, 이번엔 **그 지점을 찾는 게 작업의 대부분**이었습니다. 찾고 나니 넣는 건 한 줄씩이었습니다.

**제압만 별도 처리가 필요했습니다.**

> 제압된 손님은 **그 자리에서 소멸**하므로 `LeaveAndDespawn`을 거치지 않습니다. 그래서 제압 소멸 태스크에 따로 넣었는데, **`EnterState`에 두어야** 소멸 대기 3초 동안 **빈 슬라임이 서 있지 않습니다.**

**상품 낙하에 영향이 없는 것도 확인했습니다.** 제압 처리 순서상 상품을 바닥에 떨구고 표시를 비운 뒤에 상태 전이가 일어나므로, **숨기는 대상은 이미 빈 바구니**입니다.

### 7. 절도범만 예외로 두고, 호출 위치를 앞으로 옮겼다

```cpp
// 훔친 물건을 든 채 도주하는 연출은 유지해야 하므로 절도 실행자만 예외로 둔다.
if (Subsystem == nullptr || !Subsystem->IsEscapingShoplifter(Data.Actor))
{
    Data.Actor->SetBasketDisplayVisible(false);
}
```

**새 조건을 만들지 않고 기존 판정 함수를 재사용**했습니다.

> 그러면 **"도주 중인 절도범"의 정의가 한 곳에서 관리**되고, **제압된 빌런과 절도를 실행하지 않은 빌런이 자동으로 걸러집니다.** 조건을 새로 쓰면 그 세 경우를 다시 나열해야 하고, 원본이 바뀔 때 같이 안 바뀝니다.

**그리고 호출 위치가 중요했습니다.**

> 이 줄을 **`MoveToLocation` 앞**에 둬야 합니다. 뒤에 두면 이미 목적지에 있는 경우(`AlreadyAtGoal`) **즉시 파괴되는 분기로 빠져서 이 줄이 실행되지 않습니다.**
>
> 조기 반환이 있는 함수에 코드를 끼워 넣을 때는 **"모든 분기가 이 줄을 지나는가"** 를 봐야 한다는 걸 다시 확인했습니다.

**중복 호출 안전성도 확인했습니다.** 표시 전환 함수가 카운터나 토글 없이 숨김과 틱만 조작해서 **몇 번 불려도 결과가 같습니다.** 결제를 마친 손님이 퇴장 태스크에서 또 불려도 무해합니다.
