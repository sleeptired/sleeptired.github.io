# **[UE5] 조명·Lumen GI·태양 그림자 최적화와 A/B 검증**

오늘은 이세계 편의점의 `MiddleTestMap`에서 로컬 라이트, Lumen GI 품질, 시간대별 태양·달 그림자 비용을 줄였습니다. 설정을 바꾸는 것에서 끝내지 않고, 같은 위치와 조건에서 GPU 시간과 화면을 비교해 실제 반영 효과를 확인했습니다.

가장 큰 효과는 과도하게 넓었던 로컬 라이트 범위를 정리한 데서 나왔습니다. 이후 GI 기본 품질을 High로 조정하고, 방향광의 잦은 회전으로 반복되던 그림자 캐시 무효화를 줄였습니다.

## **1. 최적화 측정에서 FPS보다 GPU 시간을 먼저 본 이유**

FPS는 GPU뿐 아니라 게임 스레드 등 프레임을 결정하는 병목의 영향을 받습니다. GPU 작업이 줄어도 CPU가 더 오래 걸리면 FPS는 같은 비율로 오르지 않습니다.

이번 PIE 측정에서는 최적화 후 게임 스레드가 약 12~15ms로 GPU보다 긴 장면이 많았습니다. 따라서 **GPU 최적화의 효과는 Average GPU frametime으로 판단하고, FPS는 실제 실행 결과로 함께 기록**했습니다.

| 측정 조건 | 내용 |
| :--- | :--- |
| 엔진 / PC | UE 5.8 / Ryzen 5 5600X · RTX 3070 |
| 실행 | PIE 새 창, 뷰포트 1920×1062 |
| 렌더 배율 | 88%, 약 1690×935 |
| 게임 상태 | 1일차 영업 전, 손님 없음 |
| 평균 측정 | FPS Chart 20초 × 2회, 두 번째 회차는 순서를 뒤집어 진행 |
| 보조 확인 | `stat gpu`, 화질 스크린샷, 밝기 비교, 설정값 조회 |

로컬 라이트 전후 비교는 서로 다른 PIE 세션입니다. GI와 태양 회전은 같은 세션의 기준값도 다시 측정해 세션 차이를 확인했습니다. 시각·장면 정의가 단계마다 다르므로 **각 단계의 평균 개선율을 더해 전체 개선율로 사용하지 않았습니다.**

## **2. 로컬 라이트**

### **① 문제: 건물 조명 반경이 164m**

기존 실내 라이트 14개의 반경이 모두 약 164m여서 멀리 떨어진 다른 건물의 화면까지 영향 범위에 들어갔습니다. 벽에 막혀 실제로 밝아지지 않는 픽셀도 조명·그림자 계산 대상이 될 수 있었습니다.

**밝기와 영향 반경은 다른 설정**입니다. 실내가 어둡다고 반경을 크게 늘리면 필요 없는 공간까지 계산할 수 있으므로, 화면을 유지하는 데 필요한 범위를 먼저 찾았습니다.

| 대상 | 최종 반경 | 그림자 |
| :--- | :--- | :--- |
| 매장 주 조명 4개 | 5,500cm | 유지 |
| 창고 조명 3개 | 3,000cm | 유지 |
| 매장 구석 보조등 | 1,500cm | 해제 |
| 다른 건물 조명 6개 | 3,500cm | 유지 |

매장 조명을 4,000cm까지 줄이면 더 가벼워지지만 밤 문 앞 보도가 약 28% 어두워졌습니다. 5,500cm는 최종 반영 측정에서 문 앞 보도 약 9%, 먼 보도 약 14% 감소로 화면 변화를 줄이는 절충안이었습니다.

매장 주 조명 그림자 해제는 벽·간판으로 빛이 새는 변화가 있어 채택하지 않았습니다.

<br>

### **② 결과: 11개 장면 평균 GPU 약 32% 감소**

| 장면 | GPU 전 → 후 | FPS 전 → 후 |
| :--- | :--- | :--- |
| 낮 매장 안 | 18.51 → 11.96ms | 46.6 → 66.4 |
| 낮 매장 뒤 숲길 | 18.08 → 11.54ms | 47.1 → 67.9 |
| 낮 창고 안 | 19.09 → 14.68ms | 44.8 → 55.8 |
| 밤 매장 안 | 19.70 → 12.71ms | 44.2 → 63.7 |
| 밤 매장 앞 | 21.43 → 14.87ms | 40.5 → 55.4 |
| **11개 장면 GPU 평균** | **17.97 → 12.26ms** | 장면별 결과로 비교 |

평균 GPU 시간은 5.71ms, 약 32% 줄었습니다. 감소분의 대부분은 `stat gpu`의 `Lights`였습니다. 낮 매장 안은 9.09 → 4.16ms, 밤 매장 앞은 10.49 → 5.35ms로 내려갔습니다.

밤에 발생하던 `One Pass Projection max lights overflow` 경고도 측정 장면에서 사라졌습니다. 경고 한도를 늘리는 대신 실제 겹치는 라이트 범위를 정리한 결과입니다.

<br>

### **③ Movable 변경은 가로등 페이드 동작도 복구했다**

가로등은 시간대에 따라 밝기를 바꾸는 코드가 있었지만 BP의 라이트 Mobility가 Static이라 의도한 밝기·색·페이드 변경이 막혀 있었습니다.

Movable로 변경한 뒤 18:00에 밝기 0, 18:07에 7,000, 19:00에 15,000으로 점진적으로 켜지는 것을 확인했습니다. 최대 밝기 15,000과 색상 `FFEB93`은 유지했습니다.

이번 설정에서 밤 비용도 줄었지만, **Movable이 모든 상황에서 더 저렴하다는 뜻은 아닙니다.** 런타임에 변경하는 기능과 현재 렌더링 구성에 맞춰 선택한 결과입니다.

## **3. Lumen GI**

GI(Global Illumination)는 주변 표면에서 반사되어 들어오는 간접광을 처리합니다. Lumen을 끄는 대신 GI 품질 묶음을 Epic에서 High로 바꿨습니다.

```ini
; Config/DefaultGameUserSettings.ini
[ScalabilityGroups]
sg.GlobalIlluminationQuality=2
```

이번 변경은 GI만 대상으로 하며 다른 품질 단계와 해상도 배율은 그대로입니다. High에서는 스크린 프로브 간격, 조명 갱신량, AO 등 여러 관련 설정이 함께 바뀝니다.

### **① 같은 세션에서 Epic과 High 비교**

| 장면 | Epic GPU | High GPU | 감소 |
| :--- | :--- | :--- | :--- |
| 낮 매장 안 | 11.63ms | 9.52ms | 2.11ms |
| 낮 숲길 | 11.17ms | 9.11ms | 2.06ms |
| 광장 큰 나무 방향 16:30 | 12.90ms | 11.08ms | 1.82ms |
| 밤 매장 앞 | 14.30ms | 12.74ms | 1.56ms |
| **4개 장면 평균** | **12.50ms** | **10.61ms** | **약 1.89ms, 15%** |

별도 적용 전 세션과 비교한 평균은 12.33 → 10.61ms로 약 14% 감소입니다. 위 표는 세션 차이를 줄인 비교값입니다.

나무 수관·어두운 벽·보도·매장 구석의 밝기 차이는 비교 문서에서 0~255 기준 0.5 미만으로 기록됐습니다. 다만 정지 화면 수치가 같아도 움직일 때 간접광의 갱신이나 노이즈 차이는 있을 수 있어 레벨 디자인 담당의 최종 화질 판정은 남아 있습니다.

<br>

### **② Compute 시간 감소를 GPU 프레임 감소에 그대로 더할 수 없다**

GI High에서는 `LumenScreenProbeGather`와 `LumenSceneLighting`이 줄어 Compute 큐 비용이 크게 감소했습니다. 하지만 `r.Lumen.AsyncCompute=1` 상태에서는 일부 작업이 Graphics 큐와 겹쳐 실행됩니다.

따라서 **Compute 큐에서 줄어든 시간 전체가 프레임 GPU 시간 감소로 이어지지는 않습니다.** 실제 프레임에서 얻은 이득은 이번 측정의 약 1.6~2.1ms입니다.

<br>

### **③ PIE와 Standalone, 패키징은 설정 경로가 다르다**

PIE에서는 에디터가 가진 품질값을 사용하고 시작 처리에서 다시 적용하기도 합니다. 기본 파일을 만들었다고 PIE 값까지 자동으로 2가 되는 것은 아니었습니다.

| 실행 방식 | 이번에 확인한 내용 |
| :--- | :--- |
| PIE | 시작 후 `sg.GlobalIlluminationQuality 2`를 입력해 측정 |
| Standalone | GI 2, 프로브 간격 32로 시작하는 것 확인 |
| 패키징 빌드 | 실제 실행 확인 남음, 기존 사용자 설정의 GI 3 오버라이드 확인 필요 |

기본 설정과 저장된 사용자 설정은 별개입니다. 기존 PC에 GI 3이 저장돼 있으면 새 기본값 2보다 우선할 수 있습니다. 패키징 검증에서는 기존 사용자 설정을 백업하고, 기본값 적용과 기존 설정 유지 상황을 구분해서 확인해야 합니다.

## **4. 태양 회전**

### **① 기존에는 0.1초마다 방향광 회전**

시간대 컨트롤러는 게임 시각 알림마다 태양·달을 조금씩 돌렸습니다. 방향광 방향이 바뀌면 VSM 그림자 캐시가 무효화되어, 작고 자주 일어나는 회전이 반복 비용을 만들었습니다.

이를 마지막 적용 각도와 비교해 **0.25° 이상 변했을 때만 회전**하도록 바꿨습니다. 시계나 게임 시간의 진행 속도를 바꾼 것은 아닙니다.

```cpp
// 처음 적용하거나 설정한 각도 이상 달라졌을 때 회전
const bool bShouldRotate = !bHasAppliedSunRotation ||
    FMath::Abs(FMath::FindDeltaAngleDegrees(
        LastAppliedSunPitch, SunPitch)) >= SunRotationStepDegrees;

if (bShouldRotate)
{
    LastAppliedSunPitch = SunPitch;
    bHasAppliedSunRotation = true;
}
```

위 코드는 회전 여부 판정 부분입니다. 태양·달 회전 호출이 이 결과를 사용합니다.

밤에는 지평선 아래 해도 계속 존재해 해·달 두 방향광의 비용이 함께 발생했습니다. 해 높이가 −10°보다 낮으면 태양 액터를 숨기도록 했고, 숨김 전환 시 하늘이 갑자기 바뀌지 않는지는 실제 플레이로 확인했습니다.

<br>

### **② 0.5°에서 0.25°로 조정한 이유**

처음 0.5°는 그림자가 뚝뚝 움직이는 느낌이 있어 0.25°로 줄였습니다. 같은 세션에서 두 값을 비교하니 GPU 차이는 −0.15~+0.10ms로 두 회차 흔들림 안이었습니다.

각도 한 번의 변화량은 절반으로 줄이면서 측정 가능한 추가 비용이 나타나지 않아 0.25°를 채택했습니다. 다만 0.25°에서도 움직임이 충분히 자연스러운지는 후속 플레이 확인이 남아 있습니다.

| 장면 | 반영 전 흉내(BF) | 최종 0.25° | 감소 |
| :--- | :--- | :--- | :--- |
| 숲길 16:30 | 10.70ms | 9.50ms | 1.20ms |
| 매장 안 16:30 | 10.58ms | 9.93ms | 0.65ms |
| 밤 매장 앞 | 16.06ms | 12.73ms | 3.33ms |

`Shadow Depths`는 장면별 약 3.0~3.9ms에서 1.2~1.3ms로 감소했습니다. 밤 3.33ms는 **회전 간격 조정과 태양 숨김을 함께 적용한 결과**이며, 태양 숨김만의 단독 기여는 별도로 측정하지 않았습니다.
