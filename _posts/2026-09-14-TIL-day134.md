## 지나가는 행인 시스템 구현 — 손님 코드를 재사용하지 않았다

> 매장 주변 다른 길을 **그냥 지나가는 NPC**를 만들었습니다. 쇼핑을 전혀 하지 않고 걸어서 지나가기만 합니다. 손님 시스템에 이미 스폰·외형·이동이 다 있어서 재사용할까 했는데, **따져보니 별도 클래스로 가는 게 맞았습니다.**

---

### 1. 만든 것

| 구분 | 이름 | 역할 |
| :--- | :--- | :--- |
| C++ | `ACSPedestrianSpawner` | 레벨 배치 액터. **스폰 판단·경로 계산·매 프레임 이동·퇴장·풀링을 전부** 담당 |
| C++ | `ACSPedestrianCharacter` | **컨트롤러 없는 경량 캐릭터.** 활성화/비활성화와 외형 적용만 |
| BP | 캐릭터·스포너 BP | 캡슐·메시 값은 손님과 동일, 종족 DA 6종 연결 |
| 맵 | 스포너 1개 배치 | 남쪽 길 양 끝을 `EndpointA` / `EndpointB`로 |

**신규 파일 4개. 손님 시스템 코드는 한 줄도 안 고쳤습니다.**

```
[BeginPlay]  전용 난수 스트림 초기화 → 설정 검증 → 풀 미리 생성 → 스폰 타이머
[7초마다]    조건 검사 → 종족 추첨 → 방향 50% → 출발·퇴장 점 → 경로 → 풀에서 꺼내 활성화
[Tick]       경로 점 통과 판정 → 끼임 판정 → 다음 점 방향으로 이동 입력
[마감 정산]  전원 반납
```

### 2. 손님 캐릭터를 재사용하지 않은 이유

`ACSCustomerCharacter`를 그대로 쓰면 **행인 하나가 이만큼을 끌고 옵니다.**

| 딸려오는 것 | 행인에게 필요? |
| :--- | :---: |
| 상태 컴포넌트 · 구매 판단 컴포넌트 | ✗ |
| **BeginPlay에서 장바구니 액터를 추가 스폰** (행인 1명 = 액터 2개) | ✗ |
| DropOrigin 2개, 쇼핑백 앵커, 속마음 위젯 | ✗ |
| **AIController + StateTree 컴포넌트** | ✗ (행동이 "걷기" 하나뿐) |
| 0.075초 간격 Tick의 Idle/Walk 전환 판정 | ✗ (항상 걷기) |

**그런데 결정적인 건 성능이 아니라 이것이었습니다.**

> 손님이 퇴장할 때 **`NotifyCustomerDespawned`를 방송**합니다. 행인이 이걸 타면 **빈손 퇴장률 통계가 오염됩니다.** 행인은 원래 아무것도 안 사는데, 통계에는 *"아무것도 안 사고 나간 손님"* 으로 잡힙니다.
>
> 게다가 마감 종에서 `DespawnAllCustomers`가 월드의 손님을 전부 정리하는데, **행인까지 같이 쓸려갑니다.**

**"무겁다"는 고칠 수 있지만 "통계가 틀린다"는 고치기 어렵습니다.** 예외 분기를 넣으면 손님 코드 곳곳에 *"행인이면 건너뛰기"* 가 생기고, 나중에 경로가 하나 추가될 때마다 또 빠뜨립니다. **별도 클래스면 애초에 그 경로를 안 지납니다.**

### 3. AIController 없이 스포너가 직접 걷게 했다

행인 캐릭터에는 **컨트롤러가 없습니다.** 스포너가 `Tick`에서 직접 이동 입력을 줍니다.

```cpp
// 스포너 Tick — 활성 행인이 있을 때만 돈다
행인마다:
  지나친 경로 점 넘기기 → 마지막 점을 지났으면 반납
  → 끼임 판정
  → 다음 경로 점 방향으로 AddMovementInput
```

**왜 이렇게 했나**

*   **행동이 "걷기" 하나**입니다. StateTree로 표현할 상태가 없습니다.
*   컨트롤러 + PathFollowing 비용이 **인원수만큼 선형으로** 늘어납니다. *"많이 생성되는 것을 전제로"* 가 요구사항이었습니다.
*   경로는 스폰할 때 **한 번만** 계산하면 되고, 그 뒤로는 **점을 따라가기만** 하면 됩니다.

**대신 스포너 `Tick`은 활성 행인이 0명이면 끕니다.** 아무도 안 걸을 때 빈 Tick이 도는 걸 막으려고요.

> 손님은 *"진열대로 가서 → 구경하고 → 줄 서고 → 나간다"* 라 상태 기계가 필요했지만, 행인은 **직선 목록을 순회하는 것**이 전부입니다. **필요한 만큼만 만드는 게 맞다**고 판단했습니다.

### 4. Visual DA가 아니라 Archetype DA를 참조했다

외형을 손님과 공유하려고 처음엔 `Visual` 데이터 에셋만 참조하려 했는데, **확인해보니 안 됐습니다.**

| 데이터 | 어디에 있나 |
| :--- | :--- |
| 메시 · ABP · 폴백 애니메이션 | **Visual DA** |
| **`CharacterScale`** (종족 크기) | **Archetype DA** |
| **`SpawnWeightBase`** (등장 비율) | **Archetype DA** |

> Visual DA만 쓰면 **오크가 인간 크기로 걸어다닙니다.** 크기가 외형이 아니라 종족 설정 쪽에 있었습니다.

그래서 **Archetype DA 배열을 참조하되 세 필드만 읽습니다.** 구매 성향·빌런 확률 같은 나머지는 무시합니다.

> 나중에 **거리 행인의 종족 비율을 손님과 다르게** 하고 싶어지면, 그때 가중치만 덮어쓰는 작은 구조체를 추가하면 됩니다. **지금은 필요 없으니 안 만들었습니다.**

### 5. 난수 스트림을 손님과 분리했다

```cpp
// 행인 전용 FRandomStream. cs.Seed를 쓰지 않는다.
```

**왜 같이 안 쓰나**

> 손님 스포너의 마스터 스트림은 **종족/시드/빌런/쓰레기를 고정된 횟수로 뽑도록** 공들여 맞춰져 있습니다. `cs.Seed`를 고정하면 같은 결과가 재현되는 구조입니다.
>
> 행인이 이 스트림을 같이 쓰면 **행인이 몇 명 생겼느냐에 따라 손님 결과가 통째로 밀립니다.** 재현성이 깨집니다.

행인은 **연출용이라 재현이 필요 없어서** `cs.Seed`를 쓰지 않고 독립 스트림으로 뒀습니다. **재현이 필요한 쪽과 아닌 쪽을 섞지 않는 게** 핵심입니다.

### 6. 풀링 — 그리고 속도를 CDO 기준으로 "대입"한 이유

퇴장하면 `Destroy` 대신 **숨기고 풀에 반납**합니다. 재사용할 때 크기·위치·외형·속도를 다시 적용합니다.

```cpp
// 활성화할 때마다: CDO의 MaxWalkSpeed × 배율을 "대입"
행인->MaxWalkSpeed = CDO기본속도(300) * 랜덤(0.85, 1.15);
```

**현재 속도에 곱하지 않고 CDO 값에 곱해 대입하는 이유**

> 현재값에 곱하면 **풀에서 재사용할 때마다 배율이 누적**됩니다. 세 번 재사용하면 $300 \times 1.1^3$ 이 되어 점점 빨라집니다.
>
> **기준값을 항상 CDO에서 가져오면 몇 번을 재사용해도 같은 범위**가 나옵니다. 풀링은 **"상태가 남는다"** 는 게 전제라, 재사용 시 초기화하는 값의 **기준을 어디서 가져오는지**가 중요했습니다.

`PrewarmPoolSize`로 시작할 때 미리 만들어 두는 것도 넣었습니다. **첫 스폰 순간에 액터 생성 + 메시 교체 + 애니메이션 초기화가 한꺼번에 일어나면 끊김이 보여서**, 로딩 구간으로 옮겼습니다.

### 7. 위치나 경로가 실패해도 건너뛰지 않게 했다

| 실패 | 처리 |
| :--- | :--- |
| NavMesh 투영 실패 | 경고 로그 후 **영역 중심** 사용 |
| 경로 탐색 실패 | 출발 → 퇴장 **직선 경로** |
| 부분 경로만 나옴 | 끝에 퇴장 점을 **추가** |

**전부 "경고만 남기고 스폰은 유지"** 입니다.

> 행인은 **거리를 채우는 연출**이라, 실패할 때마다 건너뛰면 *"어떤 날은 거리가 텅 비는"* 상태가 됩니다. 위치가 조금 어긋나는 것보다 **아무도 없는 게 더 눈에 띕니다.**
>
> 손님 스포너도 같은 정책이라 **맞췄습니다.** 두 스포너가 같은 상황에서 다르게 행동하면 나중에 헷갈립니다.

**대신 끼임 판정을 넣었습니다.** 4초 동안 20 cm 미만으로 움직이면 경고 로그 후 반납합니다.

> 직선 경로가 벽에 막힌 경우가 **이 판정으로 정리됩니다.** 실패를 관대하게 받아준 만큼 **그 결과를 치울 장치**가 필요했습니다.

### 8. 통과 판정을 "거리"가 아니라 "진행 방향 기준 남은 거리"로

```
다음 점까지 남은 거리를 진행 방향으로 투영해서 40 cm 이하면 통과
```

**단순 거리로 하지 않은 이유**

> 점을 **지나쳐 버린 경우**(남은 거리가 음수)도 통과로 처리해야 합니다. 거리로만 보면 지나친 뒤 거리가 다시 멀어져서, **되돌아가서 점을 찍고 가는** 이상한 움직임이 나옵니다.

그리고 이 값이 코너 모양을 결정합니다.

| 값 | 결과 |
| :--- | :--- |
| 너무 작음 | 코너에서 점을 정확히 찍고 도는 느낌, 살짝 빗나가면 멈칫 |
| 너무 큼 | 코너를 크게 깎아 **벽 쪽으로 붙음** |

### 9. 큰 종족만 코너를 바깥으로 밀었다

```cpp
// 몸 반경이 NavAgentRadius(75)보다 큰 종족만 코너 점을 바깥으로 옮긴다
```

**왜 일부 종족만인가**

> **NavMesh는 `AgentRadius` 하나(75)로 깎여** 있습니다. 그래서 경로 꼭짓점도 **벽에서 75 cm만** 떨어져 있습니다.
>
> 몸 반경이 75보다 큰 종족은 그 경로를 그대로 따라가면 **몸이 벽에 파묻힌 채 코너를 돕니다.** 부족한 만큼(`몸 반경 − 75`)을 바깥으로 밀어야 합니다.
>
> 반대로 75보다 작은 종족은 **이미 여유가 있어서** 밀 필요가 없습니다. `CharacterScale`이 1 이하인 종족에는 이 보정이 동작하지 않는데, **의도한 동작**이라 주석에 적어뒀습니다.

다만 **`AgentRadius` 값을 ini에서 자동으로 읽지 않습니다.** ini를 바꾸면 스포너 설정도 같이 맞춰야 한다는 걸 문서에 경고로 남겼습니다.

> 자동으로 읽게 만들 수도 있었는데, **엔진 설정을 런타임에 파싱하는 코드를 추가하는 비용**이 *"바꿀 때 같이 맞춘다"* 보다 크다고 봤습니다. 대신 **경고를 남긴다**는 조건을 붙였습니다.

### 10. 하루 흐름과의 연결

| 시점 | 동작 |
| :--- | :--- |
| 마감 정산 요청 | **활성 행인 전원 반납** (옵션) |
| 정산 UI가 떠 있는 동안 | **스폰 중지** (옵션과 무관하게 항상) |

두 번째가 필요했던 이유가 있습니다.

> **정산 UI는 게임을 멈추지 않습니다.** 그래서 스폰 타이머가 계속 돌고, UI를 보고 있는 동안 **행인이 계속 생성됩니다.** 확인하고 나면 거리에 행인이 잔뜩 있습니다.

*"영업 중에만 행인을 만들지"* 는 **옵션으로 뒀고 기본은 꺼짐**입니다. 손님 스포너는 이 조건을 **항상** 적용하는데, 행인은 **준비 단계나 마감 활동 중에도 거리에 사람이 있는 게 자연스러울 수 있어서** 선택지로 남겼습니다.

설정을 전부 **레벨 배치 액터의 디테일 패널**에 둔 것도 팀 관례를 따른 것입니다. 서브시스템은 디테일 패널이 없어 경로를 코드에 박아야 하는데, **레벨마다 길이 다르므로** 액터 쪽이 맞습니다.

### 11. 추후 작업 설계 — "측정"을 0단계로 뒀다

남은 작업 두 개를 설계했습니다.

| 작업 | 지금 문제 | 방향 |
| :--- | :--- | :--- |
| **① 거리·판정 기반 최적화** | 플레이어가 실내에 있거나 멀리 있어도 **같은 수로 생성**되고, 모든 행인의 이동이 매 프레임 돈다 | 스폰 상한 조절 → 먼 행인 갱신 주기 늘리기 → 렌더링 거리 제한 |
| **② 코너 몰림** | 모든 경로가 **같은 코너 꼭짓점**을 지나 한 줄로 모인다 | 행인마다 길 폭 안의 좌우 비율을 뽑아 **차선 오프셋** |

**그런데 작업 순서의 0번을 "현재 성능 측정"으로 잡았습니다.**

> **스포너당 최대 3명** 규모라 **최적화 효과가 작을 수 있습니다.** 측정 없이 수치를 정하면 *"줄인 것 같은데 체감이 없는"* 작업이 됩니다.
>
> 그래서 문서에 **"측정 없이 수치를 정하지 않음"** 이라고 못 박고, 마지막에 재측정해서 0단계와 비교하도록 순서를 짰습니다.

**그리고 최적화(①)보다 코너 몰림(②)을 먼저** 두었습니다.

> ②는 **눈에 보이는 문제**이고, **스폰할 때 1회 계산**이라 다른 작업과 독립적입니다. ①은 측정 결과에 따라 안 할 수도 있는 작업입니다.
>
> **"확실히 개선되는 것"과 "효과가 불확실한 것"이 있으면 확실한 쪽을 먼저** 하는 게 맞다고 봤습니다.

코너 몰림의 원인도 정리해뒀습니다. **NavMesh 경로는 String Pulling 때문에 코너 안쪽 꼭짓점으로 수렴**합니다. 스폰 때 양옆으로 흩어놓아도 **코너에서 전원이 한 줄로 모였다가 다시 퍼집니다.**

> 지금 넣어둔 코너 보정은 **모든 행인을 같은 거리만큼** 미는 것이라 이 문제를 해결하지 못합니다. **몰림을 풀려면 행인마다 다른 오프셋**이 필요한데, 그게 ②의 차선 오프셋입니다.
>
> **지금 구현이 무엇을 해결하고 무엇을 해결하지 않는지** 문서에 명시해둔 게, 다음 작업을 설계할 때 바로 이어졌습니다.
