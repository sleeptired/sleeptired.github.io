## 빌런 시스템 구조 설계 — 그리고 아직 못 정한 것

> 편의점 빌런(절도·진열대 헤집기·미성년 주류 시도) 시스템의 구조를 잡았습니다. **구현은 아직 안 했고, 오늘은 구조만** 정했습니다. 그런데 정하고 나니 **더 근본적인 질문 하나가 남아서** 그걸 같이 기록해둡니다.

---

### 1. 오늘 정한 것 3가지

#### 판단 ① 빌런이라고 StateTree를 갈아 끼우지 않는다

*"빌런이면 다른 트리를 돌린다"* 는 기술적으로 가능합니다 (`StopLogic()` → 교체 → `StartLogic()`). 그런데:

| 문제 | 내용 |
| :--- | :--- |
| 공통 흐름 복제 | 쇼핑 → 계산 → 퇴장이 **트리마다 통째로 복사**됨. 빌런 4종이면 트리 5개 유지보수 |
| 수정 전파 | 지금 진행 중인 회피/슬롯/혼잡도 수정이 **트리 5개에 전부** 반영돼야 함 |
| 이미 답이 있음 | `bCheckoutAbandoned` 하나로 `ReturnItems` 분기를 만들어 쓰고 있음 |

> **결론: 트리는 하나. 손님이 들고 있는 "예약된 행동" 값을 조건으로 읽어 분기한다.** 어제 정리한 *"조건은 읽기만, 굴림은 태스크에서"* 가 그대로 적용되는 자리였습니다.

#### 판단 ② 빌런 행동은 두 종류이고, 절반은 트리를 안 건드려도 된다

| 종류 | 예시 | 필요한 작업 |
| :--- | :--- | :--- |
| **(A) 판단 왜곡형** | 10대가 술을 사려 함, 가격을 무시함 | **코드 0줄.** 소비 성향 DataAsset만 다른 걸 끼움 |
| **(B) 행동 분기형** | 절도, 진열대 헤집기, 새치기 | 새 태스크 1개 + 새 상태 1개 |

10대 주류 건은 결국 `ComputeCategoryScore()`가 Alcohol에 `-1.0`(하드 차단)을 반환하느냐의 문제입니다. **`BlockedCategories`에서 Alcohol만 뺀 사본 DA**를 그 손님에게만 주입하면 구매 판단 코드는 한 글자도 안 고치고 동작이 나옵니다.

> ⚠️ **절대 하면 안 되는 것:** 런타임에 `Decision->Archetype->BlockedCategories.Remove(...)`
> DataAsset은 **전 손님이 공유하는 인스턴스가 하나뿐**이라, 빌런 한 명 때문에 **그 종족 전원이 그 순간부터 술을 삽니다.** 반드시 *다른 에셋으로 갈아 끼우는* 방식이어야 합니다.
>
> 어제 정리한 *"본체 구조체는 트리당 1개, 100명이 공유"* 와 **완전히 같은 함정**입니다. 공유 자원을 개인 사정으로 수정하면 안 된다 — 대상만 바뀌었습니다.

#### 판단 ③ "빌런이다/아니다"와 "갑자기 저지른다"는 같은 코드로 표현된다

```
스폰 시  : VillainChance 굴림 → 계획형 빌런인가? (1회)
             └ 계획형이면 PlanWeight 가중랜덤으로 "무슨 짓을 할지" 확정
런타임   : 기회(Opportunity)가 올 때마다 굴림
             ├ 계획형이고 계획과 일치 → TriggerChance (높음, 0.8)
             └ 그 외 모든 손님       → ImpulseChance × Impulsiveness (낮음, 0.02)
발동 시  : PendingAction에 래치(latch) → 태스크가 처리할 때까지 고정
```

| 설정 | 결과 |
| :--- | :--- |
| `VillainChance = 0`, `ImpulseChance > 0` | **순수 확률형** (아무나 가끔 저지름) |
| `VillainChance = 1`, `ImpulseChance = 0` | **순수 이분법** (빌런만 저지름) |
| 둘 다 값이 있음 | **혼합형** |

### 2. 구현 순서 — 데이터 계층부터

| 단계 | 내용 | 건드리는 파일 |
| :--- | :--- | :--- |
| **V1** | 데이터 계층 + 스폰 시 판정 | 스포너 + 새 파일 4개 |
| V2 | 굴림 "기회" 심기 | 태스크 2곳, 각 1줄 |
| V3 | 조건 1개 추가 (`HasPendingVillainAction`) | Conditions |
| V4 | 트리 배선 (`Villain` 상태를 **맨 위**에) | ST_Customer |
| V5 | 절도 태스크 + `CommitShoplift` | Tasks + Subsystem |

**V1을 먼저 하는 이유:** 행동을 하나도 구현하지 않은 채로 **확률 분포만 로그로 검증**할 수 있습니다. 반대로 태스크부터 만들면 *"빌런이 안 나타난다"* 가 **확률 문제인지 트리 배선 문제인지 구분이 안 됩니다.**

> 구매 판단을 만들 때 검증 서브시스템으로 평균 장바구니를 먼저 확인한 것과 같은 순서입니다. **관측 수단을 행동보다 먼저 만든다**가 두 번째 적용 사례가 됐습니다.

**트리 배선에서 다시 만난 문제 하나** — `Browse ✓→ Shopping`을 **`Browse ✓→ Root`** 로 바꿔야 합니다. Root를 안 거치면 진열대에서 절도가 래치돼도 `Villain` 상태가 후보에 안 들어갑니다. `Checkout ✗→ Root`로 고쳐 `ReturnItems`를 찾게 만든 것과 **정확히 같은 문제**입니다. 이 패턴에 세 번째로 걸렸습니다.

### 3. ⭐ 아직 못 정한 것 — 빌런은 언제 정해지는가

구조를 다 잡고 나서 남은 질문입니다.

> **① 스폰 시점에 스포너가 "이 손님은 빌런"으로 확정하는가?**
> **② 평범한 손님이 매장 안에서 확률적으로 빌런으로 변질되는가?**

#### 두 안의 성격

| | **A. 스폰 확정** | **B. 런타임 변질** |
| :--- | :--- | :--- |
| 결정 시점 | 스폰 1회 | 기회가 올 때마다 |
| 확률의 의미 | **그대로 빌런 비율** | 실효 확률 = $1-(1-p)^N$ |
| 재현성 | 시드 고정으로 완전 재현 | 기회 횟수에 의존해 흔들림 |
| 튜닝 | 직관적 (0.3 = 30%) | 역산 필요 ($p = 1-(1-P)^{1/N}$) |
| 플레이어 개입 | **불가** (이미 정해짐) | **가능** (상황에 반응) |
| 판단 왜곡형(A) 적용 | 안전 | **위험** |

#### A안의 강점 — 검증과 일관성

*   **시드 고정 → 같은 손님이 같은 빌런.** V1 검증 자체가 이 성질에 기대고 있습니다.
*   **판단 왜곡형은 스폰 시점에만 안전하게 적용됩니다.** 아키타입 대체는 **예산 추첨(`EnsureBudgetInitialized`)이 아직 안 일어난 시점**에 해야 합니다. 이미 예산을 굴리고 상품을 몇 개 담은 손님의 성향 카드를 중간에 갈아 끼우면 **앞뒤 판단이 어긋납니다.**
*   스포너에서 마스터 스트림을 추가로 소비하지 않으려고 **손님 시드에서 XOR로 파생**시키는 처리까지 이미 넣어뒀습니다. (`CustomerSeed ^ 0x5645524C`)

#### B안의 강점 — 게임 루프가 생긴다

*   **플레이어 행동이 빌런 발생률에 영향을 줄 수 있습니다.** 계산대에 오래 자리를 비우면, 매장이 혼잡하면, 손님 근처에 아무도 없으면 확률이 올라가는 식.
*   A안은 플레이어가 **관찰**만 할 수 있고, B안은 **예방**할 수 있습니다. 이 차이가 큽니다 — 빌런이 "재수 없으면 걸리는 이벤트"가 되느냐 **"내 운영이 만든 결과"** 가 되느냐입니다.
*   이미 만든 **인내심 타임아웃과 자연스럽게 이어집니다.** 오래 기다린 손님이 포기하는 대신 그냥 들고 나가는 분기는 설득력이 있습니다.

#### 정리하면서 바뀐 질문

두 안을 나란히 놓고 보니 **이게 배타적 선택이 아니라는 걸** 알았습니다. 판단 ③의 확률 축 2개가 이미 둘 다 지원합니다. 스폰 축은 *"무슨 짓을 할 예정인가(계획)"*, 런타임 축은 *"지금 저지를 것인가(발동)"* 로 **의미가 다릅니다.**

그리고 더 중요한 제약이 하나 있습니다.

> **판단 왜곡형(A)은 런타임 변질이 구조적으로 불가능합니다.** 예산과 구매 판단이 이미 굴려진 뒤라 성향 카드를 바꾸면 일관성이 깨집니다.
> **행동 분기형(B)은 둘 다 가능합니다.** 절도·진열대 헤집기는 "지금 이 순간의 결심"으로 표현해도 어색하지 않습니다.

그래서 질문이 **"둘 중 뭐냐"에서 "어떤 행동을 어느 축에 배정하느냐"** 로 바뀌었습니다.

| 행동 | 축 | 근거 |
| :--- | :--- | :--- |
| 미성년 주류 시도 | **스폰 확정** | 성향 카드 교체가 예산 추첨 전이어야 함 |
| 절도 | **런타임 우세** (계획형도 허용) | 감시 여부·혼잡도에 반응해야 게임이 됨 |
| 진열대 헤집기 | 런타임 | 상황 의존적, 되돌릴 수 있는 피해 |
| 새치기 | 런타임 | 대기 시간이라는 명확한 유발 조건이 있음 |

#### 아직 결정 못 한 것

*   절도의 **두 축 비중**. 계획형 위주로 갈지, 충동형 위주로 갈지에 따라 플레이 체감이 달라집니다. 숫자를 정하려면 기획 목표치가 필요합니다.
*   런타임 축을 쓰면 **"기회"를 어디에 심을지**가 곧 게임 디자인입니다. 지금은 `ArrivedAtShelf` / `AfterPickup` 두 곳만 있는데, *"주변에 플레이어가 없을 때"* 같은 상황 조건을 넣으면 훨씬 재밌어지지만 판정 비용이 붙습니다.
*   B안을 강하게 쓰면 **A안 기반의 V1 검증 방식이 약해집니다.** 확률 검증을 어떻게 할지 다시 설계해야 합니다.

> **다행인 건 지금 구조가 두 축을 다 지원해서, DataAsset 숫자만 바꾸면 전환된다는 점입니다.** 오늘 구조 작업의 실제 성과는 빌런 기능이 아니라 **"이 결정을 나중으로 미룰 수 있게 만든 것"** 인 것 같습니다. 결정을 못 내렸는데 진행이 막히지 않는 상태가 됐습니다.

### 4. 어느 쪽을 택하든 반드시 필요한 것

**① 래치(latch)는 필수**

```
굴림은 태스크 안에서 1회 → PendingAction에 저장 → 조건은 읽기만
```

조건 안에서 매번 굴리면 **Root 재선택마다 결과가 뒤집힙니다.** 어제 정리한 확률 조건의 함정 그대로입니다.

**② 실효 확률 보정**

기회를 진열대 N곳마다 굴리면 방문 1회당 실제 발생률은 $1-(1-p)^N$이 됩니다. 목표 확률 $P$를 맞추려면 $p = 1-(1-P)^{1/N}$로 **역산**해야 합니다. 이걸 모르면 *"설정은 2%인데 실제로는 10%가 넘게 나온다"* 가 됩니다.

**③ 한 방문에 한 번만**

`bActionTriggeredThisVisit` 체크가 없으면 한 손님이 진열대마다 절도를 시도합니다.

**④ 외형으로 티 내지 않기**

빌런이어도 **외형은 원본 아키타입 기준**으로 적용합니다. 대체 아키타입은 소비 성향만 바꾸는 카드라 Visual이 비어 있을 수 있고, 무엇보다 **겉모습만 보고 빌런을 알아채면 게임이 안 됩니다.**

### 5. 협의가 필요한 항목

**계산대 파트** — 10대가 술을 담는 것까지는 손님 파트가 처리하지만 **막는 건 계산대의 몫**입니다. 지금 계산대는 손님 연령대를 알 방법이 없습니다.

```cpp
// GetQueueSlotLocation과 같은 급의 최소 계약 하나
ECSAgeBracket GetCustomerAgeBracket(const ACSCustomerCharacter* Customer) const;
```

**소비심리 파트** — ① `Impulsiveness`를 충동 확률 배율로 써도 되는지 ② 대체 아키타입 DA를 만들지, 차단 해제 오버라이드 필드를 추가할지 ③ **빌런 발생률 목표치** (이 숫자가 있어야 위 §3의 결정도 가능)

> 빌런 프로필을 아키타입 DA가 아니라 **스포너가 `TMap`으로 들고 있게** 한 것도 협의 전 임시 조치입니다. 아키타입 DA는 소비심리 파트 소유라 지금 필드를 늘리면 계속 충돌합니다. 합의되면 옮기고 맵은 지우면 됩니다. **남의 파일을 안 건드리고 진행하는 방법**을 또 하나 찾은 셈입니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **공유 자원을 개인 사정으로 고치지 않는다** | DataAsset을 런타임 수정하면 종족 전원이 바뀐다. StateTree 본체 구조체와 같은 함정 |
| **관측 수단을 행동보다 먼저** | V1(데이터+로그)을 먼저 만들면 "안 나타난다"가 확률 문제인지 배선 문제인지 구분된다 |
| **전이는 Root로** | `Browse ✓→ Shopping`을 Root로. 같은 패턴에 세 번째로 걸렸다 |
| **배타적으로 보이는 선택지가 아닐 수 있다** | 스폰 확정 vs 런타임 변질은 확률 축 2개로 공존 가능. 질문이 "어떤 행동을 어느 축에"로 바뀌었다 |
| **제약이 배정을 결정한다** | 판단 왜곡형은 예산 추첨 전이어야 하므로 스폰 축 고정. 구현 제약이 설계 선택지를 좁혀줬다 |
| **좋은 구조 = 결정을 미룰 수 있게 하는 것** | 오늘 성과는 빌런 기능이 아니라, 못 정한 채로도 진행이 막히지 않는 상태를 만든 것 |
| **확률은 기회 횟수와 함께 봐야 한다** | N번 굴리면 실효 확률은 $1-(1-p)^N$. 목표치에서 역산할 것 |
