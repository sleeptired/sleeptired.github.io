## 계산 포기 행동 구현 — 인내심 타임아웃 · 상품 반환 · 트리 재구성

> 플레이어가 계산을 안 해주면 손님이 **하염없이 기다리기만 하던 문제**를 해결했습니다. 인내심을 넘기면 포기하고, 들고 있던 상품을 처리한 뒤 나갑니다. 구현 자체보다 **"어떻게 배치할 것인가"** 와 **"어떻게 무한 루프를 막을 것인가"** 에 시간을 더 썼습니다.

### 1. 오늘 만든 것

| 단계 | 내용 |
| :--- | :--- |
| **STEP5** | 인내심 타임아웃 + 들고 있던 상품을 **양옆 발치에 쌓아 내려놓기** |
| **STEP6** | 50% 확률로 **진열대에 되돌려놓으러 가기** |
| **트리 재구성** | `ReturnItems` 상태 추가 + **전이·조건 재설계** ← 오늘 가장 중요한 수정 |

**목표 동작**

```
인내심 초과 → 계산 포기
  ├─ 50%: 그 자리에 떨구고 퇴장
  └─ 50%: 상품을 든 채 진열대로 이동
           ├─ 빈 슬롯 있음 → 하나씩 되돌려놓음
           └─ 빈 슬롯 없음 → 그 진열대 앞에 떨굼
           → 퇴장
```

두 경로 모두 **마지막은 퇴장이고, 다시 줄을 서지 않습니다.**

### 2. STEP5 — 인내심 타임아웃

`WaitInQueue` 태스크의 `Tick`에 경과 시간을 누적하고, 초과하면 `Failed`를 반환합니다.

```cpp
Data.ElapsedWaitTime += DeltaTime;

float Patience = Data.PatienceOverride;
if (Patience <= 0.0f)
{
    // 태스크에서 따로 지정하지 않았으면 Subsystem이 주는 값을 쓴다.
    Patience = Subsystem->GetPatienceSeconds(Data.Actor);
}

if (Patience > 0.0f && Data.ElapsedWaitTime >= Patience)
{
    Subsystem->AbandonCheckout(Data.Actor, Data.ElapsedWaitTime);
    return EStateTreeRunStatus::Failed;
}
```

*   **`EnterState`에서 `ElapsedWaitTime = 0.0f` 초기화가 필수**입니다. 재진입 시 타이머가 이어지면 두 번째 줄서기에서 즉시 포기합니다.
*   `PatienceOverride`(태스크 파라미터)를 0으로 두면 Subsystem 값을 쓰는 **2단 구조**로 했습니다. 테스트할 때 트리에서 8초로 바꿔가며 확인하고, 실제 운영은 Subsystem 기본값(30초)을 씁니다.

**`AbandonCheckout`의 순서에 의미가 있습니다.**

```
1. LeaveQueue()          ← 가장 먼저. 이 순간 뒷사람 순번이 당겨진다
2. bCheckoutAbandoned = true
3. 상품 처리 (떨구기 or 목록 유지)
4. OnCheckoutAbandoned 방송   ← 반드시 마지막
```

> **방송이 마지막인 이유:** 먼저 방송하면 구독하는 쪽이 *"상품을 들고 있는데 포기함"* 같은 **모순된 중간 상태**를 보게 됩니다. 이벤트는 **상태 정리가 끝난 뒤**에 알려야 합니다.

### 3. 떨구기 배치 — 오늘 가장 오래 고민한 부분

의도는 **"손님이 들고 있던 물건을 자기 양옆 발치에 차곡차곡 내려놓는다"** 입니다.

#### 검토했던 대안들

| 방식 | 문제 |
| :--- | :--- |
| 바닥 한 지점에 모아 놓기 | 여러 개면 서로 파고들어 물리가 사방으로 튕겨냄 |
| 원형으로 흩뿌리기 | **손님 정면에도 생김** → 나가면서 자기 물건을 밟고 지나감 |
| 좌우로 계속 벌리기 | 개수가 많으면 ±120cm까지 벌어져 **옆 손님 자리 침범** |
| 한 열에 무한정 쌓기 | 상품 10개면 **2m 높이 탑** |
| 고정 간격으로 쌓기 | 큰 상품은 겹치고, 작은 상품은 공중에 뜸 |
| 코드에 위치를 숫자로 | 종족별 외형이 달라지면 대응 불가 |
| **화살표 기준 + 크기 기반 쌓기** ✅ | 종족별 조정은 BP에서, 개수 처리는 코드에서 |

#### 역할 분담 — 화살표는 기준점, 개수는 코드

| | 담당 | 이유 |
| :--- | :--- | :--- |
| **어디서부터** 쌓기 시작할지 | **화살표 (BP)** | 종족마다 키·팔 위치가 다름. 눈으로 맞춰야 정확 |
| **몇 개를** 어떻게 쌓을지 | **코드** | 개수는 런타임에 정해짐. BP가 미리 알 수 없음 |

화살표는 **상품 하나하나의 자리가 아니라 "0번 자리"** 입니다. 나머지는 거기서부터 코드가 계산하므로 **상품이 3개든 20개든 알아서 처리됩니다.**

```
   상품 10개일 때 (좌우 번갈아 배정)

     ⑨              ⑩          ← 2번째 열 (1번째가 팔 높이를 넘어서)
     ⑦              ⑧
     ⑤              ⑥
     ③              ④
     ①              ②          ← 화살표 위치 (0번 자리)
   ─────────────────────────
          [손님] → 계산대 방향
```

> **숫자로 위치를 주면 종족별 대응이 안 됩니다.** 고블린은 작고 다른 종족은 크면 발치 높이도 팔 간격도 달라지는데, 코드에 `if (고블린) -30 else -40` 같은 분기를 넣으면 종족이 추가될 때마다 코드를 고쳐야 합니다. **화살표를 두면 종족 BP마다 뷰포트에서 드래그하면 끝**입니다. 계산대가 `QueueStartPoint` 화살표로 줄 위치를 정하는 것과 같은 방식이라 프로젝트 일관성도 생깁니다.

#### 간격을 고정값으로 못 쓰는 이유

| 상품 | 고정 20cm 간격일 때 |
| :--- | :--- |
| 작은 사탕 (높이 8cm) | 12cm 공중에 떠 있다가 떨어짐 |
| 큰 도시락 (높이 30cm) | **10cm 겹쳐서 생성** → 물리가 사방으로 튕겨냄 |

그래서 **스폰한 상품의 바운딩 박스를 재서** 다음 높이를 정합니다.

```cpp
const FVector Extent = Spawned->GetComponentsBoundingBox(false).GetExtent();
const float ItemHeight = Extent.Z * 2.0f;
ColumnTopZ[SideIndex] += ItemHeight + DropStackGap;
```

**`DropMaxStackHeight`가 절대 높이가 아니라 상대 높이인 것도 같은 이유**입니다. 화살표에서부터 누적한 값과 비교하므로, 화살표를 무릎에 두든 발치에 두든 **"기준점에서 80cm"** 로 일정합니다. 종족 키가 달라져도 이 값을 바꿀 필요가 없습니다.

세부 처리 2가지 — **미세한 흔들림(3cm)** 과 **Yaw 랜덤**. 완전히 정렬되면 인위적으로 보입니다.

### 4. STEP6 — 진열대 반환

#### 50%라는 임시값의 근거

*   전부 진열대로 보내면 매장이 항상 깔끔해져서 **"계산을 안 해주면 손해"라는 압박이 사라집니다.**
*   전부 그 자리에 버리면 계산대 앞이 금방 난장판이 됩니다.
*   절반씩 섞으면 **두 행동이 다 보여서 기능 검증에 적합**합니다.

> 임시값을 정할 때도 근거가 필요합니다. *"일단 절반"* 이 아니라 **"검증 목적상 두 경로가 다 나와야 하니까 절반"** 이라고 적어두면, 나중에 밸런싱할 때 이 값을 바꿔도 되는지 판단할 수 있습니다.

#### 물리를 켜고 끄는 분기 — 놓칠 뻔한 함정

```cpp
Product->SetActorEnableCollision(true);

// 진열대에 놓을 상품은 물리를 켜지 않는다.
// TryPlaceItem이 Attach하는데, 물리가 켜져 있으면
// 시뮬레이션이 Attach를 무시하고 슬롯에서 떨어져 나간다.
if (bEnableDropPhysics)
{
    Product->EnableWorldDropPhysics();
}
```

| 경로 | 물리 | 이유 |
| :--- | :---: | :--- |
| 바닥에 떨구기 | **ON** | 플레이어가 내려놓은 상품과 동일하게 자연스럽게 안착 |
| 진열대에 놓기 | **OFF** | 물리가 켜져 있으면 **Attach가 무시되어 슬롯에서 떨어져 나감** |

같은 함수(`RespawnSelectProduct`)를 두 경로가 공유하므로 **파라미터 하나로 분기**했습니다. 기본값을 `true`로 둬서 STEP5 호출부는 수정이 필요 없었습니다.

#### 남은 상품을 모았다가 한 번에 떨구는 이유

슬롯이 꽉 차서 못 놓은 상품은 **즉시 떨구지 않고 목록에 모아뒀다가** 마지막에 `DropCustomerItems`를 한 번 호출합니다.

> `DropCustomerItems`가 **좌우 열 배치를 상품 개수 기준으로 한 번에 계산**하기 때문입니다. 하나씩 즉시 떨어뜨리면 매번 첫 번째 자리에 겹쳐 놓게 됩니다. **"배치를 계산하는 함수"는 전체를 한 번에 받아야 한다**는 걸 놓칠 뻔했습니다.

#### 탐침(Probe) 방식 — 동작하지만 의도와 다른 사용

빈 슬롯이 있는 진열대를 찾을 때, 아직 상품 액터를 만들기 전이라 **손님 액터를 `CanPlaceItem`에 넘겨서** 확인했습니다.

```cpp
if (ICSShelfPlaceable::Execute_CanPlaceItem(Shelf, ProbeActor))
```

팀원 구현이 타입 검사 없이 빈 슬롯 유무만 보기 때문에 동작하지만, **"이 상품을 놓을 수 있나"를 묻는 함수에 손님을 넘기는 건 의도와 다른 사용**입니다. → 진열대 파트에 `HasEmptySlot()` 전용 함수를 요청했습니다.

> 동작한다고 해서 맞는 사용은 아닙니다. **우연히 통하는 코드는 상대 구현이 바뀌는 순간 깨집니다.** 우회로 넘어가되 요청을 남겨두는 게 맞다고 판단했습니다.

### 5. 트리 재구성 

`ReturnItems` 상태를 추가하면서 **기존 전이가 새 상태를 건너뛰는 문제**가 드러났습니다.

#### 전이 목적지를 구체 상태로 못 박으면 안 된다

| | 기존 | 수정 후 |
| :--- | :--- | :--- |
| Checkout `On State Failed` | **→ Leave** | **→ Root** |

STEP5까지는 `Checkout` 실패 시 바로 `Leave`로 보냈습니다. *"실패해도 손님이 매장에 갇히지 않게"* 넣어둔 안전장치였고 잘 동작했습니다.

**그런데 `ReturnItems`를 Checkout과 Leave 사이에 끼워 넣자, 포기한 손님이 그대로 Leave로 직행해 새 상태를 건너뛰었습니다.**

```
Checkout 실패 → Root 재선택
    Shopping   : 조건 실패 → 건너뜀
    Checkout   : Abandoned Invert에 걸림 → 건너뜀
    ReturnItems: HasItems ✔ + Abandoned ✔ → 진입 ✅
```

> **배운 것:** 전이는 **구체적 목적지가 아니라 "재평가 지점"으로 보내는 게 확장에 강합니다.** `→ Leave`는 그 순간의 정답이지만 미래를 못 박습니다. `→ Root`는 셀렉터가 **우선순위와 조건을 다시 평가**하므로, 나중에 상태를 끼워 넣어도 **기존 전이를 수정할 필요가 없습니다.**
>
> 앞서 `Shopping`의 `On Failed → Root`가 전체를 연결한다고 정리했는데, 같은 패턴을 `Checkout`에도 적용한 셈입니다. **한 곳에서 통한 패턴이 다른 곳에서도 통하는지 확인**하는 게 리팩터링의 실마리가 됐습니다.

#### 재평가에는 반드시 재진입 차단이 짝을 이뤄야 한다

Root로 되돌리면 **이전 상태가 다시 선택될 수 있습니다.** 그래서 진입 조건에 가드를 걸어야 합니다.

**최종 조건 구성**

| 상태 | 조건 |
| :--- | :--- |
| **Shopping** | `Has Unvisited Shelf` + `Wants More Items` + `Has Abandoned Checkout` **(Invert ✔)** |
| **Checkout** | `Has Items In Cart` + `Has Abandoned Checkout` **(Invert ✔)** |
| **ReturnItems** | `Has Items In Cart` + `Has Abandoned Checkout` (Invert 해제) |
| **Leave** | **조건 없음** (항상 성립하는 폴백) |

**차단한 무한 루프 3종**

| 루프 | 차단 방법 |
| :--- | :--- |
| 포기한 손님이 **다시 줄 섬** | Checkout에 Abandoned **Invert** |
| 포기한 손님이 **다시 쇼핑함** | Shopping에 Abandoned **Invert** |
| 반환 후 **또 Checkout 진입** | 같은 플래그로 계속 차단 |

> **Shopping에도 가드가 필요해진 이유**가 흥미로웠습니다. 원래 Shopping은 *"다 둘러보면 끝"* 이라 자연히 종료됐는데, `Wants More Items` 조건이 들어오면서 **아직 안 본 진열대가 남은 채로도 계산대에 갈 수 있게** 됐습니다. 그러면 포기한 뒤 Root로 돌아왔을 때 *"아직 볼 게 남았네"* 하며 다시 쇼핑을 시작해 영원히 안 나갑니다.
>
> **조건 하나를 추가하면 그 상태의 종료 경로가 바뀌고, 그게 다른 상태의 가드 필요성으로 번집니다.** 상태 기계에서 조건 추가가 국소적 변경이 아니라는 걸 체감했습니다.

`ReturnItems`는 **Leave보다 위**에 배치해야 합니다. 셀렉터는 **순서가 곧 우선순위**라, 아래에 두면 조건 없는 Leave가 먼저 걸립니다.

### 6. 임시값을 함수로 격리하는 패턴

이번에 같은 패턴을 **두 번** 썼습니다.

```cpp
// [임시] 지금은 기본값을 그대로 반환. 소비심리 연동 시 이 함수 내부만 교체.
float GetPatienceSeconds(const ACSCustomerCharacter* Customer) const;
float GetReturnToShelfChance(const ACSCustomerCharacter* Customer) const;
```

| 항목 | 지금 | 나중 |
| :--- | :--- | :--- |
| 인내심 | `DefaultPatienceSeconds`(30초) 고정 | 손님 성격(급함/느긋함)별 값 |
| 반환 확률 | `DefaultReturnToShelfChance`(0.5) 고정 | 성향(예의 바름/정리 습관)별 값 |

**둘 다 `Customer` 포인터를 파라미터로 받습니다.** 지금은 쓰지 않지만, **나중에 손님별로 달라질 때 시그니처를 안 바꾸기 위해서**입니다. 호출부(태스크, `AbandonCheckout`)는 어느 쪽이든 수정이 필요 없습니다.

> 며칠 전 정리한 *"교체 예정 로직은 얇은 껍데기로 감싼다"* 를 이제 **의식적으로 반복 적용**하고 있습니다. 패턴이 손에 붙는다는 게 이런 거구나 싶었습니다.

### 7. 안전장치 정리

상품이 증발하면 **재고가 사라지는 것**이라 여러 겹으로 막았습니다.

| 지점 | 안전장치 |
| :--- | :--- |
| `ReturnProducts::EnterState` | 진열대가 없거나 경로 탐색 실패 → **그 자리에 떨구고 성공 종료** |
| `ReturnProducts::ExitState` | 어떤 경로로든 상품이 남은 채 상태를 떠나면 → 떨구기 |
| `DropCustomerItems` | 일부 생성에 실패해도 **목록은 비운다** (남기면 "들고 있는" 상태로 판정이 꼬임) |
| `ReturnCustomerItemsToShelf` | 진열대가 아니면 그냥 떨구기 |
| `TryPlaceItem` 실패 | 슬롯 초과 배치가 **구조적으로 불가능** (false 반환) |

> 공통 원칙은 **"손님을 붙잡아두지 않는다"** 입니다. 경로를 못 찾았을 때 `Running`을 유지하면 손님이 영원히 서 있게 되므로, **실패해도 성공으로 종료시키고 상품만 안전하게 처리**하는 쪽을 택했습니다.

---

### 8. 테스트 전략 — 확률을 고정해서 경로별로 검증

```
1. DefaultReturnToShelfChance = 1.0  → 진열대 경로만 검증
2. DefaultReturnToShelfChance = 0.0  → 떨구기 경로만 검증
3. DefaultReturnToShelfChance = 0.5  → 섞인 동작 확인
```

> 확률이 들어간 기능은 **그대로 두면 원하는 경로가 언제 나올지 몰라 검증이 안 됩니다.** 값을 극단으로 고정해 경로를 하나씩 확인한 뒤 마지막에 되돌리는 게 훨씬 빠릅니다. `Patience Override = 8`로 줄인 것도 같은 이유입니다.

특히 확인한 항목:

- **화살표를 옮기면 떨구는 위치도 따라 옮겨지는가** ← 화살표 방식 자체의 검증
- **크기가 다른 상품을 섞어도 겹치지 않는가** (작은 사탕 + 큰 도시락) ← 크기 기반 간격 검증
- **되돌려놓은 뒤 줄을 다시 서지 않는가** ← 무한 루프 검증
- 슬롯 1개 남은 진열대에 상품 3개 → **1개는 슬롯에, 2개는 앞에 떨어지는가**
- 정상 계산한 손님은 `ReturnItems`를 거치지 않는가 ← 회귀

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **전이는 재평가 지점으로 보낸다** | `→ Leave`는 그 순간의 정답이지만 미래를 못 박는다. `→ Root`면 상태를 끼워 넣어도 기존 전이 수정 불필요 |
| **재평가와 재진입 차단은 세트** | Root로 되돌리면 이전 상태가 다시 뽑힐 수 있다. `bCheckoutAbandoned` 같은 가드가 반드시 짝을 이뤄야 한다 |
| **조건 추가는 국소적 변경이 아니다** | `Wants More Items` 하나가 Shopping의 종료 경로를 바꾸고, 그게 가드 필요성으로 번졌다 |
| **BP와 코드의 역할을 나눈다** | "어디서부터"는 눈으로 맞추는 BP 화살표, "몇 개를"은 런타임을 아는 코드 |
| **고정값은 크기가 다른 대상을 못 다룬다** | 간격을 실제 바운드로 재야 사탕과 도시락이 섞여도 겹치지 않는다 |
| **임시값에도 근거를 적는다** | "일단 절반"이 아니라 "두 경로가 다 나와야 검증되니까 절반" |
| **동작한다 ≠ 올바른 사용** | 탐침 방식은 우연히 통하는 것. 우회하되 전용 함수를 요청해둔다 |
| **이벤트는 상태 정리 후에 방송** | 먼저 쏘면 구독자가 모순된 중간 상태를 본다 |
| **확률 기능은 값을 극단으로 고정해 검증** | 1.0 → 0.0 → 0.5 순서로 경로를 하나씩 확인 |
