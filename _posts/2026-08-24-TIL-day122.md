## 빌런 제압 — 손실을 "빼는" 대신 "성립하지 않게" 만들기

> 마법 지팡이로 절도범을 맞추면 **멈추고, 훔친 상품을 떨구고, 몇 초 뒤 사라지는** 기능을 만들었습니다. 그 과정에서 손실 처리 흐름 전체를 다시 읽었고, StateTree의 **재선택** 동작 때문에 하루를 잡아먹은 버그도 하나 잡았습니다.

---

### 1. 오늘 만든 것

| 항목 | 범위 |
| :--- | :--- |
| **제압 기능 1차** | 피격 → 제압 확정 → 상품 낙하 → 소멸 (연출 없이 완결) |
| **손실 흐름 정리** | 손실이 확정되는 경로 / 차단되는 경로를 코드 위치까지 문서화 |
| **빨간 외곽선** | 절도 시작 시 스텐실 4번 → 빨간 외곽선, 제압 시 복원 |

**의도적으로 안 한 것: 쓰러지는 연출(랙돌).** 훅만 만들고 **내용은 비워** 뒀습니다. 빈 훅이어도 *멈추고, 떨구고, 사라진다*는 완결됩니다.

### 2. ⭐ 손실 차단의 원리 — 상쇄가 아니라 조건 불성립

이 기능의 핵심 질문은 *"제압하면 손실을 어떻게 되돌리나"* 였는데, 코드를 읽어보니 **되돌릴 필요가 없었습니다.**

> **손실 여부는 `SelectProducts` 배열이 비어 있는지 하나로 갈립니다.**

```
ReportShopliftEscaped()  ← 손실이 발생하는 단 하나의 지점
  게이트 1~3 통과
  게이트 4: SelectProducts.Num() == 0 이면 조용히 return   ★
  → 금액 합산 → OnShopliftEscaped 방송 (손실 확정)
```

그리고 `DropCustomerItems()`가 마지막에 `ClearSelectItems()`를 부릅니다. 그러면:

| 경로 | 결과 |
| :--- | :--- |
| **제압 성공** | 낙하로 목록이 비워짐 → 소멸 시 게이트 4에서 조기 return → **손실 방송 자체가 없음** |
| **도주 성공** | 목록이 남은 채 소멸 → 금액 합산 → 손실 확정 |

> **손실 차단이 "손실을 상쇄하는 계산"이 아니라 "손실 조건을 성립하지 못하게 만드는 방식"** 이었습니다. 제압 처리에 *"손실 취소"* 분기를 따로 넣지 않아도 되고, 동시에 **상품 실물이 바닥에 되살아나 있으니 재고도 보존**됩니다.
>
> 상태를 되돌리는 코드를 쓰기 전에 **"애초에 그 상태가 성립하는 조건이 뭔가"** 를 먼저 봐야 한다는 걸 배웠습니다. 조건 쪽을 건드리면 되돌리기가 필요 없어집니다.

그래서 제압된 손님도 **다른 손님과 똑같이** `NotifyCustomerDespawned()`를 통과시킵니다. 특별 분기가 없습니다. (빈손 퇴장률 같은 다른 통계는 정상 집계돼야 하므로 이 호출을 빼면 안 됩니다.)

**손실 집계를 퇴장 태스크마다 흩어놓지 않고 `NotifyCustomerDespawned()` 한 곳에 모은 것**도 같은 사고입니다. 소멸 경로가 정상 퇴장 / 강제 퇴장 / 마감 정리 / 제압 후 소멸 **네 개**인데, 전부 이 함수를 지나갑니다. **모든 경로가 반드시 지나는 지점**에 두면 누락이 구조적으로 불가능합니다.

### 3. 순서가 곧 제약인 코드

`HandleMagicHitOnCustomer()`는 **순서를 바꾸면 안 되는** 함수가 됐습니다.

```
1. CanSubdueCustomer() 실패 → return false
2. MarkSubdued()가 false(중복 피격) → return true
3. RecoveredGold 계산        ★ 반드시 낙하 전
4. LeaveQueue()
5. DropCustomerItems()       ★ 여기서 손실이 0이 된다
6. BeginSubduedReaction()    (지금은 빈 훅)
7. OnVillainSubdued 방송
```

| 순서 제약 | 어기면 |
| :--- | :--- |
| 회수액을 **낙하 전에** 계산 | `Drop`이 목록을 비우므로 **항상 0 G**가 방송됨 |
| 낙하를 **연출 전에** | 낙하 기준점이 캐릭터에 붙은 화살표라, 랙돌로 몸이 뒤집힌 뒤 부르면 **상품이 땅밑·벽에 박힘** |
| `LeaveQueue()`를 파괴 전에 | 줄에서 맞으면 **파괴된 손님이 대기열에 남아 뒷사람 순번이 밀림** |

> 두 번째가 특히 재밌었습니다. **아직 만들지도 않은 랙돌 때문에 지금 코드의 순서가 정해졌습니다.** 나중에 연출을 넣을 사람이 순서를 바꾸지 않도록 주석에 이유를 적어뒀는데, 이런 게 **"미래를 위한 주석"** 인 것 같습니다.

### 4. 상태의 소유자를 누구로 할 것인가

기절·소멸 타이머를 **캐릭터의 `FTimerHandle`로 만들면 안 됐습니다.**

> 캐릭터에 타이머만 걸면 **StateTree는 그 사실을 모르고 계속 돕니다.** `LeaveAndDespawn`이 여전히 `MoveToLocation`을 재발급해서 **쓰러진 손님이 바닥을 미끄러져 출구로 가거나**, Root가 다른 상태를 재선택해 버립니다.

그래서 **`Subdued` 상태를 Root의 첫 번째 자식으로** 추가하고, 그 상태의 태스크가 대기 시간과 파괴를 책임지게 했습니다.

**그러자 "멈춘다"는 요구사항이 공짜로 해결됐습니다.** 기존 태스크들이 전부 `ExitState`에서 `StopMovement()`를 부르고, StateTree는 **새 상태의 `EnterState`보다 이전 상태의 `ExitState`를 먼저** 실행하기 때문입니다.

*(다만 `Shoplift`가 올려둔 `MaxWalkSpeed`는 상태를 떠나도 유지되므로 `DisableMovement()`로 확실히 끊었습니다.)*

### 5. ⭐ 재선택 타이머 리셋 버그 — `bShouldStateChangeOnReselect`

**증상:** 상품은 정상으로 떨어지고 손님도 멈추는데, `SubduedDespawnDelay`가 지나도 **영원히 사라지지 않습니다.** 로그에 `EnterState`의 "소멸 대기 시작"이 **초당 60줄** 찍혔습니다.

**원인 추적**

```
IsSubdued는 한 번 켜지면 꺼지지 않는다
  → 이미 Subdued에 있는데도 Root의 On Tick 전이가 매 틱 다시 발동
  → 대상이 현재 상태와 같으므로 StateTree는 재선택(Sustained)으로 처리
  → FStateTreeTaskBase의 기본값 bShouldStateChangeOnReselect = true
  → 재선택에도 EnterState가 다시 호출
  → EnterState의 ElapsedTime = 0 이 매 프레임 실행 → 타이머가 Delay에 도달 못 함
```

엔진 소스에서 분기를 찾으니 정확히 그 조건이었습니다.

```cpp
const bool bShouldCallEnterState =
    CurrentTransition.ChangeType == EStateTreeStateChangeType::Changed
    || (CurrentTransition.ChangeType == EStateTreeStateChangeType::Sustained
        && Task.bShouldStateChangeOnReselect);
```

**`ForceLeave`는 왜 안 겪었나** — `ShouldForceLeaveStore()`가 `IsForcedToLeave()`로 **스스로 false가 되기** 때문입니다. 그 함수 주석에 이미 같은 사고가 기록되어 있었습니다.

> 이게 없으면 Root의 On Tick 매 틱마다 확인해 손님이 퇴장 상태에 재진입하며 제자리에서 좌우로 움직인다.

그런데 제압은 `IsSubdued`가 **진입 조건이자 계속 참인 플래그**라 같은 방식을 쓸 수 없었습니다.

**채택한 해결:** 태스크 생성자에서 `bShouldStateChangeOnReselect = false`.

| | 채택: 생성자 플래그 | 대안: `EnterState`에서 `ChangeType` 가드 |
| :--- | :--- | :--- |
| `EnterState` 호출 | **최초 1회** | 매 프레임(안에서 되돌아 나옴) |
| `StopMovement` / `DisableMovement` | 1회 | 매 프레임 재호출 |
| 로그 도배 | 사라짐 | 본문 전체를 감싸지 않으면 그대로 |
| 나중에 연출을 넣을 때 | `ExitState`에도 자동 적용 | 새로 추가하는 사람이 **가드를 또 걸어야 함** |

엔진 헤더 주석이 이 플래그의 용도를 정확히 설명하고 있었습니다 — **"action type task(애니메이션 재생 등)는 true, state like task는 false"**. `Subdued`는 명백히 후자입니다.

> **에셋 재작업이 필요 없다는 점**도 중요했습니다. `bShouldStateChangeOnReselect`는 `UPROPERTY`가 아니라 **에셋에 직렬화되지 않고 로드 시 C++ 생성자 값이 그대로 적용**됩니다. 며칠 전 *"에디터에서 안 만진 필드는 직렬화되지 않는다"* 를 배웠는데, 이번엔 **애초에 직렬화 대상이 아닌 것**이 오히려 유리하게 작동했습니다.
>
> 배운 것: **"조건이 계속 참인 상태"는 상태 기계에서 특별 취급이 필요합니다.** 진입 조건이 스스로 꺼지는 설계(`ForceLeave`)와 계속 켜져 있는 설계(`Subdued`)는 **다른 방어가 필요합니다.**

### 6. 제압 자격 4단 게이트 — 각각이 막는 악용

`CanSubdueCustomer()`의 검사 4개는 전부 **다른 사고를 막습니다.**

| 게이트 | 막는 것 |
| :--- | :--- |
| `IsSubdued()` | 재타격 → **상품이 두 번 떨어져 재고가 늘어남** |
| `PlannedVillainAction != Shoplift` | 일반 손님을 때려서 **장바구니를 털어버리는** 상황 |
| **`bVillainActionDone == false`** | **아무나 때려서 빌런을 색출하는 플레이가 최적해가 되는 것** |
| `bCheckoutDone` | 정상 결제를 마치고 봉투 든 손님 보호 |

> 세 번째가 **게임 디자인 판단**이었습니다. 절도를 실행하기 **전** 빌런은 겉보기에 일반 손님과 구분이 안 됩니다. 이걸 허용하면 *"의심되면 일단 때려본다"* 가 지배 전략이 되어 게임이 망가집니다.
>
> 그래서 기본값은 **"이미 절도를 저질러 도주 중인 빌런"** 만 제압 가능이고, 바꿀 여지는 `bAllowSubdueBeforeShoplift` 스위치로 남겼습니다. **기본값으로 게임 디자인을 표현하고, 스위치로 실험 여지를 남기는** 형태입니다.

중복 피격은 **두 겹**으로 막았습니다. `CanSubdueCustomer`의 `IsSubdued()` 검사와, `MarkSubdued()`의 bool 반환. 한 프레임에 투사체 두 발이 동시에 맞는 경우까지 커버하기 위해서입니다.

### 7. 빨간 외곽선 — "만들지 않기로 한 것"이 더 많았다

절도를 시작한 손님에게 빨간 외곽선을 켰습니다. **신규 파일 0개.**

| 만들 뻔한 것 | 실제 판단 |
| :--- | :--- |
| `CSOutlineHighlightComponent` 공용 컴포넌트 | ❌ 프로젝트에 **외곽선 전용 공용 컴포넌트가 애초에 없음.** 진열대도 액터 멤버 함수 + 백업 TMap 방식 → **같은 형태를 따름** |
| 장바구니까지 빨갛게 하는 옵션 | ❌ `BasketActor`가 **Attach된 별개 액터**라 `GetComponents<>()`에 안 잡힘 → **추가 코드 없이 요구사항과 일치** |
| 머리 위 마커 / 화면 밖 화살표 / 미니맵 | ❌ 이번 범위 제외 |
| 10개 맵 수정 | ❌ 맵들이 머티리얼 **원본을 직접 참조** → 에셋 1개만 고치면 전부 반영 |

머티리얼은 기존 `TutorialMask`(스텐실 3) 체인을 **그대로 복제해 비교값만 4로** 바꿨습니다.

$$\text{VillainMask} = \mathrm{saturate}(1 - |\,\text{NeighborStencilMax} - 4\,|)$$

**표시 시점은 B안(절도 시작 후)** 을 골랐습니다. 스폰부터 빨갛게 하면 **정체가 처음부터 노출돼 감시 게임플레이가 사라집니다.** 절도 순간부터 켜면 *"도둑이야!"* 추격이 성립합니다.

그리고 이 머티리얼은 **`SceneDepth`와 비교하지 않아** 벽·진열대 뒤에서도 그려집니다. 원래는 투시 방지를 고려해야 하나 싶었는데, **추격이 목적이라 오히려 그대로가 맞았습니다.**

**남는 제약 2가지도 기록해뒀습니다.**

*   **스텐실 4번은 이제 예약됨** — 다른 기능이 4를 쓰면 색이 섞입니다. 스텐실 값은 **프로젝트 전역 자원**이라는 걸 처음 의식했습니다.
*   **같은 손님에 `UCSTutorialMarkerComponent`를 붙이면 안 됨** — 그 컴포넌트도 **자기 TMap에 원본 값을 백업**하기 때문에, 동시에 켜지면 끌 때 빨간 상태가 남습니다. **같은 자원을 각자 백업하는 두 시스템**은 공존할 수 없습니다.

### 8. 랙돌을 후순위로 미룬 판단

쓰러지는 연출은 **훅만 만들고 비웠습니다.**

```cpp
void BeginSubduedReaction(FVector ImpactDirection, float KnockbackStrength);
void EndSubduedReaction();
```

**지금 안 쓰는 인자를 미리 넣은 이유:** 나중에 랙돌을 붙일 때 `AddImpulse(ImpactDirection * KnockbackStrength)`로 **맞은 방향으로 넘어지게** 하려면 그 값이 필요합니다. 훅을 만들 때 인자를 빼두면 **나중에 시그니처를 다시 고쳐야** 합니다.

조사해보니 미루기를 잘했습니다.

*   PhysicsAsset 6개가 **전부 임포트 자동 생성 수준**입니다. 엘프는 바디가 8개뿐이고, 대부분 종족이 **발 바디가 없으며**, 드워프는 손가락에 바디가 있는 등 **좌우가 비대칭**입니다.
*   그대로 켜면 에러 없이 시뮬레이션은 되지만 **엘프가 통나무처럼 넘어집니다.**

> **그래서 순서를 이렇게 잡았습니다: 코드로 랙돌만 먼저 켜서 6종족을 실제로 쓰러뜨려 본다 → 그 화면을 보고 어느 에셋을 얼마나 손봐야 할지 정한다.**
>
> **그 화면을 보기 전에는 6개 에셋을 얼마나 고쳐야 하는지 정할 근거가 없습니다.** 추측으로 먼저 편집하면 다시 열게 됩니다. 며칠 전 *"관측 수단을 행동보다 먼저"* 와 같은 사고인데, 이번엔 **"판단 근거를 만드는 최소 작업을 먼저"** 라는 형태였습니다.

종족별 BP가 없다는 것도 확인했습니다(`BP_CSCustomer` 하나 + `DA_Visual_*` 6개로 메시만 교체). 그래서 **연출은 C++ 기본 구현에 두고, 종족마다 달라지는 값(`SubduedImpulseScale`)만 DataAsset**으로 빼기로 했습니다.

| 랙돌 / 사운드 | 2차 |

> **또 "구독자 0명"입니다.** 지난주에 *"파둔 구멍은 목록으로 남겨야 잊히지 않는다"* 고 적었는데, 이번엔 그 목록에 두 개를 더 얹은 셈입니다. 이번엔 문서 §5에 **미구현 목록을 명시적으로** 남겼습니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **되돌리기보다 조건 불성립** | 손실을 상쇄하는 대신 **손실 조건이 성립하지 않게** 만들면 취소 분기가 필요 없다 |
| **모든 경로가 지나는 지점에 집계를 둔다** | 소멸 경로가 4개인데 전부 `NotifyCustomerDespawned`를 지난다 → 누락이 구조적으로 불가능 |
| **아직 없는 기능이 지금 순서를 정한다** | 랙돌 때문에 "낙하는 연출보다 먼저"가 확정됐다. 이유를 주석으로 남긴다 |
| **타이머의 소유자는 상태 기계 안에** | 캐릭터에 걸면 StateTree가 모르고 계속 돌아 쓰러진 손님이 미끄러진다 |
| **"계속 참인 조건"은 특별 취급이 필요** | 스스로 꺼지는 조건과 계속 켜진 조건은 다른 방어가 필요하다 (`bShouldStateChangeOnReselect`) |
| **기본값으로 게임 디자인을 표현한다** | "때려서 색출"이 최적해가 되지 않게 기본은 도주 중만 제압. 스위치로 실험 여지만 남긴다 |
| **스텐실 값은 전역 자원** | 4번을 쓰는 순간 다른 기능이 못 쓴다. 같은 자원을 각자 백업하는 두 시스템은 공존 불가 |
| **판단 근거를 만드는 최소 작업을 먼저** | 6종족을 실제로 쓰러뜨려 보기 전에는 PhysicsAsset을 얼마나 고칠지 정할 수 없다 |
| **훅 인자는 지금 안 써도 미리 넣는다** | 나중에 시그니처를 고치면 붙이는 사람이 두 번 일한다 |
