## 장바구니 슬라임 추적 구현 

> 손님 손에 **Attach**되어 있던 장바구니가 **진열대를 파고드는 문제**가 있었습니다. 오프셋을 조정하는 대신 **아예 떼어내서 월드에 따로 서고 손님 발자국을 따라다니게** 만들었습니다.

| :--- | :--- | :--- |

### 2.  Attach를 떼어낸 이유 — 오프셋 조정으로는 못 고친다

먼저 **얼마나 파고드는지 수치로** 확인했습니다.

$$\text{캡슐 밖으로 삐져나오는 길이} \approx \text{앵커 거리} + \text{메시 반폭} - \text{캡슐 반경} = 55 - 31.9s$$

| 종족 | `CharacterScale` | 삐져나오는 길이 |
| :--- | ---: | ---: |
| 고블린 | 0.5 | **약 39 cm** |
| 오크 | 1.0 | 약 23 cm |

> **장바구니 크기는 종족과 무관하게 같은데 몸집만 달라집니다.** 그래서 **작은 종족일수록 더 많이 파고듭니다.** 캡슐은 진열대에 막히지만 **장바구니는 충돌이 없어서** 그대로 뚫고 들어갑니다.
>
> 앵커 위치를 아무리 조정해도 **"몸 밖에 붙어 있다"** 는 구조 자체가 원인이라 해결되지 않습니다.

**그리고 해결의 근거도 수치에서 나왔습니다.**

> NavMesh는 `AgentRadius`(75)만큼 장애물에서 깎여 있습니다. 장바구니 반폭이 **약 55**라, **중심을 NavMesh 위에 두기만 하면** 이론상 진열대 영역과 겹치지 않습니다.
>
> **"떼어낸다"가 답이 될 수 있었던 건 이 부등식 때문**이었습니다. `BasketRadius(50) < AgentRadius(75)`를 유지하는 한 NavMesh 제한만으로 관통이 막힙니다.

### 3.  생성 시점을 `BeginPlay`에서 입장 확정으로 옮긴 이유

기존에는 **행인을 포함한 모든 손님**이 태어나자마자 장바구니를 들고 있었습니다.

| 안 | 트리거 | 판단 |
| :--- | :--- | :--- |
| **A ✅** | `MarkEnteredStore()` 호출 순간 | **확정 지점이 하나라 빠질 경로가 없음.** 레벨 배치에 영향 없음 |
| B | 실내 영역에 처음 들어온 순간 | 실내 영역 액터가 없는 맵은 대체 경로 필요 + **매 틱 영역 검사** |
| C | 첫 상품을 담을 때 | 구현은 제일 쉽지만 **빈손으로 다니다 갑자기 생김** |

A를 고른 결정적 이유는 **입장 확정 지점이 코드에 하나뿐**이라는 것이었습니다. **거기만 잡으면 새 입장 경로가 생겨도 자동으로 따라옵니다.**

**숨기기가 아니라 아예 안 만들기를 택한 것**도 이유가 있습니다.

> 입장 확률 판정 때문에 **그냥 지나가는 손님 비율이 높습니다.** 숨긴 채 들고만 다니면 **매 틱 추적 계산이 헛돕니다.** 안 만들면 그 비용이 0입니다.

**안전망은 따로 걸었습니다.** 상품을 담는 함수 첫 줄에서도 생성을 확인합니다.

> **앞으로 누가 입장 확정을 거치지 않는 경로를 만들더라도 상품 표시가 사라지지 않게** 하려는 것입니다. 여러 번 불러도 안전하도록 만들어서 비용이 거의 없습니다.

### 4. 상태 컴포넌트는 "방송만" 하게 했다

입장 확정을 알리는 델리게이트를 상태 컴포넌트에 추가했는데, **거기서 장바구니를 만들지 않습니다.**

```
상태 컴포넌트 : bHasEnteredStore가 false → true로 바뀔 때만 Broadcast
손님 캐릭터   : 구독 → EnsureBasketSpawned()
```

> **역할을 섞지 않으려고** 나눴습니다. 상태 컴포넌트가 액터를 스폰하기 시작하면 *"상태를 담는 그릇"* 이라는 정의가 무너집니다.
>
> 그리고 **나중에 입장 효과음이나 통계 같은 다른 구독자가 붙어도 되는 구조**가 됩니다. 만약 컴포넌트가 직접 스폰했다면 두 번째 소비자가 생길 때 다시 델리게이트로 바꿔야 합니다.

`MarkEnteredStore()`는 **이미 입장 상태면 즉시 리턴**하게 해서 중복 방송을 막았습니다. 며칠 전 다른 시스템에서 *"경로를 늘리면 멱등성이 필요해진다"* 를 배웠는데, 여기서는 **방송 자체를 한 번으로 못 박는** 방식으로 처리했습니다.

### 5. AIController도 물리도 쓰지 않은 이유

추적 방식으로 네 가지를 놓고 비교했습니다.

| 안 | 관통 방지 | 비용 / 문제 | 판단 |
| :--- | :--- | :--- | :---: |
| Attach + 오프셋 조정 | **불가** (구조가 원인) | 최저 | ✗ |
| Pawn + `MoveToActor` | NavMesh 경로라 잘 막힘 | 슬라임마다 **Controller · CharacterMovement · 경로 탐색**. 멈춤·재경로 판단이 잦아 **끊기는 느낌** | 과함 |
| 물리 + 스프링 | 설정에 따라 다름 | **떨림·밀림·튕김 튜닝 지옥** | ✗ |
| **키네마틱 벡터 추적 + NavMesh 제한** ✅ | NavMesh 침식으로 막고 스윕으로 보강 | 틱마다 레이캐스트 1~2회 | ✓ |

> 두 번째가 *"제대로 된"* 방법처럼 보였는데, **슬라임은 경로를 계획할 필요가 없습니다.** 손님이 이미 지나간 길을 따라가기만 하면 됩니다.
>
> 그리고 `MoveToActor`는 **목표가 계속 움직이면 재경로 판단이 잦아 멈칫거립니다.** 펫처럼 부드럽게 따라와야 하는데 오히려 부자연스러워집니다. **"손님이 지나간 곳은 이미 갈 수 있는 곳"** 이라는 사실을 쓰면 경로 탐색 자체가 불필요합니다.

### 6. 레퍼런스 알고리즘에서 버린 것들

2007년에 쓰인 **2D 추적 알고리즘 글**을 참고했는데, **개념만 가져오고 구현은 전부 대체**했습니다.

| 원문 (2007, 2D) | 이번 구현 |
| :--- | :--- |
| `sin`/`cos` **룩업 테이블 360칸** | **사용 안 함** — 지금은 삼각함수가 비싸지 않음 |
| `atan2(abs(..))` + **사분면 보정** | **사용 안 함** — 벡터로 바로 처리 |
| `Px += sin * 2` (**프레임당 2픽셀**) | `Velocity × DeltaTime` (**초 단위**) |
| 매 프레임 정확히 목표를 향함 | **도착 감속 + 가속 보간 + 정지 반경** |
| **장애물 고려 없음** | **발자국 경로 + NavMesh 레이캐스트 제한** |

특히 **사분면 보정을 버린 이유**가 명확했습니다.

> 원문이 사분면 분기를 넣은 건 `atan2`에 **절댓값을 씌워서** 결과가 0~90도밖에 안 나오기 때문입니다. **절댓값을 안 씌우면 처음부터 -180~180이 나오고**, 벡터로 가면 **각도가 아예 등장하지 않습니다.**
>
> 원문에는 **실제 버그**도 있었습니다. `270 + temp` 경로에서 인덱스 **360**이 나올 수 있는데 배열 크기가 360입니다. 옮겨 썼다면 그대로 가져왔을 겁니다.

**프레임 의존성**도 그대로 두면 안 되는 부분이었습니다. `× 2`는 *"프레임당 2픽셀"* 이라 **프레임레이트에 따라 추적 속도가 달라집니다.**

> **오래된 레퍼런스는 "왜 이렇게 동작하는가"를 이해하는 용도**로 읽고, 구현은 현재 엔진 기준으로 다시 쓰는 게 맞았습니다. 개념(방향 × 속도 × 시간)은 그대로지만 **코드는 한 줄도 남지 않았습니다.**

### 7. 발자국 따라가기 — 그리고 멈췄을 때의 Park 모드

목표 지점을 **두 모드로** 나눴습니다.

| 모드 | 조건 | 목표 |
| :--- | :--- | :--- |
| **Trail** | 손님이 걷는 중 | 발자국을 **최신부터 거꾸로** 따라가 경로 길이 145 cm 지점 |
| **Park** | 손님이 0.25초 이상 멈춤 | 손님 **뒤 → 대각선 → 옆** 순서로 검사해 처음 통과한 자리 |

**왜 직선 거리가 아니라 "발자국 경로 길이"인가**

> 직선으로 145 cm 뒤를 잡으면 **손님이 모서리를 돌 때 슬라임이 벽을 뚫고 질러갑니다.** 발자국 경로를 따라가면 **손님이 실제로 걸은 길**을 그대로 밟습니다.
>
> 이게 5번에서 말한 *"손님이 지나간 곳은 이미 갈 수 있는 곳"* 을 쓰는 방식입니다.

**Park 후보 순서를 뒤부터 검사하는 이유**도 있습니다. 손님이 진열대를 볼 때 **슬라임이 앞을 막으면 안 됩니다.** 뒤가 막혔을 때만 옆으로 갑니다. 5개 후보가 전부 실패하면 손님 발 위치로 보냅니다.

발자국 간격과 개수도 **부등식으로 잡았습니다.**

```
간격(20) × 개수(64) = 약 12.8 m  >  추적 거리(145 cm)
```

> **간격 × 개수가 추적 거리보다 충분히 길어야** Trail 모드가 유지됩니다. 짧으면 발자국이 모자라 계속 Park 모드로 떨어집니다.

### 8. NavMesh 경계에서 "멈추던" 것을 "미끄러지게" 고쳤다

처음 구현에서는 NavMesh 경계에 막히면 **그 자리에 섰습니다.** 그래서 **진열대 모서리에서 슬라임이 멈칫거렸습니다.**

```cpp
// 수정 전 — 경계 2cm 앞에서 정지, 미끄러지기 없음
To = From + Direction * AllowedLength;
```

> 경계에서 2 cm 떨어진 상태로 **조금이라도 바깥을 향하면** 허용 이동량이 0이 됩니다. **경계와 거의 평행하게 가도** 한 프레임 이동량(약 6 cm) 안에서 경계를 넘으면 막힘 처리됐습니다.

**고치려면 경계 법선이 필요했는데, 쓰고 있던 API가 법선을 안 줬습니다.**

| API | 주는 것 |
| :--- | :--- |
| `NavigationSystemV1::NavigationRaycast` | 충돌 **지점만** |
| **`ARecastNavMesh::NavMeshRaycast`** | 충돌 지점 + **`HitNormal`** |

그래서 Recast 전용 정적 함수로 바꾸고, **경계 법선을 이용해 남은 이동량을 경계 방향으로 미끄러뜨렸습니다.** 최대 2회까지 반복합니다(복잡한 모서리 대응).

> **성능도 확인했습니다.** 막히지 않은 평소 프레임은 검사 횟수가 그대로이고, **막힌 프레임에만** 레이캐스트가 최대 2회 늘어납니다. 반대로 **끼임 순간이동(Park 자리 탐색 최대 16회)이 줄어들어** 전체 비용은 같거나 줄어듭니다.
>
> **"비용이 늘어나는 경로"와 "줄어드는 경로"를 같이 세어본 게** 판단에 도움이 됐습니다.

Recast가 아닌 NavMesh면 기존 API로 폴백하게 두었습니다.

### 9. 막힌 프레임의 속도 정리와 끼임 판정 구간화

미끄러지기만으로는 부족한 게 둘 더 있었습니다.

**① 막혀도 속도가 벽 쪽을 향한 채 유지됐다**

> 목표가 모서리를 돌아 방향이 바뀌어도, **가속도 제한(1200 cm/s²) 때문에 벽 쪽 속도를 빼는 데 0.3~0.6초**가 걸립니다. 그동안 계속 경계를 밀어붙입니다.

→ **막힌 프레임에는 실제로 움직인 만큼만 속도로 남기게** 했습니다. 원래 이동량의 90% 미만만 움직였으면 속도를 실제 이동량으로 줄입니다.

**② 끼임 판정이 매 프레임 누적이라 너무 예민했다**

```
수정 전: "이동량의 50% 미만" → 매 프레임 누적 → 경계를 스치기만 해도 1초 뒤 순간이동
수정 후: 0.25초 구간 동안 실제 이동 거리를 보고, 목표가 60cm 이상 멀 때만 끼임
```

> **"목표가 충분히 멀 때만"** 이라는 조건이 핵심이었습니다. 슬라임이 **도착해서 멈춰 있거나, 계산 줄에서 대기 중일 때**는 안 움직이는 게 정상인데, 그걸 끼임으로 보면 멀쩡히 서 있다가 순간이동합니다.
>
> **"안 움직인다"와 "못 움직인다"를 구분하는 게** 이 판정의 전부였습니다.

세 수정(A 미끄러지기 / B 속도 정리 / C 구간 판정)을 **한 묶음으로** 넣은 이유도 있습니다. **A만 넣으면 B 때문에 여전히 벽을 밀고, C 없이 넣으면 미끄러지는 중에도 끼임으로 잡힙니다.**

### 10. 순간이동을 "복구 장치"로만 남겼다

두 조건에서 손님 옆 자리로 순간이동합니다.

| 사유 | 조건 | 의미 |
| :--- | :--- | :--- |
| `TooFar` | 손님과 수평 거리 > 800 cm | 슬라임이 너무 느리거나 **손님이 순간이동함** |
| `Stuck` | 끼임 구간 > 1.5초 | **진열대 반대편에 갇힘** / NavMesh 끊김 |

> 순간이동은 **보기 좋은 동작이 아닙니다.** 그래서 8·9장의 수정으로 **"정말 못 가는 경우"에만** 발생하도록 먼저 줄이고, 그 뒤에 남는 것만 복구하게 했습니다.
>
> **사유를 문자열로 남겨 로그에 찍게** 한 것도 그래서입니다. 순간이동이 잦다면 **`Stuck`인지 `TooFar`인지에 따라 손볼 곳이 완전히 다릅니다.**

계산을 **취소**했을 때도 순간이동을 겁니다. 숨어 있던 자리에서 **그대로 끌려오면 이상하기 때문**입니다.

### 11. 디버그를 색으로 구분했다

콘솔 CVar 하나로 켜고, **표시마다 다른 색**을 줬습니다.

| 색 | 의미 | 이렇게 보이면 |
| :--- | :--- | :--- |
| 회색 점들 | 손님 발자국 | **끊겨 있으면** 손님이 순간이동한 것 |
| 초록 구 | 이번 프레임 목표점 | 슬라임이 향하는 곳 |
| **청록 원** | 슬라임 — **Trail 모드** | 정상 걷기 추적 |
| **노랑 원** | 슬라임 — **Park 모드** | 손님 멈춤 / 발자국 부족 |
| 파랑 / 빨강 구 | Park 후보 **통과 / 실패** | **전부 빨강이면** 둘 자리가 없음 |
| 주황 구 + 선 | NavMesh 경계 막힘 지점 + **법선** | 선이 경계에 수직이고 안쪽을 향해야 정상 |

> **모드를 색으로 나눈 게 가장 유용했습니다.** 청록/노랑만 보면 *"지금 왜 옆에 서 있는지"* 가 바로 보입니다.
>
> 그리고 **경계 법선을 선으로 그린 것**이 8장 구현을 검증하는 수단이 됐습니다. **선 방향이 이상하면 미끄러지기가 엉뚱한 쪽으로 갑니다.**

CVar는 `ECVF_Cheat`이고 그리기는 `#if ENABLE_DRAW_DEBUG` 안이라 **Shipping에는 안 들어갑니다.**

### 12. 추후 작업 — 계단에서 뜨거나 파묻히는 문제 (설계만)

현재 코드는 슬라임 높이를 **손님 발 높이로 복사**합니다.

```cpp
NewLocation.Z = Foot.Z;   // 계단 문제의 원인
```

입구 계단을 실측해보니 **한 단이 37.4 cm, 7단**입니다. 손님과 슬라임이 **다른 단에 있으면 그 차이만큼 뜨거나 파묻힙니다.**

수정 설계를 A~E로 정리하고 **A+B+C+D를 한 묶음**으로 잡았습니다.

| # | 내용 |
| :---: | :--- |
| A | 슬라임 **자기 발밑을 레이캐스트**해서 바닥 높이 사용 |
| B | 바닥 높이(물리)와 보이는 높이(보간)를 분리 + **진행 방향 앞을 미리 봐서** 오르막 선반영 |
| C | A를 넣으면 **스윕 구체가 계단 챌면에 걸리므로** 스윕 높이를 올림 |
| D | 순간이동 시에도 새 자리에서 바닥을 찾아 **보간 없이 즉시** 맞춤 |

> **묶어야 하는 이유가 명확했습니다.** *"A만 넣으면 C 때문에 계단 앞에서 막히고, B 없이 넣으면 계단식으로 뚝뚝 튑니다."* 8장의 A+B+C와 같은 구조인데, **부분 적용이 오히려 나빠지는 경우**라 한 묶음으로 명시했습니다.

E(NavMesh 스텝 높이)는 **조건부**로 남겼습니다. 엔진 기본 스텝 높이 **35 cm < 계단 한 단 37.4 cm**라 **계단 NavMesh가 끊겼을 가능성**이 있는데, **`P`로 확인한 뒤 끊겼을 때만** 프로젝트 설정을 바꾸기로 했습니다.

> **설정 변경은 영향 범위가 넓어서** 확인 없이 건드리지 않기로 했습니다. 손님·행인 이동에도 같이 영향을 줍니다.
