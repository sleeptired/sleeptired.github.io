## 상점 레벨·피크타임 분석과 손님 유입량 연동

> *"레벨이 오르면 손님이 더 많이 왔으면 좋겠다"* 는 요구에서 시작했는데, **먼저 기존 시스템을 읽는 데 시간의 절반을 썼습니다.** 읽어보니 손댈 필요가 없는 것들이 많았고, 대신 **아무도 쓰지 않는 코드**가 여럿 나왔습니다.

---

### 1. 오늘의 흐름 — 분석이 먼저였다

```
① 성장(EXP·레벨) / 게임 시간 / 피크타임 데이터를 전수 분석  ← 파일 무수정
② 그 과정에서 "죽어 있던 것" 5가지 발견
③ 그중 피크타임을 실제로 동작하게 만들면서 레벨 연동까지 구현
```

분석은 **에디터를 켜지 않고** C++ 정독 + `.uasset` **바이너리 직접 파싱**으로 했습니다. 에셋을 열면 저장 여부와 무관하게 변경 표시가 붙을 수 있어서, **읽기만 하는 단계에서는 파일을 건드리지 않는 쪽**을 택했습니다.

---

### 2. 성장 시스템 — 읽어보고 알게 된 것

| 질문 | 답 |
| :--- | :--- |
| EXP는 어디서 오르나 | **결제 완료 단 한 곳** (`RecordCheckoutTransaction`) |
| 얼마나 | **판매 수량 × 500** — **금액이 아니라 개수** |
| 만렙 | 10레벨 / 누적 1,125,000 EXP = **상품 2,250개 판매** |
| 레벨은 내려가나 | 아니오. `FMath::Max(Current, Calculated)` |

*   폐기·정산·발주·만족도 **어디서도 EXP가 오르지 않습니다.** 즉 현재 성장 곡선은 "얼마를 벌었나"가 아니라 **"몇 개를 팔았나"** 입니다. 1G짜리와 1000G짜리가 같은 500 EXP입니다.
*   레벨 구간 증가분이 **25,000씩 등차**(25k → 50k → … → 225k)로 늘어납니다.

> **가장 뜻밖이었던 것:** 레벨 테이블이 `DA_StoreProgression`에 있는 줄 알았는데, **C++ 생성자 하드코딩**이었습니다. DA를 파싱해보니 **직렬화된 오버라이드가 `MaximumReputationScore` 하나뿐**이었습니다.
>
> DataAsset이 존재한다고 해서 값이 거기 있는 게 아닙니다. **에디터에서 한 번도 안 만진 필드는 직렬화되지 않아 생성자 값이 그대로 쓰입니다.** "데이터로 뺐다"와 "데이터로 조정 가능하다"는 다른 얘기였습니다.

### 3. 시간 체계 — 기준이 세 갈래로 섞여 있다

| 항목 | 값 |
| :--- | :--- |
| 시간 변수 | `CurrentGameMinutes` = 자정 00:00부터의 경과 **분** (0~1560) |
| 배속 | C++ 기본 1.5 → **`BP_CSStoreGameMode` CDO가 10.0으로 오버라이드** |
| 하루(09:00~24:00, 900분) | **실제 90초** |
| 틱 구조 | 0.1초 반복 타이머 × `10.0 × 0.1` = **1틱 = 게임 1분** |

**그런데 시간 기준이 통일돼 있지 않았습니다.**

| 기준 | 쓰는 곳 |
| :--- | :--- |
| **게임 분** | 태양 회전, 야간 조명, 스케줄 이벤트, 거래 타임스탬프 |
| **실제 초** | 손님 스폰 타이머, **상품 신선도 감소** |
| **영업일** | 발주 배송 |

> 신선도와 손님 스폰이 **실제 초** 기준이라 **배속(10.0)을 바꿔도 이 둘만 영향을 안 받습니다.** 배속을 조정해 밸런스를 잡으려 하면 다른 시스템만 움직이고 이 둘은 제자리에 남습니다. 지금 당장 문제는 아니지만 **밸런싱 단계에서 반드시 터질 자리**라 기록해뒀습니다.

### 4. 분석이 찾아낸 "죽어 있던 것" 5가지

| # | 항목 | 상태 |
| :---: | :--- | :--- |
| 1 | `OnScheduleEventFired` | **구독자 0명** — 피크타임 이벤트가 발행만 되고 아무 일도 안 일어남 |
| 2 | `DeliveryArrival`(08:00) | **구조적으로 절대 발화 불가** |
| 3 | `FCSStoreScheduleEventData::EventType` | 어디서도 **읽히지 않는 필드** |
| 4 | `DT_StorePhase` | 읽는 함수는 있는데 **그 함수를 부르는 곳이 없음** |
| 5 | 상품 `StoreLevelUnlockCondition` | **선언만 있고 검사 코드가 없음** |

**②가 특히 흥미로웠습니다.** 발화 조건은 `이전시각 < 트리거 <= 현재시각`인데,

```
StartStoreFlow()  : 시각 480(08:00)으로 세팅하되 시계는 정지 상태로 시작
                    → UpdateGameClock()이 즉시 리턴 → 08:00~09:00 구간은 흐르지 않음
개점 상호작용     : 시각이 540으로 점프 + CheckScheduleEvents(539.99, 540)
                    → 480 행은 539.99 < 480 이 거짓 → 건너뜀
```

**시간이 흐르지 않는 구간에 트리거를 걸어둔 것**이라 코드상 절대 도달하지 않습니다. 데이터 테이블에 행이 멀쩡히 있어서 **"설정은 했는데 왜 안 뜨지"** 로 보였을 상황입니다.

> 며칠 전 *"델리게이트는 구독자 0명인 채로 먼저 파둬도 된다"* 고 정리했는데, ①은 그 상태가 **오래 방치된 결과**였습니다. 미리 파두는 건 여전히 맞지만, **"파둔 구멍" 목록을 어딘가 남겨두지 않으면 잊힌다**는 반대편 교훈을 같이 얻었습니다.

### 5.  구현 — 손잡이가 두 개여야 하는 이유

레벨과 피크가 **생성 간격**과 **동시 상한** 양쪽에 걸립니다. 처음엔 간격만 조정하면 될 줄 알았는데, 코드를 보니 안 됩니다.

```cpp
if (SpawnedCustomers.Num() >= GetCurrentMaxAlive()) return;
```

**`TrySpawnCustomer()`는 상한에 닿으면 즉시 리턴합니다.** 간격을 25초 → 4초로 줄여도 **상한이 2명이면 거기서 막힙니다.** 타이머는 부지런히 도는데 매번 이 줄에서 되돌아갑니다.

```cpp
// 전 — 에디터에 박힌 고정값
if (SpawnedCustomers.Num() >= MaxAliveCustomers) return;

// 후 — 현재 레벨/피크에 해당하는 상한
if (SpawnedCustomers.Num() >= GetCurrentMaxAlive()) return;
```

> **이 한 줄이 데이터 테이블의 "동시 상한" 열 전체를 작동시킵니다.** 빠뜨리면 값을 아무리 넣어도 전부 무시되는데, **에러도 로그도 안 납니다.** 유량 제어에는 대개 **속도와 총량 두 개의 손잡이**가 있고, 한쪽만 돌리면 다른 쪽이 병목이 된다는 걸 배웠습니다.

레벨별 기본값 (피크는 간격 `÷1.8`, 상한 `×1.8`):

| Lv | 평시 | 피크 |
| :---: | :--- | :--- |
| 1 | 25.0초 / 2명 | 13.9초 / 4명 |
| 5 | 14.0초 / 5명 | 7.8초 / 9명 |
| 10 | 4.0초 / 10명 | 2.2초 / 18명 |

### 6. 데이터 에셋 설계에서 판단한 것

**① `EditFixedSize`** — 에디터에서 **값은 고치되 원소를 추가·삭제할 수 없게** 합니다. 생성자가 10칸을 채우므로 배열 크기가 어긋날 일이 없습니다. 기존 `UCSStoreProgressionDataAsset`의 `RequiredTotalExperience`와 같은 패턴이라 규칙을 맞췄습니다.

**② 배열 해석을 데이터 에셋 안에 뒀습니다.** 스포너가 직접 인덱싱하지 않고 `GetSpawnIntervalSeconds(Level, bPeak)` 같은 함수로만 접근합니다.

> **"인덱스 + 1 = 레벨"과 "피크는 나누고 곱한다"는 이 데이터의 규칙이지 스포너의 사정이 아닙니다.** 기존 `UCSStoreProgressionDataAsset`도 배열은 public이지만 해석은 전부 함수로 노출하고 `ACSStoreGameState`가 직접 인덱싱하지 않습니다. 같은 폴더의 같은 종류 에셋이라 **관례를 따르는 쪽**을 택했습니다.

**③  레벨별 값을 선형에 가깝게 둬야 하는 이유**

여기서 두 곡선이 **곱해진다**는 걸 뒤늦게 깨달았습니다.

```
레벨업 필요 EXP : 25,000 → 225,000   (9배 증가 — 감속 역할)
Lv10 손님 유입  : Lv1의 몇 배?
```

손님 수를 Lv10에서 Lv1의 **20배**로 키우면, 필요 EXP가 9배 늘어나는 감속을 **유입 증가가 추월**해서 **후반 레벨업이 오히려 빨라지는 눈덩이 현상**이 생깁니다. 그래서 25초 → 4초(약 6배), 2명 → 10명(5배) 정도로 눌러뒀습니다.

> **밸런스 곡선은 혼자 있는 게 아니라 다른 곡선과 곱해집니다.** 유입량만 보고 "레벨이 오르면 확 늘어야 재밌지"라고 정했으면 진행 곡선이 뒤집혔을 겁니다. 값을 정하기 전에 **이 값이 무엇과 곱해지는지** 먼저 봐야 했습니다.
