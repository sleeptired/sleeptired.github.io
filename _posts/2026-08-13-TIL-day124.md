## 절도 빌런 구현 — 결정을 내리자 구조가 줄어들었다

> 어제 *"빌런은 스폰 시 확정인가, 런타임에 변질되는가"* 를 고민했습니다. 오늘 **스폰 확정형으로 결정**하고, 범위를 **절도 하나**로 줄여 끝까지 구현했습니다. 결정을 내린 뒤에 설계가 오히려 **단순해진** 게 오늘의 가장 큰 수확입니다.

---

### 1. 어제의 질문에 답하기 — 스폰 확정형

**결정:** 스폰 시점에 확률을 한 번 굴려 확정. 손님 하나의 빌런 여부는 평생 안 바뀝니다.

그리고 이 결정이 **어제 계획했던 파일 4개를 없앴습니다.**

| | 어제 계획 | 오늘 실제 |
| :--- | :--- | :--- |
| 전용 컴포넌트 | `CSCustomerVillainComponent` 신규 | ❌ **불필요** → 기존 `CSCustomerStateComponent`에 필드 2개 |
| 전용 DataAsset | `CSVillainProfileDataAsset` 신규 | ❌ **불필요** → 기존 아키타입 DA에 필드 2개 |
| 스포너의 프로필 맵 | `TMap<AgeBracket, Profile>` | ❌ **불필요** → 아키타입이 이미 연령대별 |
| BP 작업 | `BP_CSCustomer`에 컴포넌트 추가 | ❌ **불필요** |
| 신규 파일 | 4개 | **1개** (`CSVillainTypes.h`) + 디버그용 2개 |

**왜 이렇게 줄었나**

*   **스폰 확정형이면 굴림이 스포너에서 한 번에 끝납니다.** 손님이 들고 있어야 하는 건 *"무슨 짓을 할 예정인가"* 값 하나뿐이라 전용 컴포넌트를 만들 이유가 없습니다.
*   그 값은 `bCheckoutDone`, `bCheckoutAbandoned`와 **성격이 완전히 같은 "이번 방문의 개인 플래그"** 입니다. → `CSCustomerStateComponent`가 정확한 자리.
*   `CustomerState`는 `ACSCustomerCharacter` 생성자에서 `CreateDefaultSubobject`로 만들어지므로 **BP를 열 필요조차 없습니다.**
*   빌런 수치는 연령대별인데, **연령대별 카드는 이미 아키타입 DA**이고 6종족 에셋도 이미 있습니다.

> **런타임 변질형을 택했다면 저 파일들이 다 필요했습니다.** 손님이 스스로 굴려야 하니 전용 컴포넌트에 스트림·기회·래치를 들고 있어야 하고, 프로필도 따로 관리해야 합니다.
>
> **결정을 미루면 두 경우를 다 지원하는 구조가 필요하고, 결정을 내리면 한쪽에 필요한 것만 만들면 됩니다.** 어제는 "결정을 미룰 수 있게 만든 게 성과"라고 적었는데, 오늘은 반대로 **결정이 곧 단순화**라는 걸 배웠습니다. 미룰 수 있게 해두는 건 좋지만, 미룬 상태로 구현에 들어가면 필요 없는 걸 만들게 됩니다.

### 2. 범위를 절도 하나로 줄였다

금지 물품 구매(미성년 주류)는 **이번 범위에서 제외**했습니다.

```
스폰      : 확률 굴림 → 이 손님은 절도범
Shopping  : 평범하게 진열대를 돌며 물건을 담음   ← 일반 손님과 100% 동일
쇼핑 종료 : 계산대로 안 가고 Shoplift 상태 진입 → [빌런 발생] (주황)
퇴장      : 출구 도착 → 사라짐              → [빌런 도망침] (빨강)
```

> **절도 하나가 끝까지 도는 것을 먼저 확인하고, 다음 행동은 같은 틀에 하나씩 얹습니다.** 두 종류를 동시에 만들면 *"안 되는 게 절도 문제인지 주류 문제인지"* 구분이 안 됩니다.

`ECSVillainAction`에는 미구현 값(`UnderageAlcohol`, `MessUpShelf`, `QueueCut`)도 **자리만 표시해서** 넣어뒀습니다. 다만 이게 함정이 되어서, `VillainActionWeights`에 미구현 값을 넣으면 **빌런이 되고도 아무 일이 안 생깁니다.** 함정 표에 적어뒀습니다.

**절도범도 평범하게 쇼핑한다**는 게 핵심입니다. 물건을 담은 뒤 계산대를 지나쳐 나가는 그림이어야 합니다.

### 3. 배정 통로를 하나로 — 3중 가드

```cpp
bool UCSCustomerStateComponent::AssignVillainAction(ECSVillainAction NewAction)
{
    if (NewAction == ECSVillainAction::None)      { return false; }  // ① 해제 불가
    if (bVillainActionDone)                       { return false; }  // ② 이미 저질렀음
    if (PlannedVillainAction != ECSVillainAction::None) { return false; }  // ③ 덮어쓰기 금지

    PlannedVillainAction = NewAction;
    return true;
}
```

| 가드 | 막는 것 |
| :--- | :--- |
| ① **None 대입 거부** | *"빌런이었는데 조건이 false가 되어 트리가 이상하게 흐르는"* 경로 자체를 없앰 |
| ② 이미 저지른 손님 | 한 방문 1회 원칙 |
| ③ 이미 배정된 손님 | 스폰 때 1회 호출이 전제지만, **실수로 두 번 불려도 결과가 안 흔들리게** |

> 필드를 `public`으로 열어두고도 *"직접 대입하지 말고 이 함수를 쓰라"* 고 주석으로 못 박았습니다. **배정 규칙을 한 곳에만 두는 게 목적**이라, 규칙이 여러 곳에 흩어지는 걸 막는 쪽이 접근 제한보다 중요했습니다.

`bVillainActionDone`이 없으면 Root를 재선택할 때마다 빌런 상태가 계속 참이라 **손님이 그 상태에 갇힙니다.** `bCheckoutAbandoned`가 하던 역할과 정확히 같습니다.

### 4. ⭐ 시드를 재사용하면 안 되는 이유

```
마스터 스트림 (ACSCustomerSpawner)
   ├─ 종족 배정 굴림
   ├─ 손님별 파생 시드 발급 ──▶ 개인 스트림 (PurchaseDecisionComponent)
   └─ 빌런 판정용 시드 발급 ──▶ 지역 스트림 (TrySpawnCustomer 안에서만 존재)
```

**`CustomerSeed`를 그대로 재사용하면 안 됩니다.**

> 같은 시드로 만든 두 스트림은 **첫 번째 난수가 완전히 같은 값**입니다. 그러면 *"예산이 낮게 뽑힌 손님이 빌런이 되기 쉬움"* 같은 **의도치 않은 상관관계가 데이터에 생깁니다.** 손님마다 개인 스트림을 나눈 것과 같은 이유로, **독립이어야 할 굴림은 시드도 독립**이어야 합니다.

시드는 눈에 안 보이는 상관관계를 만들 수 있다는 걸 이번에 처음 의식했습니다. 밸런싱 로그를 볼 때 *"왜 가난한 손님만 훔치지?"* 같은 현상이 나오면 원인을 못 찾았을 것 같습니다.

**스트림을 손님에게 심지 않고 지역 변수로 둔 것**도 의도적입니다.

```cpp
const int32 VillainSeed = MasterStream.RandHelper(MAX_int32);
FRandomStream VillainStream(VillainSeed);   // 이 함수 안에서만 존재
```

스폰 확정형이라 굴림이 여기서 끝나므로, **"스폰 때만 쓰는 통"이라는 게 코드 모양으로 드러납니다.** 나중에 런타임 굴림이 필요해지면 그때 컴포넌트로 옮기면 됩니다.

**`RollVillainAction`이 스트림을 인자로 받는 이유**도 같은 맥락입니다. *어느 통에서 뽑을지*는 이 함수가 정하지 않습니다. **시드 발급 정책은 호출부에 모아둬야 재현성 구조가 한곳에 보입니다.**

가중 랜덤은 기존 `PickArchetypeBySpawnWeight`와 **완전히 같은 누적 가중 방식**으로 맞췄고, 컨테이너는 **`TArray`를 유지**했습니다. `TMap`으로 바꾸면 순회 순서가 흔들려 **시드를 고정해도 결과가 달라집니다.**

### 5. ⭐ 델리게이트를 처음부터 2개로 나눴다

절도를 방송 하나로 처리하면 **나중에 "빌런 검거" 기능이 들어올 때 반드시 깨집니다.**

```
절도 시작 → 손실 500G 방송 → 통계에 -500 박힘
플레이어가 검거 → 물건 회수
                → 통계는 여전히 -500  ❌
```

| 방송 | 시점 | 의미 | 구독 대상 |
| :--- | :--- | :--- | :--- |
| `OnShopliftStarted` | 도주 시작 | **경고. 손실 확정 아님** | 연출 / UI / 디버그 |
| `OnShopliftEscaped` | 퇴장 직전 | **확정 손실** | 통계, 평판 |

인자 이름을 **`AtRiskGold`** 와 `LostGold`로 다르게 둔 것도 같은 이유입니다. 누가 실수로 `Started`를 구독해 매출을 깎지 않도록 **이름으로 알립니다.**

> 검거 기능은 아직 안 만들지만 **"손실 확정 시점"을 지금 나눠둡니다.** 방송을 나중에 **추가**하는 건 기존 구독자를 깨지 않지만, **하나였던 방송을 둘로 쪼개는 건 구독자를 전부 고쳐야 합니다.** 무엇을 미루고 무엇을 지금 해야 하는지의 기준이 여기서 나왔습니다.

같은 판단으로 `CommitShoplift`에서 **`ClearSelectItems()`를 부르지 않습니다.** 상품을 들고 나가는 게 이 기능의 목적이고, 검거를 붙일 때 되돌려놓으려면 **원본 정보가 남아 있어야** 합니다. 덕분에 나중에 회수가 붙으면 `ReportShopliftEscaped`의 `SelectProducts.Num() == 0` 검사가 **검거된 절도범을 자동으로 걸러줍니다** — 별도 플래그가 필요 없습니다.

### 6. ⭐ 트리 배치가 조건을 대신한다

`Shoplift` 상태를 **`Shopping`과 `Checkout` 사이**에 넣었습니다.

```
Root (Selector)
├─ Shopping     [기존 조건 그대로 — 수정 없음]
│   ├─ MoveToShelf
│   └─ Browse            ✓→ Shopping  (그대로 둠)
├─ Shoplift     [Is Villain(Shoplift) AND Has Items In Cart]   ← 신규
│   Task: Shoplift        ✓→ Leave    ✗→ Root
├─ Checkout     [기존 조건 그대로 — 수정 없음]
├─ ReturnItems  [기존 조건 그대로 — 수정 없음]
└─ Leave        [기존]
```

| 위치 | 얻는 것 |
| :--- | :--- |
| **Shopping보다 뒤** | 절도범도 평범하게 물건을 담는다. 맨 위에 두면 **첫 상품을 집자마자 튄다** |
| **Checkout보다 앞** | 쇼핑이 끝나 Root를 재선택하는 순간 계산대보다 먼저 잡힌다 → **`Checkout`에 `NOT 빌런` 조건을 안 붙여도 됨** |
| **`✓→ Leave` 직접 지정** | Root를 안 거치므로 `HasItemsInCart`가 평가될 일 자체가 없다 → 절도범이 줄을 서는 게 **구조적으로 불가능** |

> **기존 상태 4개의 조건을 하나도 안 고쳤습니다.** 조건을 추가해 막는 대신 **순서로 해결**한 셈입니다. 셀렉터에서 순서가 우선순위라는 성질을 이렇게도 쓸 수 있다는 걸 배웠습니다.

**어제 "반드시 바꿔야 한다"던 게 오늘은 안 바꿔도 됐다**

어제 정리에서는 `Browse ✓→ Shopping`을 **`→ Root`로 바꿔야 한다**고 적었습니다. 오늘은 **그대로 뒀습니다.**

| | 어제 (런타임 래치 전제) | 오늘 (스폰 확정) |
| :--- | :--- | :--- |
| 빌런 확정 시점 | 진열대에서 **래치될 수 있음** | 스폰 시 이미 확정 |
| 그래서 | Browse 직후 Root를 거쳐야 래치를 감지 | **감지할 게 없음.** Shopping 순환이 끝나고 Root를 재선택할 때 자연히 잡힘 |

> 같은 트리인데 **결정 방식이 바뀌니 필요한 전이도 바뀌었습니다.** 어제 적은 *"이 패턴에 세 번째로 걸렸다"* 는 말이 오늘은 틀린 얘기가 됐습니다. **어제의 결론이 전제에 딸린 결론이었다는 걸** 알게 된 게 재밌었습니다.

**`Has Items In Cart`를 AND로 묶은 이유:** 빈손 절도범이 도주 모션만 하고 나가는 걸 막습니다. **새 조건을 만들지 않고 이미 있는 조건을 재사용**했습니다.

### 7. 태스크는 극단적으로 얇게

`FCSTask_Shoplift`에는 **`Tick`도 `ExitState`도 없습니다.**

```cpp
FCSTask_Shoplift() { bShouldCallTick = false; }   // 어제 배운 플래그를 바로 적용

EnterState:
    Subsystem->CommitShoplift(Actor);              // 대기열 정리 + 표시 + 방송
    Movement->MaxWalkSpeed = FleeWalkSpeed;        // 도주 연출 (450, 기본은 250)
    return Succeeded;                              // 이동은 Leave가 담당
```

*   **실제 퇴장 이동은 이미 있는 `LeaveAndDespawn`이 처리합니다.** `✓→ Leave` 전이로 연결했습니다.
*   `MaxWalkSpeed`는 상태를 떠나도 유지되므로 **Leave까지 빠른 걸음이 이어집니다.** 상태 간에 값이 남는 성질을 의도적으로 이용했습니다.
*   **`MarkVillainActionDone()`을 태스크가 아니라 서브시스템(`CommitShoplift`)에서 호출**합니다. 태스크가 깜빡해도 트리가 그 상태에 갇히지 않습니다. → 어제 가이드에서는 태스크 `ExitState`의 책임이었는데, **더 안전한 자리로 옮겼습니다.**
*   장바구니는 **일부러 안 숨깁니다.** 물건을 든 채 빠르게 나가는 게 플레이어의 단서입니다.

**손실 확정은 `LeaveAndDespawn::Tick`의 `Destroy()` 바로 앞**에 넣었습니다. 일반 손님은 서브시스템 내부에서 걸러지므로 **범용 퇴장 태스크에 조건 분기가 필요 없습니다.**

### 8. 확률은 두 값의 곱이다

```
20대 절도범 비율 = SpawnWeightBase × VillainChance

최종 권장 : 0.17 × 0.08 = 1.4%    ← 100명에 1~2명. 검증하려면 한참 봐야 함
검증용   : 0.17 × 0.8  = 13.6%   ← 7~8명당 1명. 금방 보임
```

> 어제 정리한 *"확률은 기회 횟수와 함께 봐야 한다"* 의 다른 버전입니다. 이번엔 곱셈이고, 어제는 $1-(1-p)^N$이었습니다. **설정값 하나만 보고 체감 빈도를 짐작하면 안 된다**는 게 공통점입니다.

**`VillainChance`와 `SpawnWeightBase`의 성격이 다르다는 점**도 주석에 명시했습니다. `SpawnWeightBase`는 **상대 가중치**라 하나를 올리면 다른 종족이 줄어들지만, `VillainChance`는 **독립 확률**이라 다른 종족에 영향을 주지 않습니다. 반대로 `VillainActionWeights`는 다시 상대 가중치입니다. **같은 파일 안에 두 성격이 섞여 있어서** 헷갈릴 수 있어 적어뒀습니다.

검증은 `DA_Archetype_20s_Adventurer` **하나만** 열어서 채우고, 나머지 5종족은 `VillainChance = 0`으로 둡니다.

### 9. 검증 순서와 디버그 도구

**① 스폰 판정만** (트리 배선 전) — 태스크·조건이 없어도 `[빌런배정]` 로그만으로 확인됩니다.

*   `cs.Seed 12345` 고정 후 PIE 두 번 → **같은 순번의 손님이 같은 빌런인가** (아니면 시드 발급이 잘못됨)
*   20대 빌런 비율이 `VillainChance`에 수렴하는가
*   **`[구매검증 요약]` 기준선을 다시 잰다** — 마스터 스트림 소비가 손님당 2회 → 3회로 늘어 **이전 수치와 1:1 비교가 안 됩니다.** 평균값 자체는 같은 값에 수렴해야 정상입니다.

**② 절도 행동** — 물건을 담고 나서 도주하는가(담자마자 튀면 상태 위치가 잘못됨), 주황 → 빨강 순서, **두 메시지의 금액이 같은가**, 줄을 안 서는가, 봉투를 안 받는가, 일반 손님 흐름이 그대로인가.

디버그 서브시스템은 `CSPurchaseVerificationSubsystem`과 **같은 구조**로 만들어 방송만 구독해 화면에 찍습니다. **게임 로직에 관여하지 않으므로 검증이 끝나면 파일 2개만 지우면 됩니다.**

---

### 10. 협의 사항과 부수 발견

**소비심리 파트** — 아키타입 DA에 필드 2개 추가 승인만 필요합니다. `UCSPurchaseDecisionComponent`는 안 건드립니다. **순수 필드 추가라 기존 동작이 안 바뀝니다.**

> **부수 발견:** 현재 6종족 전부 `CategoryPreference`와 `BlockedCategories`가 **비어 있어서** `ComputeCategoryScore()`가 항상 `0.5`를 반환합니다. 즉 **카테고리 판단이 점수에 아무 기여를 못 하는 상태**입니다. 빌런과는 무관하지만 공유해야 할 사항입니다.
>
> 빌런 작업을 하면서 그쪽 코드를 읽다 발견했습니다. **남의 파트 코드를 읽는 게 이런 부수 효과가 있다**는 걸 처음 경험했습니다.

**통계 / 평판 파트** — `OnShopliftEscaped`를 구독. `OnShopliftStarted`는 연출용이라 매출 차감에 쓰면 안 됩니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **결정을 내리면 구조가 줄어든다** | 스폰 확정으로 정하자 신규 파일 4개 → 1개. 미룬 상태로 구현에 들어가면 필요 없는 걸 만든다 |
| **성격이 같은 값은 같은 자리로** | 빌런 플래그는 `bCheckoutDone`·`bCheckoutAbandoned`와 성격이 같다 → 새 컴포넌트가 아니라 기존 상태 컴포넌트 |
| **독립이어야 할 굴림은 시드도 독립** | 같은 시드로 만든 두 스트림은 첫 난수가 같다 → 눈에 안 보이는 상관관계가 생긴다 |
| **쪼개는 건 지금, 늘리는 건 나중** | 방송 추가는 구독자를 안 깨지만, 하나를 둘로 쪼개면 전부 고쳐야 한다. 그래서 손실 확정 시점만 미리 나눴다 |
| **배치가 조건을 대신한다** | Shoplift를 Shopping과 Checkout 사이에 두어 기존 조건 4개를 하나도 안 고쳤다 |
| **결론은 전제에 딸려 있다** | 어제 "반드시 Root로 바꿔야 한다"던 전이가 결정 방식이 바뀌자 불필요해졌다 |
| **범위를 줄이면 원인이 좁혀진다** | 절도 하나만 끝까지 돌려서, 안 될 때 무엇 때문인지 구분이 된다 |
| **남의 코드를 읽으면 부수 발견이 있다** | 카테고리 점수가 항상 0.5로 고정돼 있던 걸 빌런 작업 중에 발견 |
