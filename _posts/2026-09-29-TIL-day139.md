### 1. 수동 저장 제거

어제 *"영업 중 수동 저장을 허용할 것인가"* 를 기획 판단으로 넘겼는데, **답이 "수동 저장 자체를 없앤다"** 로 나왔습니다.

| | 이전 | 이후 |
| :--- | :--- | :--- |
| 저장 | 자동 + 준비 단계 한정 수동 | **자동만** |
| 메뉴 | 저장·불러오기 | **불러오기 전용** (저장 버튼 항상 숨김) |

> 수동 저장을 허용하면 **"저장 가능한 상태"를 늘 유지해야** 합니다. 영업 중 아무 때나 누를 수 있으면 걸어가는 손님, 계산 중인 결제, 진행 중인 StateTree를 전부 저장 대상으로 만들어야 합니다.
>
> **자동 저장 한 지점으로 좁히면 그 시점만 안전하게 만들면 됩니다.** 제약을 늘려서 구현 범위를 줄인 셈입니다.

**다만 수동 슬롯 코드와 저장 버튼은 지우지 않고 남겼습니다.** 2단계 "세이브 파일 슬롯(새로 시작)" 기능에서 재사용할 예정이라서요.

> 쓰지 않는 코드를 남기는 건 보통 피하는데, 이번엔 **용도가 확정된 상태**라 남겼습니다. *"언젠가 쓸지도"* 가 아니라 *"다음 단계에서 이걸 쓴다"* 면 다릅니다.

### 2. 저장 즉시 X

옮기고 나니 새 문제가 생겼습니다. **영업 종료 시점에는 손님이 아직 남아 있습니다.**

> 손님이 집은 상품은 **손님 안에 데이터로만 들어 있고 세이브에는 담기지 않습니다.** 그 상태로 저장하면 **상품이 증발합니다** — 진열대에도 없고 바닥에도 없고 세이브에도 없습니다.

그래서 **조건이 맞을 때까지 기다리는 구조**를 넣었습니다.

```
마감 자유 시간 진입
  └─ 0.2초 간격으로 반복 확인
       └─ "상품을 들고 있는 손님이 0명인가?" → 예: 저장
  └─ 10초 지나면: 경고 로그 + 현재 상태로 저장 (타임아웃)
```

**타임아웃을 둔 이유**

> 조건이 영영 안 맞을 수 있습니다. 도주 중인 절도 손님이 매장을 못 빠져나가거나, 예상 못 한 경로로 손님이 남으면 **저장이 영원히 안 됩니다.**
>
> **"저장 못 함"보다 "조금 틀린 저장"이 낫습니다.** 대신 **경고 로그를 남겨** 그 상황이 실제로 발생하는지 알 수 있게 했습니다.

그리고 **기다리는 도중에 플레이어가 잠자기를 확인하면**, 손님 정리 직후 평판 정산 **전에** 즉시 저장합니다. 기다리다가 저장 기회를 놓치지 않게요.

### 3. 대기를 줄이려고 원인 쪽을 손봤다

대기 조건이 *"상품을 든 손님 0명"* 이라, **도주 중인 절도 손님이 가장 큰 지연 요인**이었습니다. 이 손님은 매장 밖으로 나가야 사라집니다.

대기 시간을 늘리는 대신 **애초에 그런 손님이 덜 생기게** 했습니다.

```
21:00 이후 생성된 손님에게는 빌런 배정을 생략
```

> **마감 직전에 태어난 절도범은 도주를 마칠 시간이 없습니다.** 그러면 저장이 계속 밀립니다. 아예 배정하지 않으면 대기가 짧아집니다.

**여기서 신경 쓴 디테일이 하나 있습니다.**

```
추첨 자체는 수행하고 결과만 버린다  ← 난수 뽑기 횟수를 유지
```

> 추첨을 건너뛰면 **마스터 스트림의 뽑기 횟수가 달라집니다.** 그러면 **21시를 넘겼는지에 따라 이후 모든 손님의 종족·시드가 밀립니다.**
>
> 시드를 고정해도 결과가 달라지는 셈이라, **재현성이 깨집니다.** 그래서 **뽑고 나서 버리는** 형태로 만들었습니다.
>
> 8월에 *"행인이 손님 스트림을 쓰면 행인 수에 따라 손님 결과가 밀린다"* 를 배웠는데, 이번엔 **같은 스트림 안에서 조건 분기 때문에 밀리는** 경우였습니다. 분기를 넣을 때 **"이 경로가 난수를 몇 번 소모하는가"** 를 맞춰야 한다는 걸 다시 확인했습니다.

### 4. 당일 집계까지 저장

아침에 저장할 때는 **하루살이 데이터를 저장할 필요가 없었습니다.** 방금 전부 0으로 리셋됐으니까요. **이게 원래 설계의 큰 이점**이었습니다.

시점을 옮기니 **그 이점이 통째로 사라졌습니다.**

| 저장 시점 | 당일 집계 상태 |
| :--- | :--- |
| 다음 날 아침 | **방금 리셋됨** → 저장 불필요 |
| **영업 종료 직후** | **하루치가 전부 쌓여 있음** → 저장 필수 |

그래서 새로 저장하게 된 것들입니다.

*   단계, 오늘 개점 여부
*   당일 **매출·원가·이익·판매 수량·결제 수**
*   **폐기·임대료·마법진 강화·직원 고용·임금·발주 지출**
*   **도난 손실**, 폐기·도난 상품 목록
*   **결제 거래 목록**과 다음 거래 번호
*   평판 일일 카운터 — 입장 손님·정상 결제·결제 포기·빈손 퇴장·가격 불만·쓰레기 목격

> **"불러온 뒤 잠자기 정산이 같은 결과가 나와야 한다"** 가 기준이었습니다. 하나라도 빠지면 **로드 후 정산 금액이 달라집니다.**
>
> 평판 서브시스템을 세이브 참가자로 새로 추가한 것도 그래서입니다. 그쪽 카운터가 **잠자기 시점에 평판 증감을 계산하는 입력**이라, 복원 안 하면 **평판이 엉뚱하게 계산**됩니다.

복원 후에는 **통계 변경 방송**을 한 번 쏘게 했습니다. 실시간 정산 창이 열려 있으면 옛 값을 유지하기 때문입니다.

> 어제 정리한 *"세이브 지점 하나가 설계의 절반"* 이 **역방향으로 증명됐습니다.** 지점을 한 칸 옮겼을 뿐인데 **저장 대상이 두 배로** 늘었습니다.

### 5. 복원에 기존 함수 재사용

불러온 상태가 마감 자유 시간이면, **기존 마감 진입 함수를 그대로 호출**합니다.

> 새 복원 경로를 만들지 않고 **원래 그 상태로 들어가는 함수**를 재사용했습니다. 확인해보니 **부작용이 없었습니다.**
>
> *   임대료·인건비는 **복원된 처리일이 같아** 중복 청구되지 않습니다 — 어제 정리한 *"중복 방지 가드가 로드에서도 값을 한다"* 가 여기서 또 맞았습니다.
> *   *"영업 종료"* 안내도 **직전 단계가 영업 중일 때만** 뜨게 되어 있어 다시 표시되지 않습니다.

> 어제 *"기존 진입점은 행위를, 복원은 결과를 재현한다"* 를 배웠는데, **이번엔 반대 사례**였습니다. 부수 효과가 **이미 가드로 막혀 있으면** 그대로 재사용해도 됩니다. **함수를 새로 만들지 말지는 "부수 효과가 있는가"가 아니라 "그 부수 효과가 복원 시에도 발동하는가"** 로 판단해야 했습니다.

같은 상태를 **다시 저장하지 않도록** 건너뛰기 플래그를 세웁니다. 안 그러면 불러오자마자 마감 자유 시간이라 **또 저장**됩니다.

### 6. [구조] 데이터 테이블 참조를 경로로 저장했다

어제까지 만든 구조 중 오늘 다시 값을 한 부분입니다.

> **로드는 레벨 재오픈을 동반하므로 테이블 포인터가 무효화**됩니다. 행 핸들을 그대로 저장하면 복원 시 **테이블이 널**입니다.
>
> 그래서 **행 이름 + 테이블 경로**로 기록하고, 복원할 때 다시 핸들로 되돌립니다. 경로 해석이 실패하면 **월드에서 찾은 상품 테이블로 폴백**합니다.

**어제 신선도에서 배운 것과 같은 종류**였습니다 — *"저장한 값의 기준이 로드 후에도 유효한가"*. 그때는 **월드 시간**이었고 이번엔 **에셋 포인터**입니다.

### 7. [구조] SaveId를 에디터 이벤트 두 곳에서 관리한 이유

레벨 배치 액터를 다시 찾으려면 안정적인 GUID가 필요한데, **발급만으로는 부족했습니다.**

| 시점 | 처리 | 왜 |
| :--- | :--- | :--- |
| 저장 직전 | 비어 있으면 **발급** | 레벨 에셋에 직렬화되어 유지 |
| **복사·Alt 드래그** | **재발급** | **복제하면 GUID까지 복사**되어 두 액터가 같은 ID를 갖게 됨 |
| 런타임 | 없으면 **자동 부착** | 기존 액터·BP를 수정하지 않아도 됨 |

> 두 번째를 놓쳤으면 **에디터에서 진열대를 복사한 순간 세이브가 조용히 깨졌을** 겁니다. 복원할 때 같은 ID의 액터가 둘이라 **어느 쪽에 상태를 넣을지 정해지지 않습니다.**
>
> **"고유해야 하는 값"은 발급뿐 아니라 복제 경로까지 막아야** 고유합니다.

런타임 자동 부착 덕분에 **레벨의 기존 액터와 BP를 하나도 수정하지 않았습니다.**
