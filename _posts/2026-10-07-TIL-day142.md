# **[UE5] 봉인석·소환 수레 저장과 복원**

오늘은 세이브·로드에서 빠져 있던 **바닥 봉인석, 퀵바 봉인석, 아티팩트로 소환한 수레**의 저장·복원을 구현했습니다. 추가로 소환 수레에 실린 상자도 불러온 뒤 **실린 상태를 유지**하도록 수정했습니다.

이번 작업에서 중요한 점은 **액터를 다시 생성하는 것만으로는 저장 당시의 상태가 돌아오지 않는다**는 것입니다. 봉인석은 내부 보상 정보가 있어야 열리고, 수레 위 상자는 수레와의 연결 및 적재 칸 등록까지 복원해야 같이 움직입니다.

---

## **1. 바닥 봉인석 저장·복원**

### **① 기존 문제: 골드는 사용했는데 보상이 사라진다**

가챠 우물에서 뽑기를 하면 봉인석이 생성되고 골드가 차감됩니다. 하지만 봉인석을 열지 않은 채 영업을 끝내고 불러오면, 봉인석은 사라지고 골드만 사용한 상태로 남았습니다.

* **원인:** 봉인석은 게임 실행 중 생성되는 액터인데, 저장 데이터에 봉인석을 기록하는 항목이 없었습니다.
* **결과:** 레벨을 다시 열면 기존 액터는 사라지고, 저장된 정보가 없으므로 봉인석을 다시 만들 수 없습니다.

쉽게 말하면 **돈을 내고 받은 보상 상자를 저장 목록에서 빠뜨린 것**입니다.

<br>

### **② 위치와 클래스 외에 무엇을 저장해야 할까?**

봉인석의 클래스와 위치만 저장하면 겉모습은 다시 만들 수 있습니다. 하지만 봉인석 안에 무엇이 들어 있는지는 복원되지 않습니다.

이를 해결하기 위해 `FCSGachaSealRecord`에 봉인석을 다시 만들고 개봉하는 데 필요한 정보를 기록했습니다.

| 저장 정보 | 필요한 이유 |
| :--- | :--- |
| **액터 클래스 경로** | 같은 종류의 봉인석 생성 |
| **월드 트랜스폼** | 저장한 위치·회전으로 복원 |
| **바닥 물리 상태** | 바닥에 놓였던 봉인석의 물리 다시 활성화 |
| **보상 종류·식별자·수량** | 상품 또는 아티팩트 보상의 종류와 수량 유지 |
| **상품·아티팩트 데이터 행 참조** | 개봉 시 필요한 원래 보상 데이터 조회 |
| **보상 생성 클래스 경로** | 보상을 생성할 액터 클래스 유지 |
| **표시 이름** | 저장 당시의 보상 표시 정보 유지 |

보상 구조체 전체를 그대로 저장하지 않고, **개봉에 필요한 값과 에셋 경로를 따로 기록**했습니다. 기존 보상 구조체에는 `SourceCatalog` 같은 객체 참조가 포함되어 있어, 프로젝트의 저장 규칙에 맞는 레코드로 분리했습니다.

> **핵심**
> 봉인석은 외형뿐 아니라 **안에 들어 있는 보상의 상태**까지 저장해야 정상적으로 복원됩니다.
{: .prompt-tip }

<br>

### **③ 지연 생성으로 보상을 먼저 설정하기**

복원할 때는 기존 우물의 봉인석 생성 흐름과 맞춰 **지연 생성(Deferred Spawn)**을 사용했습니다.

1. `SpawnActorDeferred`로 봉인석 생성 준비
2. `RestoreSaveRecord`에서 보상 데이터를 확인하고 `InitializeReward`로 설정
3. `FinishSpawning`으로 생성 마무리
4. 바닥 봉인석이면 저장된 물리 상태 적용

쉽게 말하면 **빈 상자를 완성하기 전에 내용물을 먼저 채워 넣는 방식**입니다. 생성이 마무리되기 전에 보상 정보를 설정하여, 초기 동작에 필요한 상태를 준비합니다.

보상 테이블이나 행을 찾지 못하면 경고를 남기고 생성을 중단합니다. 보상이 없는 봉인석을 만들어 놓으면 열 수도 없고 정상적으로 사용할 수도 없기 때문입니다.

<br>

### **④ 바닥과 퀵바에서 중복 저장되지 않게 하기**

봉인석을 집으면 퀵바에 들어가며, 손에 든 봉인석도 퀵바 항목입니다. 따라서 월드의 봉인석을 수집할 때는 **퀵바에 들어 있는 봉인석을 제외**했습니다.

| 봉인석 상태 | 저장하는 곳 |
| :--- | :--- |
| 바닥에 놓인 미개봉 봉인석 | 월드의 `GachaSeals` 목록 |
| 퀵바에 보관하거나 손에 든 봉인석 | 퀵바 슬롯 레코드 |

같은 봉인석을 두 곳에 기록하면 불러올 때 바닥과 퀵바에 하나씩 생길 수 있습니다. **저장 책임을 한 곳으로 정하는 것**이 중복 복원을 막는 기준입니다.

복원 시에는 기존 봉인석을 제거한 뒤 저장된 레코드로 다시 생성합니다. 이때 제거 작업은 퀵바 복원보다 먼저 실행해야, 방금 복원한 퀵바 봉인석을 다시 지우지 않습니다.

<br>

## **2. 퀵바 봉인석의 빈 보상 문제**

### **① 겉모습은 있는데 열리지 않는 이유**

기존 퀵바 저장은 봉인석을 일반 도구로 처리하여 `ToolClass`만 기록했습니다. 그래서 불러온 뒤 봉인석은 보이지만 내부 보상은 비어 있었습니다.

| 단계 | 기존 동작 |
| :--- | :--- |
| 저장 | 일반 도구 분기에서 클래스만 기록 |
| 복원 | 해당 클래스로 액터만 생성, 보상 초기화 없음 |
| 내려놓기 | `bHasReward == false`라 개봉 처리 중단 |
| 다시 줍기 | 보상 없는 봉인석이라 상호작용 중단 |

단순히 **아이템이 화면에 보이는지**만 확인했다면 놓칠 수 있는 버그였습니다. 복원한 아이템이 원래 기능까지 수행하는지 확인해야 합니다.

<br>

### **② 상속 관계에서는 검사 순서가 중요하다**

봉인석은 `ACSUsableToolActor`를 상속받습니다.

```cpp
ACSGachaSeal : public ACSUsableToolActor
```

따라서 일반 도구인지 먼저 검사하면 봉인석도 그 조건에 들어갑니다. **더 구체적인 봉인석 타입을 먼저 검사**하도록 변경했습니다.

아래는 분기 순서를 설명하기 위한 축약 예시입니다.

```cpp
// 봉인석은 도구이므로 먼저 확인해 보상 정보까지 기록
if (const ACSGachaSeal* Seal = Cast<ACSGachaSeal>(Item))
{
    if (Seal->HasSealedReward())
    {
        SlotRecord.bHasGachaSeal = true;
        Seal->CaptureSaveRecord(SlotRecord.GachaSeal);

        // 퀵바에 다시 보관하므로 바닥 물리는 사용하지 않음
        SlotRecord.GachaSeal.bWorldDropPhysics = false;
    }
}
else if (const ACSUsableToolActor* Tool = Cast<ACSUsableToolActor>(Item))
{
    // 일반 도구는 기존 방식으로 기록
}
```

복원할 때는 5단계의 공용 생성 함수로 **보상이 설정된 봉인석**을 만든 뒤, 기존 퀵바 처리로 다시 보관합니다. 선택 슬롯 복원도 기존 흐름을 사용하여, 손에 들고 저장한 봉인석은 다시 손에 들도록 했습니다.

> **상속과 조건 검사**
> 부모 타입 검사에는 자식 타입도 포함됩니다. 자식에게 별도 처리가 필요하다면 **자식 분기를 부모 분기보다 먼저** 배치해야 합니다.
{: .prompt-tip }

<br>

### **③ 이전 세이브의 정보 부족 처리**

수정 전 세이브에는 퀵바 봉인석의 클래스만 있고, 내부 보상 정보는 없습니다. 이미 빠진 보상은 해당 세이브만으로 되살릴 수 없습니다.

따라서 이전 형식의 봉인석 클래스만 발견되면 **경고를 남기고 복원을 생략**했습니다. 불러올 때마다 열 수도 주울 수도 없는 빈 봉인석이 생성되는 것을 막기 위한 처리입니다.

<br>

## **3. 불러온 봉인석이 작아지는 문제**

### **① 원인: 기본 크기의 중복 적용**

테스트 중 바닥 봉인석을 불러오면 원래보다 작아지는 문제를 발견했습니다.

봉인석의 루트 메시에는 기본 크기 `0.45`가 설정되어 있습니다. 저장한 액터 트랜스폼에도 이 크기가 포함되어 있었는데, 이 프로젝트의 생성 경로에서는 전달한 크기가 클래스 기본 루트 크기에 다시 곱해졌습니다.

$$
0.45 \times 0.45 = 0.2025
$$

즉, 원래 크기인 `0.45`로 복원하려 했지만 실제로는 약 `0.20`이 되었습니다.

<br>

### **② 해결: 생성 시 위치·회전만 전달하기**

봉인석은 기존 우물에서도 클래스 기본 크기를 사용하므로, 복원 시에도 **저장된 위치·회전만 전달하고 크기는 기본값을 사용**하도록 수정했습니다.

```cpp
// 기본 크기가 두 번 적용되지 않도록 위치·회전만 사용
const FTransform SpawnTransform(
    InSpawnTransform.GetRotation(),
    InSpawnTransform.GetLocation());
```

이 트랜스폼을 지연 생성과 `FinishSpawning`에 사용했습니다. 이전 세이브에 크기 `0.45`가 기록되어 있어도 생성 시 해당 크기를 다시 적용하지 않으므로 정상 크기로 복원됩니다.

**이번 해결은 클래스 기본 크기를 사용하는 봉인석에 맞춘 처리**입니다. 플레이 중 크기가 달라지는 액터라면 그 크기까지 보존할 방법을 별도로 설계해야 합니다.

<br>

## **4. 아티팩트로 소환한 수레 저장·복원**

### **① 같은 클래스여도 생성 방식에 따라 구분해야 한다**

소환 아티팩트를 사용하면 보유량은 줄어들지만, 소환한 수레는 저장되지 않았습니다. 불러오면 **아티팩트는 사용한 상태인데 수레는 없는 상황**이 되었습니다.

레벨에 배치된 수레와 소환 수레는 같은 블루프린트를 사용하므로, 클래스만 검사해서는 둘을 구분할 수 없습니다.

| 수레 종류 | 불러올 때의 처리 |
| :--- | :--- |
| 레벨 배치 수레 | 레벨이 다시 생성하며 기본 위치에 배치 |
| 아티팩트 소환 수레 | 저장 레코드를 바탕으로 저장 위치에 다시 생성 |

이를 구분하기 위해 소환 직후 `UCSSaveIdComponent`를 붙였습니다. 이 컴포넌트가 **고유 식별자(SaveId)**와 **런타임 생성 여부**를 관리합니다.

```cpp
// 소환 수레를 저장 대상에서 구분하도록 식별자 컴포넌트를 추가
UCSSaveIdComponent::FindOrAddComponent(Cart);
```

<br>

### **② SaveId는 불러온 뒤에도 이어받아야 한다**

`FCSSummonedCartRecord`에는 수레의 SaveId, 클래스 경로, 월드 트랜스폼을 기록했습니다.

복원할 때는 기존 런타임 수레를 제거하고, 레코드마다 다시 생성한 수레에 **저장 당시의 SaveId를 적용**합니다.

```cpp
// 저장 당시 식별자와 런타임 생성 상태를 이어받음
SaveIdComponent->OverrideSaveId(CartRecord.SaveId, true);
```

여기서 런타임 생성 상태도 유지해야 합니다. 이를 `false`로 바꾸면 다음 저장에서 소환 수레 수집 조건을 통과하지 못해 다시 저장되지 않을 수 있습니다.

쉽게 말하면 **수레를 새로 만들더라도 저장 시스템에서는 같은 수레로 이어서 관리하는 것**입니다.

수레 생성에도 위치·회전만 사용하여, 봉인석에서 발견한 크기 중복 적용 문제를 피했습니다.

<br>

## **5. 수레 위 위치와 실제 적재 상태의 차이**

### **① 상자가 수레 위에 있어도 같이 움직이지 않는다**

7단계로 수레를 복원한 뒤에도 상자는 저장 위치의 바닥 상자로 생성되었습니다. 눈으로 보면 수레 위에 있지만 **수레를 밀면 상자가 따라오지 않는 문제**가 있었습니다.

상자의 위치만 복원했기 때문에 수레 부착과 적재 칸 등록은 이루어지지 않았습니다.

| 상태 | 의미 |
| :--- | :--- |
| **수레 위 위치에 있음** | 상자의 좌표만 수레 위에 있음 |
| **수레에 실려 있음** | 수레에 부착되고 적재 칸에 등록되어 같이 이동 |

그래서 7-1단계에서는 **객체 사이의 관계**까지 복원했습니다.

<br>

### **② 상자에 수레 식별자를 저장하기**

`FCSCrateRecord`에 `CartSaveId`를 추가했습니다. 상자의 부모가 소환 수레이면 그 수레의 SaveId를 기록합니다.

```cpp
// 실려 있던 소환 수레의 식별자
// 비어 있거나 다시 싣지 못하면 바닥 상자로 복원
UPROPERTY()
FGuid CartSaveId;
```

상자 위치는 그대로 저장합니다. 이 위치는 다시 실을 칸을 찾는 기준이자, 적재 실패 시 바닥에 복원할 위치로 사용합니다.

<br>

### **③ 수레를 먼저 만들고 상자를 나중에 싣기**

상자를 다시 실으려면 해당 수레가 이미 존재해야 합니다. 따라서 수레 복원을 상자 복원보다 먼저 실행했습니다.

1. `RestoreSummonedCarts`로 수레 생성 및 SaveId 복원
2. `TMap<FGuid, ACSCartActor*>`에 복원된 소환 수레 수집
3. 상자의 `CartSaveId`로 해당 수레 조회
4. 기존 `TryPlaceItem` 인터페이스로 상자 다시 적재

아래는 상자를 다시 싣는 핵심 처리입니다.

```cpp
// 저장된 식별자로 상자가 실려 있던 수레를 조회
ACSCartActor** Cart = SummonedCartsBySaveId.Find(CrateRecord.CartSaveId);

if (Cart != nullptr
    && ICSShelfPlaceable::Execute_TryPlaceItem(
        *Cart, Crate, CrateRecord.Transform.GetLocation()))
{
    // 적재에 성공한 상자는 바닥 물리를 켜지 않음
    continue;
}
```

수레가 저장 당시 위치·회전으로 복원되므로, 저장한 상자 위치와 가장 가까운 빈 칸이 원래 적재 칸이 됩니다. **현재 칸 배치가 유지된다는 전제**로 칸 번호를 별도 저장하지 않고 기존 위치 기반 배치 기능을 사용했습니다.

### **④ 기존 적재 기능을 재사용하는 이유**

단순히 `AttachToActor`만 호출하면 수레의 적재 칸 정보는 비어 있을 수 있습니다. 그러면 상자가 붙어 있는데도 게임 로직에서는 빈 칸으로 판단할 수 있습니다.

플레이어가 상자를 실을 때 사용하는 `TryPlaceItem`을 호출하면 다음 처리를 기존 규칙대로 수행합니다.

* 적재에 필요한 물리 상태 정리
* 빈 칸 선택 및 칸 위치에 배치
* 수레에 부착
* 적재 칸의 `OccupyingCrate` 등록
* 상자의 보관 상태 처리

이 방식으로 수레 내부의 `protected` 적재 칸을 직접 수정하지 않고 정상 상태를 만들었습니다. 적재 성공 후에는 바닥 물리를 켜지 않도록 하여 부착 상태를 유지했습니다.

수레를 찾지 못하거나 적재에 실패하면 **경고를 남기고 저장 위치의 바닥 상자로 복원**합니다. 연결 실패 때문에 상자까지 사라지는 일을 막기 위한 폴백(Fallback)입니다.
