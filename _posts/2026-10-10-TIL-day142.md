# **[UE5] NPC 코너 몰림 해결 — 스플라인 기준선과 레인 경로**

오늘은 거리의 행인들이 코너에서 한곳으로 모이는 문제를 해결했습니다. 스폰 영역에서는 서로 다른 위치에 생성되지만, 코너를 돌면 같은 지점을 지나 한 줄로 겹치는 현상이 있었습니다.

이를 해결하기 위해 **스플라인으로 도로 기준선을 만들고, 스폰 위치에 따라 각 행인의 옆 간격을 유지하는 레인 경로**를 적용했습니다.

---

## **1. 출발점은 다른데 코너에서 모이는 이유**

### **① 랜덤 출발점이 랜덤 경로를 뜻하지 않는다**

기존에는 출발 영역과 도착 영역에서 랜덤 지점을 뽑고, 그 사이 경로는 NavMesh 길찾기에 맡겼습니다.

| 대상 | 기존 이동 방식 |
| :--- | :--- |
| **손님** | AIController의 `MoveToLocation`과 엔진 PathFollowing 사용 |
| **행인** | 스폰 시 `FindPathSync`로 점 배열을 만들고 스포너가 이동 입력 전달 |

이동을 따라가는 방식은 다르지만, 두 경우 모두 경로 모양은 NavMesh 최단 경로가 결정했습니다.

장애물 안쪽 모서리를 따라가는 최단 경로에서는 출발점이 달라도 같은 코너 지점으로 모일 수 있습니다. 이번 도로 배치에서도 **출발 위치의 옆 간격이 코너에서 사라지는 것**이 핵심 원인이었습니다.

여기에 Pawn 충돌이 Ignore이고 회피도 꺼져 있어, 같은 위치로 이동한 NPC가 서로 겹친 채 지나갔습니다.

> **핵심**
> 출발점과 도착점을 흩어 놓아도, 그 사이를 모두 같은 최단 경로 규칙으로 계산하면 코너에서 다시 모일 수 있습니다.
{: .prompt-tip }

<br>

### **② 코너마다 랜덤 판정 박스를 두면 해결될까?**

코너에 경유 영역을 두는 방법도 검토했지만, 각 박스에서 독립적으로 랜덤 지점을 뽑는 것만으로는 원하는 동선을 만들기 어려웠습니다.

* 박스 사이 경로는 여전히 최단 경로여서 다른 모서리에 다시 모일 수 있습니다.
* 어떤 박스에서는 왼쪽, 다음 박스에서는 오른쪽을 선택하면 지그재그로 이동합니다.
* 손님처럼 `MoveTo` 요청을 구간마다 끝내고 다시 시작하면 감속·정지 구간이 생길 수 있습니다.

따라서 경유점을 늘리는 것보다 **도로의 전체 모양과 NPC별 옆 위치를 함께 지정하는 방식**을 선택했습니다.

<br>

## **2. 스플라인은 모두가 걷는 선이 아니라 기준선**

### **① 하나의 기준선으로 여러 경로 만들기**

스플라인은 길의 위치와 진행 방향을 알려주는 중심선입니다. 각 NPC가 실제로 걷는 위치는 중심선에서 옆으로 떨어진 거리로 정합니다.

$$
P(s) = C(s) + R(s) \times d(s)
$$

| 기호 | 의미 |
| :--- | :--- |
| `s` | 스플라인을 따라 진행한 거리 |
| `C(s)` | 해당 거리의 기준선 위치 |
| `R(s)` | 해당 거리의 기준선 오른쪽 방향 |
| `d(s)` | NPC의 옆 거리, 레인 오프셋 |

예를 들어 중심선 왼쪽 100cm에서 출발한 행인은 왼쪽 레인을, 오른쪽 100cm에서 출발한 행인은 오른쪽 레인을 사용합니다. 코너에서는 기준선의 방향이 바뀌므로 옆 방향도 함께 바뀝니다.

따라서 **바깥쪽 NPC는 큰 곡선으로, 안쪽 NPC는 작은 곡선으로 돌면서 레인 간격을 유지**할 수 있습니다.

<br>

### **② 생성 위치가 곧 레인이다**

레인은 새로 랜덤 선택하지 않고, 기존 스폰 위치를 기준선에 대응시켜 결정했습니다.

1. 끝점 박스 안에서 스폰 지점 선택
2. 스폰 지점과 가장 가까운 기준선 위치 확인
3. 기준선 오른쪽 방향과의 내적으로 옆 거리 계산
4. 해당 위치의 이동 가능한 반폭으로 나눠 레인 비율 결정

$$
\text{LaneRatio} = \frac{\text{스폰 위치의 옆 거리}}{\text{도로 반폭} - \text{몸 반경}}
$$

레인 비율은 `-1 ~ 1` 범위로 사용합니다. 구간별 폭이 달라지면 같은 비율을 해당 구간 폭에 적용합니다.

$$
d(s) = \text{LaneRatio} \times (\text{구간 반폭}(s) - \text{몸 반경})
$$

아래는 계산 원리를 설명한 축약 예시입니다.

```cpp
// 기준선에서 옆으로 떨어진 거리로 레인 비율을 계산
const float LaneRatio = FMath::Clamp(
    SpawnSideDistance / StartLaneLimit, -1.0f, 1.0f);

// 구간의 이동 가능한 폭에 같은 비율을 적용
const FVector LanePoint = CenterPoint
    + RightDirection * LaneRatio * LaneLimitAtDistance;
```

실제 경로 생성에서는 폭이 유효한지 확인하고 NavMesh 투영도 수행합니다. 도로 폭이 일정한 구간에서는 스폰 때의 옆 간격이 유지됩니다.

<br>

### **③ NavMesh를 계속 사용하는 이유**

스플라인이 경로 모양을 정하더라도, 만들어진 점이 실제로 걸을 수 있는 위치인지 확인해야 합니다.

스플라인을 샘플링해 경로 점을 만들고 `ProjectPointToNavigation`으로 NavMesh에 투영합니다. 투영 실패 시 레인 오프셋을 줄여 재시도하는 방어 처리도 넣었습니다.

| 역할 | 담당 |
| :--- | :--- |
| 도로 모양과 NPC별 옆 위치 | 스플라인 + 레인 계산 |
| 이동 가능한 바닥 위치 확인 | NavMesh 투영 |
| 행인의 실제 이동 | 기존 스포너의 점 배열 추종 |

행인은 `MOVE_NavWalking`을 사용하므로 NavMesh 범위도 필요합니다. 테스트 경로에 없던 남쪽 도로 구간에는 NavMesh 볼륨 2개를 추가했습니다.

## **3. 코너 스플라인에서 생긴 고리 문제**

### **① 자동 탄젠트가 항상 원하는 곡선을 만들지는 않는다**

처음에는 코너 스플라인에 자동 탄젠트를 사용했습니다. 하지만 긴 직선과 짧은 코너 구간이 연결되면서 탄젠트가 과하게 커졌고, 코너 앞에서 기준선이 뒤로 되돌아가는 작은 고리가 생겼습니다.

그 결과 레인 미리보기에서도 여러 선이 다시 한 점으로 모였습니다. **레인 계산뿐 아니라 기준선 자체의 곡선 형태도 확인해야 하는 문제**였습니다.

<br>

### **② 반지름 400cm 원호와 직접 지정 탄젠트**

코너를 반지름 400cm의 90도 원호로 만들고, 22.5도 간격의 5점을 사용했습니다. 각 점의 탄젠트도 진행 방향에 맞춰 직접 지정했습니다.

| 설정 | 이유 |
| :--- | :--- |
| 코너 반지름 **400cm** | 레인 최대 옆 거리 230cm보다 크게 설정 |
| 원호 점 **5개** | 0도부터 90도까지 곡선 방향을 명확하게 지정 |
| 직접 지정 탄젠트 | 코너 앞에서 뒤로 돌아가는 고리 방지 |
| 원호 앞뒤 보조점 | 긴 직선과 코너의 연결 형태 조정 |

안쪽 레인이 중심으로 말려 들어가지 않으려면 코너 반지름이 옆 오프셋보다 커야 합니다. 이번 설정은 다음처럼 여유가 있습니다.

$$
400 - 230 = 170 > 0
$$

도로 반폭 `230`은 걷는 도로 폭 약 620cm와 NavMesh 에이전트 반경 75cm를 바탕으로 정했습니다.

$$
620 / 2 - 75 = 235
$$

여기서 여유를 두어 230으로 설정했습니다. NPC 경로 계산에서는 실제 몸 반경도 별도로 고려합니다.

<br>

## **4. 1차 테스트 — 스플라인을 써도 한쪽으로 모였다**

### **① 문제의 원인은 추가한 레인 규칙**

1차 테스트에서는 행인이 출발 직후 옆으로 움직이며 거의 한 줄로 모였습니다. 기준선은 정상이어도 레인에 적용한 규칙이 원하는 동작과 맞지 않았습니다.

| 원인 | 나타난 동작 |
| :--- | :--- |
| **우측 통행** | 전체 레인 비율을 오른쪽 일부 범위로 압축해 출발 직후 몰림 |
| **레인 흔들림 ±40cm** | 좁아진 레인 폭에서 옆 간격과 순서가 섞여 보임 |
| **마지막 25% 도착 보간** | 도착 박스의 랜덤 위치로 이동하며 마지막 구간에서 비스듬히 꺾임 |

원하는 동작은 **스폰 위치에서 직진하고, 코너에서도 같은 레인을 유지하며, 도착까지 흔들리지 않는 것**이었습니다. 마주 오는 행인끼리 겹쳐 지나가는 것은 허용했습니다.

<br>

### **② 요구한 동작에 맞게 규칙 단순화**

우측 통행, 레인 노이즈, 도착 보간을 코드에서 제거했습니다.

| 항목 | 최종 동작 |
| :--- | :--- |
| 출발 | 스폰 위치로 정한 레인 사용 |
| 직선 | 흔들림 없이 해당 레인으로 이동 |
| 코너 | 같은 레인 비율로 곡선을 따라 이동 |
| 도착 | 도착 거리에서도 출발 레인 유지 |
| 양방향 | 같은 규칙 사용, 서로 겹치는 통행 허용 |

도착 박스에서 뽑은 점은 이제 **기준선의 어느 거리에서 멈출지**를 정하는 데 사용합니다. 최종 위치의 옆 거리는 출발 레인에 맞춰 계산하므로 도착 직전 다른 레인으로 건너가지 않습니다.

출발 보간 설정 `StartBlendDistance`는 남겨 두었습니다. 이번처럼 구간 폭이 일정하면 영향이 없고, 다리처럼 폭이 달라지는 구간에서 출발 위치를 레인에 연결할 때 사용합니다.

> **배운 점**
> 자연스러운 이동을 만들기 위한 우측 통행이나 노이즈도, 원하는 간격 유지 규칙과 충돌하면 몰림을 다시 만들 수 있습니다. 실제 목표 동작을 기준으로 기능을 선택해야 합니다.
{: .prompt-tip }

## **5. 행인 스포너에 연결하기**

행인은 이미 스포너가 경로 점 배열을 따라 이동시키는 구조였습니다. 따라서 **경로를 만드는 부분을 교체하고 기존 이동 처리는 재사용**할 수 있었습니다.

| 스포너 설정 | 동작 |
| :--- | :--- |
| `Route` 지정, 레인 경로 생성 성공 | `BuildLanePath` 결과 사용 |
| `Route` 없음 또는 레인 경로 생성 실패 | 기존 NavMesh 경로와 코너 보정 사용 |

다음 지점 통과 판정, 끼임 감지, 풀 반납 등은 기존 기능을 유지했습니다. 행인에게 새 AIController를 추가할 필요도 없었습니다.

테스트 맵에는 다음을 배치했습니다.

| 대상 | 설정 |
| :--- | :--- |
| `StreetRoute_Pedestrian_U` | U자 기준선 17점, 코너 2곳 |
| `PedestrianEndpoint_U_A/B` | 양 끝의 스폰·퇴장 박스 |
| `PedestrianSpawner_U` | 끝점 2개와 Route 지정 |
| 스폰 간격 / 최대 행인 수 | 기존 BP 기본값 7초 / 3명 |

스폰 박스 폭은 레인 분포와 직접 연결됩니다. 박스가 좁으면 스폰 위치도 좁게 분포하므로 여러 레인을 계산해도 행인이 한 줄처럼 보일 수 있습니다.


## **6. 다음 작업을 위한 손님 적용 설계**

손님은 거리 이동 외에도 입장·쇼핑·결제·퇴장이 있으므로 행인과 동일하게 전체 이동을 교체하지는 않습니다. **거리 구간에 레인 경로를 적용하고 매장 안 이동은 기존 NavMesh 방식**을 사용할 계획입니다.

| 상황 | 확정한 설계 |
| :--- | :--- |
| 스폰 → 가게 앞 | 스폰 레인으로 걸으며 입구 거리 통과 시 입장 여부 1회 판정 |
| 입장하지 않고 통과 | 기존 상태 전환대로 Leave로 이동, 현재 위치에서 같은 레인 사용 |
| 매장 안 쇼핑·계산대 | 기존 이동 유지 |
| 쇼핑 후 퇴장 | 매장 안에서 레인 합류점까지 NavMesh 경로, 이후 기억한 레인 사용 |

### **① 퇴장할 때 원래 레인을 기억하기**

퇴장 레인을 문 위치로 계산하면 모든 손님이 같은 가장자리로 몰릴 수 있습니다. 따라서 스폰 때의 레인 비율을 상태 컴포넌트에 기억하고 퇴장 때 재사용하기로 했습니다.

cm 단위 옆 거리보다 비율을 저장하면 입구 쪽 도로 폭이 달라도 같은 상대 위치로 합류할 수 있습니다.
