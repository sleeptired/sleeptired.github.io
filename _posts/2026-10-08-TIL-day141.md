# **[UE5] 실내 비·눈 차단과 날씨 연출 범위 개선**

오늘은 실내에서 비·눈이 내리지 않으면서, 문이나 창문 너머 바깥에는 계속 비·눈이 보이도록 날씨 연출을 개선했습니다.

기존에는 실내 판정에 따라 캐릭터 주변 파티클을 숨기고 문 앞의 고정 파티클을 보여주었습니다. 하지만 판정 영역을 드나들 때 연출이 바뀌는 느낌이 있었고, 반대편 문이나 먼 창밖에는 비가 보이지 않았습니다.

이를 해결하기 위해 **Weather Blocker로 실내 파티클을 제거하고, Coverage Area로 필요한 바깥 구간을 채운 뒤, 거리 페이드로 멀리서 보이는 경계를 완화**했습니다.


## **1. 기존 실내 판정 방식의 한계**

### **① 플레이어 위치에 따라 표시를 바꾸는 구조**

기존 구조에서는 `IndoorArea` 또는 문 앞 `JudgeBox`에 플레이어가 들어가면 다음처럼 표시를 전환했습니다.

| 플레이어 상태 | 캐릭터 주변 파티클 | 문 앞 Zone 파티클 |
| :--- | :--- | :--- |
| 실외 | 표시 | 숨김 |
| 실내 또는 문 앞 판정 영역 | 숨김 | 표시 |

실내에 파티클이 떨어지는 것은 막을 수 있지만, **플레이어가 어디에 서 있는지에 따라 바깥 연출까지 달라지는 문제**가 있었습니다.

* 판정 영역 밖에서 문을 보면 문 앞 파티클이 숨겨져 있습니다.
* 판정 영역에 들어가면 고정 파티클이 표시되어 경계가 드러납니다.
* 문 앞 영역만으로는 옆문·창문·반대편 문 너머까지 덮기 어렵습니다.
* 캐릭터 파티클과 고정 파티클을 함께 켜면 겹치는 구간의 밀도가 높아집니다.

이번에는 **실내외에 따라 전체 파티클을 숨기는 대신, 비·눈이 있으면 안 되는 공간의 입자만 제거**하는 방식으로 변경했습니다.

<br>

## **2. Weather Blocker — 건물 안 입자만 제거하기**

### **① 블로커 박스의 역할**

Weather Blocker는 비·눈을 차단할 공간을 지정하는 박스입니다. 캐릭터 주변 파티클을 계속 표시하면서, 파티클이 박스 안에 있으면 Niagara에서 제거합니다.

쉽게 말하면 **건물 내부를 파티클 금지 구역으로 지정하는 것**입니다.

| 구성 요소 | 역할 |
| :--- | :--- |
| `UCSWeatherBlockerComponent` | 차단할 박스 범위와 등록·해제 관리 |
| `ACSWeatherBlockerVolume` | 맵에 직접 배치할 수 있는 액터 |
| `UCSWeatherSubsystem` | 등록된 블로커 정보를 모아 이펙트에 전달 |
| `ACSWeatherEffectActor` | Niagara User 파라미터에 박스 배열 설정 |
| `NM_KillInsideBlockers` | 파티클 위치가 박스 안인지 계산 |
| 엔진 기본 `KillParticles` | 판정 결과에 따라 파티클 제거 |

박스는 충돌과 오버랩을 사용하지 않고 내비게이션에도 영향을 주지 않습니다. 플레이어 이동을 막는 벽이 아니라 **파티클 계산에 사용하는 공간 정보**입니다.

<br>

### **② 회전된 박스는 어떻게 판정할까?**

C++에서는 각 박스의 중심, 절반 크기, Yaw를 배열로 전달합니다.

| 파라미터 | 내용 |
| :--- | :--- |
| `BlockerCenters` | 박스의 월드 중심 |
| `BlockerHalfExtents` | 스케일이 반영된 박스 절반 크기 |
| `BlockerYaws` | 박스의 Yaw 회전값, 라디안 단위 |

건물이 회전되어 있으므로 월드 좌표에서 바로 X·Y 범위를 검사하면 맞지 않습니다. 파티클 위치에서 박스 중심을 빼고 **박스 회전의 반대 방향으로 돌려 로컬 좌표로 변환**합니다.

변환한 좌표가 아래 조건을 모두 만족하면 박스 안입니다.

$$
|L_x| \le E_x,\quad |L_y| \le E_y,\quad |L_z| \le E_z
$$

* `L`: 박스 기준으로 변환한 파티클 위치
* `E`: 박스의 절반 크기

아래는 공용 모듈의 좌표 계산 부분입니다.

```hlsl
// 박스 중심을 기준으로 파티클 위치를 계산
float3 D = ParticlePos - C;

// 박스 회전의 반대 방향으로 돌려 로컬 좌표로 변환
float S = sin(-Y);
float Co = cos(-Y);
float LX = D.x * Co - D.y * S;
float LY = D.x * S + D.y * Co;
float LZ = D.z;

// 세 축 모두 박스 범위 안인지 확인
bool bInside = (i < Count)
    && (abs(LX) <= E.x)
    && (abs(LY) <= E.y)
    && (abs(LZ) <= E.z);
```

이번 박스는 **Yaw만 지원**하므로 배치할 때 Pitch·Roll은 0으로 둡니다.

<br>

### **③ Spawn과 Update에서 모두 검사하는 이유**

| 검사 시점 | 필요한 이유 |
| :--- | :--- |
| **Particle Spawn** | 실내에서 생성된 입자를 즉시 제거 |
| **Particle Update** | 밖에서 생성된 뒤 이동하면서 실내로 들어온 입자 제거 |

생성 시점만 검사하면 비스듬히 떨어지는 비나 천천히 이동하는 눈이 나중에 건물 안으로 들어올 수 있습니다. 따라서 이동 계산 뒤에도 블로커 판정을 실행했습니다.

비와 눈이 같은 `NM_KillInsideBlockers` 모듈을 사용하여, 박스 판정 수정이 두 시스템에 함께 반영되도록 했습니다.

<br>

### **④ CPU Niagara에서 발생한 컴파일 문제**

처음 계획한 HLSL을 그대로 사용했을 때 CPU VM에서 컴파일되지 않는 부분이 있었습니다.

| 처음 시도 | 실제 적용 | 이유 |
| :--- | :--- | :--- |
| 실행 중 정해지는 개수만큼 반복 | 고정 상한 16회 반복 + `i < Count` 검사 | 이번 CPU VM 컴파일 경로에서 동적 반복이 처리되지 않음 |
| `all(abs(L) <= E)` | X·Y·Z를 각각 비교 | 해당 VM에 `all(bool3)` 연산이 없음 |
| `Particles.Alive` 직접 설정 | 판정값 출력 후 `KillParticles` 사용 | 실제 소멸 처리를 엔진 기본 모듈에 맡김 |

최종적으로 비·눈 Niagara 에셋 모두 **컴파일 에러 0, 경고 0**을 확인했습니다.

> **현재 제한**
> 공용 모듈의 고정 반복 상한은 **16개**입니다. 블로커 배열의 17번째 이후 항목은 현재 검사하지 않습니다. 제한을 늘리면 입자별 검사량도 늘어나므로 함께 고려해야 합니다.
{: .prompt-warning }

## **3. 컴포넌트 생성자에서 발생한 중단 문제**

블로커를 추가한 뒤 에디터 시작 시 디버거가 `0x80000003` 예외로 멈추는 문제가 있었습니다.

콜스택을 확인하니 블로커 컴포넌트 생성자의 `SetBoxExtent()` 호출에서 엔진의 상태 갱신이 실행되고 있었습니다. 엔진이 CDO(Class Default Object)를 만드는 시점에도 생성자가 호출되므로, **아직 등록되지 않은 컴포넌트에서 렌더·물리·오버랩 갱신을 수행하는 것이 문제**였습니다.

생성자에서는 갱신을 수행하지 않고 초기값만 설정하는 `InitBoxExtent()`로 변경했습니다.

```cpp
// 생성자에서는 박스 크기의 초기값만 설정
InitBoxExtent(FVector(500));

// 충돌과 오버랩을 사용하지 않는 프로파일로 설정
SetCollisionProfileName(UCollisionProfile::NoCollision_ProfileName);
```

수정 후 빌드와 에디터 정상 시작을 확인했습니다.

> **배운 점**
> 생성자에서 호출할 함수는 **값만 초기화하는지, 이미 등록된 상태를 전제로 갱신하는지** 구분해야 합니다.
{: .prompt-tip }

## **4. Coverage Area — 문 밖 먼 구간의 비·눈 채우기**

### **① 블로커가 정상인데도 문 밖에 비가 없는 이유**

실내 파티클을 제거한 뒤에도 가게 중앙이나 정문에서 반대편 문을 보면 먼 바깥에 비가 없었습니다.

캐릭터 주변 생성 평면은 **4000 × 4000**입니다. 실내에 서 있으면 생성 범위의 상당 부분은 건물에 가려 제거되고, 먼 문 밖은 생성 범위 밖이라 처음부터 파티클이 없습니다.

즉, **차단 판정 문제가 아니라 생성 범위 문제**였습니다.

캐릭터를 따라다니는 평면 전체를 크게 늘리면 보이지 않는 공간에도 많은 입자를 생성하게 됩니다. 대신 문·창문으로 보이는 구간을 **월드에 고정된 Coverage Area**로 덮었습니다.

<br>

### **② 캐릭터 비와 영역 비의 담당 나누기**

두 시스템을 함께 재생하면 겹치는 부분에 비가 두 배로 생길 수 있습니다. 그래서 **입자가 처음 생성된 위치**를 기준으로 담당을 나눴습니다.

| 생성 위치 | 담당 시스템 |
| :--- | :--- |
| Coverage 안 | 월드 고정 Coverage 파티클 |
| Coverage 밖의 캐릭터 주변 | 캐릭터를 따라가는 기존 파티클 |

캐릭터 파티클은 Spawn에서 Coverage 박스 안의 입자를 제거합니다. Coverage 파티클에는 이 제외 배열을 적용하지 않고, 해당 박스 윗면에서 생성합니다. 건물 블로커는 두 시스템 모두에 적용합니다.

| 검사 종류 | Spawn | Update |
| :--- | :--- | :--- |
| **건물 블로커** | 검사 | 검사 |
| **캐릭터 파티클의 Coverage 제외** | 검사 | 검사하지 않음 |

Coverage 제외를 Update에서도 수행하면 밖에서 생성되어 안으로 이동하는 입자가 경계에서 사라집니다. 바람 방향에 따라 빈 띠가 생길 수 있으므로, **생성 위치로 담당을 나누는 검사는 Spawn에서만** 수행했습니다.

이 방식은 실내외 판정에 따라 켜고 끄지 않아 영역 전환 순간의 표시 변경을 피할 수 있습니다.

<br>

### **③ 면적이 커지면 생성량도 맞춰야 한다**

같은 생성량으로 더 넓은 면적에 뿌리면 비가 성겨집니다. 같은 Niagara 에셋을 사용하면서, Coverage의 스폰 레이트를 면적에 비례해 조정했습니다.

$$
\text{SpawnRateScale} = \frac{\text{Coverage 너비} \times \text{Coverage 높이}}{4000 \times 4000}
$$

BMStestMap의 Coverage는 XY 기준 **8700 × 5000**이므로 배수는 약 `2.72`입니다. 기존 스폰 레이트 `300`을 기준으로 Coverage 생성량은 초당 약 `816`개가 됩니다.

두 시스템은 같은 비·눈 에셋을 사용하므로 입자의 크기·속도·수명은 유지하고, **단위 면적당 생성량을 맞추는 방식**입니다.

Coverage 생성 높이도 캐릭터 파티클과 맞춰 경계에서 시작 높이가 다르게 보이지 않도록 했습니다.

**생성 후 제거되는 입자에도 생성 비용은 있습니다.** 블로커와 제외 검사는 표시와 밀도를 정리하는 역할이며, 입자를 제거한다고 생성 비용까지 사라지는 것은 아닙니다.

<br>

### **④ 초기화 순서도 중요하다**

Coverage 컴포넌트를 만들기 전에 블로커 배열을 전달하면 새 컴포넌트에는 차단 정보가 빠질 수 있습니다. 따라서 적용 순서를 다음처럼 맞췄습니다.

1. 새 날씨 이펙트 생성
2. Coverage 컴포넌트 생성 및 원본 파티클의 제외 영역 설정
3. 원본과 Coverage 컴포넌트에 블로커 배열 전달
4. 실내 판정과 표시·색감 상태 재적용

등록·해제 시에도 정보를 다시 전달하여, 레벨 시작 때 블로커와 이펙트의 생성 순서가 달라도 최종 상태를 맞추도록 했습니다.

<br>

## **5. 멀리서 보이는 비 섬과 거리 페이드**

### **① 특정 구간에만 비가 몰려 보이는 현상**

Coverage로 문 밖을 채웠지만, 멀리서 보면 고정 영역에만 비가 내려 **비가 내리는 섬처럼 보이는 문제**가 생겼습니다.

이를 완화하기 위해 파티클 머티리얼에 카메라 깊이 기반 페이드를 추가했습니다.

$$
\text{Fade} = 1 - \operatorname{saturate}\left(\frac{\text{PixelDepth} - \text{FadeStart}}{\text{FadeEnd} - \text{FadeStart}}\right)
$$

| 카메라 깊이 | 페이드 결과 |
| :--- | :--- |
| 2500 이하 | 기존 투명도 유지 |
| 2500 ~ 3500 | 점점 투명해짐 |
| 3500 이상 | 보이지 않음 |

`PixelDepth`는 카메라 정면 방향의 깊이이므로 정확한 직선거리와는 다릅니다. 이번에는 기존 머티리얼에 간단히 적용할 수 있는 깊이 기반 방식을 사용했습니다.

엔진 기본 머티리얼을 직접 수정하지 않고 `M_WeatherParticle`을 만들고, 비·눈용 머티리얼 인스턴스를 각각 적용했습니다.

<br>

### **② Additive 머티리얼에서 페이드를 한 번만 곱하기**

기존 파티클은 Additive 블렌드입니다. 이번 머티리얼에서는 페이드 값을 **Opacity에만 곱했습니다.**

```text
최종 Opacity = 기존 Opacity × Fade
```

Opacity와 Emissive 양쪽에 같은 페이드를 곱하면 시각적 기여에 페이드가 두 번 적용되어 의도보다 빠르게 어두워질 수 있습니다.

이 작업은 **보이는 정도를 조정하는 것**입니다. 머티리얼에서 투명해져도 Niagara 입자의 생성·시뮬레이션이 자동으로 줄어드는 것은 아닙니다.

<br>

### **③ 1차 해결에서 생긴 부작용**

거리 페이드만 적용하니 멀리 보이는 비 섬은 사라졌지만, 가게 안에서 반대편 문 너머 비까지 함께 흐려지거나 사라졌습니다.

**문 밖 비를 보여주기 위해 넓힌 범위가 페이드 때문에 다시 안 보이는 상황**이었습니다. 거리값만 조정하기보다, 어떤 시점에서 페이드가 필요한지 기준을 추가했습니다.

<br>

## **6. Coverage 안에서는 페이드 해제하기**

### **① 캐릭터 대신 카메라 위치로 판단하기**

Coverage 안의 시점에서는 문 너머 비를 유지하고, 박스 밖 멀리서는 거리 페이드를 적용하도록 변경했습니다.

| 카메라 위치 | 동작 |
| :--- | :--- |
| Coverage 안 | 거리 페이드 해제 |
| 박스 밖 경계에서 0 ~ 1500 | 거리 페이드 서서히 적용 |
| 박스 밖 경계에서 1500 이상 | 거리 페이드 완전히 적용 |

실내 판정 박스가 아니라 **Coverage 박스의 XY 범위**를 기준으로 합니다. 카메라가 높아져도 같은 지면 구역을 보고 있다면 동일한 기준으로 처리합니다.

<br>

### **② MPC로 여러 파티클 머티리얼에 같은 값 전달하기**

`MPC_Weather`는 **Material Parameter Collection**입니다. 같은 월드에서 여러 머티리얼이 함께 읽을 수 있는 파라미터 묶음으로, 이번에는 `FadeBypass`를 전달하는 데 사용했습니다.

* C++ 이펙트 액터: 카메라 위치로 `FadeBypass` 계산
* `MPC_Weather`: 계산한 값 보관
* 비·눈 머티리얼: 같은 값을 읽어 페이드 적용량 조절

컴포넌트마다 동적 머티리얼 인스턴스를 만들고 같은 값을 넣는 대신, **공통 값 하나를 전달**하도록 구성했습니다. 게임 중 변경한 값은 월드의 컬렉션 인스턴스에 적용되며 에셋 기본값을 수정하는 것은 아닙니다.

<br>

### **③ FadeBypass 계산**

카메라 XY를 박스 로컬 좌표로 변환한 뒤 박스 바깥까지의 최단 거리를 구합니다. 박스 안이면 거리는 `0`입니다.

$$
d_x = \max(|L_x| - E_x, 0),\quad d_y = \max(|L_y| - E_y, 0)
$$

$$
d = \sqrt{d_x^2 + d_y^2}
$$

여러 Coverage가 있으면 가장 가까운 박스까지의 거리를 사용합니다.

$$
\text{FadeBypass} = 1 - \operatorname{clamp}\left(\frac{d}{1500}, 0, 1\right)
$$

| 박스까지 거리 | FadeBypass | 의미 |
| :--- | :--- | :--- |
| 0, 박스 안 포함 | 1 | 거리 페이드 해제 |
| 750 | 0.5 | 거리 페이드 일부 적용 |
| 1500 이상 | 0 | 기존 거리 페이드 적용 |

머티리얼에서는 다음처럼 두 값을 보간합니다.

```text
최종 Opacity = 기존 Opacity × Lerp(Fade, 1, FadeBypass)
```

`FadeBypass`가 1이면 곱하는 값이 1이 되어 원래 투명도를 유지하고, 0이면 거리 페이드가 그대로 적용됩니다. 경계에서 값을 연속적으로 바꿔 갑자기 켜지거나 꺼지는 느낌도 줄였습니다.

<br>

### **④ Tick 종료 조건을 다시 정리하기**

기존 이펙트 액터는 실내외 색감 페이드가 끝나면 Tick을 껐습니다. 하지만 이제 카메라가 움직일 때 Coverage 거리도 계속 계산해야 합니다.

따라서 Tick 활성 조건을 **색감 페이드 진행 중이거나 Coverage 페이드 계산이 필요한 경우**로 바꿨습니다.

```cpp
// 색감 페이드 또는 Coverage 계산이 필요할 때 Tick 유지
bPostProcessFading || IsCoverageFadeEnabled()
```

색감 페이드 완료와 액터 전체 Tick 종료를 분리한 것입니다. 날씨 액터가 종료될 때는 `FadeBypass`를 기본값 0으로 되돌리도록 했습니다.

## **7. 맵에 적용할 때 확인한 기준**

블로커는 건물 BP를 수정하지 않고 **맵마다 Volume으로 직접 배치**했습니다. 건물 BP와 일반 스태틱 메시가 섞여 있어 배치 방식을 통일하고, 아직 이전 방식을 사용하는 맵에 영향을 주지 않기 위해서입니다.

| 영역 | 배치 기준 |
| :--- | :--- |
| **Blocker** | 건물 바닥부터 지붕까지, 입구와 처마 모양에 맞게 조정 |
| **IndoorArea** | 들어갈 수 있는 실내의 벽 안쪽만 덮음, 색감 전환 담당 |
| **Coverage** | 실내에서 문·창문으로 보이는 바깥 구간을 덮음 |

입구 쪽 블로커가 문 밖까지 나가면 보여야 할 비도 제거됩니다. 반대로 건물 내부를 덜 덮으면 실내에 비가 남습니다. 건물 전체 바운딩 박스를 무조건 쓰기보다 입구·처마·플레이어 상호작용 위치에 맞춰 조정했습니다.

블로커가 하나라도 등록된 맵에서는 실내에서도 캐릭터 파티클을 표시하므로, **해당 맵의 차단이 필요한 건물들을 함께 처리해야 합니다.**

기존 Zone 인스턴스는 새 방식 적용 맵에서 제거했습니다. 다른 맵에서 사용 중인 클래스와 에셋은 남겨 두었습니다. `IndoorArea`도 실내 색감 전환에 계속 사용합니다.
