## 손님 AI 행동 구현 — StateTree 태스크 5종 + 조건 2종

> 지금까지 만든 Character / AIController / StateComponent / Spawner / Subsystem 위에 **실제 행동 트리**를 올려 손님 AI MVP를 완성했습니다. 입장 → 진열대 순회 → 상품 구매 → 계산 대기 → 퇴장까지 한 사이클이 돕니다.

---

### 1. 구현 범위

**StateTree 태스크 5종** (`Features/Customers/StateTree/`)

| 태스크 | 역할 |
| :--- | :--- |
| `PickNextShelf` | 다음 진열대 선정 + 손님이 설 위치 계산 |
| `MoveToLocation` | NavMesh 기반 이동 (**범용** — 특정 목적에 묶이지 않음) |
| `BrowseShelf` | 진열대 앞에서 구경 → 확률로 상품 집기 |
| `WaitInQueue` | 계산대 줄 서기 + 순번 변동 시 앞으로 이동 |
| `LeaveAndDespawn` | 퇴장 지점으로 이동 후 소멸 |

**조건 2종**

| 조건 | 용도 |
| :--- | :--- |
| `HasUnvisitedShelf` | Shopping 상태 진입 판정 |
| `HasItemsInCart` | Checkout 상태 진입 판정 |

**에셋 3종** — `BP_CSCustomerAIController`(ST_Customer 지정) / `BP_CSCustomer`(마네킹 메시, AI Controller Class) / `BP_CSCustomerSpawner`(CustomerClass 지정)

추가로 `CSCustomerCharacter`에 **손님 간 폰 콜리전 무시**를 넣었습니다. 같은 통로에서 서로 밀치며 이동이 막히는 문제를 없애기 위한 조치입니다.

### 2. ST_Customer 트리 구조

```
Root
├─ Shopping  [조건: Has Unvisited Shelf]
│   Task: Pick Next Shelf
│   전이: On Failed → Root
│   ├─ MoveToShelf : Move To Location  → 성공 시 Browse / 실패 시 Shopping
│   └─ Browse      : Browse Shelf      → 성공 시 Shopping (재진입 = 다음 진열대)
├─ Checkout  [조건: Has Items In Cart]
│   Task: Wait In Queue                → 성공·실패 모두 Leave
└─ Leave     [조건 없음]
    Task: Leave And Despawn            → Tree Succeeded
```

**전체 흐름**

```
스폰 (영업 시간에만, bCanSpawnCustomers 게이트)
 → 안 가본 진열대를 하나 골라 이동
 → 1.5초 구경 → 재고 있으면 확률로 상품 집기
 → 다음 진열대 반복
 → 다 둘러보면 Shopping 실패 → Root 재선택
      산 게 있으면 → 계산대 줄 서기
      없으면      → 바로 퇴장
 → 플레이어가 계산대에서 스캔·결제
 → CompleteFrontCheckout() → 손님 퇴장·소멸, 뒷줄 전진
```

### 3. 설계 의도 5가지

#### ① 태스크는 얇게, 로직은 Subsystem 경유

진열대 선택·재고 판정·집기·대기열 같은 **실제 로직은 전부 `UCSCustomerRuntimeSubsystem`을 거칩니다.** 그 결과 **태스크 코드에 진열대·상품 클래스가 한 번도 등장하지 않습니다.**

> 팀원이 진열대 구조를 바꿔도 수정 범위가 Subsystem 한 파일로 제한됩니다. 어제까지 "모든 접촉은 서브시스템 경유"를 고집한 이유가 여기서 실제로 검증됐습니다.

#### ② 손님별 값은 전부 InstanceData에

**StateTree는 트리 에셋 하나를 여러 손님이 공유합니다.** 태스크 구조체 멤버에 상태를 두면 손님끼리 타이머·순번이 엉킵니다.

| 두는 곳 | 결과 |
| :--- | :--- |
| 태스크 구조체 멤버 | ❌ 모든 손님이 같은 값을 공유 → 타이머·순번 충돌 |
| **InstanceData** | ✅ 손님(인스턴스)마다 별도 보관 |

> 태스크 구조체는 **함수에 가깝고**, InstanceData가 **그 함수의 지역 변수**에 해당한다고 이해하면 헷갈리지 않습니다.

#### ③ `PickNextShelf`는 부모 상태에 상주(Running 유지)

자식 상태들(`MoveToShelf`, `Browse`)이 이 태스크의 **Output(진열대, 좌표)을 바인딩해서 읽습니다.** 그런데 태스크가 완료되면 **인스턴스 데이터가 정리되어 자식이 값을 못 읽습니다.**

그래서 `PickNextShelf`는 목표를 정한 뒤에도 **완료하지 않고 Running 상태로 부모에 남아 있습니다.** 자식들이 살아 있는 동안 Output이 유지되어야 하기 때문입니다.

> **"태스크의 수명 = 그 값이 필요한 기간"** 이라는 규칙. 이건 실행 순서가 아니라 **데이터 수명**으로 상태 구조를 설계해야 한다는 뜻이라, StateTree를 쓰면서 가장 낯설었던 부분입니다.

#### ④ 장바구니 담기를 태스크에서 호출하지 않음

`Subsystem::TakeProduct` **내부에서** `AddToSelectItem`까지 처리합니다.

```
TakeProduct() 내부:
  ProductId 확보 → 슬롯 해제 → 상품 Destroy → 장바구니 기록 → 델리게이트 방송
```

*   **재고 차감과 장바구니 기록을 한 덩어리로 묶어** *"상품은 사라졌는데 안 산 상태"* 가 생기지 않게 했습니다.
*   부작용으로, **태스크에서 또 담으면 같은 상품이 두 번 들어갑니다.** 호출하는 쪽에서 "이건 이미 처리됐다"를 알아야 하므로 함수 주석에 명시해 뒀습니다.

> 원자성을 위해 한 함수에 묶으면, 대신 **"이 함수가 어디까지 하는지"** 를 호출자가 알아야 합니다. 트레이드오프를 인지하고 선택한 지점.

#### ⑤ `Shopping`의 `On Failed → Root`가 전체를 연결

```
다 둘러봄 → PickNextShelf가 nullptr → Shopping 실패 → Root 재선택
  → Shopping 조건 실패 → 건너뜀
  → Checkout 조건 검사 → 산 게 있으면 줄서기 / 없으면 Leave
```

**"다 봤는데 안 샀으면 그냥 나간다"가 별도 코드 없이 셀렉터 구조만으로 성립합니다.** `Leave`에 조건을 두지 않은 것도 **마지막 폴백이 항상 선택 가능해야** 하기 때문입니다.

| 상태 | 조건 | 역할 |
| :--- | :--- | :--- |
| Shopping | Has Unvisited Shelf | 볼 게 남았을 때만 |
| Checkout | Has Items In Cart | 산 게 있을 때만 |
| **Leave** | **없음** | **항상 성립하는 폴백** |

> 분기를 `if`로 짜지 않고 **"조건 + 우선순위 + 폴백"** 으로 표현하는 게 셀렉터의 사고방식입니다. 상태가 늘어나도 기존 전이를 안 건드리고 사이에 끼워 넣을 수 있습니다.

### 4. ⚠ StateTree 시작 타이밍 — 이전 판단이 뒤집힌 지점

**어제까지 "손님이 안 움직이면 `Start Logic Automatically`부터 확인하라"고 정리해 뒀는데, 오늘 그 설정이 오히려 원인이었습니다.**

자동 시작을 쓰면 컨트롤러가 폰에 **빙의하기 전에** 트리가 켜져서 아래 에러가 납니다.

```
UStateTreeComponentSchema::SetContextData:
Could not find context actor of type CSCustomerCharacter
```

| 순서 | 자동 시작 | Possess 시작 |
| :--- | :--- | :--- |
| ① AIController 생성 | 컴포넌트가 **즉시 트리 시작** | 대기 |
| ② Possess 완료 | 이미 실패한 뒤 | **여기서 `StartLogic()`** |
| 결과 | Context Actor를 못 찾아 실패 | 정상 동작 |

**해결:** `BP_CSCustomerAIController`의 **`Event On Possess`에서 `StartLogic()` 호출**로 변경했습니다.

> ⚠️ 이 설정을 자동 시작으로 되돌리면 **손님이 스폰만 되고 전혀 움직이지 않습니다.** 에러 로그가 뜨긴 하지만 크래시가 아니라 조용히 아무 일도 안 일어나는 형태라, 원인을 찾는 데 시간이 걸렸습니다.
>
> **배운 것:** *"컴포넌트가 자동으로 해준다"* 는 옵션은 **그 자동 실행 시점이 내가 필요한 데이터가 준비된 시점보다 빠를 수 있습니다.** Context 바인딩처럼 **다른 객체와의 연결에 의존하는 초기화**는 자동에 맡기지 말고 연결 완료 시점에 직접 호출하는 게 안전합니다.

### 5. 기존 시스템 연동 — 인터페이스 설계의 보상 확인

팀원 코드를 **한 줄도 수정하지 않고** 붙였습니다.

| 사용 대상 | 방식 |
| :--- | :--- |
| `ACSShelfActor` | 레벨에서 자동 수집. **Attach된 상품 = 재고**로 판정 |
| `ICSShelfPlaceable` | `Execute_RemovePlacedItem`으로 슬롯 해제 (플레이어가 진열품을 다시 집을 때와 동일 규약) |
| `ACSProductPickupActor` | **`GetProductId()`** 로 `DT_ProductMaster` RowName 획득 |
| `ACSCheckoutCounterActor` | `RegisterCounter` → 줄 좌표 위임 / 결제 시 `CompleteFrontCheckout` 수신 |
| `ACSStoreGameState` | `bCanSpawnCustomers`를 스폰 게이트로 사용 |

**여기서 가장 의미 있었던 건 계산대입니다.** 어제까지는 테스트용 `ACSDemoMockCounter`를 쓰고 있었는데, 오늘 팀원의 실제 계산대(`ACSCheckoutCounterActor`)로 교체했습니다.

> **손님 파트 코드 수정 0줄.** 실제 계산대가 `ICSCustomerCounterInterface`를 구현하고 `RegisterCounter`를 호출하는 것만으로 붙었습니다. *"인터페이스에 함수 하나만 두는 최소 계약"* 이 실제로 값을 한 사례라, 설계 판단이 검증된 셈입니다.

`ProductId` 접근도 직접 멤버 접근에서 **`GetProductId()` getter**로 정리됐습니다. 팀원 헤더에 getter가 추가되면서 캡슐화를 유지한 채 연동이 가능해졌습니다.

### 6. 검증 결과

**쇼핑**

- 진열대 정면 약 120cm 지점까지 이동, 진열대마다 1.5초 정지
- 방문 순서는 손님마다 랜덤, **중복 방문 없음**
- 진열된 상품을 약 50% 확률로 가져감 (상품 액터 소멸)
- **가져간 자리에 플레이어가 다시 진열 가능** ← 슬롯 해제가 정상 동작한다는 결정적 증거
- 빈 진열대는 구경만 하고 통과 / 손님 5명 동시 순회 정상

**계산 · 퇴장**

- 산 손님은 `QueueStartPoint` 위치에 줄 섬, 안 산 손님은 바로 퇴장
- 계산대 상호작용 → 계산 UI에 **손님이 실제로 가져간 상품·수량·가격이 정확히 표시**
- 스캔 → 결제 → 출구 이동 후 소멸 (**Character + AIController 둘 다** 정리 확인)
- 뒷줄 손님 한 칸 전진, 3명 이상에서도 순서 유지 / 결제 후 HUD 매출 증가
- 다음 날에도 스폰·쇼핑·계산·퇴장 정상 반복

> 특히 **"가져간 자리에 재진열 가능"** 과 **"UI 주문 목록이 실제 구매 목록과 일치"** 두 가지가 핵심 검증 항목이었습니다. 앞은 `RemovePlacedItem` 규약이, 뒤는 `TakeProduct`가 장바구니 기록까지 묶어 처리한 설계가 각각 맞았는지를 보는 지표입니다.

### 7. 알려진 제약 / 임시 구현

| 항목 | 현재 상태 | 대응 |
| :--- | :--- | :--- |
| **동선·구매 판단** | `PickRandomUnvisitedShelf`(어디 갈지), `TestPurchaseChance`(뭘 살지) 임시 랜덤 | 소비심리 파트 담당 영역. `[임시/테스트용]` 주석 유지 후 교체 |
| **인내심 타임아웃** | 미구현 — 계산해주지 않으면 계속 대기 | 현재 사양상 정상. `WaitInQueue::Tick`에 타이머 + Subsystem에 포기 델리게이트 추가로 확장 |
| **줄 선 손님 겹침** | 손님 간 콜리전 무시의 부작용 | 기능 문제 아님. 같은 목표에 몰릴 때 **좌표를 분산**시키는 것이 근본 해결 → `GetShelfBrowseLocation` 내부 수정 예정 |

> 세 번째가 **트레이드오프의 흔적**입니다. 이동 간섭을 없애려고 콜리전을 껐더니 겹쳐 보이는 문제가 생겼습니다. 콜리전을 다시 켜는 게 아니라 **목표 좌표를 분산**하는 방향이 맞습니다 — 원인이 "물리적 충돌"이 아니라 "여러 손님이 같은 좌표를 목표로 삼는 것"이기 때문입니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **태스크 수명 = 데이터 수명** | `PickNextShelf`가 Running으로 남는 이유. 실행 순서가 아니라 **값이 필요한 기간**으로 상태 구조를 설계한다 |
| **공유 에셋에는 상태를 두지 않는다** | 트리 하나를 여러 손님이 공유 → 손님별 값은 전부 InstanceData |
| **분기를 조건 + 폴백으로 표현** | `if` 대신 셀렉터. `Leave`에 조건이 없는 게 "항상 성립하는 마지막 선택지" 역할 |
| **자동 초기화는 시점을 의심한다** | `Start Logic Automatically`가 Possess보다 빨라서 Context Actor를 못 찾았다. 연결에 의존하는 초기화는 직접 호출 |
| **원자성 vs 호출자 인지 부담** | 재고 차감 + 장바구니 기록을 묶으면 안전하지만, "이 함수가 어디까지 하는지"를 호출자가 알아야 한다 |
| **최소 계약의 값을 실제로 확인** | 목 계산대 → 실제 계산대 교체에 손님 파트 **수정 0줄**. 어제 예상한 보상이 그대로 나왔다 |
| **어제의 결론도 뒤집힐 수 있다** | 디버깅 노트 1순위였던 `Start Logic Automatically`가 오늘은 원인이었다. 기록은 **갱신 가능한 가설**로 남긴다 |
