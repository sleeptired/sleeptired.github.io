## 진열대 접근 지점 소유권 이전 

> 손님이 진열대 앞에 설 위치를 **손님이 계산하던 방식**에서 **진열대가 소유하고 제공하는 방식**으로 옮겼습니다. 그런데 구현을 마치고 돌려보니 **회전이 전혀 안 됐습니다.** 원인은 C++이 아니라 **저장하지 않은 에셋**이었습니다.

---

### 1. 오늘의 두 갈래

| 구분 | 내용 |
| :--- | :--- |
| **리팩터링** | 접근 지점의 소유자를 손님 → 진열대로 이전, 도착 판정 기준 통일, 디버그 드로우 모듈 신설 |
| **버그 추적** | 도착 후 마커 방향으로 안 도는 문제 → **StateTree 에셋 배선 누락** |

### 2. 바꾼 규칙 6가지

| # | 규칙 | 이전 |
| :---: | :--- | :--- |
| ① | **좌표의 소유자는 진열대다** | 손님 태스크가 `진열대 위치 + Forward × 거리`를 매번 계산 |
| ② | **반경은 하나다** | 정지 반경과 성공 반경이 달라 `+100` 여유값으로 덮음 |
| ③ | **실패는 감추지 않는다** | — (fallback으로 옆으로 끌고 감) |
| ④ | **못 갈 진열대는 고르지 않는다** | 설치 여부만 보고 뽑은 뒤 태스크가 실패 |
| ⑤ | **계산은 진열대당 1회** | 손님마다 매번 계산 |
| ⑥ | **Z는 판정에서 뺀다** | 캡슐 높이가 도착 판정에 섞임 |

①이 나머지를 전부 끌고 왔습니다. **좌표를 만드는 주체가 바뀌자 반경·유효성·캐시의 위치도 따라 바뀌었습니다.**

> 이전 구조는 손님이 `진열대 위치 + Forward × BrowseDistance`로 좌표를 만들었는데, **진열대 회전이나 메시 형태에 따라 벽 안쪽 좌표가 나왔습니다.** 진열대만 아는 정보(정면이 어디고 앞에 뭐가 있는지)로 계산해야 하는 값을 손님이 짐작하고 있었던 셈입니다.

④는 특히 효과가 좋았습니다. `IsShelfSelectable()` 한 줄로 **추첨 단계에서 미리 거르니**, 진열대 순회 3곳의 중복 필터가 사라지고 *"갈 곳을 모르는 진열대를 골라놓고 실패하는"* 경로 자체가 없어졌습니다.

### 3. 이름 규칙 탐색을 버렸다

```
이전: "CustomerBrowsePoint"라는 이름의 ArrowComponent를 런타임에 탐색 (선택 사항)
이후: 생성자에서 CreateDefaultSubobject로 BrowsePointMarker를 항상 생성
```

| | 이름 규칙 탐색 | 생성자 컴포넌트 |
| :--- | :--- | :--- |
| 존재 보장 | 없음 (BP에서 빠뜨릴 수 있음) | **항상 존재** |
| 오타 | 런타임에야 드러남 | 불가능 |
| 기본값 | BP마다 제각각 | 코드에 명시 (`(120, 0, 0)`, `Yaw 180°`) |

> **"규칙으로 지키는 것"과 "구조로 지키는 것"의 차이**입니다. 이름 규칙은 사람이 지켜야 하지만, 생성자에서 만들면 **안 만들 방법이 없습니다.** 며칠 전 *"이름이 설계를 지킨다"* 를 적었는데, 이번엔 한 단계 더 나아가 **이름에 의존하지 않는 쪽**이 답이었습니다.

마커의 기본 회전을 `Yaw 180°`로 둔 것도 의도적입니다. 화살표가 가리키는 방향이 **"손님이 바라볼 방향"(진열대 쪽)** 이라, 편집자가 뷰포트에서 화살표만 보고 맞출 수 있습니다.

### 4. 매직 넘버 `+100`은 무엇을 덮고 있었나

기존 도착 판정에 이런 코드가 있었습니다.

```cpp
MoveToLocation(Target, AcceptanceRadius);        // bStopOnOverlap 기본 true
// Tick에서
if (Dist2D <= AcceptanceRadius + 100.0f) { ... } // ← 왜 +100인가?
```

원인을 찾아보니 **`bStopOnOverlap`이 켜져 있으면 캡슐이 목표에 닿는 순간 멈춥니다.** 즉 **실제 정지 거리가 종족별 캡슐 반경만큼 달라집니다.** 고블린(37.5)과 오크(120)가 서로 다른 거리에서 멈추는데 판정 반경은 하나이니, 그 차이를 `+100`이라는 여유값으로 덮고 있었던 겁니다.

```cpp
MoveToLocation(Target, AcceptanceRadius, /*bStopOnOverlap=*/false);
if (Dist2D <= AcceptanceRadius) { ... }   // 여유값 제거
```

> **매직 넘버는 대개 다른 곳의 불일치를 덮는 반창고입니다.** `+100`이 왜 있는지 물었더니 정지 반경과 판정 반경이 어긋나 있다는 진짜 문제가 나왔고, 그걸 고치니 숫자 자체가 필요 없어졌습니다.
>
> 그리고 `Dist2D`(Z 제외)로 바꾼 것도 같은 맥락입니다. **종족별 캡슐 높이가 도착 판정에 섞이지 않게** 하는 것이 목적입니다.

### 5. NavMesh 투영을 일부러 좁게 잡았다

마커 위치를 NavMesh 높이에 맞출 때, **XY는 그대로 두고 Z만** 보정합니다.

```
ProjectPointToNavigation(마커 위치, extent = (0, 0, 300))
```

**extent의 XY를 0으로 준 게 핵심입니다.** 이러면 **마커 XY가 NavMesh 폴리곤 안에 실제로 있을 때만** 통과하고, 밖에 있으면 실패합니다. XY에 여유를 주면 **옆 폴리곤 높이를 잘못 가져와서** 엉뚱한 Z가 나옵니다.

그리고 실패 시 **fallback 없이 무효 처리 + 에러 로그**입니다.

> 지난주 오크 버그는 **투영 범위가 종족마다 달라 큰 종족만 실패**하는 문제였는데, 이번엔 반대로 **투영을 일부러 좁게 잡아 실패를 드러냈습니다.** 여유를 주면 *"어쨌든 동작하는 것처럼 보이는"* 상태가 되고, 그러면 **원인이 "마커를 잘못 놨다" 하나로 좁혀지지 않습니다.**
>
> "조용한 폴백이 공범"이라는 교훈을 이번엔 **설계 단계에서** 적용했습니다.

**계산은 지연 + 캐시**입니다. `BeginPlay` 시점엔 NavMesh 빌드가 안 끝났을 수 있어서, **최초 호출 시 1회만** 계산하고 이후엔 캐시를 씁니다. 무효화 지점은 진열대가 움직이는 **세 곳**(`OnConstruction`, 들어 올릴 때, 새 자리에 놓을 때)뿐입니다.

### 6. C++는 살아 있는데 한 번도 안 불렸다

구현을 마치고 돌려보니 **손님이 위치까지는 정확히 가는데 방향을 안 돌았습니다.**

**결론부터: 죽은 코드가 아니었습니다.** 컴파일되고 도달 가능한 정상 코드인데, **그 기능을 켜 주는 StateTree 에셋을 저장하지 않았습니다.**

```cpp
UPROPERTY(EditAnywhere, Category = "Parameter")
bool bFaceTargetOnArrival = false;   // ← 아무도 true로 바꿔주지 않았다
```

이 값을 `true`로 바꾸는 주체는 **StateTree 에셋의 노드 설정뿐**입니다. 그 설정이 없으니 회전을 적용하는 두 곳의 `if` 블록에 **절대 진입하지 못하고**, `ApplyArrivalFacing()`의 **호출 횟수는 0회**였습니다.

> 더 무서운 건, 설령 `true`였더라도 `FacingRotation`이 바인딩되지 않아 `ZeroRotator`가 들어갔을 거라는 점입니다. 그러면 *"방향을 안 보는"* 게 아니라 **전원이 월드 +X를 보고 서는** 다른 증상이 나왔을 겁니다.
>
> **C++ 기본값이 `false`인 기능은 에셋이 켜주지 않으면 존재하지 않는 것과 같습니다.** 컴파일도 되고 테스트도 통과하는데 **실행만 안 됩니다.** 며칠 전 *"에디터에서 안 만진 필드는 직렬화되지 않는다"* 를 배웠는데, 이번엔 그 성질이 **기능 전체를 조용히 꺼놓은** 형태로 돌아왔습니다.

### 7. 같은 원인에서 파생된 문제 2개

**① 판정 반경도 진열대 값을 안 쓰고 있었다**

`AcceptanceRadius` Output이 바인딩되지 않아, 태스크가 진열대의 `BrowseAcceptanceRadius`(70)가 아니라 **자기 기본값 50**을 쓰고 있었습니다.

> 즉 *"진열대가 판정 반경을 소유한다"* 는 **이번 작업의 설계 의도가 정작 진열대 이동 경로에서 작동하지 않는 상태**였습니다. 진열대별로 값을 조정해도 아무 변화가 없습니다.
>
> 다만 `MoveToLocation`과 Tick 판정이 **둘 다 같은 값**을 쓰므로 *"정지 반경 = 성공 반경"* 이라는 **내부 일관성은 안 깨졌습니다. 값만 틀렸습니다.** 그래서 겉으로는 아무 문제 없어 보였습니다.

게다가 50은 `AgentRadius = 75`보다 작아서, **진열대·벽에 막혀 반경 안으로 못 들어오는** 경우가 생길 수 있습니다.

**② `ReturnProducts`는 배선과 무관하게 회전 코드가 아예 없다**

`TargetFacing`을 받아오긴 하는데 **디버그 드로우에만 전달**하고 회전에 적용하는 코드가 없습니다. 여기는 **C++ 수준의 진짜 미사용**이라, 배선을 고쳐도 상품을 되돌려놓으러 간 손님은 여전히 방향을 안 봅니다.

> **같은 증상(회전 안 됨)인데 원인이 두 층에 따로 있었습니다.** 하나를 고쳐도 다른 하나가 남습니다.

### 8. 아직 못 정한 것 — 방안 A vs B

| | **A. 에셋에 배선** | **B. C++만 수정** |
| :--- | :--- | :--- |
| 방법 | `MoveToLocation` 노드에 Output 2개 바인딩 + 체크박스 켜기 | 회전 적용을 `BrowseShelf`로 옮김 (**이미 `TargetShelf` 바인딩 있음**) |
| 장점 | 설계 의도 그대로 + **판정 반경 문제(§8-①)도 함께 해결** | 에셋 무수정, **배선 누락으로 조용히 죽는 구조가 사라짐** |
| 단점 | **노드를 새로 추가할 때 배선을 빠뜨리면 같은 문제가 조용히 재발** | 판정 반경 문제는 별도 처리 필요 |

> 판단이 갈리는 지점은 **"설계의 정합성"과 "실수에 대한 내성"** 중 무엇을 살 것인가입니다. A는 구조가 깔끔하지만 **사람이 매번 배선해야** 하고, B는 좀 덜 예쁘지만 **잊어버릴 수가 없습니다.**
>
> 오늘 이 문제 자체가 **배선을 빠뜨려서 생긴 것**이라, 같은 사고가 또 날 가능성을 무시하기 어렵습니다. 다만 A를 택하면 반경 문제까지 한 번에 정리되니 아직 결론을 못 냈습니다.

어느 쪽이든 `ReturnProducts`의 회전 미적용과 잔존 `BrowseDistance` 정리는 **별도로** 필요합니다.

### 9. 다음 단계 메모 — 몸 크기 문제 정리

지난주 오크 버그의 근본 대응도 함께 정리했습니다.

| 항목 | 방향 |
| :--- | :--- |
| `AgentRadius` | **Supported Agents와 `RecastNavMesh-Default` 양쪽을 75로 통일** |
| 진열대 | 콜리전 없는 Box 추가 + **Dynamic Obstacle** 체크 |
| 설치 제한 | 마커 기준으로 **오크 반경에 맞춘 영역**을 만들고, 그 영역을 정면으로만 확보 |
| **종족 스케일 하향** | 20·30대 **0.8** / 오크 **1.0** / 엘프 **0.9** / 드워프 **0.7** |

> 오크를 **1.6 → 1.0** 으로 내리는 게 핵심입니다. 지난주에 코드로 임계값 의존을 없앴지만, **애초에 몸이 통로보다 큰 것 자체가 설계 문제**였습니다. 코드로 버틸 수 있게 만드는 것과, 그 상황을 안 만드는 것은 다릅니다.
>
> 설치 제한 범위를 **표시할지 말지**는 아직 고민 중입니다. 안 보여주면 플레이어가 왜 안 놓이는지 모르고, 보여주면 화면이 지저분해집니다.
