# **[UE5] 체험판 규칙을 분리하고 3일의 플레이를 종료하기**

오늘은 이세계 편의점의 체험판을 구현했습니다. 목표는 **3일 동안 기본 영업·직원 고용·마법진 강화를 경험하고, 레벨 3에서 체험을 마치는 흐름**입니다.

데모 판정 기반부터 성장 제한, 필수 과제, 안내 문구, 3일차 종료 처리를 연결했습니다. 진행을 제한하는 과정에서 **규칙을 정하는 위치, 실제 적용하는 경로, 화면에 보여 주는 시점**을 함께 살펴볼 수 있었습니다.

데모 타깃·판정 기반은 커밋했고, 레벨·유물 제한은 빌드와 테스트를 마쳤습니다. 이후 과제·안내·종료 처리도 빌드에 반영했으며, 1일차부터 3일차 종료까지 한 번 진행한 경로를 로그로 확인했습니다. 세부 화면 검증과 저장 차단·배포용 정리는 아직 남아 있습니다.

<br>

## **1. 체험판 규칙을 한곳에서 판단하기**

체험판에는 레벨 상한, 마지막 영업일, 허용 유물, 기능별 접근 범위처럼 여러 시스템이 함께 알아야 하는 규칙이 있습니다. 이번에는 `UCSDemoRules`를 공통 판정의 입구로 만들었습니다.

| 구분 | 역할 |
| :--- | :--- |
| `ConvenienceStoreDemo` | 데모용 게임 빌드 타깃 |
| `CS_DEMO_BUILD` | 데모·정식 타깃을 구분하는 컴파일 플래그 |
| `UCSDemoRules` | 레벨·일차·콘텐츠·기능 접근에 대한 공통 판정 |
| 체험판 시뮬레이션 | 에디터 PIE에서 체험판 규칙을 확인하는 개인 설정 |

다른 시스템은 “데모인가”, “이 콘텐츠를 허용하는가”를 공통 함수에 묻습니다. 여러 곳에서 같은 기준을 사용하면 상한이나 허용 목록을 확인할 위치가 명확해집니다.

여기서 구분해야 할 점은 **판정 함수를 만드는 것과 실제 동작에 연결하는 것은 별도 작업**이라는 것입니다. `IsSaveEnabled()`가 체험판에서 false를 반환하더라도, 저장 경로가 이를 사용하도록 연결하기 전에는 저장이 계속 동작합니다. 현재 저장 차단은 후속 단계입니다.

낚시·펫·채집도 접근 판정은 준비했지만 시스템 자체가 아직 없어 실제 기능 연결은 하지 않았습니다. 이번에 연결한 기능은 요정의 집입니다.

> **배운 점:** 공통 규칙의 구현 여부와 각 시스템의 적용 여부를 따로 기록해야 완료 범위를 정확히 알 수 있습니다.

## **2. 하루 1레벨은 경험치보다 지급 시점이 중요했다**

체험판은 1일차 레벨 1, 2일차 레벨 2, 3일차 레벨 3으로 진행합니다. 판매 경험치는 다음 레벨 직전까지만 쌓이고, 부족한 경험치를 다음 날 지급합니다.

| 시점 | 처리 |
| :--- | :--- |
| 당일 판매 | 다음 레벨 직전까지 경험치 누적 |
| 처음 상한에 도달 | “오늘 밤 자고 일어나면 가게 레벨이 오릅니다.” 알림 |
| 날짜 변경 | 레벨업 지급을 대기 상태로 표시 |
| 눈뜨기 연출 종료·HUD 복귀 | 부족한 경험치 지급, 기존 레벨업·해금 연출 연결 |
| 레벨 3 도달 | 경험치·레벨 성장 정지 |

날짜가 바뀌는 순간 경험치를 지급하면 암전·기상 연출 중에 레벨업 효과음과 안내가 시작될 수 있습니다. 그래서 **일차 변경과 플레이어에게 레벨업을 보여 주는 시점을 나눴습니다.**

`bBusinessDayLevelPending`으로 지급 대기를 표시하고, `ApplyPendingBusinessDayLevel()`에서 실제 지급을 처리했습니다. 정산 화면이나 HUD에서 수면 없이 다음 날로 넘어가는 경로는 그 자리에서 지급하도록 연결했습니다.

또한 `FinishSleep`은 월드 정리 과정의 `EndPlay`에서도 호출될 수 있어, 월드가 정리되는 중에는 레벨업을 지급하지 않도록 했습니다. 정상 플레이뿐 아니라 **종료·정리 과정에서 같은 함수가 호출되는 경우**도 확인해야 했습니다.

경험치 가득 알림은 별도의 “하루 한 번” 플래그 대신, 이번 거래에서 처음 상한에 도달했는지를 기준으로 처리했습니다. 조건의 변화로 표현할 수 있는 부분은 저장할 상태를 늘리지 않고 해결했습니다.

## **3. 콘텐츠 제한은 추첨·목록·사용을 함께 맞추기**

우물 유물은 공통 허용 목록의 5종만 사용할 수 있도록 구성했습니다.

| 적용 경로 | 처리 |
| :--- | :--- |
| 우물 추첨 | 허용 유물만 후보에 포함 |
| 보상 목록 보기 | 같은 허용 목록으로 표시 |
| 유물 사용 | 목록 밖 유물은 사용 실패, 소모하지 않음 |

추첨만 제한하면 표시 목록이나 실제 사용 조건과 어긋날 수 있습니다. **플레이어가 보는 범위와 실행 가능한 범위가 같은 기준을 쓰도록 연결**했습니다.

기능 접근은 단순한 켬·끔 대신 **사용 가능 / 겉모습만 / 사용 불가**로 나눴습니다. 요정의 집은 외형을 유지하면서 상호작용하면 정식판 안내를 띄웁니다. 기존 대사와 계약 처리 앞에서 접근 여부를 판단하도록 했습니다.

이 방식으로 체험판에서 기능을 제한하면서도, 월드에서 보이는 시설과 안내를 연결할 수 있었습니다. 다만 공통 판정 기반만으로 배포 에셋 제외까지 끝나는 것은 아니므로 Cook 정리는 별도로 남겨 뒀습니다.

<br>

## **4. 무료 처리는 표시와 결제 조건을 함께 바꾸기**

체험판의 직원 고용·일급과 마법진 2단계 강화는 무료입니다. 비용 반환값을 0으로 바꾸는 것에 더해, 실제 결제 함수도 0G를 정상적인 비용으로 처리하도록 수정했습니다.

확인한 지점은 다음과 같습니다.

- 최소 1G 보정 등이 끝난 비용에 체험판 무료 규칙을 적용하기
- 0G일 때 자금 차감 없이 고용·강화가 성공하도록 처리하기
- 자금이 음수여도 무료 기능을 사용할 수 있도록 조건 맞추기
- 화면에는 “무료”, 일급에는 “없음”으로 안내하기

임대료·발주·우물 비용은 기존대로 유지했습니다. “체험판은 무료”라는 표현보다 **어떤 기능의 어떤 비용이 무료인지 범위를 명확히 하는 것**이 필요했습니다.

마법진은 2단계까지 체험할 수 있습니다. 다음 강화가 정식판 전용이면 원래 강화비 데이터를 표시하되 버튼을 막고 정식판 안내를 보여 줍니다. 비용 표시와 실행 허용 여부도 각각 의미를 갖도록 정리했습니다.

<br>

## **5. 필수 과제는 생성 순서와 예외 경로까지 보기**

2일차에는 진열 직원 고용, 3일차에는 마법진 2단계 강화를 마쳐야 개점할 수 있습니다. `UCSDemoTaskSubsystem`에서 과제를 관리하고, 고용·강화 이벤트로 완료를 확인합니다.

처음에는 월드 시작 때 과제를 설정하는 흐름을 검토했지만, 서브시스템 시작이 고용소 지원자 생성보다 앞설 수 있었습니다. 실제 구현은 **영업일 시작 이벤트에서 과제를 설정**하도록 했습니다. 체험판은 과제가 없는 1일차부터 시작합니다.

| 예외 상황 | 처리 |
| :--- | :--- |
| 이미 과제를 완료함 | 다시 요구하지 않음 |
| 오늘 이미 개점함 | 이후 고객 입장 마감·재개는 막지 않음 |
| 대상이 없는 테스트 맵 | 경고를 남기고 과제를 건너뜀 |
| 과제를 수행할 수 없는 상태 | 오류 로그를 남기고 개점 차단 해제 |
| 완료 이벤트를 놓침 | 입간판이 개점 가능 여부를 물을 때 완료 조건 재확인 |

진행을 막는 기능은 정상 조건뿐 아니라 **차단을 해제하는 조건**도 필요했습니다. 오류가 생겼을 때 플레이가 영구적으로 막히지 않게 하고, 로그로 원인을 찾을 수 있도록 했습니다.

<br>

## **6. 종료 조건은 다음 날 진행의 공통 경로에 연결하기**

마지막 밤에는 수면 위젯 버튼을 “체험판 마치기”로 바꾸고, 다음 날을 시작하는 공통 함수 `StartNextBusinessDay`에서 마지막 날 여부를 검사합니다.

수면 위젯·정산 화면·HUD 마감 업무에서 다음 날로 가더라도 같은 검사를 거치게 했습니다. 마지막 날이면 `RequestEnd(Completed)`로 종료를 요청하고, 종료 화면을 띄운 뒤 게임을 일시정지합니다.

`UCSDemoSessionSubsystem`은 종료 요청과 종료 여부를 관리합니다. 레벨·일차가 제한을 초과했을 때 종료하는 방어 경로도 추가했습니다. 다만 이 비정상 경로는 아직 별도로 실행해 확인하지 않았습니다.

종료 화면은 현재 테스트용 일반 `UserWidget`입니다. 스팀 찜하기·디스코드·돌아가기 버튼은 **화면에 보이지만 기능은 연결하지 않은 상태**입니다. 게임 진행 종료와 배포용 종료 UI 완성을 구분해 기록했습니다.

<br>

## **7. 코드에서 정한 내용과 실제 화면은 다를 수 있다**

오늘은 실제 위젯을 확인하면서 설계 문서와 화면의 차이도 발견했습니다.

| 발견한 내용 | 배운 점 |
| :--- | :--- |
| 코드에는 경험치 숫자·MAX LEVEL 문구가 있지만 실제 상단바에 표시 칸이 없음 | 문자열을 설정하는 코드만으로 화면 표시를 단정할 수 없음 |
| 다음 목표가 3줄이면 확인 버튼과 겹침 | 실제 창 크기에 맞춰 레벨 3 목표를 2줄로 정리 |
| 과제 외곽선이 지원자 이름표 글씨에도 적용됨 | 대상 액터 안의 컴포넌트별 표현까지 확인 필요 |
| 기존 경고 배너로 정식판을 안내함 | 재사용한 UI의 시각적 의미가 새 용도에 맞는지 확인 필요 |

이름표 외곽선은 공용 튜토리얼 마커 자체를 바꾸는 대신, 데모 과제 마커를 켠 뒤 글씨 컴포넌트의 외곽선만 해제하도록 수정했습니다. 해당 수정의 최종 화면 결과는 아직 확인이 남아 있습니다.

종료 화면 X를 눌러 맵을 다시 열 때 에디터가 종료되는 문제도 있었습니다. 작업 기록의 로그에서는 에디터 실행 취소 기록이 옛 위젯 인스턴스를 통해 임시 월드를 붙잡은 연결이 확인됐습니다. **당시 에디터 상태와 관련된 것으로 추정하며, 재시작 후에도 재현되는지는 아직 확인하지 못했습니다.** 현재 해당 버튼 경로는 제거했습니다.

## **8. 로그로 확인한 사실과 남은 검증 나누기**

18:02 에디터 빌드에는 마지막 소스 수정인 17:59까지의 변경이 반영됐습니다. 이 빌드로 체험판 시뮬레이션을 켜고 진행한 실행을 로그와 대조했습니다.

| 시각 | 확인한 진행 |
| :--- | :--- |
| 18:39:58 | 1일차 체험판 시작 |
| 18:41:04 | 2일차 진입 |
| 18:42:11 | 3일차 진입 |
| 18:43:28 | 3일차·레벨 3에서 완료 사유로 종료 |

시작·종료 로그가 기록됐고, 이후 4일차 시작 로그는 없었습니다. 종료 화면 생성 실패 오류도 없었습니다. 반면 **화면 배치와 버튼 문구를 직접 확인한 결과는 아니므로**, UI까지 모두 정상이라고 판단하지 않았습니다.

2일차 진열 직원 고용 후 개점은 로그에서 확인했습니다. 3일차 강화는 직접 성공 로그가 없어, 개점 성공과 과제 건너뜀·오류 로그가 없다는 점으로 완료된 것으로 추정했습니다.

또한 개점 시 `InputMode:UIOnly`의 비포커스 위젯 포커스 오류가 반복됐습니다. 종료 처리 관련 오류가 없었다는 사실과 실행 전체에 오류가 없었다는 주장은 다릅니다. 발생 위젯은 추가 확인이 필요합니다.

에디터의 “3일차 마감 직전” 시작 기능은 구현했지만 아직 실행하지 않았습니다. 하루를 건너뛰는 테스트 경로와 실제 1일차부터 진행하는 경로도 별도로 확인해야 합니다.

## **9. 오늘 배운 점과 다음 확인**

- **규칙과 적용 경로를 나누기:** 판정 함수가 있어도 실제 호출 경로를 연결해야 동작이 바뀝니다.
- **지급과 표현 시점을 맞추기:** 레벨업처럼 여러 연출을 발생시키는 이벤트는 플레이어가 볼 수 있는 시점에 실행해야 합니다.
- **차단과 해제 조건을 함께 만들기:** 필수 과제가 진행을 막을 때는 생성 순서와 완료 이벤트 누락도 고려해야 합니다.
