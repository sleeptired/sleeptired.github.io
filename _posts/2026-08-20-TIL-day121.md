## 오크만 길을 못 찾는 버그 — 좌표 기준이 두 개였다

> 양방향 거리 통행 + 영역 기반 스폰을 넣고 나니 **오크(가장 큰 종족)만** 가게 앞 판정 지점에 도달하지 못했습니다. 다른 종족은 전부 정상이었습니다. **"왜 하나만"** 을 파고들다 좌표 기준을 잘못 이해하고 있었다는 걸 알게 됐습니다.

---

### 1. 오늘 한 일

| 항목 | 내용 |
| :--- | :--- |
| **버그 추적** | 오크 경로 실패 — 원인 확정 후 근본 수정 |
| **기능 구현** | 양방향 통행(A↔B 50%) + TriggerBox 영역 기반 스폰 |
| **문서** | 팀원용 스포너 설정 가이드 / 소비심리 시스템 지도 (읽기 전용 조사) |

### 2.  이분 탐색으로 임계값을 특정하기

*"오크만 이상하다"* 는 관찰에서 시작해 **`CharacterScale`만 바꿔가며** 재현했습니다.

| Scale | 캡슐 반높이 (180 × Scale) | 결과 |
| :---: | :---: | :---: |
| 1.60 | 288 | **고장** |
| 1.40 | 252 | **고장** |
| **1.38** | **248.4** | **정상** |
| 1.30 | 234 | 정상 |

1.38과 1.40 사이에서 갈립니다. 이 구간에서 **반경은 103.5 → 105로 사실상 같고, 반높이만 250을 넘습니다.**

그리고 `RecastNavMesh-Default` 설정을 열어보니:

```
NavDataConfig.DefaultQueryExtent = (X=50, Y=50, Z=250)
```

**임계값 250 = `DefaultQueryExtent.Z`.** 숫자가 정확히 일치하는 순간 원인이 확정됐습니다. 임계 스케일은 $250 \div 180 = 1.3889$.

> **"큰 종족이라서"는 원인이 아니라 증상의 재진술입니다.** 크기를 연속적으로 바꿔가며 **정확히 어디서 갈리는지** 찾으니 숫자 하나가 나왔고, 그 숫자를 프로젝트 설정에서 검색하니 원인이 나왔습니다. **경계값을 특정하면 원인이 특정된다**는 걸 처음 체감했습니다.

### 3.  원인 — 한 함수의 반환값이 성질 다른 세 곳에 쓰였다

언리얼에는 **좌표 기준이 두 개**입니다.

| 쓰는 곳 | 기준점 | 필요한 Z |
| :--- | :--- | :--- |
| `SpawnActorDeferred(SpawnTransform)` | 액터 원점 = **캡슐 중심** | 지면 + 반높이 |
| `AIController::MoveToLocation(목표)` | `GetActorFeetLocation()` = **발바닥** | **지면 그대로** |

그런데 `PickPointInArea()`는 마지막에 **캡슐 중심 높이로 올려서** 반환하고 있었고, 그 **하나의 반환값이 세 곳에** 그대로 쓰였습니다.

```cpp
const FVector SpawnLocation = PickPointInArea(StartArea, ...);        // 스폰   → 캡슐 중심이 맞음  ✅
State->ExitLocation        = PickPointInArea(EndArea, ...);           // nav 목표 → 지면이어야 함  ❌
State->StorefrontLocation  = PickPointInArea(StorefrontPoint, ...);   // nav 목표 → 지면이어야 함  ❌
```

**스폰에만 맞는 보정이 nav 목표 두 개에도 딸려 갔습니다.**

**그리고 코드 주석에 이렇게 적혀 있었습니다.**

```cpp
// Z가 캡슐 중심 높이로 올라가 MoveToLocation의 도착 판정과도 맞는다.
```

> **이 전제가 틀렸고, 그게 버그의 출발점이었습니다.** 도착 판정은 발바닥 기준입니다. 잘못된 이해가 주석으로 기록되면 **그 뒤로는 아무도 의심하지 않게 됩니다.** 주석이 근거가 되어버리는 구조라, 틀린 주석은 틀린 코드보다 오래 삽니다.

### 4.  왜 오크만? — 투영이 오차를 조용히 삼켜주고 있었다

`MoveToLocation`은 경로 탐색 전에 목표를 NavMesh 폴리곤에 **투영**합니다. 그 검색 범위가 `DefaultQueryExtent`입니다.

```
목표 Z = 지면 + 반높이          ← 잘못된 값
   ↓ NavMesh 투영 (수직 ±250 안에서 폴리곤 탐색)
반높이 ≤ 250  →  지면 폴리곤 발견 → Z가 지면으로 되돌아감 → 정상 (오차가 삼켜짐)
반높이 >  250  →  폴리곤 못 찾음  → 경로 요청 실패
```

도로 지면 Z가 약 38일 때 종족별로:

| 종족 | 반높이 | 목표 Z | 투영 검색 범위 | 지면 38 포함? |
| :--- | ---: | ---: | :--- | :---: |
| 고블린 | 90 | 128 | −122 ~ 378 | O |
| 모험가 | 180 | 218 | −32 ~ 468 | O |
| 엘프 | 234 | 272 | 22 ~ 522 | **O (여유 16)** |
| **오크** | **288** | **326** | **76 ~ 576** | **X** |

> **모든 종족이 같은 버그를 갖고 있었는데, 엔진이 조용히 고쳐주고 있었습니다.** 엘프는 여유가 **16**으로 아슬아슬하게 살아 있었습니다. 지형이 조금만 높았어도 엘프까지 터졌을 겁니다.
>
> **"하나만 고장 났다"는 건 하나만 잘못됐다는 뜻이 아닙니다.** 전부 잘못됐는데 **허용 오차 안에 들어 있었을 뿐**일 수 있습니다. 이 경우 "정상인 것들"을 근거로 원인을 좁히면 오히려 헤맵니다.

### 5. 왜 실패가 조용했나

```cpp
Data.AIController->MoveToLocation(State->StorefrontLocation, Data.AcceptanceRadius);
return EStateTreeRunStatus::Running;   // ← 반환값을 확인하지 않음
```

*   `MoveToLocation`이 `Failed`를 반환하는데 **확인하지 않습니다.**
*   바로 위의 `StorefrontLocation.IsNearlyZero()` 검사는 **통과합니다** (326은 0이 아니므로).
*   결과: **로그 한 줄 없이** 실패합니다.

그리고 `ExitLocation`도 같은 이유로 실패하므로 **오크는 어디로도 경로를 못 잡습니다.**

```
Approach 진입 → MoveTo 실패 → Idle
   → Tick 폐점 판정 → Failed → Leave 진입 → ExitLocation MoveTo도 실패 → Failed
   → Root → HasEnteredStore == false → Approach 재진입 → 반복 (매 프레임)
```

화면상으로는 **"그 방향에서 맴도는"** 모습이 됩니다.

> **반환값을 안 보면 실패가 조용해진다** — 지난주 "조용한 폴백"에 이어 **두 번째로 같은 종류의 교훈**을 만났습니다. 이번엔 폴백이 아니라 **무시된 반환값**이 범인이었습니다. 형태는 달라도 원인은 같습니다: **실패했다는 사실이 어디에도 안 남는 것.**

### 6. 해결 — 보정을 필요한 곳에서만

```cpp
// PickPointInArea() — 반환은 지면 Z
const FVector CapsuleCenter = Ground + FVector(0, 0, BodyHalfHeight);
if (IsBodyBlockedAt(CapsuleCenter, ...)) { ... }   // 겹침 검사만 캡슐 중심으로
return Ground;                                      // nav 목표로도 쓰이므로 지면 기준

// 호출부 — 스폰에서만 반높이를 더한다
const FVector SpawnGround   = PickPointInArea(StartArea, ...);
const FVector SpawnLocation = SpawnGround + FVector(0, 0, BodyHalfHeight);
```

**함께 고쳐진 것 3가지**

| 항목 | 내용 |
| :--- | :--- |
| **폴백 경로 불일치** | 영역 없음 / 크기 없음 / 투영 실패 세 폴백은 Z 보정이 **안 된 값**을 반환하고 있었음. **정상 경로만 보정되어 서로 어긋나 있었다** → 네 경로가 지면 기준으로 통일 |
| 스포너 위치 폴백 시 파묻힘 | 큰 종족이 바닥에 반쯤 묻히던 문제 해결 |
| **`DefaultQueryExtent` 의존 제거** | 스케일이 2.0, 3.0이 되어도 다시 안 터짐 |

> 검증 항목에 **"`CharacterScale`을 2.5까지 올려도 정상인지"** 를 넣었습니다. 임계값을 넘겼는데도 동작해야 **임계값 의존이 진짜 사라진 것**입니다. 우회책(B안: QueryExtent를 600으로)을 골랐다면 이 검증을 통과 못 합니다.

### 7. 아닌 것을 지우는 것도 진단이다

원인을 찾는 동안 **9개 후보를 배제**했습니다.

| 배제한 후보 | 근거 |
| :--- | :--- |
| 박스가 오크보다 작아 중심 붕괴 | BoxExtent 200 > 반경 120, 경고 로그도 없음 |
| 오크가 통로에 낌 | 회랑 실효 폭 530 > 오크 지름 240 |
| `MaxStepHeight` 45 | 전 종족 동일값 → 종족 차이를 만들 수 없음 |
| 손님끼리 막음 | 캡슐이 `ECC_Pawn` Ignore, RVO 꺼짐 |
| 손님이 NavMesh를 깎음 | `bCanEverAffectNavigation = False` |
| 도달 반경 | 오크가 **오히려 더 먼 거리**에서 도착 처리됨 (방향이 반대) |

> **"전 종족 동일값이라 종족 차이를 만들 수 없다"** 같은 논리가 후보를 빠르게 지워줍니다. **증상이 종족별로 갈리면, 종족별로 다른 값만 용의자**입니다. 이 필터 하나로 절반이 사라졌습니다.

### 8. 영역 기반 스폰 — 종족 크기가 만드는 편차

지점 액터 대신 **TriggerBox 영역**에서 뽑도록 바꿨는데, 여기서도 크기가 변수였습니다.

```
실제 뽑히는 범위 = BoxExtent − 캡슐 반경
```

| 종족 | 반경 | BoxExtent 200일 때 산포 |
| :--- | ---: | ---: |
| 고블린 | 37.5 | ±162.5 |
| 모험가 | 75 | ±125 |
| **오크** | **120** | **±80** |

**오크의 산포가 고블린의 절반**이고, BoxExtent가 120 이하면 **오크는 박스 중심 한 점으로 붕괴**합니다. 그래서 가이드에 **"한 변 240 초과"** 를 필수 규칙으로 넣고 경고 로그도 달았습니다.

배치 규칙 3가지도 함께 정리했습니다.

| 규칙 | 이유 |
| :--- | :--- |
| **회전 금지** | `GetActorBounds()`가 **AABB**를 돌려주므로 45도 돌리면 실제보다 **1.41배** 넓게 잡혀 인도 밖까지 후보가 튐 |
| **박스를 지면 근처에** | Z 투영 탐색 범위가 `max(반높이×2, 200)`이라 **종족마다 다름**. 박스가 뜨면 **작은 종족만 투영 실패** |
| **NavMesh 겹침 200 이상** | 현재 도로-매장 NavMesh 겹침이 **46 유닛뿐**. 볼륨을 조금만 움직이면 끊겨서 **아무도 가게에 못 들어옴** |

> 두 번째가 4절과 **정확히 반대 방향의 같은 문제**입니다. 4절은 큰 종족이 터졌고, 이건 **작은 종족이 터집니다.** 둘 다 "종족마다 다른 탐색 범위"가 원인인데 어느 쪽이 걸리느냐만 다릅니다.

### 9. 이름을 바꾸면 레벨 할당이 풀린다

양방향이 되면서 프로퍼티 이름을 바꿨습니다.

| 이전 | 이후 | 이유 |
| :--- | :--- | :--- |
| `EntrancePoint` | **`StreetEndpointA`** | 어느 쪽이 입구인지 **손님마다 다름** (50% 확률로 뒤집힘) |
| `ExitPoint` | **`StreetEndpointB`** | 위와 같음 |

> **언리얼은 값을 프로퍼티 "이름"으로 저장합니다.** 이름이 바뀌면 **레벨에 배치된 인스턴스의 기존 할당이 전부 풀립니다.** CoreRedirect를 넣지 않았으니 에디터에서 다시 꽂아야 합니다.
>
> 더 나쁜 건 **크래시가 안 난다**는 점입니다. 손님이 스포너 위치에서 태어나 그 자리에서 사라질 뿐이라, 모르는 사람은 원인을 찾기 어렵습니다. **컴파일은 통과하는데 데이터만 조용히 비는** 종류의 변경이라, 팀원용 설정 가이드를 따로 썼습니다.

가이드는 **로그 → 원인 → 해결** 표와 **"로그가 없는데 이상할 때"** 표를 나눠서 구성했습니다. 증상만 보고 역추적할 수 있어야 실제로 쓰이니까요.

### 10. 소비심리 시스템 지도 만들기

별개로 **소비/심리 파라미터가 지금 어디에 어떻게 붙어 있는지**를 읽기 전용으로 조사했습니다. 코드는 한 줄도 안 고쳤습니다.

**확인된 것 — 값은 있는데 아직 판단에 안 붙은 항목 6개**

| 항목 | 상태 |
| :--- | :--- |
| `BrandLoyalty` / `PromotionSensitivity` | 미사용 (할인·행사 시스템 자체가 없음) |
| `DwellTimeSeconds` | 미사용 (체류시간은 `EvaluationBudget`으로만 간접 표현) |
| `FCSProductDataRow.BaseDemand` | 상품별 기본 수요가 점수식에 미반영 |
| `StoreEntryChance` | **1.0 고정 = 전원 입장** (임시값) |
| 평판 → 유입 배율 | `TODO(평판)` |

**구조적으로 눈에 띈 것**

*   점수 가중치가 **가격 3 : 카테고리 1 : 예산 1** — 가격이 가장 강한 결정 요인인데, 이 **가중치가 DA가 아니라 컴포넌트에 있습니다.** 종족별로 다르게 하려면 DA로 옮겨야 합니다.
*   `Impulsiveness`는 **구매 점수식에 안 들어가고** 인내심·되돌려놓기 **행동 두 곳에만** 쓰입니다.
*   집는 순간의 가격을 `SalePriceAtPickup`으로 **동결 저장**해서, **손님이 판단할 때 본 가격과 결제 금액이 항상 일치**합니다.

> 지도를 만들고 나니 **"이 값을 바꾸면 무엇이 움직이는가"** 가 표 하나로 보입니다. 밸런싱을 시작하기 전에 이걸 먼저 만든 게 맞았던 것 같습니다. 미사용 6개를 미리 알고 있으면 **"값을 바꿨는데 아무 일도 안 일어나는"** 시간 낭비를 피할 수 있습니다.

### 오늘의 정리

| 배운 것 | 내용 |
| :--- | :--- |
| **경계값을 특정하면 원인이 특정된다** | 1.38/1.40 사이 → 250 → 설정값과 일치. "큰 종족이라서"는 증상의 재진술일 뿐 |
| **하나의 반환값을 성질 다른 곳에 쓰지 않는다** | 스폰(캡슐 중심)과 nav 목표(발바닥)는 기준이 다르다. 한쪽에 맞춘 보정이 나머지를 망친다 |
| **틀린 주석은 틀린 코드보다 오래 산다** | 잘못된 전제가 주석으로 기록되면 그 뒤로 아무도 의심하지 않는다 |
| **엔진이 오차를 삼켜주면 버그가 숨는다** | 전 종족이 같은 버그였는데 투영이 조용히 고쳐주고 있었다. 엘프는 여유 16 |
| **"하나만 고장"이 "하나만 잘못"은 아니다** | 정상인 것들을 근거로 좁히면 오히려 헤맨다 |
| **반환값을 안 보면 실패가 조용해진다** | 조용한 폴백에 이은 두 번째 사례. 형태는 달라도 "실패가 안 남는다"는 같다 |
| **종족별로 갈리는 증상은 종족별로 다른 값만 용의자** | 이 필터 하나로 후보 절반이 사라졌다 |
