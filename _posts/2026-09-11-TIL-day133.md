## 날씨 실내·실외 판정 구현과 눈 연출 버그 두 개

> 비·눈이 **실내에서도 캐릭터에게 쏟아지던 문제**를 해결하려고 실내·문 앞 판정을 만들었습니다. 만들다 보니 **눈 연출 버그 두 개**가 같이 드러나서 함께 고쳤습니다.

### 2. 판정은 서브시스템이 하고, 액터는 박스만 갖게 했다

영역 액터가 스스로 *"플레이어가 들어왔으니 이펙트를 꺼라"* 를 하지 않습니다. **오버랩 이벤트를 서브시스템에 알리기만** 합니다.

```
JudgeBox / IndoorBox 오버랩
  → Subsystem::NotifyShelterOverlapChanged(OtherActor)
      → EvaluateSheltered()      등록된 모든 박스를 조회
      → 바뀌었으면 ApplyShelterState()
```

**왜 이렇게 나눴나**

> 영역이 **여러 개**입니다(문 앞 2곳, 실내 2곳). 각 액터가 자기 판단으로 끄고 켜면 **문턱에서 두 액터가 서로 반대 명령을 내립니다.** 정문 박스를 나가면서 실내 박스에 들어가는 순간, 나가는 쪽은 *"켜라"*, 들어가는 쪽은 *"꺼라"* 를 같은 프레임에 보냅니다.
>
> **판정 주체가 하나면 이런 경합이 구조적으로 없습니다.** 액터는 *"뭔가 바뀌었다"* 만 알리고, 최종 판단은 한 곳에서 합니다.

```cpp
bool EvaluateSheltered(const AActor* PlayerPawn) const
{

    // 하나라도 겹치면 true

```

**이벤트 내용을 그대로 믿지 않은 이유**

> 문턱에서 **정문 박스를 나가는 이벤트**와 **실내 박스에 들어가는 이벤트**가 연달아 옵니다. 나가는 이벤트만 보고 *"밖이다"* 로 처리하면, 실내로 들어가는 중인데 **한 프레임 동안 비가 쏟아집니다.**
>
> 전체를 다시 조회하면 *"어느 박스든 하나라도 걸쳐 있으면 안"* 이 되어 **깜빡임이 안 생깁니다.** 오버랩 목록은 **이벤트가 방송되기 전에 이미 갱신**되므로, 조회하면 현재 상태가 정확히 나옵니다.

박스가 4개뿐이라 매번 전체 조회해도 비용이 무시할 수준입니다. **정확성을 위해 싼 비용을 지불한 경우**입니다.

### 4. 박스 사이 빈칸을 50 cm 이하로 못 박았다

판정 박스와 실내 박스 사이를 얼마나 띄울지가 문제였습니다. 헤더 주석에 **규칙으로 적었습니다.**

| 조건 | 근거 |
| :--- | :--- |
| 빈칸 **≤ 50 cm** | **캡슐 지름(100 cm)보다 좁아야** 문턱에서 **어느 박스에도 안 걸리는 순간**이 안 생긴다 |
| 50 cm면 충분 | 양쪽에 동시에 걸치는 구간도 50 cm라, **30 fps로 달려도(프레임당 약 33 cm) 한 프레임에 건너뛰지 않는다** |

> 빈칸이 넓으면 문턱을 지날 때마다 **밖으로 판정되어 눈이 리셋**됩니다. 반대로 겹치게 두면 오버랩 이벤트가 더 많이 발생하지만, 전체 재조회 방식이라 **겹쳐도 문제가 없습니다.**
>
> **"캡슐 지름"과 "프레임당 이동 거리"** 두 수치로 상한을 정한 게 이번 판단의 핵심이었습니다. 감으로 *"한 30 cm쯤"* 이라고 정했으면 근거가 없어서 나중에 바꿀 때 기준이 없었을 겁니다.

실제 배치는 정문만 50 cm이고 나머지 두 문턱은 **0 cm(맞닿음)** 입니다. PIE에서 문턱 여러 위치로 순간이동시켜 **전부 "안"으로 판정되는 것**을 확인했습니다.

### 5. 버그 ① — 영역을 나오면 눈이 처음부터 내렸다

**증상:** 실내나 문 앞 박스에서 밖으로 나오면 **1.35초 동안 눈이 한 송이도 없다가** 위에서부터 내려와 차오릅니다.

**원인을 찾아보니 존과 캐릭터 이펙트의 끄는 방식이 달랐습니다.**

| | 존 | 캐릭터 눈 (문제) |
| :--- | :--- | :--- |
| 영역에 들어갈 때 | `SetVisibility(false)` | **`Deactivate()` → 새 눈 생성 멈춤** |
| 영역을 나갈 때 | `SetVisibility(true)` | **`Activate(true)` → 0개부터 다시** |
| 영역 안에 있는 동안 | **계속 시뮬레이션** | 공중에 남은 눈이 바닥으로 떨어져 사라짐 |

> 존은 **안 보이는 동안에도 계속 내리고 있어서** 보이는 순간 이미 정상 상태입니다. 캐릭터 눈은 생성이 멈춰 있어서 **나오는 순간 공중이 비어 있습니다.**

**수정: `Deactivate`를 쓰지 않고 `SetVisibility`만 바꿨습니다.**

```cpp
void ACSWeatherEffectActor::SetLocalEffectActive_Implementation(bool bActive)
{
    if (bLocalEffectActive == bActive) { return; }
    bLocalEffectActive = bActive;

    TArray<UNiagaraComponent*> NiagaraComponents;
    GetComponents<UNiagaraComponent>(NiagaraComponents);
    for (UNiagaraComponent* Comp : NiagaraComponents)
    {
        Comp->SetVisibility(bActive);   // Activate / Deactivate는 부르지 않는다
    }
}
```

**알고 택한 대가:** 실내에서도 **파티클을 계속 계산합니다(CPU).** 그래도 이쪽을 택한 이유는, **보이는 품질 문제가 성능보다 체감이 크고** 눈 개수가 성능 병목이 될 수준은 아니라고 판단해서입니다.

> **비에서는 왜 안 보였나**도 계산해봤습니다. 같은 구조인데 빗방울이 빨라서 **0.2~0.4초**면 차기 때문에 눈에 안 띄었습니다. **같은 버그가 있었는데 파라미터 차이로 한쪽만 드러난** 경우입니다.

### 6. 버그 ② — 걸으면 앞쪽 낮은 곳이 비어 보였다

**증상:** 밖에서 걷거나 달리면 위쪽에는 눈이 있는데 **앞쪽 낮은 곳이 비어 보입니다.**

**원인:** 나이아가라가 **월드 스페이스**라 **캐릭터를 따라다니는 건 생성 평면뿐**이고, 이미 생긴 눈송이는 생긴 자리에서 아래로만 떨어집니다.

> 지금 **낮은 높이에 있는 눈은 2~3.7초 전에 생긴 것**입니다. 그때 생성 평면의 중심은 걷기 기준 **14~26 m 뒤**에 있었습니다. 높은 곳의 눈은 방금 생긴 거라 앞까지 차 있고요. 그래서 **"위는 있는데 앞 아래가 빈"** 모양이 됩니다.

**여섯 가지 안을 비교하고 "생성 평면을 캐릭터 정면으로 8 m 앞당기기"를 택했습니다.**

| 안 | 바뀌는 곳 | 왜 안 골랐나 |
| :--- | :--- | :--- |
| 이동 방향으로 매 프레임 앞당김 | C++ Tick | 효과는 가장 좋지만 **Tick 추가** |
| 에셋 안에서 속도 반영 | 복제 에셋 | *"나이아가라 파라미터 금지"* 제약에 걸릴 수 있음 |
| 생성 높이 낮추기 | BP Location Z | 멀리 볼 때 **눈이 생기는 천장이 가까이 보임** |
| 평면 크게 + 스폰 4배 | BP + 복제 에셋 | 눈 약 18,000개. **건물 안까지 걸침** |
| **정면으로 8 m 앞당김** ✅ | **`_Snow` 자식 BP만** | — |

**왜 이걸 골랐나**

*   게임에서 가장 흔한 **앞으로 걷기**에서 거의 해결됩니다 (5 m 앞 바닥 근처 27% → **86%**).
*   **`_Snow` 자식 BP만** 바꾸면 끝입니다. **C++·Tick·에셋·레벨·서브시스템 전부 무수정**입니다.
*   비와 부모 BP는 그대로입니다. **비는 원래 문제가 작습니다.**

**약점도 수치로 확인하고 택했습니다.**

| 상황 | 결과 |
| :--- | :--- |
| 뒤로 걷기 | **나빠짐** (평면이 등 뒤 12 m까지만 덮음) |
| 뒤돌아보기 | 새로 앞이 된 쪽 15 m 부근이 **약 3초 동안 옅음** |
| 달리기 | 좋아지지만 앞쪽 바닥은 여전히 옅음 |

**앞당김 거리를 12 m로 더 키우지 않은 이유**도 있습니다. 앞은 더 좋아지는데 **뒤가 거의 0이 되고**, 무엇보다 **11.5 m를 넘으면 평면이 가게 문 안까지 닿습니다.** 8 m면 정문 판정 박스 끝에서 가게를 봐도 평면 끝이 문보다 3.5 m 앞입니다.

> **"가장 좋은 안"이 아니라 "가장 흔한 상황에서 좋고 부작용 범위를 아는 안"** 을 골랐습니다. 수치 표를 만들어 두니 *"왜 8 m인가"* 에 답할 수 있고, 나중에 뒤로 걷기가 거슬리면 **대안(Tick 방식)이 이미 적혀 있습니다.**

### 7. 부착 회전을 0으로 맞춰야 했던 이유

8 m 앞당김을 넣었더니 **평면이 캐릭터 정면이 아니라 엉뚱한 방향에 붙었습니다.**

> 부모 BP가 이펙트 액터를 캐릭터에 붙일 때 **Rotation을 `KeepWorld`로 부착**합니다. 그래서 **붙는 순간 캐릭터가 보고 있던 각도만큼 로컬 축이 틀어집니다.**
>
> 스폰할 때 캐릭터가 90°를 보고 있었으면, **평면이 그 뒤로 계속 캐릭터 오른쪽에** 붙어 다닙니다. **날마다 방향이 달라집니다.**

```
_Snow BeginPlay
  → Parent: BeginPlay              (부착이 여기서 끝남)
  → Set Actor Relative Rotation (0,0,0)
```

**부모의 부착 규칙을 `SnapToTarget`으로 바꿔도 같은 결과**인데, **자식에서 처리했습니다.**

> 부모를 고치면 **비(`_Rain`)까지 영향을 받습니다.** 비는 지금 문제가 없는데 굳이 건드릴 이유가 없습니다. **문제가 있는 쪽에서만 고치는 게** 안전합니다.

**카메라가 아니라 몸(캡슐)에 붙이는 방식도 유지**했습니다. 카메라에 붙이면 **위아래를 볼 때 평면이 기울어집니다.** 플레이어 캡슐이 카메라 좌우(Yaw)는 따라 돌고 위아래(Pitch)는 안 따라가므로, **몸에 붙이면 좌우만 따라오는 지금 동작이 맞습니다.**

### 8. 문 앞 영역에 박스를 두 개 둔 이유

`ACSWeatherZoneActor`에 **보이는 범위용**과 **판정용** 박스를 따로 뒀습니다.

| 박스 | 크기 | 콜리전 | 역할 |
| :--- | :--- | :--- | :--- |
| `VisualBox` | Extent (800, 800, 500) | **없음** | 비·눈이 내리는 범위. **윗면**에서 생성 |
| `JudgeBox` | Extent (400, 400, 500) | Pawn만 Overlap | **플레이어 판정** |

**왜 판정 박스를 더 작게 뒀나**

> 판정 박스가 연출 범위와 같으면, **경계에 딱 서 있을 때 화면이 어색합니다.** 판정상으로는 "안"인데 눈앞에는 비가 딱 잘려 있습니다.
>
> 판정을 **절반 크기로** 두면 안으로 들어간 뒤에도 **바깥쪽에 비가 더 내리고 있어서** 처마 아래에 선 느낌이 납니다.

그리고 **파티클은 충돌이 없어서 지붕을 뚫습니다.** 그래서 `VisualBox`는 **처마 바깥에** 두어야 하고, 그 위치는 판정에 쓰기엔 부적절합니다. **두 박스가 서로 다른 제약을 받으니 나눌 수밖에 없었습니다.**

`VisualBox`를 옮기거나 크기를 바꾸면 **생성 평면이 자동으로 따라가게** `OnConstruction`에서 위치·스케일을 계산합니다. 에디터에서 박스만 드래그하면 됩니다.

### 9. 그 외 구현하면서 정한 것들

**① 존은 고르지 않고 전부 켭니다.**

> 어느 문 앞에 있는지 판정해서 그 존만 켤 수도 있는데, **안 보이는 문 쪽은 어차피 벽에 가려집니다.** 판정 코드를 안 만들어도 결과가 같습니다.

**② 사운드는 이펙트 액터 한 곳에서만 재생합니다.**

> 존에도 사운드를 넣으면 **두 번 들립니다.** 데이터 필드 주석에 *"파티클만 넣고 사운드는 넣지 않음"* 이라고 적어뒀습니다.

**③ 존은 구독이 아니라 등록 시점에 상태를 받습니다.**

> **1일차 날씨가 존의 `BeginPlay`보다 먼저 정해집니다.** 알림만 구독하면 첫 방송을 이미 놓친 뒤라, `RegisterZone`에서 **바로 현재 에셋과 보이기 상태를 적용**합니다. 며칠째 반복해서 쓰고 있는 *"구독 + 즉시 동기화"* 패턴입니다.

**④ 이펙트를 새로 스폰한 프레임에 판정을 즉시 반영합니다.**

> 실내에서 하루가 넘어가면 이펙트 액터가 새로 스폰되는데, 그냥 두면 **새 이펙트가 실내에 한 번 뿌려집니다.** 스폰 직후 `UpdateShelterState(true)`로 현재 판정을 강제 적용합니다.

**⑤ 실내 영역을 청결도용 액터와 따로 만들었습니다.**

> 이미 실내를 나타내는 액터가 있어서 재사용할까 했는데, **그 코드가 "레벨에 하나만 있다"고 보고 처음 찾은 것만 씁니다.** 창고용을 하나 더 두면 **청결도 판정이 창고 박스를 잡을 수 있습니다.**
>
> **재사용하려다 남의 시스템을 깨뜨릴 뻔한** 경우입니다. 액터를 따로 만드는 비용(파일 2개)이 그 위험보다 쌉니다.

**⑥ 판정 대상은 플레이어 폰 하나입니다.**
