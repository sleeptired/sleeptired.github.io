# Unreal Engine 5 최적화 기법 — 검증과 쉬운 해설

> **기준:** 첨부한 `최적화 기법(1).txt`의 모든 주제와 질문을 검토했습니다. 먼저 첨부한 `최적화 기법.txt`도 내용이 같습니다.  
> **확인일:** 2026년 10월 23일 / 에픽의 UE 5.8 공식 문서 중심  
> **문서 목적:** 메모의 정확성을 확인하고, 생략된 원리와 적용 조건을 설명하는 학습 자료입니다. 실제 프로젝트의 성능을 측정한 결과는 아닙니다.

메뉴 이름·위치와 기능 지원 범위는 엔진 버전, 에디터 언어, 렌더링 방식에 따라 달라집니다. 메뉴가 다르면 괄호 안의 영문 이름으로 검색하세요. 아래의 수치 예시는 설명용이며, 일괄 적용할 권장값은 아닙니다.

**찾아보기:** 측정·도구는 1~2절, 메시·텍스처는 3~9절, NPC는 10절, 조명·반사는 11~17절, 반투명·폴리지는 18~19절, 적용 순서와 명령어는 20~21절입니다. 원문의 `?` 항목은 해당 절에 “원문의 질문”으로 표시했습니다.

## 먼저 알아둘 핵심

**최적화는 현재 가장 오래 걸리는 작업을 찾고, 그 작업을 줄이는 과정입니다.** 폴리곤·드로우 콜·조명·AI 중 어느 하나만 줄인다고 항상 FPS가 오르지는 않습니다.

원문에서 특히 고쳐야 하는 부분은 다음과 같습니다.

| 원문 요지 | 판정 | 정확한 이해 |
| --- | --- | --- |
| 비헤이비어 트리는 매 틱 전체를 실행하므로 StateTree가 유리하다 | 수정 필요 | UE의 Behavior Tree는 이벤트 기반입니다. 두 방식 모두 태스크·조건·갱신 주기에 따라 비용이 달라집니다. |
| MassEntity는 멀티스레드라서 무조건 가볍다 | 조건 필요 | 데이터 배치 처리와 메모리 접근 효율이 핵심입니다. 모든 처리가 자동으로 병렬 실행되지는 않습니다. |
| 머티리얼이 2개면 드로우 콜은 2개다 | 조건 필요 | 일반 메시의 한 렌더 패스에서 이해하는 근사입니다. 전체 프레임에는 그림자 등 다른 패스와 배칭도 관여합니다. |
| 병합한 메시가 조금만 보여도 무조건 전체를 그린다 | 조건 필요 | 병합 방식과 섹션 구성에 따라 컬링 단위가 달라집니다. 큰 병합은 불필요한 렌더링을 늘릴 수 있습니다. |
| 멀리 있으면 드로우 콜은 의미가 없다 | 수정 필요 | 멀리 있는 작은 물체도 개별 렌더링 명령 비용을 만들 수 있습니다. HLOD가 필요한 이유입니다. |
| HLOD를 쓰려면 월드 파티션이 필수다 | 수정 필요 | 일반 HLOD도 있습니다. 월드 파티션에서는 HLOD Layer를 사용하는 별도 작업 흐름을 씁니다. |
| 큰 텍스처가 조금만 보이면 텍스처 전체가 렌더링된다 | 수정 필요 | 일반 스트리밍은 필요한 밉을 통째로 올릴 수 있다는 메모리 문제입니다. 모든 텍셀을 화면에 그린다는 뜻은 아닙니다. |
| 버추얼 텍스처 설정 후 30분을 기다려야 한다 | 수정 필요 | 셰이더 컴파일·에셋 처리 시간은 환경에 따라 다릅니다. 고정된 대기 시간은 없습니다. |
| 나나이트는 4~5만 트라이앵글부터 유리하다 | 근거 없는 고정 기준 | 공통 임계값은 없습니다. 실제 장면과 목표 하드웨어에서 비교해야 합니다. |
| 베이킹이 정답이고 루멘은 쓰면 안 된다 | 수정 필요 | 고정 조명, 낮·밤 변화, 움직이는 배치물, 목표 사양에 맞춰 선택합니다. |
| 빛은 4개까지만 쓸 수 있다 | 수정 필요 | 맵 전체 조명 수 제한이 아닙니다. 일반적인 Stationary 그림자 채널의 중첩 제한과 관련됩니다. |
| Movable은 조명의 영향을 받지 않는다 | 틀림 | 움직일 수 있는 설정입니다. 조명과 그림자의 영향을 받습니다. |
| 루멘에서 액터 병합은 금지다 | 과도한 일반화 | 방 전체와 가구를 한 메시로 만드는 등 과도한 병합이 문제입니다. 결과를 시각화해 판단합니다. |
| Final Gather Quality를 높이면 절대 안 된다 | 수정 필요 | 정식 품질 조절 옵션입니다. 노이즈 감소와 GPU 비용을 함께 비교합니다. |
| GI의 Screen Space는 거울 반사 기능이다 | 용어 구분 필요 | SSGI는 확산 간접광, SSR은 반사상입니다. 서로 다른 설정입니다. |
| Shader Complexity는 중앙 십자선 한 픽셀만 본다 | 틀림 | 화면 전체 픽셀의 셰이더 복잡도를 색으로 시각화합니다. |
| Shift + L은 콘솔 창을 숨긴다 | 수정 필요 | 기본 설정에서는 뷰포트의 통계 표시를 켜고 끄는 기능입니다. |

각 판정의 설명과 공식 자료는 아래 해당 절에 정리했습니다.

## 1. 최적화 전에 CPU·GPU·메모리를 구분하기

### 1-1. 어떤 비용이 줄어드는가?

| 비용 | 쉽게 말하면 | 대표 원인 | 확인 수단 |
| --- | --- | --- | --- |
| CPU 게임 처리 | 게임의 규칙과 상태를 계산하는 시간 | AI, Tick, 경로 탐색, 충돌, 액터 생성·제거 | `stat unit`, Unreal Insights |
| CPU 렌더 준비 | GPU에 보낼 그리기 작업을 준비하는 시간 | 많은 메시·섹션·렌더링 명령 | `stat unit`, `stat scenerendering` |
| GPU 처리 | 실제 화면을 만드는 시간 | 그림자, 루멘, 복잡한 머티리얼, 반투명 겹침 | `stat gpu`, GPU 프로파일러 |
| 메모리·스트리밍 | 데이터 보관과 불러오기 부담 | 고해상도 텍스처, 많은 에셋, 로딩 지연 | `stat streaming`, 메모리·스트리밍 분석 |

**병목**은 전체 진행을 가장 오래 붙잡는 부분입니다. 예를 들어 GPU 조명 계산이 병목인 장면에서 AI 코드만 줄이면 GPU 시간은 거의 바뀌지 않을 수 있습니다.

### 1-2. FPS와 프레임 시간

`프레임 시간(ms) = 1000 ÷ FPS`

| 목표 | 한 프레임에 쓸 수 있는 시간 |
| --- | --- |
| 30 FPS | 약 33.33ms |
| 60 FPS | 약 16.67ms |
| 120 FPS | 약 8.33ms |

CPU와 GPU는 일부 작업을 겹쳐 진행하므로 표시 시간을 단순히 모두 더해 프레임 시간을 계산하지 않습니다. VSync, 프레임 제한, 대기 시간도 수치에 영향을 줍니다.

### 1-3. 측정 조건 맞추기

1. 같은 PC, 해상도, 그래픽 품질, 카메라 위치를 사용합니다.
2. 셰이더 컴파일과 초기 로딩이 끝난 뒤 측정합니다.
3. 같은 손님 수·날씨·영업 상태처럼 비교 가능한 상황을 만듭니다.
4. 에디터에서 원인을 찾고, 패키징한 Development 빌드 등에서도 결과를 확인합니다.
5. 평균뿐 아니라 손님 생성·날씨 전환 때 발생하는 순간 끊김도 확인합니다.

**자료:** [Stat Commands][S01], [렌더링 최적화 가이드][S02]

## 2. 에디터에서 무엇을 확인할 수 있나?

### 2-1. 통계 창

원문의 `도구 → 검사 → 통계`는 레벨 에셋을 점검하는 출발점으로 적절합니다. 에디터에서 **Statistics / 통계** 창을 찾아 열고, 목록 종류를 선택하세요.

메시 수·인스턴스 수·트라이앵글·메모리 등은 선택한 통계 종류에 따라 확인할 수 있습니다. 다만 **레벨에 존재하는 에셋의 통계와, 현재 프레임에 실제로 처리한 양은 다릅니다.** 창에 표시되는 많은 폴리곤이 항상 화면에 전부 그려지는 것은 아닙니다.

### 2-2. 자주 쓰는 분석 도구

| 도구 | 적합한 질문 |
| --- | --- |
| `stat unit` | CPU 게임 처리, 렌더 준비, GPU 중 어디부터 볼까? |
| `stat scenerendering` | 현재 장면의 메시 렌더링 관련 통계는 어떤가? |
| `stat RHI` | 그래픽 API 계층의 렌더링 통계는 어떤가? |
| `stat gpu` / GPU 프로파일러 | 그림자·간접광·반투명 등 어떤 GPU 작업이 오래 걸릴까? |
| Unreal Insights | 어떤 함수·태스크·스레드가 시간을 쓰고, 언제 끊길까? |
| RenderDoc | 한 프레임의 그리기 명령, 리소스, 렌더 타깃이 어떻게 구성될까? |

통계 항목의 **이름**을 기준으로 보세요. 원문의 “Counters의 두 번째 줄”처럼 위치를 외우면 버전이나 설정에 따라 다른 값을 읽을 수 있습니다. 평균값도 해당 항목의 평균이며, FPS의 평균과 혼동하면 안 됩니다.

RenderDoc은 무료 외부 그래픽 디버거이며 UE 연동 플러그인이 있습니다. 프레임 내부 구조를 깊게 확인할 때 유용합니다. 일반 실행 성능의 전후 비교는 프로파일러 측정과 함께 판단하세요.

**자료:** [렌더링 최적화 가이드][S02], [Unreal Insights][S03], [RenderDoc 연동][S04]

## 3. LOD — 작게 보일 때 간단한 메시로 바꾸기

**판정: 방향은 맞지만 “멀어지면 찌그러뜨린다”보다 “덜 자세한 모델로 전환한다”가 정확합니다.**

LOD는 Level of Detail의 약자입니다. 가까이에서는 자세한 메시를 쓰고, 화면에서 작아지면 트라이앵글이 적은 메시를 사용합니다.

| 단계 | 설명용 예시 |
| --- | --- |
| LOD0 | 원본에 가까운 20,000 트라이앵글 |
| LOD1 | 10,000 트라이앵글 |
| LOD2 | 3,000 트라이앵글 |
| LOD3 | 500 트라이앵글 |

위 수치는 예시입니다. 물체의 실루엣과 중요도에 따라 다르게 설정합니다. 트라이앵글은 메시 표면을 구성하는 삼각형입니다.

### Screen Size는 무엇인가?

물체의 **바운딩 구를 화면에 투영했을 때의 상대적 크기**를 기준으로 LOD 전환을 판단합니다. 바운딩 구는 물체를 감싸는 가상의 구입니다.

- 값이 클 때: 화면에서 크게 보이는 상태입니다.
- 값이 작을 때: 화면에서 작게 보이는 상태입니다.
- 거리가 같아도 물체 크기나 카메라 시야각이 다르면 전환 결과가 달라질 수 있습니다.

따라서 `1 = 실제 메시가 화면 면적을 정확히 100% 채움`으로 외우지는 마세요. 실제 형상 대신 경계를 이용하는 크기 지표입니다.

### 에디터 작업 흐름

1. Static Mesh 에셋을 엽니다.
2. LOD Settings에서 LOD 개수와 자동 생성 설정을 확인합니다.
3. 각 LOD의 Reduction Settings에서 삼각형 감소 정도를 조절합니다.
4. 자동 전환 크기를 사용하거나 Screen Size를 직접 조절합니다.
5. 실제 플레이 카메라에서 전환 시 형태가 튀는지 확인합니다.

**LOD는 주로 기하 처리량을 줄입니다.** 머티리얼 섹션 수를 그대로 두면 드로우 콜은 기대만큼 줄지 않을 수 있습니다.

**자료:** [자동 LOD 생성][S05], [LOD 생성과 사용][S06], [투영된 바운딩 구 기준][S07]

## 4. 드로우 콜·머티리얼·인스턴싱·액터 병합

### 4-1. 드로우 콜이란?

**GPU에 특정 조건으로 메시 등을 그리라고 내리는 명령**입니다. 물체가 화면에서 작아도 명령을 준비하고 제출하는 비용이 생깁니다.

일반 메시가 몸체·유리처럼 두 머티리얼 섹션으로 나뉘면, 한 렌더 패스에서 따로 그리는 작업이 생길 수 있습니다. **섹션**은 메시 안에서 머티리얼 등을 기준으로 나눈 그리기 구역입니다.

원문의 “머티리얼 2개 = 드로우 콜 2개”는 기본 원리 설명에는 도움이 되지만, **프레임 전체의 확정 공식은 아닙니다.**

- 깊이·그림자·베이스 패스 등 같은 물체를 다른 목적으로 처리할 수 있습니다.
- 같은 메시·머티리얼의 배칭과 인스턴싱으로 명령이 합쳐질 수 있습니다.
- Nanite는 일반 메시와 다른 렌더링 경로를 사용합니다.

**패스**는 화면을 만드는 과정의 한 단계입니다. “전체 렌더링 명령 수”와 “특정 패스의 메시 명령 수”를 구분해서 비교하세요.

**자료:** [Mesh Drawing Pipeline][S08], [Nanite 개요][S14]

### 4-2. 같은 물체가 반복되면 인스턴싱 검토

같은 상자 100개를 배치한다면, 동일한 메시 데이터를 공유하고 위치·회전·크기 등의 차이만 별도로 전달하는 방식이 유리할 수 있습니다.

대표 도구는 **ISM(Instanced Static Mesh)**과 **HISM(Hierarchical Instanced Static Mesh)**입니다. HISM은 계층적 공간 구조도 이용합니다. 어느 쪽이 적합한지는 인스턴스 변경 빈도와 렌더링 방식에 따라 달라집니다.

단, “100개를 인스턴싱하면 전체 프레임이 무조건 1드로우 콜”은 아닙니다. 섹션·LOD·그림자 패스 등에 따라 달라집니다. 상품별 상호작용이 필요하면 해당 게임 로직도 함께 설계해야 합니다.

**자료:** [Instanced Static Mesh][S09]

### 4-3. 액터 병합은 방법마다 다르다

| 방법 | 무엇을 하는가? | 확인할 점 |
| --- | --- | --- |
| Merge | 선택한 메시를 합칩니다. 머티리얼도 합칠 수 있습니다. | 여러 섹션이 남으면 섹션별 그리기 작업도 남을 수 있습니다. |
| Simplify | 합친 뒤 단순화한 프록시 메시를 만듭니다. | 전체 메시 단위의 컬링 때문에 과한 병합이 불리할 수 있습니다. |
| Batch | 같은 메시들을 인스턴싱 형태로 묶습니다. | 단순히 거대한 메시 하나로 만드는 방식과 다릅니다. |
| Approximate | 복잡한 원본으로부터 근사 메시를 생성합니다. | 원본과 결과의 형태·재질 차이를 확인합니다. |

에픽 문서에서 Merge는 섹션 단위, Simplify는 전체 메시 단위의 오클루전 컬링으로 설명합니다. Nanite의 클러스터 컬링도 별도이므로 **“어떤 병합이든 조금만 보이면 전부 그린다”는 단정은 피해야 합니다.**

일반적으로 함께 보이는 작은 고정 장식끼리 묶는 것은 검토할 만합니다. 여러 방이나 건물 전체를 한꺼번에 합치면 가림 처리·조명·텍스처 관리에서 불리해질 수 있습니다. 기본 메뉴는 `Actor → Merge Actors` 계열이며 버전에 따라 위치가 달라집니다.

**자료:** [Merging Actors][S10]

## 5. 컬링 — 필요 없는 렌더링을 제외하기

**판정: “렌더링 대상에서 제외한다”는 설명은 맞습니다.** 다만 컬링 종류와 게임 로직 중단은 구분해야 합니다.

| 종류 | 제외하는 기준 | 예시 |
| --- | --- | --- |
| 프러스텀 컬링 | 카메라 시야 범위 밖 | 플레이어 뒤에 있는 물체 |
| 거리 컬링 | 설정 거리보다 멂 | 아주 멀리 있는 작은 장식 |
| 오클루전 컬링 | 다른 물체에 가려짐 | 큰 건물 뒤에 완전히 숨은 상자 |

가려졌다고 모든 작업이 사라지는 것은 아닙니다. AI·충돌·Tick은 별도로 계속 실행될 수 있고, 그림자나 반사 계산에서 필요한 물체도 있습니다. 컬링 자체의 검사 비용도 있습니다.

오클루전 확인에 사용할 수 있는 에디터 명령은 다음과 같습니다.

```text
r.VisualizeOccludedPrimitives 1
```

확인이 끝나면 같은 명령의 값을 `0`으로 바꿉니다. 일반적인 가림 결과 점검용이며, 모든 렌더링 경로의 최종 GPU 작업량을 한 번에 보여주는 도구는 아닙니다.

**자료:** [Visibility and Occlusion Culling][S11]

## 6. HLOD와 월드 파티션 — 둘의 역할 구분

### 6-1. HLOD

HLOD는 **여러 물체를 멀리서 볼 때 대신 보여줄 대표 묶음을 만드는 방식**입니다. 개별 LOD가 한 물체의 디테일을 바꾼다면, HLOD는 여러 물체의 표현을 묶어 바꿉니다.

예를 들어 먼 거리에서 건물과 간판·외부 장식이 각각 작게 보이면, 각각을 처리하기보다 단순한 대표 표현으로 교체해 비용을 줄일 수 있습니다.

**원문의 “멀리 있으면 드로우 콜이 의미 없다”는 반대입니다.** 작게 보이는 물체를 개별적으로 그리는 비용이 상대적으로 아까워지므로 HLOD를 검토합니다.

월드 파티션이 없는 레벨의 HLOD와, 월드 파티션에서 HLOD Layer를 사용하는 방식이 있습니다. HLOD 자체에 월드 파티션이 반드시 필요한 것은 아닙니다.

**자료:** [일반 HLOD][S12], [World Partition HLOD][S13]

### 6-2. 월드 파티션

**큰 월드를 공간 셀로 나누고, 스트리밍 소스 주변의 필요한 셀을 로드·언로드하는 시스템**입니다. 스트리밍 소스는 플레이어처럼 어떤 영역을 필요로 하는지 판단하는 기준입니다.

주된 목적은 큰 월드의 데이터 로딩과 관리입니다. 자동으로 모든 AI·머티리얼·조명을 최적화하는 기능은 아닙니다. 항상 로드되도록 설정된 액터 등도 있어, “멀면 무조건 모든 데이터가 내려간다”는 뜻도 아닙니다.

작은 가게 중심 게임에서는 현재 로딩·메모리 문제가 실제로 있는지부터 확인하세요. 큰 구조를 도입하는 비용도 함께 고려해야 합니다.

**자료:** [World Partition][S17]

## 7. 텍스처의 밉맵과 타일링

### 7-1. 밉맵은 텍스처의 작은 버전들

밉맵은 같은 이미지를 여러 해상도로 준비하는 방식입니다.

`2048×2048 → 1024×1024 → 512×512 → 256×256 → …`

화면에서 작게 보이는 표면에 작은 밉을 사용하면 불필요한 세부 샘플링을 줄이고, 멀리서 생기는 깜빡임이나 무늬 떨림도 완화할 수 있습니다. 텍스처 스트리밍은 상황에 맞는 밉 데이터를 메모리에 가져옵니다.

원문의 문제는 **“일부만 보여도 필요한 고해상도 밉 전체를 메모리에 올릴 수 있다”**로 고치면 정확합니다. **이미지 전체를 화면에 그린다는 의미는 아닙니다.** 렌더링되는 픽셀과 메모리에 상주하는 데이터는 구분하세요.

### 7-2. 반복 타일링과 스트리밍 타일은 다른 용어

| 용어 | 의미 |
| --- | --- |
| 반복 타일링 텍스처 | 벽돌·바닥처럼 같은 이미지를 UV로 반복해서 사용하는 표현 방식 |
| 버추얼 텍스처의 타일 | 큰 텍스처를 스트리밍하기 위해 나눈 작은 데이터 조각 |

반복 텍스처는 큰 표면에서도 비교적 작은 원본을 재사용할 수 있습니다. 대신 반복 무늬가 눈에 띌 수 있어 데칼, 색 변화, 다른 텍스처와의 혼합 등을 사용합니다. 경계가 끊기는 현상은 반복에 맞지 않는 원본이나 UV 설정에서도 생깁니다.

**자료:** [Texture Streaming Overview][S52], [Streaming Virtual Texturing의 일반 스트리밍 비교][S18]

## 8. 버추얼 텍스처 — 필요한 조각을 가져오기

### 8-1. SVT와 RVT

| 방식 | 역할 |
| --- | --- |
| SVT: Streaming Virtual Texturing | 저장된 텍스처를 작은 타일로 나눠 필요한 데이터를 스트리밍합니다. |
| RVT: Runtime Virtual Texturing | 지형·오브젝트의 머티리얼 결과 등을 런타임에 가상 텍스처로 캐시합니다. 지형과 물체의 경계 혼합 등에 사용합니다. |

원문에서 “쪼개 놓은 타일 중 보이는 부분을 가져온다”는 설명은 **SVT에 가깝습니다.** SVT와 RVT를 같은 기능으로 외우지는 마세요.

**자료:** [Virtual Texturing 개요][S19], [Runtime Virtual Texturing][S20]

### 8-2. 기본 설정 흐름

1. 프로젝트의 `Engine → Rendering → Virtual Textures`에서 지원 옵션을 확인합니다.
2. 엔진이 요구하면 재시작하고, 셰이더 컴파일 등이 끝날 때까지 기다립니다.
3. 지원되는 일반 텍스처 에셋을 선택합니다.
4. 우클릭의 `Convert to Virtual Texture`로 변환합니다.
5. 참조 머티리얼의 Texture Sample이 Virtual Sampler Type으로 변환됐는지 확인합니다.

이 변환 메뉴는 대상 텍스처를 SVT로 바꾸는 기능입니다. 변환 창에는 참조하는 머티리얼도 표시될 수 있습니다. 모든 에셋 종류가 같은 메뉴를 가지거나, RVT가 이 메뉴만으로 만들어지는 것은 아닙니다.

텍스처 에디터에서 `Virtual Texture Streaming`만 수동으로 켜면, 참조 머티리얼의 샘플러 유형도 직접 맞춰야 할 수 있습니다. **30분은 필수 대기 시간이 아닙니다.**

### 8-3. 언제나 이득인가?

필요한 타일 위주로 메모리를 사용할 수 있지만, 타일 관리와 샘플링 비용이 생깁니다. 작은 텍스처까지 전부 변환하기보다 실제 메모리와 프레임 시간을 비교하세요.

**자료:** [SVT 변환과 비용][S18], [Virtual Texturing 설정][S21]

## 9. Nanite — 자동 LOD를 포함한 가상화 지오메트리

**판정: “LOD의 업그레이드 버전”은 입문용 비유입니다. 실제로는 데이터 형식·스트리밍·가시성 판정·렌더링을 함께 다루는 시스템입니다.**

### 9-1. 클러스터란?

Nanite는 메시의 삼각형을 **클러스터라는 작은 묶음**으로 구성합니다. 화면에서 필요한 디테일을 선택하고, 가려지거나 불필요한 묶음을 제외하며, 세부 데이터를 스트리밍합니다.

원문의 “보이는 부분 위주로 처리한다”는 방향은 맞습니다. 다만 다음처럼 이해하세요.

- 최종 가시 픽셀만을 아무 비용 없이 딱 한 번 계산하는 것은 아닙니다.
- 가시성 검사·머티리얼·그림자 등 다른 비용도 남습니다.
- 텍스처 메모리는 별도로 관리합니다.
- 원본의 모든 세부 지오메트리를 항상 같은 방식으로 상주시킬 필요를 줄입니다.

**자료:** [Nanite 개요][S14], [Nanite 기술 세부사항][S15]

### 9-2. 몇 폴리곤부터 이득인가?

**“40,000~50,000 트라이앵글 이상이면 이득”이라는 공통 규칙은 없습니다.** 높은 지오메트리 복잡도를 처리하는 데 강점이 있지만, 인스턴스 수·머티리얼·화면 해상도·겹침·변형·하드웨어가 결과를 바꿉니다.

낮은 폴리곤 메시에서 준비 비용이 상대적으로 부담이 될 수는 있습니다. 그렇다고 낮은 폴리곤은 전부 손해라고 단정할 수도 없습니다. 단순 메시 하나보다 실제 레벨 전체에서 전후를 비교하세요.

### 9-3. 설정과 확인

1. 지원되는 메시 에셋의 Nanite Settings에서 활성화합니다.
2. 뷰포트의 `Nanite Visualization → Clusters` 등으로 확인합니다.
3. 사용한 머티리얼·변형 기능·플랫폼의 지원 범위를 확인합니다.
4. 기존 표현과 GPU 시간·화질을 비교합니다.

Nanite를 켜도 반투명 이펙트와 무거운 조명이 자동으로 해결되지는 않습니다. 지원 기능은 버전별로 변하므로 예전 버전의 제한을 그대로 적용하지 마세요.

**자료:** [Nanite 콘텐츠 작업][S16]

## 10. 대량 NPC: AnimToTexture·MassEntity·StateTree

이 세 가지는 모두 NPC 최적화에 관련될 수 있지만, **줄이려는 비용이 서로 다릅니다.**

| 기능 | 주로 다루는 부분 |
| --- | --- |
| AnimToTexture | 캐릭터의 애니메이션 표현 |
| MassEntity | 많은 개체의 데이터 저장과 일괄 계산 |
| StateTree / Behavior Tree | 개체의 행동 상태와 의사결정 |

### 10-1. `anime to texture` → AnimToTexture

애니메이션 프레임의 정점 위치·노멀 또는 본 위치·회전 등을 **텍스처 데이터로 베이크하고, 머티리얼에서 읽어 움직임을 표현**하는 도구입니다. 텍스처는 사진뿐 아니라 숫자 데이터도 저장할 수 있습니다.

반복해서 걷는 배경 군중 같은 대상에서 일반적인 캐릭터별 애니메이션 처리 부담을 줄이는 방법으로 검토합니다.

다만 텍스처 메모리·GPU 연산·머티리얼 비용으로 부담이 옮겨갑니다. 일반 Skeletal Mesh의 애니메이션 블렌딩·IK·소켓·래그돌을 동일하게 쓸 수 있다고 가정하면 안 됩니다. 전환이나 상호작용이 필요하면 별도 설계가 필요합니다.

**자료:** [AnimToTexture API][S22], [에픽 애니메이션 성능 가이드][S23]

### 10-2. `매쓰 엔티티` → MassEntity

MassEntity는 **데이터 지향 계산 프레임워크**입니다. 대량 개체의 비슷한 데이터를 메모리에 모으고, 필요한 로직으로 묶어서 처리합니다.

| 개념 | 쉬운 뜻 | 예시 |
| --- | --- | --- |
| Entity | 데이터를 묶어 식별하는 개체 | 행인 한 명의 ID |
| Fragment | 개체가 가진 작은 데이터 단위 | 위치, 속도 |
| Processor | 데이터를 읽고 처리하는 로직 | 위치 += 속도 × 시간 |
| Archetype | 같은 종류의 데이터 구성을 가진 집합 | 위치·속도를 모두 가진 행인들 |
| Chunk | 데이터를 연속적으로 저장하는 메모리 묶음 | 여러 행인의 위치·속도 묶음 |

원문의 “데이터와 로직 분리”는 맞습니다. **멀티스레드만이 이점의 이유는 아닙니다.** 데이터 접근 효율과 일괄 처리도 중요합니다. 실제 병렬화에는 읽기·쓰기 의존성과 사용하는 기능의 스레드 제약이 관여합니다.

MassEntity만 추가한다고 이동·회피·행동·렌더링이 전부 완성되는 것은 아닙니다. 관련 기능을 조합하고 프로젝트에 맞게 구성해야 합니다.

**자료:** [MassEntity Overview][S24]

### 10-3. StateTree가 Behavior Tree보다 무조건 가벼운가?

**아닙니다.** UE의 Behavior Tree는 매 프레임 전체 트리를 무조건 순회하는 방식이 아니라 **이벤트 기반**으로 설계돼 있습니다. 단, 틱을 쓰는 Task와 주기적으로 실행하는 Service 등을 많이 만들면 비용이 생깁니다.

StateTree도 Tick Task, Evaluator, On Tick 조건 등을 비싸게 구성하면 무거워질 수 있습니다. “걷기 → 대기 → 도망가기”처럼 상태와 전환이 뚜렷한 흐름은 StateTree로 표현하기 편할 수 있지만, 성능 우위를 보장하는 말은 아닙니다.

기존 AI를 전부 교체하기 전에 경로 탐색 빈도, 감지 범위, 충돌, 이동 컴포넌트, 애니메이션과 불필요한 Tick부터 측정하세요.

**자료:** [Behavior Tree의 이벤트 기반 실행][S25], [StateTree Overview][S26], [StateTree의 Tick 사용 예][S27]

| --- | --- | --- |
| 직접광 | 광원에서 표면에 직접 도착하는 빛 | 전등이 계산대를 비춤 |
| 확산 간접광 / GI | 표면에서 퍼져 나와 다른 표면을 밝히는 빛 | 밝은 벽에서 튕긴 빛이 옆 벽을 밝힘 |
| 반사 / Reflection | 재질에 주변 환경의 반사상이 나타남 | 금속 냉장고에 매장이 비침 |

`Dynamic Global Illumination Method`와 `Reflection Method`는 별도 설정입니다. GI를 바꾸었다고 반사 방식까지 같은 것으로 바뀐다고 가정하면 안 됩니다.

루멘 GI를 사용하면 베이크한 정적 조명이 표시되지 않습니다. 반면 지원 조건을 맞추면 **베이크한 조명과 독립적인 Lumen Reflections**를 조합하는 구성도 가능합니다. 따라서 “루멘의 일부 기능 사용 = 베이킹 전체 금지”로 단순화하지 마세요.

**자료:** [Lumen GI와 Reflections 설정][S28]

## 12. Mobility — 라이트와 물체에서 뜻이 어떻게 다른가?

### 12-1. 라이트의 Mobility

다음은 주로 **베이크 조명을 사용하는 구성**에서의 기본 구분입니다. 실제 그림자 표현은 렌더링 방식에 따라 달라집니다.

| 설정 | 런타임 변경 | 조명 처리의 기본 방향 | 예시 |
| --- | --- | --- | --- |
| Static | 위치·회전·조명 변경을 전제로 하지 않음 | 고정 표면의 조명·그림자를 미리 계산 | 항상 같은 상태인 장식 조명 |
| Stationary | 위치·회전 고정, 밝기·색 등 일부 변경 가능 | 베이크한 간접광과 동적 직접광·그림자 조합 | 제자리에서 켜고 끄는 고정 전등 |
| Movable | 위치·회전·밝기·색 변경 가능 | 실시간 조명·그림자 | 손전등, 회전하는 태양 |

Stationary 조명의 밝기를 바꾸어도 **이미 베이크한 간접광까지 자동으로 새로 계산되지는 않습니다.**

### 12-2. 일반 물체의 Mobility

일반 물체에서는 주로 **그 물체가 런타임에 이동·변경될 수 있는가**를 나타냅니다. 라이트에서는 **빛을 어떤 방식으로 계산하고 변경할 수 있는가**까지 관계됩니다.

- **Static 물체:** 움직이지 않는 구조물 등에 적합하며, 지원되는 구성에서 자기 표면의 라이트맵을 사용할 수 있습니다.
- **Stationary 물체:** 이동하지 않으면서 일부 변경을 허용하는 중간 성격입니다. 컴포넌트별 활용·지원 조건을 확인합니다.
- **Movable 물체:** 캐릭터, 문, 이동 가능한 상품 등에 적합합니다. 실시간 조명과 그림자의 영향을 받습니다.

Movable 물체는 자기 표면에 베이크한 라이트맵을 그대로 사용하는 대신, 베이크 환경에서는 Volumetric Lightmap 같은 공간 조명 데이터를 이용할 수 있습니다.

**“Static Mesh”는 에셋 종류이고 “Mobility: Static”은 움직임 설정입니다.** Static Mesh 에셋을 사용하는 물체도 Mobility를 Movable로 설정해 움직일 수 있습니다.

**자료:** [Light Mobility][S29], [Actor Mobility][S30], [Static Light][S31], [Movable Light][S32], [Stationary Light][S35]

## 13. 베이크·라이트맵·UV

### 13-1. 베이킹은 무엇을 저장하나?

“빛을 사진으로 저장한다”는 비유는 시작점으로 괜찮습니다. 정확히는 **고정된 표면에 도달한 조명과 그림자 등의 계산 결과를 텍스처 데이터로 미리 저장**합니다. 대표적인 데이터가 라이트맵입니다.

베이크하면 실시간 계산 부담을 줄일 수 있지만, 라이트맵 메모리·저장 용량·샘플링 비용은 남습니다. 동적 물체와 조명의 처리도 따로 필요합니다. “베이크하면 모든 장면의 비용이 동일해진다”는 설명은 틀립니다.

**자료:** [Static Light Mobility][S31], [CPU Lightmass][S33]

### 13-2. UV가 왜 중요할까? — 원문의 질문

**UV는 3D 표면을 2D 이미지 위에 펼쳐 놓은 좌표**입니다. 종이 상자를 펼친 전개도처럼 생각하면 됩니다.

라이트맵은 2D 텍스처이므로, “어느 픽셀의 조명 결과를 메시의 어느 면에 붙일지”를 UV로 연결합니다.

| 문제가 있는 UV | 왜 문제가 되나? |
| --- | --- |
| 서로 다른 면이 같은 위치에 겹침 | 서로 다른 조명 결과를 같은 픽셀에 기록하려고 충돌합니다. |
| UV 조각 사이 여백 부족 | 필터링·압축 과정에서 이웃 조각의 빛·그림자가 번질 수 있습니다. |
| 중요한 면이 너무 작은 영역을 차지함 | 해당 면에 배정되는 픽셀이 적어 그림자가 뭉개집니다. |
| 잘못된 UV 채널 지정 | 베이킹에 적합하지 않은 UV를 사용하게 됩니다. |

색상 텍스처용 UV는 반복·겹침을 사용해도 괜찮은 경우가 있지만, **라이트맵용 UV는 겹치지 않게 별도로 준비하는 것이 기본**입니다. 예를 들어 색상은 UV0, 라이트맵은 UV1을 쓸 수 있습니다. 실제 사용할 채널은 `Light Map Coordinate Index`로 확인합니다.

UE의 자동 라이트맵 UV 생성은 유용하지만, 원본 UV를 재배치하는 성격이라 모든 잘못된 메시나 UV를 자동 수리해 주지는 않습니다.

**자료:** [Understanding Lightmapping][S34], [Generating Lightmap UVs][S36]

### 13-3. 빛은 4개까지만 쓸 수 있나? — 원문의 질문

**아닙니다. 맵 전체에 둘 수 있는 라이트 수 제한이 아닙니다.**

일반적인 Stationary 조명의 프리컴퓨티드 그림자 처리에는 **최대 4개의 중첩 그림자 채널** 제약이 있습니다. 복잡한 중첩 배치에서는 더 적게 허용될 수도 있고, Directional Light도 채널을 차지할 수 있습니다. 초과하면 빨간 X와 함께 더 비싼 동적 그림자 처리로 넘어갈 수 있습니다.

원문의 RGBA 추측은 **빛의 색이 4종류라서 제한된다**는 뜻이라면 틀립니다. 핵심은 각 조명의 그림자 정보를 배정할 수 있는 채널 수입니다.

따라서 **Stationary Light의 영향 범위를 줄이고 중첩을 점검**해야 합니다. Static·Movable 라이트까지 합쳐 게임 전체에 4개만 배치할 수 있다는 뜻은 아닙니다.

확인: `Optimization Viewmodes → Stationary Light Overlap`.

**자료:** [Stationary Light의 중첩 제한][S35]

### 13-4. CPU Lightmass로 베이크하는 기본 흐름

1. 고정 조명 중심의 구성이 게임에 맞는지 정합니다.
2. 프로젝트의 `Allow Static Lighting`이 활성화돼 있는지 확인합니다.
3. 월드의 `Force No Precomputed Lighting` 때문에 베이크가 막히지 않는지 확인합니다.
4. 베이크 GI를 사용할 경우 Lumen GI와의 표시 관계를 정리합니다. `Dynamic GI: None`은 동적 GI를 끄는 선택이지 베이크 실행 버튼이 아닙니다.
5. 움직이지 않을 구조물과 고정 라이트의 Mobility를 맞춥니다.
6. 라이트맵 UV·채널·해상도와 Lightmass Importance Volume을 점검합니다.
7. `Build → Build Lighting Only`로 빌드합니다.

엔진 버전과 레벨 유형, 특히 World Partition 레벨의 정적 조명 지원 조건도 확인해야 합니다. **GPU Lightmass는 별도의 플러그인·요구 사항과 설정 흐름**이 있으며, CPU Lightmass 설정을 전부 동일하게 적용하지 않습니다.

**자료:** [Lightmass Basics][S37], [Rendering Settings][S38], [Lumen과 정적 조명][S28], [GPU Lightmass][S39]

### 13-5. Preview·Medium·High·Production의 차이 — 원문의 질문

아래는 CPU Lightmass의 기본 품질 프리셋에 대한 설명입니다.

| 품질 | 용도 | 차이 |
| --- | --- | --- |
| Preview | 배치 중 빠른 확인 | 빌드가 빠르지만 노이즈·빛샘 등이 더 나타날 수 있습니다. |
| Medium | 중간 확인 | 시간과 품질의 중간 단계입니다. |
| High | 상세 확인 | 더 긴 계산으로 품질을 높입니다. |
| Production | 최종 결과 확인 | 계산 시간이 길어지는 대신 더 정밀한 결과를 목표로 합니다. |

이 프리셋은 **베이크 계산 품질**을 조절합니다. 메시의 UV나 라이트맵 해상도를 자동으로 해결하지는 않습니다. Production이라고 낮은 해상도의 그림자가 무조건 선명해지는 것은 아닙니다.

**자료:** [Lightmass 품질 모드][S37]

### 13-6. 라이트맵 해상도

같은 표면에 배정할 조명 픽셀 수를 정하는 값입니다. 보통 `64 → 128 → 256 → 512`처럼 2의 거듭제곱 값을 사용합니다.

해상도를 가로·세로 각각 두 배로 하면 **기본 텍셀 수는 네 배**가 됩니다. 실제 메모리는 압축·밉·아틀라스 등의 영향도 받습니다. 큰 바닥·벽과 작은 소품에 같은 값을 일괄 적용하지 마세요.

확인 순서는 **UV 오류 → Lightmap Density → 해상도 → 빌드 품질**처럼 잡을 수 있습니다. 라이트맵을 사용하지 않는 루멘 전용 구성이라면 해상도만 올려도 루멘 품질은 좋아지지 않습니다.

**자료:** [Lightmapping과 해상도][S34], [Lightmap Density 뷰][S40]

### 13-7. 베이크한 뒤 캐릭터 그림자가 없다면?

Static 라이트만으로 고정 배경을 베이크했다고 해서, 나중에 움직이는 캐릭터의 동적 그림자까지 자동으로 생기지는 않습니다.

고정 전등 아래 캐릭터 그림자가 필요하면 Stationary 같은 구성을, 광원 자체도 움직이면 Movable을 검토합니다. 함께 확인할 항목은 라이트와 캐릭터의 `Cast Shadows`, 동적 그림자 설정과 거리, 렌더링 방식입니다.

베이크에 참여한 구조물·라이트의 위치를 바꾸면 다시 빌드해야 합니다. 반대로 원래 Movable로 설계된 캐릭터가 움직인다는 이유로 매번 라이트맵을 다시 굽지는 않습니다.

**자료:** [Static Light와 동적 물체][S31], [Stationary의 동적 그림자][S35]

## 14. Lightmass 설정과 Importance Volume

### 14-1. Static Lighting Level Scale

베이크에서 **얼마나 세밀한 공간 디테일을 계산할지**에 관련된 값입니다.

- 줄이면: 더 작은 디테일을 계산할 수 있지만 빌드 시간이 크게 늘어납니다.
- 늘리면: 큰 장면에서 계산을 줄일 수 있지만 세부 조명 정확도가 떨어질 수 있습니다.

원문의 “캐릭터 키가 두 배니까 반드시 값을 2로 바꾼다”는 규칙은 아닙니다. 기본 단위가 cm라는 사실과 별개로, 최종 조명 디테일에 맞춰 선택합니다. 최후에만 만질 수 있는 금지 옵션도 아닙니다.

### 14-2. 다른 주요 설정

| 설정 | 의미 | 높이거나 늘렸을 때 |
| --- | --- | --- |
| Indirect Lighting Quality | 간접광 계산 샘플 품질 | 노이즈·얼룩 감소 가능, 빌드 시간 증가 |
| Indirect Lighting Smoothness | 계산 결과를 부드럽게 섞는 정도 | 노이즈가 가려질 수 있으나 세부 그림자도 흐려질 수 있음 |
| Num Indirect Lighting Bounces | 간접광이 반사되는 횟수 | 빛 분포가 달라짐. 모든 반사가 같은 비용을 추가하는 것은 아님 |

이들은 CPU Lightmass 설정입니다. GPU Lightmass는 자체 샘플 설정과 지원 옵션을 확인합니다.

**자료:** [CPU Lightmass World Settings][S33], [GPU Lightmass][S39]

### 14-3. Lightmass Importance Volume

원문의 `라이프매스 임포턴스 볼륨`은 **Lightmass Importance Volume**입니다. 플레이 가능한 공간처럼 중요한 영역에 베이크 계산을 집중하도록 범위를 지정합니다.

**볼륨 안만 굽고 바깥은 전혀 계산하지 않는 기능은 아닙니다.** 바깥은 낮은 품질로 처리될 수 있습니다. 맵 전체를 과도하게 크게 감싸기보다 필요한 공간을 담습니다. 여러 볼륨을 멀리 떨어뜨리면, 이들을 모두 감싸는 큰 경계가 계산 범위에 영향을 줄 수 있습니다.

**자료:** [Lightmass Importance Volume][S37]

## 15. 해가 뜨고 지는 게임은 어떻게 하나? — 원문의 질문

**태양 방향이 계속 바뀌고 그림자도 따라 움직여야 한다면, 태양 역할의 Directional Light를 Movable로 사용하는 구성이 기본 후보입니다.** Stationary는 런타임 회전용 설정이 아닙니다.

간접광까지 어떤 방식으로 처리할지에 따라 구성이 달라집니다.

| 요구 사항 | 검토할 구성 | 주의점 |
| --- | --- | --- |
| 실시간 태양 이동과 자연스러운 간접광 변화 | Movable 태양 + Lumen | 목표 GPU에서 비용과 품질 비교 |
| 실시간 태양 이동, 낮은 사양 우선 | Movable 태양 + 단순화한 환경광·별도 연출 | 루멘 수준의 간접광 변화를 동일하게 얻는 것은 아님 |
| 시간대가 몇 가지로 고정됨 | 시간대별 조명 상태를 별도로 제작 | 상태 전환과 데이터 관리 비용 고려 |
| 실내는 고정, 바깥 일부만 변함 | 정적·동적 조명을 조합한 설계 | 베이크한 간접광과 실제 시간대가 어긋날 수 있음 |

위 표는 기능 원리를 바탕으로 한 **설계 선택지**입니다. 프로젝트를 측정해 확정한 추천은 아닙니다.

건설로 진열대를 옮기는 게임에서는 옮긴 물체의 과거 그림자가 배경 라이트맵에 남지 않도록 해야 합니다. 바뀌는 물체와 고정 배경을 구분하고, 조명 처리도 함께 설계하세요.

**자료:** [Movable Light][S32], [Lumen 설정과 정적 조명 관계][S28]

## 16. Lumen — 간접광·반사를 실시간으로 계산하기

### 16-1. Ctrl + L은 루멘 전용 기능인가?

아닙니다. 대기광으로 설정된 Directional Light의 태양 방향을 조절하는 단축키 계열입니다. 그림자가 움직이는 것만으로 루멘 사용을 판단할 수는 없습니다. 직접광과 동적 그림자는 루멘이 없어도 가능합니다.

루멘 사용 여부는 프로젝트 설정과 디버그 뷰로 확인합니다.

**자료:** [Sky Atmosphere의 태양 조절 단축키][S41]

### 16-2. Surface Cache와 Card

**Surface Cache는 루멘이 표면의 머티리얼·조명 정보를 재사용하도록 만드는 캐시**입니다. Card는 표면을 여러 방향에서 캡처하기 위한 표현입니다.

```text
r.Lumen.Visualize.CardPlacement 1
```

뷰포트 `Lumen → Surface Cache`에서 **분홍색 영역은 캐시 커버리지가 부족한 부분**입니다. 시각화의 모든 색상이 오류를 뜻하지는 않습니다.

복잡한 방과 가구를 통째로 한 메시로 만들기보다 벽·바닥·천장 등을 나눠야 잘 표현될 수 있습니다. 따라서 **“루멘에서 모든 병합 금지”보다 “과도한 병합을 피하고 캐시 결과 확인”**으로 이해하세요.

**자료:** [Lumen Technical Details: Surface Cache][S42]

### 16-3. 소프트웨어 레이 트레이싱은 무엇인가?

레이 트레이싱은 **광선이 어느 표면에 닿는지 추적하는 계산**입니다. 루멘은 화면 정보 추적에 더해 소프트웨어 또는 하드웨어 방식의 추적을 사용합니다.

| 방식 | 표면을 찾는 대표 데이터 | 특징 |
| --- | --- | --- |
| Software Ray Tracing | 메시의 Signed Distance Field | 거리장으로 장면을 근사해 추적 |
| Hardware Ray Tracing | 삼각형 기반 가속 구조 등 | 전용 하드웨어를 활용하며 품질·갱신 비용이 다름 |

**간접광과 반사를 위한 계산 방식**에 관련된 설정입니다. 일반적인 그림자 방식이나 반사 강도 하나를 뜻하지 않습니다. 소프트웨어 방식도 GPU에서 실행될 수 있으며, “Software = CPU가 전부 계산”은 아닙니다.

**자료:** [Lumen 성능 가이드][S43]

### 16-4. 메시 디스턴스 필드와 글로벌 디스턴스 필드 — 원문의 질문

디스턴스 필드는 공간의 각 위치에 **가장 가까운 물체 표면까지의 거리**를 저장한 데이터입니다. SDF는 표면 안쪽·바깥쪽을 부호로도 구분합니다.

빈 공간에서 “가장 가까운 표면까지 멀다”는 것을 알면 광선을 작은 간격으로 계속 검사하는 대신 크게 전진시킬 수 있습니다.

| 종류 | 쉬운 이해 | 성격 |
| --- | --- | --- |
| Mesh Distance Field | 메시 하나의 표면까지 거리를 저장한 3D 지도 | 개별 형상 디테일 보존에 유리 |
| Global Distance Field | 여러 메시의 거리장을 합친 장면 지도 | 넓은 공간 추적에 유리하지만 세부 표현은 더 거칠 수 있음 |

“디스턴스 필드는 무조건 비싸고 글로벌은 무조건 싸다”보다, **해상도·검사 대상 수·장면 겹침에 따라 비용이 달라진다**고 이해하세요. 둘 다 원본 삼각형과 완전히 같은 정밀도를 보장하지는 않습니다.

**자료:** [Mesh Distance Fields][S44]

### 16-5. Detail Tracing과 Global Tracing

- **Detail Tracing:** 가까운 구간에서는 개별 메시 거리장을 사용하고, 이후는 글로벌 거리장을 이용합니다. 메시가 많이 겹치는 장면에서는 부담이 커질 수 있습니다.
- **Global Tracing:** 글로벌 거리장 위주로 추적해 비용을 줄입니다. 작은 형상의 표현에서는 차이가 날 수 있습니다.

따라서 원문의 Detail 설명은 방향이 맞고, Global도 정확한 메뉴 용어는 **Global Tracing**입니다. 장면에서 품질과 GPU 시간을 비교하세요.

### 16-6. 벽을 뚫고 빛이 새는 이유

아주 얇은 벽이나 한쪽 면뿐인 형상은 거리장에 충분히 표현되지 않을 수 있습니다. 에픽의 **10cm 이상 벽 두께 권고는 특히 소프트웨어 레이 트레이싱의 거리장 제약 맥락**에서 나옵니다.

벽 두께·닫힌 형상·분리된 모듈·거리장 품질을 점검하세요. 10cm만 맞추면 모든 빛샘이 사라지는 보증은 아닙니다.

**자료:** [Lumen Technical Details: Software Ray Tracing][S42]

### 16-7. 이미시브 조명이 지글거리는 이유와 대응

Emissive는 **표면 자체가 빛나도록 만드는 머티리얼 출력**입니다. 루멘에서 주변을 밝히는 데도 참여할 수 있습니다. 특히 작고 매우 밝은 발광면은 간접광 샘플링에서 노이즈를 만들기 쉽습니다.

실무에서 검토할 순서는 다음과 같습니다.

1. 발광면을 지나치게 작고 밝게 만들었는지 확인합니다.
2. 전등의 외형 발광과 실제로 주변을 비추는 역할을 나눕니다. 필요하면 Point·Spot·Rect Light를 함께 사용합니다.
3. 조명 수·영향 범위·그림자 비용도 비교합니다.
4. 노이즈가 남으면 Final Gather Quality 등 품질 옵션을 조절하고 GPU 시간을 측정합니다.

**Final Gather Quality를 높이는 것은 정식 조절 방법입니다.** 비용이 증가하므로 필요한 만큼 조정할 문제이며, 절대 사용하면 안 되는 옵션은 아닙니다. 반대로 모든 떨림이 이미시브 원인인 것도 아니므로 반사·그림자·안티앨리어싱 문제도 구분해야 합니다.

**자료:** [Lumen의 발광면과 품질 옵션][S28], [에픽 Lumen 기술 블로그][S45]

## 17. Screen Space GI·반사·스카이라이트·Reflection Capture

### 17-1. SSGI와 SSR

| 기능 | 무엇을 계산하나? | 주된 한계 |
| --- | --- | --- |
| SSGI: Screen Space Global Illumination | 화면 정보를 이용한 확산 간접광 | 화면 밖·가려진 데이터가 부족함 |
| SSR: Screen Space Reflections | 화면 정보를 이용한 반사상 | 화면 밖 대상이 반사에서 빠지거나 화면 가장자리에서 끊길 수 있음 |
| Lumen GI / Reflections | 화면 정보와 추가 장면 표현을 이용한 간접광·반사 | 별도의 GPU 비용과 장면 표현 제약 |

원문의 GI 설정 `Screen Space`와 Reflection 설정의 `Screen Space`는 구분하세요. 같은 화면 공간 원리를 이용해도 결과와 목적이 다릅니다.

SSR은 비교적 저렴한 반사 방식이지만, 비용은 해상도·품질과 표면 상태에 따라 달라집니다. SSGI도 모든 장면에서 무조건 저렴하다고 단정하지 않습니다.

**자료:** [Post Process Effects][S46], [Rendering Settings][S38]

### 17-2. Sky Light는 하늘만 반사하나?

Sky Light는 **캡처한 환경이나 지정한 큐브맵을 이용하는 환경광**입니다. 설정에 따라 하늘뿐 아니라 장면의 정보도 캡처에 포함될 수 있습니다.

다만 장면 전체에 공통적인 환경 표현으로 가까운 벽·가구의 위치별 반사 차이를 정밀하게 재현하기는 어렵습니다. 따라서 “하늘만 가능하고 가까운 물체는 절대 불가능”은 과도한 설명입니다.

**자료:** [Sky Lights][S47]

### 17-3. Box / Sphere Reflection Capture

특정 위치 주변 환경을 **큐브맵으로 미리 캡처해 반사 재질에 적용하는 프로브**입니다. Box는 방처럼 상자형 공간, Sphere는 여러 일반 공간에서 검토할 수 있습니다.

Box의 범위는 반사를 적용하는 영향 영역과 투영을 제어하는 데 관계합니다. “상자 안 물체만 실시간으로 추적한다”는 기능은 아닙니다.

미리 캡처한 근사 표현이므로 **움직이는 캐릭터나 매번 바뀌는 상품이 자동으로 실시간 반영되지는 않습니다.** 장면 변경 후 재캡처가 필요할 수 있습니다. 거울처럼 정확한 동적 반사는 다른 방식을 검토해야 합니다.

루멘을 사용하는 구성에서는 Reflection Capture가 같은 방식으로 추가 효과를 내는지부터 확인하세요. 활성화된 반사 방식과의 조합에 따라 역할이 달라집니다.

**자료:** [Reflections Captures][S48]

## 18. Shader Complexity와 반투명 오버드로우

### 18-1. Shader Complexity는 무엇을 보여주나?

뷰포트의 `Optimization Viewmodes → Shader Complexity`로 확인합니다.

**화면 전체에서 각 픽셀에 필요한 셰이더 명령량 등을 색으로 보여주는 진단 뷰**입니다. 중앙 십자선의 한 픽셀만 분석하지 않습니다. 초록보다 빨강·분홍·흰색에 가까운 넓은 영역을 우선 살펴볼 수 있습니다.

다만 색상은 실제 GPU 밀리초 측정값이 아닙니다. 텍스처 접근·명령 종류·하드웨어 등의 비용 차이를 완벽히 반영하지 않으므로 GPU 프로파일러와 함께 사용합니다.

**자료:** [Viewport Modes: Shader Complexity][S40]

### 18-2. 반투명이 겹치면 왜 무거울까? — 원문의 질문

보통의 불투명 표면은 앞쪽 표면의 깊이를 이용해 뒤쪽의 불필요한 픽셀 계산을 줄이기 쉽습니다. 반투명 표면은 **뒤가 비쳐야 하므로 여러 겹의 색과 투명도를 계산해 섞어야** 합니다.

같은 화면 영역에 유리·연기·비 파티클이 겹치면 그 영역을 여러 번 처리합니다. 이를 **오버드로우(Overdraw)**라고 합니다. 단순히 “겹친 부분의 색을 한 번 다시 칠하는 것”보다, 여러 표면의 셰이더 실행과 합성 비용이 누적되는 문제입니다.

### 18-3. Opacity를 0으로 낮추면 비용이 사라지나?

**화면에 투명하게 보이는 것과 렌더링 명령을 제출하지 않는 것은 다릅니다.** 일반적인 Translucent 머티리얼에서 Opacity만 낮추어도 메시 제출·셰이더·합성 준비 비용 등이 남을 수 있습니다. 정확한 절감은 셰이더와 렌더링 경로에 따라 달라집니다.

완전히 불필요해진 이펙트는 거리 컬링, 생성량 조절, 컴포넌트 비활성화 등을 검토하세요. 단, 비활성화할 때 기존 파티클을 마저 재생할지 즉시 제거할지와 시스템의 시뮬레이션 상태도 확인해야 합니다.

**비·눈의 거리 페이드**는 경계가 자연스럽게 보이도록 돕지만, **투명도만 줄여 파티클 수와 시뮬레이션 비용까지 줄였다고 판단하면 안 됩니다.** 자연스러운 페이드와 실제 컬링·생성량 제어를 함께 설계합니다.

### 18-4. 개선할 때 볼 항목

| 확인할 것 | 개선 방향 |
| --- | --- |
| 화면을 크게 덮는 파티클 | 크기·수명·생성량·카메라 근처 밀도 검토 |
| 여러 층의 겹침 | 필요 없는 레이어 줄이기 |
| 넓은 투명 여백 | 파티클 텍스처와 메시 모양 검토 |
| 복잡한 반투명 머티리얼 | 굴절·텍스처 샘플·연산 단순화 |
| 멀리서 보이지 않는 이펙트 | 거리별 품질·컬링·시뮬레이션 정책 검토 |

구멍처럼 완전히 보이거나 안 보이는 표현은 Masked가 적합할 수 있습니다. 유리처럼 연속적인 반투명 표현과는 목적이 다르며, Masked도 비용이 없는 것은 아닙니다.

**자료:** [Using Transparency][S49], [셰이더 복잡도 뷰][S40]

## 19. Foliage(폴리지)란? — 원문의 질문

원뜻은 잎·수풀 등 식생입니다. UE의 **Foliage Mode는 나무·풀·바위 같은 반복 오브젝트를 브러시로 대량 배치하는 도구**입니다. 반드시 식물만 놓아야 하는 기능은 아닙니다.

| 종류 | 특성 |
| --- | --- |
| Static Mesh Foliage | 인스턴싱으로 많은 배치를 효율적으로 렌더링할 수 있습니다. |
| Actor Foliage | 일반 액터의 동작을 쓸 수 있지만 일반 액터 배치 비용도 고려해야 합니다. |

폴리지 도구를 썼다고 자동으로 저렴해지지는 않습니다. 잎의 겹침, 그림자, 바람 변형, 충돌, 인스턴스 수와 컬링 거리를 함께 확인하세요.

**자료:** [Foliage Mode][S50]

아래는 분석용입니다. 명령은 한 줄씩 입력하고, 지원 여부와 표시 항목은 현재 엔진에서 확인하세요. 개발용 콘솔·디버그 뷰는 Shipping 빌드에서 동일하게 제공되지 않을 수 있습니다.

| 명령어·조작 | 목적 | 확인 후 |
| --- | --- | --- |
| `stat unit` | Game·Draw·GPU 등 프레임 처리 시간 | 같은 명령으로 통계 토글 |
| `stat fps` | FPS와 프레임 시간 표시 | 같은 명령으로 통계 토글 |
| `stat scenerendering` | 장면 렌더링 통계 | 같은 명령으로 통계 토글 |
| `stat RHI` | RHI 계층 통계 | 같은 명령으로 통계 토글 |
| `stat gpu` | GPU 작업별 통계 | 같은 명령으로 통계 토글 |
| `stat streaming` | 텍스처 스트리밍 통계 | 같은 명령으로 통계 토글 |
| `r.VisualizeOccludedPrimitives 1` | 가림 처리된 프리미티브 점검 | 값을 `0`으로 변경 |
| `r.Lumen.Visualize.CardPlacement 1` | Lumen Card 배치 확인 | 값을 `0`으로 변경 |
| `Shift + L` | 기본 바인딩에서 뷰포트 통계 표시 토글 | 콘솔 창 닫기와 다름 |
| `Ctrl + L` 계열 | 대기광 Directional Light 방향 조절 | 실제 조명 방향을 변경하므로 원상 복구 고려 |

단축키는 뷰포트 포커스와 키 바인딩에 따라 다릅니다. 콘솔 창을 닫는 조작과 통계 표시를 숨기는 조작을 구분하세요.
