## 절도 통계 연동 설계

> 빌런이 절도에 성공했을 때의 손실을 **정산 화면**과 **상품 분석 화면**에 반영하는 설계를 했습니다. **코드와 에셋은 하나도 안 건드렸고**, 진단 → 설계 → 인수인계 사양서까지 문서로만 정리했습니다.

---

### 1. 구현 내용

시작은 *"절도 손실이 정산에 안 잡히는 것 같다"* 였는데, 경로를 끝까지 따라가 보니 **금액 파이프라인은 이미 전 구간 완성**돼 있었습니다.

```
Shoplift 태스크 → CommitShoplift → 퇴장 → ReportShopliftEscaped
  → OnShopliftEscaped 방송 → 정산 서브시스템 → RecordShopliftLoss
  → DailyShopliftLossGold 누적 → 위젯 갱신
```

WBP 안에 위젯 이름도 **실제로 존재**해서 바인딩이 정상적으로 잡히는 상태였고, 다음 날 리셋도 되어 있었습니다. 며칠 전 다른 파트가 커밋으로 추가한 배선이었습니다.

| 항목 | 실제 상태 |
| :--- | :--- |
| 절도 손실 금액 → 정산 | **이미 연결됨** |
| 절도 손실 → 별도 손실 합계 | **이미 포함됨** |
| 절도 **품목별** 정보 | **전혀 없음** ← 진짜 본론 |

**"안 보인다"고 느낀 이유도 찾았습니다.** 절도 손실 행은 `> 0`일 때만 표시되는 데다, **별도 손실 호버 팝업 안에** 들어 있어서 **마우스를 올려야 보입니다.**

> **"안 되는 것"과 "안 보이는 것"은 다릅니다.** 새 기능을 설계하기 전에 기존 경로를 끝까지 따라간 게 컸습니다. 안 그랬으면 **이미 있는 배선을 한 벌 더 만들 뻔했습니다.**
>
> 그래서 설계 문서 맨 앞에 *"진짜로 새로 만들어야 하는 것은 품목별 집계 파이프라인 하나"* 라고 못 박고 시작했습니다.

### 2. 기존 구조대로

*"왜 절도 손실이 순이익에 반영이 안 되지?"* 가 처음 의문이었습니다. 회계 흐름을 따져보니 **반영하면 안 되는 것**이었습니다.

이 프로젝트의 정산은 **실제 현금흐름 기준**입니다.

```
총지출  = 실제로 자금에서 빠져나간 돈 (발주비 + 임대료)
순이익  = 매출 − 총지출
```

> **상품이 도난당하면 "매출이 발생하지 않음"으로 이미 순이익에 반영되어 있습니다.** 그 상품의 **매입가는 발주 시점에 이미 총지출로 빠졌기** 때문입니다.
>
> 여기에 **판매가 기준** 절도 손실을 순이익에서 또 빼면 **이중 계상**이 됩니다.

즉 현재 코드가 절도·폐기를 **별도 손실(참고용 지표)** 로만 분리해 둔 것은 **회계적으로 옳은 구조**였습니다.

> 요즘 계속 *"기존 코드가 이상하면 이유부터 찾는다"* 를 겪는데, 이번엔 **누락이 아니라 의도**였습니다. 며칠 전 매장 밖 배치 건은 *"순서로 봉합한 모순"* 이라 뒤집었고, 이번엔 **건드리지 않는 게 정답**이었습니다. **같은 질문("왜 이렇게 돼 있지")에서 반대 결론이 나올 수 있다**는 게 재밌었습니다.

### 3. 금액 축을 둘로 나눴다

| 필드 | 기준 | 의미 | 합계 반영 |
| :--- | :--- | :--- | :--- |
| 기존 손실 금액 | **판매가** | *"이만큼 벌 수 있었는데 놓쳤다"* (기회손실) | 별도 손실에만 |
| 신규 원가 손실 | **매입가** | 실제 원가 손실 | **미반영** (참고 지표) |

UI 표기는 **판매가 기준**을 유지하기로 했습니다. 플레이어 체감이 직관적이기 때문입니다. 매입가 기준은 나중에 **리스크 밸런싱이나 평판 페널티를 산정할 때** 쓸 예비 필드입니다.

> 같은 사건을 두 관점에서 재는 것이라 **어느 쪽이 맞다가 아니라 용도가 다릅니다.** 하나만 저장했다면 나중에 밸런싱할 때 다시 파이프라인을 손대야 했을 겁니다.

### 4. 기존 함수를 고치지 않고 표시 전용 Getter로

기획이 *"순이익에서 절도만큼 더 빼는 연출"* 을 원할 수도 있어서 대안도 준비했는데, **기존 순이익 함수는 절대 수정하지 말라**고 문서에 굵게 적었습니다.

> 그 함수를 직접 고치면 **전일 대비 델타 값**과 **정산 화면 두 곳의 텍스트**가 한꺼번에 바뀌어 **정산 파트의 기획이 흔들립니다.**
>
> 그래서 필요하면 `GetDailyNetProfitAfterSeparateLossGold()` 같은 **표시 전용 Getter를 새로 추가**하는 쪽으로 설계했습니다.

**"계산의 진실"과 "화면에 보여줄 값"을 분리**하는 셈입니다. 며칠 전 *"파생값은 저장하지 않고 함수로 계산"* 과 같은 계열인데, 이번엔 **한 값에 두 가지 해석이 필요한** 경우였습니다.

### 5. 수명이 데이터 형태를 정한다

리포트 구조체에 상품 **표시 이름을 값으로 복사**해 두기로 했습니다.

```cpp
FName ProductId;      // 병합 키
FText DisplayName;    // 값 복사 — 참조가 아니라
int32 Quantity;
```

> **손실 집계 함수는 손님이 `Destroy()` 되기 직전에 호출되고, 직후 상품 목록 참조는 사라집니다.** ID만 들고 있다가 나중에 이름을 조회하면 되지 않느냐 싶었는데, **UI가 그리는 시점에는 이미 원본이 없습니다.**

폐기 쪽도 정확히 같은 이유로 이름 맵을 따로 들고 있었습니다. **선례를 확인하고 나서야 이 필드가 왜 필요한지 이해**했습니다.

**참조가 죽는 시점을 넘겨야 하는 데이터는 값으로 복사한다** — 며칠 전 *"기록하지 않은 정보는 복원할 수 없다"* 와 같은 이야기인데, 이번엔 **"언제 죽는지"가 형태를 결정**했습니다.

### 6.  부분 실패 시 무엇을 우선할 것인가

리포트를 조립하다가 **`ProductId`가 비어 있는 상품**을 만나면 어떻게 할지 정해야 했습니다.

```cpp
// ProductId가 비어 있어도 금액 합계에는 반영하고, 품목 목록에서만 제외한다.
// (금액과 품목이 어긋나는 것보다, 금액이 정확한 쪽이 정산에 안전하다)
if (ProductId.IsNone()) { continue; }
```

| 선택지 | 결과 |
| :--- | :--- |
| 통째로 건너뛴다 | 품목 목록은 깨끗한데 **금액이 실제보다 적게 잡힘** |
| **금액만 반영** ✅ | 금액은 정확, **품목 합계와 금액이 살짝 안 맞음** |

**정산에서는 금액이 더 중요하다**는 판단으로 후자를 골랐습니다.

> 부분 실패는 **어느 쪽으로든 어긋납니다.** 중요한 건 **어느 방향으로 어긋날지를 미리 정하고 그 이유를 주석에 남기는 것**이었습니다. 안 정해두면 나중에 *"왜 개수 합계랑 금액이 안 맞지"* 를 버그로 오해하게 됩니다.

### 7. 델리게이트 확장의 함정 3가지

이벤트 페이로드를 금액 하나에서 **리포트 구조체 추가**로 확장하면서 정리한 것들입니다.

| 함정 | 내용 |
| :--- | :--- |
| **기존 인자 유지** | 금액 인자를 지우지 않고 남겼습니다. 정산 파트가 이미 쓰고 있고, **BP에서 단순 금액만 보고 싶을 수** 있습니다 |
| **`const&` 불가** | `DYNAMIC` 델리게이트 파라미터로 `USTRUCT`은 **값 전달만** 가능합니다. `const&`로 선언하면 UHT가 막습니다 |
| **조용한 바인딩 실패** | 구독 함수 시그니처가 **하나라도 안 맞으면 런타임에 조용히 바인딩 실패**합니다. **컴파일은 통과합니다** |

> 세 번째가 무섭습니다. **에러도 경고도 없이 그냥 이벤트가 안 옵니다.** 며칠 전 *"기본값 `false`인 기능은 켜주지 않으면 없는 것"* 과 같은 종류인데, 이번엔 **시그니처 불일치**가 그 역할을 합니다.
>
> 그래서 구현 순서 체크리스트에 **"재컴파일 후 바인딩이 살아 있는지 로그로 확인"** 을 별도 항목으로 넣었습니다.

### 8. 선례가 있으면 대응표를 만든다

**폐기(Disposed) 통계가 정확히 같은 구조로 이미 구현돼 있었습니다.** 그래서 설계 대신 **복제**를 택하고, 문서 부록에 **대응표**를 만들었습니다.

| 개념 | 폐기 (기존) | 절도 (신규) |
| :--- | :--- | :--- |
| 품목 수량 맵 | `DailyDisposedProductQuantities` | `DailyStolenProductQuantities` |
| 품목 이름 맵 | `DailyDisposedProductNames` | `DailyStolenProductNames` |
| Entry 필드 | `DisposedQuantity` | `StolenQuantity` |
| 필터 | `HasWaste` | `HasTheft` |
| 요약 카드 위젯 | `DisposedProductNameText` 등 | `StolenProductNameText` 등 |

상품 분석 화면도 **① 요약 카드 ② 필터 버튼 ③ 목록 컬럼** 3층 구조를 그대로 복제하기로 했습니다.

> **대응표를 만들고 나니 설계가 거의 끝났습니다.** 새로 판단할 것이 *"어디에 끼워 넣을 것인가"* 정도로 줄었고, 구현하는 사람이 **폐기 코드를 옆에 띄워놓고 이름만 바꾸면** 되는 상태가 됐습니다.
>
> **비슷한 기능이 이미 있으면 "어떻게 만들까"가 아니라 "무엇에 대응하는가"를 먼저 정리**하는 게 빠릅니다.

다만 **순서 주의**가 하나 있습니다. 도난 엔트리를 추가하는 블록은 **폐기 블록 다음, 재고 채우기 루프 이전**에 넣어야 새로 생긴 행도 재고·폐기 수치를 채웁니다. 복제할 때 **위치까지 맞춰야** 합니다.
